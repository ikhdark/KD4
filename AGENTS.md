# Repository guidance

Treat harness prompts and instruction architecture as critical components: apply these rules strictly and review changes carefully for unintended behavior. Diagnose whether an issue requires a prompt fix, a harness implementation fix, or both; do not use prompt changes to mask implementation defects. Keep harness prompts aligned with your changes, following [the instruction architecture](codex-rs/core/instruction-architecture.md) for ownership, delivery, and maintenance. Replace outdated guidance; add instructions, prompt sections, or guidance files only when needed to improve the agent's understanding. Keep each instruction in its authoritative owner and remove duplication. Choose the best-supported version of the prompt, not automatically your own, and avoid changes made solely to produce a diff. Keep `codex-rs/protocol/src/prompts/base_instructions/default.md` concise and repository-neutral, it is the harness prompt, not KDR or KD4's.

This is Windows only project.
This is a local project.
Do not publish or republish without permission.

## Audits and reviews

Before audit/review investigation or delegation, derive categories, exclusions and detection criteria from the request; include them in every assignment. No invented exclusions, severity thresholds, sampling limits, finding caps or narrowing. Follow in-scope paths; adding categories needs user authorization.
Match coverage to the request: patch reviews cover every hunk and affected behavior; repository audits cover every relevant subsystem in the requested category; full-file reviews cover the file and relevant consumers. Only change-specific requests limit findings to new defects/changed lines. Do not substitute audit types; equivalence proves only the checked property, not other evidence or inclusion boundaries.
For broad audits/full reads, inventory scope from current manifests/modules, subject and requested exclusions. Hidden, ignored, generated and local-only paths are not implicit exclusions; include relevant paths in discovery and check effective scope, traversal limits, errors and unexplored paths before claiming coverage. Check every relevant producer, consumer and execution path against all criteria. Narrowing sets order, not coverage. Track unread ranges, mechanisms and follow-ons in the plan; finish obtainable scope in bounded batches without context-driven sampling, per-worker finding caps or module exclusions. Partial results require explicit user-approved sampling/limits or a genuine access/permission blocker after independent work. Reads, hits, summaries, snapshots, worker counts and findings are not behavioral coverage.
For requested historical survival investigations, account for every commit in range. Select production changes by requested behavior, not every changed file. Triage generated/validation/other artifact groups by paths/manifests; inspect them when they affect in-scope production or required evidence. Before deep history, check HEAD's caller, startup config, defaults and gates. Close clear survivors with concise source/equivalence evidence; trace later history deeply only for uncertain survival or lost advantage. Bulk immutable Git-object inventories use `git cat-file --batch-check`, preserving exact keys and missing results. This triage does not replace other requested review/full-read coverage. If using an evidence directory, resolve/verify its absolute path once and reuse it in later Git calls.
When integrating audit/review reports, account for every returned entry and substantive recommendation. Parse structured handoffs in-tool; fully read entries verified/integrated, consult artifacts for specific claims, and verify against original evidence. Dispositions: implemented/verified; verified/reported without edits when explicitly restricted to read-only work; rejected with evidence; out of scope; or unresolved with next action/blocker. Track unread items separately; group only shared causes/dispositions, preserving occurrence counts and retrievable references. Recover omitted output with `read_tool_output`, not producer reruns.
Report only verified findings with demonstrated behavior and production triggers. Do not narrow requested coverage to make verification easier. Unverified candidates may go only to an authorized parent/verifier with exact evidence and reproduction instructions, separately from findings. Exclude them from final findings/counts; blocked verification is a coverage gap, not a finding or clean result.
Keep reports decision-focused: status/counts/failures/gaps, outcome/disposition, findings, blockers and next actions. Evidence belongs to findings/candidates, not every examined file. Summarize coverage by subsystem/mechanism; give resume pointers only as needed. Omit file inventories/hashes and no-finding narratives unless requested. Raw dumps, extra artifacts and per-item ledgers need a request/tool contract; preserve required diagnostics and internal coverage tracking.
Update the canonical report for follow-up audits rather than rewriting stable sections or adding overlapping supplements. Preserve required evidence/standalone deliverables; state qualifications once per finding, without routine compliance/success narration.
For requested audits/reviews, write a short `.txt` report in a task-named folder under the audit directory designated by the repository. Include status, coverage, unresolved items and compact findings: ID, severity, `path:line`, defect/trigger (measured costs for performance findings), evidence reference and disposition; quote at most 3 lines. Merge delegated entries and dispositions before writing. Chat gives only brief status/count and the absolute report link. Exact machine-readable schemas take precedence; the authorized caller handles export. Reports do not expand the authorized scope or override explicit read-only restrictions. Respect no-write, inline-only and permission restrictions.
