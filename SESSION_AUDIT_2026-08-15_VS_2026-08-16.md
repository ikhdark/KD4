# Codex fork session audit: 2026-08-15 vs 2026-08-16

## Executive verdict

The 8/16 binary is faster and leaner in raw work performed per audit turn, but it is not uniformly more efficient.

On the most comparable cohort—first, long-running audit turns—the 8/16 build reduced median wall-clock duration by 32.7%, model time by 28.4%, tool time by 54.7%, total tokens by 24.4%, generations by 17.5%, and tool calls by 11.5%. Median time to first model output improved by 11.5%. Model retries fell to zero.

The main regression is prompt/context reuse. Median uncached input rose from 171,716 to 534,359 tokens (+211%) even though total tokens fell. Aggregate cache coverage fell from 89.9% to 63.6%. The new request-category telemetry attributes 83.1% of logical request content to conversation history and 10.5% to repeated unchanged context. At the same time, non-progress tokens increased from 80.0% to 87.6% of all model tokens, and only 16.6% of first-cohort model requests changed the next structured action versus 22.9% on 8/15.

The second major regression is rollout/tool-state bloat. Tool manifests occupy 5.62 MB, or 26.5% of the complete 8/16 corpus, versus 4.20 MB and 4.6% on 8/15. Rollout bytes per instrumented turn increased 26.4% despite 47.1% fewer events per turn. Each 8/16 session persisted three to six distinct manifests.

The new source-discovery path is promising: it substantially replaces ad hoc Python scans with structured source batches, reduces tool time, and actively prunes false positives. However, its telemetry is incomplete: 13 architecture-slice attempts recorded 39 missing requirements but zero completed slices, files read, bytes read, relationships, invariants, or architecture tool calls.

No defensible implementation-quality comparison is possible. The 8/16 population is overwhelmingly read-only audit work and contains zero patch events, Cargo checks, rustfmt runs, or `just` validations. The 8/15 population includes hundreds of edits and validation commands. Any claim that coding got better or worse would confuse workload mix with binary behavior.

The known 8/16 terminal partial/error defect is excluded from the regression ranking. Terminal outcome labels, final-answer publication rate, and near-zero finalization timing are therefore not treated as performance or quality evidence.

## Comparison design and caveats

Three views are used:

1. **Raw population:** all 87 old and 16 new timed turns. This describes what the binaries actually did, but workload mix is very different.
2. **First-turn cohort:** the first timed turn in each usable finalized session—24 old and 13 new. This reduces the bias from long accumulated thread history and implementation follow-ups.
3. **Long-audit cohort:** first turns lasting at least five minutes—19 old and 11 new. Both sides are dominated by repository/session audits and this is the most useful directional comparison.

Only one prompt was byte-equivalent across both days: the Repo-Atlas full-lifecycle audit. Two additional prompts were 99% text-similar (tool-use effectiveness and architecture mental-model audits), but the 8/16 runs ended before publishing a substantive final answer. Their pre-terminal work is useful for cost/latency, not task-success scoring.

The 8/16 batch also ran with high concurrency. Aggregate machine time must not be confused with elapsed wall clock.

## Token and context audit

### What improved

- Long-audit total tokens fell 24.4% and median generations fell 17.5%.
- Tokens per generation remained effectively flat: 44,474 old versus 44,122 new. The savings came from fewer generations, not smaller requests.
- Reasoning tokens fell 39.8% and visible-plus-reasoning output fell 44.3%.
- Retries disappeared in the new sample.

### What regressed

- Median long-audit uncached input increased 211.2%.
- Aggregate long-audit cache coverage fell from 89.9% to 63.6%.
- First-cohort non-progress share rose from 79.6% to 87.5%.
- In the first cohort, only 16.6% of model requests changed the next structured action, down from 22.9%.
- Requests with unchanged relevant state increased from 82.8% to 86.6%.
- Uncategorized generation purposes rose from 76.3% to 79.4% of first-cohort requests.

### Coding and validation quality

There is no matched coding cohort:

- 8/15 contains 357 successful persisted patch events and at least 270 validation-program invocations (`cargo`, `just`, rustfmt), plus npm/npx checks.
- 8/16 contains zero persisted patches and zero Rust validation commands.
- The only 8/16 multi-turn fix/debug session remained in diagnosis before the excluded terminal defect ended its work.

Therefore:

- Edit minimality, first-pass compile rate, re-edit rate, debugging recovery, validation selection, and final implementation correctness are **not measurable across binaries from this corpus**.
- Zero new-build patches is not a coding regression; it is a workload property.
- A paired edit/debug benchmark is required before shipping conclusions about coding effectiveness.

## Qualitative answer quality

Only two substantive 8/16 audit reports were stored as `final_answer` items, excluding a short explanation about why an audit turn ended. Both substantive reports were strong in several ways:

- Findings were ranked by severity/impact.
- Producer-to-consumer paths and concrete source locations were cited.
- The reports distinguished confirmed gaps from feature gates, intentional compatibility, or false positives.
- They explicitly stated that no edits/tests were performed.

Observed weaknesses:

- One architecture report cited a rollout ID/path that does not exist in the session store (`01a007b7-f759-7da1-b443-7e664fce2335`).
- “No files were changed” was sometimes phrased as “the working tree remains clean,” which is not equivalent in a shared, already-dirty worktree.
- The reports were static source audits with no executable proof; that was appropriate to the read-only request, but confidence labels should distinguish source tracing from tested behavior.
- Most 8/16 sessions reached a near-final commentary state without a stored final report. This is dominated by the excluded terminal bug and is not used to score general reasoning quality.

## Top 10 most impactful improvements to apply

### 1. Restore stable prompt/cache reuse

Make stable instructions, tool state, repository context, and unchanged history hash-stable across requests; reuse the same prompt prefix/response lineage through tool continuations and compactions. Add an alert when cache coverage falls below the baseline for matched tasks.

Expected impact: highest direct reduction in cost and model latency. The target is to reverse the +211% median uncached-input regression while preserving the 24% total-token reduction.

### 2. Turn non-progress telemetry into an active governor

Classify residual tool continuations as deterministic/unchanged when their state fingerprint and next action do not change. Activate the existing no-progress/proven-loop controls, suppress redundant generations, and require a changed obligation, evidence item, or action before another broad source pass.

Expected impact: attacks the 87.6% non-progress share, 86.6% unchanged-state rate, 16.6% action-change rate, and zero loop activations.

### 3. Deduplicate tool manifests in rollouts and history

Persist each manifest once by hash and reference it thereafter; encode tool additions/removals as deltas. Do not replay unchanged schemas into model-visible history. Keep the full dictionary available for reconstruction.

Expected impact: removes up to 26.5% of new rollout bytes and reduces dynamic-tool history churn without weakening auditability.

### 4. Make architecture closure task-relative and truthfully incomplete

Resolve task phrases/paths/symbols to ranked narrow owners. Require each critical facet to overlap the actual task obligation; broad generic edges must not satisfy closure. Return `owner_ambiguous`, `owner_too_broad`, or explicit unresolved facets instead of “complete.”

Expected impact: prevents confident misses such as hook dispatch and thread resume, reduces late relationship discovery, and makes the structured source path safe enough to replace broad exploration.

### 5. Improve semantic tool-output projection and exact recovery

Project by symbols/sections and return stable artifact ranges/handles. Recovery should retrieve the missing canonical span directly rather than retruncate it. Preserve canonical cursors, omission counts, abort status, and retention-limit reasons across wrappers and code mode.

Expected impact: preserves the existing 33.7% model-token reduction while cutting 68 projection truncations, 72 omissions, and 21 recovery retruncations.

### 6. Preserve structured nested-tool outcomes through code mode

Propagate nested success/failure, failure fingerprints, blocking disposition, source/plan evidence, and canonical-artifact requirements to the reasoning governor. A successful JavaScript cell containing a failed nested call must not be recorded as a clean outer success.

Expected impact: makes failure diagnosis and deterministic-cycle suppression reliable and should further reduce the 4.34% script-failure marker rate and repeated broad retries.

### 7. Fix and explain invalid state transitions

Repair the transition path seen three times in `2ee985a9d5c8`. Extend telemetry with state, attempted transition, reason, call/turn ID, and whether recovery succeeded.

Expected impact: removes a new state-machine regression and makes future transition failures diagnosable without replaying source-level behavior.

### 8. Complete telemetry accounting

Define whether token categories are full logical prompt content, newly materialized content, or residual content, then reconcile category totals with actual request input. Populate tool-schema/base-instruction categories, generation purposes, projected-token counts, and all architecture counters from real production paths.

Expected impact: prevents optimization against misleading zeroes. Today 79% of requests have no purpose, tool-schema tokens are always zero, deterministic dispositions are always zero, and architecture work is mostly invisible.

### 9. Add deterministic final-evidence checks

Before publishing a report, verify cited local paths/rollout IDs exist, distinguish “I made no edits” from “worktree clean,” and label source-only findings separately from tested findings. Store the evidence check result in the rollout.

Expected impact: improves user trust and catches the observed nonexistent rollout citation without requiring more model reasoning.

### 10. Establish a paired coding benchmark before the next binary decision

Run both binaries on the same immutable worktree snapshots and prompts: at minimum one read-only trace, one small Rust edit, one cross-cutting edit, one failing-test diagnosis, and one validation-repair task. Score task success, diff correctness/minimality, first-pass compile, tests selected, retries, re-edits, final evidence, tokens, cache, TTFT, and wall clock. Use the same model, effort, concurrency, and warm build lane.

Expected impact: closes the largest evidence gap in this audit. It is the only defensible way to decide whether the 8/16 binary improved actual coding rather than audit throughput.

## Recommended acceptance thresholds for the next A/B

- Matched-task cache coverage at least 85%, with uncached input no worse than 8/15.
- Non-progress token share below 70% for read-only audits and below 60% for implementation turns.
- Next-action-changed rate above 25% on audit/tool-continuation requests.
- Zero unexplained invalid transitions.
- Tool manifests below 10% of rollout bytes and no unchanged manifest replay.
- Architecture slices either task-complete with task-overlapping evidence or explicitly unresolved; no broad-owner false completeness.
- Artifact recovery retruncation below 10% of recovery calls.
- All local citations existence-checked.
- At least five matched implementation tasks with task-local validation and nonzero patch coverage.

## Bottom line

Keep the 8/16 source batching, lower tool latency, lower request count, retry elimination, build metadata, and output-artifact projection. Do not treat the binary as an across-the-board efficiency win until prompt-cache reuse, non-progress suppression, manifest churn, architecture closure, and telemetry accounting are fixed.

The clearest one-line summary is: **8/16 does less work faster, but pays much more uncached context per request and still spends most model tokens without changing the next action.**
