CONFIRMED FINDINGS BEFORE REPAIR
F01 — Generated configuration contract is stale. The Rust config source removed the token-budget table and feature, but the checked-in config schema still advertises token_budget and TokenBudgetConfigToml. Scenario: a client validates a retired key successfully, then the runtime ignores/rejects the contract it was told is valid. Repair: regenerate through the documented owner-aware config-schema workflow.
F02 — Desktop activation persistence can roll back a newer document. record_desktop_activation mutates live document/runtime before persistence and restores a whole prior document for both Failed and Superseded outcomes. Scenario: activation creates revision N+1; another evidence update persists N+2; activation sees Superseded and restores N, losing the concurrent update in memory and diverging from disk. Repair: serialize activation transitions and atomically publish document/runtime only after persistence.
F03 — Fork manifest contradicts the implementation. Task evidence remains declared schema-v9 although the runtime migrates/writes schema 11, and desktop-runtime-receipt remains planned although its core, app-server, protocol, generated, and test wiring is present. Repair: advance the evidence feature declaration and mark the desktop receipt enabled with static evidence.
F04 — Persisted wire compatibility was removed without a migration read path. Retired timing-purpose/progress and validation-status spellings still exist in fork rollouts and task-evidence documents; deserialization failure causes rollout lines (including terminal events) to be skipped. Scenario: resume an older completed turn whose timing contains source_discovery; the entire terminal line is dropped and history can appear in progress. Repair: accept history-only serde aliases into canonical current variants while preserving the new serialization/schema surface.
F05 — Initial terminal-delivery persistence claims release on failed live delivery. terminal_interaction_released is written true even when active_turn_detached is false; later updates are monotonic ORs and cannot correct the false claim. Scenario: outbound delivery fails, recovery is scheduled, but durable evidence says the interaction was released. Repair: bind release to the actual detach result.
F06 — Desktop activation challenge ownership survives connection teardown. The ownership map is populated and queried but connection_closed never removes entries. Scenario: repeated Desktop reconnects leave challenge IDs and connection IDs resident for the app-server lifetime. Repair: remove all ownership entries for the closed connection and cover the lifecycle helper.
F07 — Acknowledged terminal entries retain their full ServerNotification payload and routing sets indefinitely; acknowledgement_sent is written but never read. Scenario: a long-lived thread completes many large turns and retains every projected terminal payload after core acknowledgement. Repair: discard retry-only payload/routing state at acknowledgement and remove the dead field while retaining the fingerprint needed for duplicate/conflict classification.
F08 — Model-cache/auth scope does not distinguish credential-only accounts. API-key auth (and Headers auth without ChatGPT-Account-ID) produces the same account digest for different secrets, so an AuthManager account/key switch can reuse prior model state and the old scoped provider begins sending the new key. Repair: add a domain-separated credential digest only when stable account/user routing is absent; keep normal token refresh stable when authoritative account identity exists.
F10 — The F08 Headers-auth repair is incomplete for non-Authorization credentials. AuthHeaders deliberately accepts an arbitrary HeaderMap and HeaderAuthProvider sends the complete map, but ProviderAccountScope hashes only the Authorization value when no stable account/user identity exists. Scenario: external auth rotates an x-api-key-only credential; the account-scope digest remains unchanged, so model cache/provider state from the prior credential scope can be reused. Repair: hash a canonical, domain-separated, length-framed representation of the complete credential header map when no authoritative account/user identity exists, and cover arbitrary headers plus insertion-order stability.
