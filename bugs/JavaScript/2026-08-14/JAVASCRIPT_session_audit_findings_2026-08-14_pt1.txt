```text
fixture tier
→ relation class
→ numeric score
→ Unicode path order
```

## Dependency comparison

### 1. `contentGeneration` and semantic state

`contentGeneration` advances for every tracked addition, content change, removal, planning-only change, and extraction recovery at [indexer.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:1632). The semantic lifecycle listener then invalidates all language entries at [services.js](C:/Users/kuh/Desktop/Repo-Atlas/src/services.js:358).

The true dependency is language-specific:

- TypeScript/JavaScript: JS/TS files and relevant JS project/module configuration.
- Neither provider depends on planning-only Markdown, schemas, migrations, Dockerfiles, or the other language’s source.
- Extraction recovery with byte-identical source can affect structural summaries but cannot affect the compiler workspace.

Concrete unnecessary invalidations:

- `docs/guides/setup.md` invalidates both providers.
- A `.ts` body edit retires a warm Rust Analyzer.
- A `.rs` edit retires the TypeScript provider.
- `AGENTS.md`, `README.md`, or `SOURCEMAP.md` changes retire both.

This is the clearest high-cost mismatch.

### 2. `manifestGeneration` and graph caches

All configured metadata files are classified as `other`. That set includes Cargo/package manifests, but also `tsconfig`, `jsconfig`, Justfiles, README, AGENTS, CLAUDE, SOURCEMAP, and top-level docs at [config.js](C:/Users/kuh/Desktop/Repo-Atlas/src/config.js:60). The service graph cache keys directly on that generation at [services.js](C:/Users/kuh/Desktop/Repo-Atlas/src/services.js:751). Yet `buildGraph()` selects only:

- `Cargo.toml`
- `package.json`
- `pnpm-workspace.yaml`

as shown at [graph.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/graph.js:130).

Therefore edits to `tsconfig.json`, `Justfile`, `AGENTS.md`, `CLAUDE.md`, `README.md`, `SOURCEMAP.md`, and top-level documentation unnecessarily mark the graph stale. The next graph-dependent task, placement, summary, trace fallback, or impact request rebuilds it.

`_rebuildPlanningTermIndex()` reconstructs all per-file evidence and the full inverted map at [indexer.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:1866). It is invoked unconditionally after every successful sweep at [indexer.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:1625).

The read identity itself is good: `path + indexed hash` at [semantic.js](C:/Users/kuh/Desktop/Repo-Atlas/src/tools/semantic.js:774). This prevents conflating different indexed versions.

The miss problem is cache lifetime and partitioning:

- General analysis memos live for one trace/impact invocation at [analysisMemo.js](C:/Users/kuh/Desktop/Repo-Atlas/src/tools/analysisMemo.js:1).
- Task planning maintains separate `seedReads`, `verifiedReads`, `semanticVerificationReads`, and `semanticSeedValidationReads` maps at [taskContextTool.js](C:/Users/kuh/Desktop/Repo-Atlas/src/tools/taskContextTool.js:1925).
- Separate batch children do not share their request-local verified reads.

Within one captured fresh-snapshot scope, those namespaces have the same true dependency and could safely share a single exact-read promise map. Cross-request persistence would require care because the disk must still be revalidated against the indexed hash.

### 7. Persistent index state

The persistent artifact is monolithic: files, symbols, identifiers, planning records, health, exclusions, generations, and snapshot are serialized and gzipped together at [indexer.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:1010).

Over-invalidation occurs because:

- Watcher-named paths force `refreshRecord` even when bytes and stored metadata are identical.
- Any `recordChanged` schedules persistence at [indexer.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:1634).
- Refresh-health count changes can independently schedule persistence.
- A touch-only metadata update rewrites the whole compressed artifact even though extracted symbols, identifiers, planning terms, generations, and snapshot remain unchanged.
- Startup deliberately forces a full hash pass even after a valid cache load at [indexer.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:458). This avoids reparsing but still rereads every tracked byte once per process.

Splitting inventory metadata/health from expensive extracted state would contain these writes.

### 8. History and co-change

The raw history identity is otherwise well designed: canonical selected root, repository root, HEAD, bounds, flags, and path filters at [gitlog.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/gitlog.js:176). Working-tree edits do not invalidate history, and TTL expiry only probes state before deciding whether to remine.

Three misses remain:

- A new commit outside a selected subdirectory or custom path filter changes repository HEAD but cannot change the filtered `git log`; it still remine-loads history.
- A valid `null` history is immediately evicted at [services.js](C:/Users/kuh/Desktop/Repo-Atlas/src/services.js:825), so a selected path with no matching commits repeats both state probing and history loading on every call.
- `cochangeFor()` scans the cached commit list and recomputes totals and weighted relationships for every request at [gitlog.js](C:/Users/kuh/Desktop/Repo-Atlas/src/core/gitlog.js:361). There is no bounded `(history identity, path, limit)` result cache.

## Recommended invalidation shape

The highest-return change would be to introduce narrow dependency stamps:

- `graphGeneration`: only graph-relevant manifests.
- `summaryGeneration`: graph stamp plus the summary-specific file/symbol/document projection.
- `semanticGeneration.rust` and `.typescript`: language-specific compiler inputs.
- `planningGeneration`: only planning evidence or policy/cap changes.
- A snapshot dirty flag so the global digest is recomputed only after indexed content changes.

Then unify verified-read promises within one fresh-snapshot request, avoid no-op persistent rewrites, cache valid empty history for the TTL, and optionally add bounded planning/co-change result caches.
