## Audit result

Repo Atlas has eight material concurrency opportunities. The largest are the two global serialization layers: JSON-RPC dispatch and fresh-snapshot scopes. Together they turn independent read-only requests into `Σ latency` rather than approximately `max latency`.

This is a source-level critical-path analysis, not a runtime benchmark. I audited the current working tree, including its pre-existing uncommitted changes, and made no edits.

### 1. Global JSON-RPC and fresh-snapshot serialization

The server chains every ordinary frame onto one promise at [server.js:745](/C:/Users/kuh/Desktop/Repo-Atlas/src/server.js:745). Items inside a JSON-RPC batch are also awaited individually at [server.js:529](/C:/Users/kuh/Desktop/Repo-Atlas/src/server.js:529). After that, `withFreshSnapshot` queues the entire handler again at [indexer.js:525](/C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:525).

Consequently, two unrelated `inspect`, `context`, or `impact` requests cannot overlap—even after freshness has committed and neither can refresh the index.

Safe design: replace `_snapshotQueue` with a reader/writer epoch:

- One writer runs `ensureFresh()`.
- All admitted read-only handlers join the resulting snapshot epoch concurrently.
- A dirty refresh waits until that epoch’s readers finish.
- `select_root` and root replacement remain exclusive.
- Pure control-plane calls such as `tools/list` and `resources/list` can bypass the repository queue immediately, as `ping` already does.

Safety proof:

- Snapshot consistency: committed index state is copy-on-write; nested `ensureFresh()` is already suppressed by `AsyncLocalStorage`. Holding refresh until the reader count reaches zero prevents map replacement during the cohort. Hash-pinned reads still reject disk changes.
- Determinism: each handler has its own context and output. JSON-RPC batch results can be stored by input index and emitted in original order.
- Cancellation: existing per-request `AbortController`s remain independent. Cancellation removes only that reader; started provider work receives the same signal.
- Resources: retain `maxPendingRequests` and add a smaller active-reader limit. State-changing requests and semantic lifecycle mutations should use exclusive or per-provider lanes.

This also removes head-of-line blocking for lightweight control-plane requests. The existing test explicitly characterizes only one serialized request starting at [server.test.js:799](/C:/Users/kuh/Desktop/Repo-Atlas/test/server.test.js:799).

### 2. MCP `batch` children

After validation, every unique child is created and immediately awaited before the next is launched at [batchTool.js:159](/C:/Users/kuh/Desktop/Repo-Atlas/src/tools/batchTool.js:159). Up to sixteen otherwise independent operations therefore contribute additively to latency.

Safe initial concurrency set:

- `inspect.index_status`
- `inspect.crate_graph` and `inspect.crate_summary`
- `context.path` and `context.placement`
- `impact.cochange`
- structural symbol-definition lookups

Semantic-capable children should use per-language lanes so one provider retirement cannot race another child unpredictably. Canonical duplicate keys should still execute once.

Safety proof:

- Snapshot consistency: every child already uses the outer captured snapshot through `invokeInScope`; no child creates another freshness scope.
- Determinism: preallocate result slots, run unique executions concurrently, then clamp and render strictly by operation index. Shared instructions are already finally sorted.
- Cancellation: use a bounded sliding window, stop admission when the common signal aborts, abort all admitted children, and await settlement before rejecting. This preserves a single cancellation result and prevents detached work.
- Resources: cap active children, for example at four, despite the existing sixteen-operation input bound. Use one lane per semantic provider and one shared-process lane for resource-heavy subprocess work.

The existing same-snapshot contract is tested at [batchTool.test.js:864](/C:/Users/kuh/Desktop/Repo-Atlas/test/batchTool.test.js:864); only the sequential execution assumption at [batchTool.test.js:186](/C:/Users/kuh/Desktop/Repo-Atlas/test/batchTool.test.js:186) would need replacement.

### 3. Rust and TypeScript task evidence

`context.task` groups seeds by language but then awaits each language group sequentially at [taskContextTool.js:394](/C:/Users/kuh/Desktop/Repo-Atlas/src/tools/taskContextTool.js:394). The individual seeds within one language are already concurrent.

Rust and TypeScript groups are independent:

- They occupy separate `semanticEntries` keys.
- They use different child processes and protocols.
- Results are not used to seed the other language.
- Final candidate merging is language-agnostic.

This matters because first-lease waits can expose up to 8.5 seconds for Rust and 500 ms for TypeScript in the current tree at [services.js:485](/C:/Users/kuh/Desktop/Repo-Atlas/src/services.js:485), before targeted query deadlines are considered.

Safety proof:

- Snapshot consistency: both leases bind the same content generation, and each group performs post-query seed/hash and lease revalidation.
- Determinism: launch groups with `Promise.allSettled` in sorted language order, return immutable group results, then merge results in that same order.
- Cancellation: both groups receive the same request signal; a fatal error retires only its language entry.
- Resources: at most two groups exist—Rust and TypeScript—so process concurrency remains statically bounded.

Safe design: query one sorted frontier concurrently, then consume settled results in the original frontier order before allocating node budgets or constructing the next frontier.

Safety proof:

- Snapshot consistency: every semantic helper revalidates the generation and hash-pinned target content.
- Determinism: cap allocation, first-parent selection, deduplication, and failure handling occur only during ordered consumption—not inside concurrent workers.
- Cancellation: provider requests already accept the shared signal. Await all admitted requests before leaving the frontier.
- Resources: use a small provider-specific cap. ### 5. Index refresh per-file preparation

After the already-concurrent repository walk, refresh processes candidate files one at a time at [indexer.js:1578](/C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:1578). Each candidate independently performs confined open/stat/read/hash and parsing before mutating the transaction’s working maps.

Safe design: split indexing into:

1. Bounded concurrent preparation producing immutable `{record, symbols, identifiers, planningEvidence, failure}` values.
2. Ordered single-threaded commit into the copied maps and posting sets.

Safety proof:

- Snapshot consistency: no prepared result is published until every candidate succeeds. Any failed read still discards the complete transaction using the existing checkpoint.
- Determinism: commit prepared results in the original sorted candidate order; generation counts and posting-set mutations remain single-threaded.
- Cancellation: refresh is deliberately shared and currently not request-cancellable. A pool should drain admitted reads after failure, then perform the same rollback.
- Resources: use the existing filesystem pool scale—currently twelve—not unbounded `Promise.all`. Per-file size and total cache/cardinality limits remain unchanged.

Parsing is synchronous JavaScript, so concurrency primarily overlaps filesystem validation and reads; it does not claim CPU parallelism.

### 6. Rust and JavaScript graph discovery

`buildGraph` completes all Rust manifest and Cargo work before starting JavaScript workspace discovery at [graph.js:139](/C:/Users/kuh/Desktop/Repo-Atlas/src/core/graph.js:139) and [graph.js:192](/C:/Users/kuh/Desktop/Repo-Atlas/src/core/graph.js:192).

The JavaScript scan can start immediately while Rust processing continues. Their source manifests are disjoint (`Cargo.toml` versus `package.json`/pnpm metadata), and neither branch consumes the other’s result.

Safety proof:

- Determinism: await both branches and retain the existing name/kind/manifest sort before merging.

These sequences are genuine dependencies:

- Refresh must commit before a fresh snapshot is captured.
- Summaries require the graph.

- Later BFS depths depend on the prior frontier, though nodes within a frontier do not.
- TypeScript’s implementation fallback depends on an empty outgoing-call result.
- Final cap allocation and rendering must remain ordered even when evidence collection is concurrent.

2. **High — semantic generations omit compiler-visible inputs.** Rust invalidation recognizes Rust files and `Cargo.toml`; TypeScript recognizes JS/TS files and a small config list ([indexer.js](/C:/Users/kuh/Desktop/Repo-Atlas/src/core/indexer.js:187)).
