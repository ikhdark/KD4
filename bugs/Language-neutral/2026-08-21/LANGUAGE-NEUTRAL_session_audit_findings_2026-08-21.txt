First, make “turn completes correctly” a release gate. A publish should fail validation if a basic tool-using turn can enter `active_without_pending_tool`, retain `running_process` after the process is gone, or exceed a reasonable orchestration budget after the tool itself has completed. Otherwise you can keep shipping local fixes while the underlying lifecycle remains broken.

Second, bisect the behavior historically instead of only debugging HEAD. If you have a known publish where turns worked well, run the same small deterministic workload against each publish between that version and now. Measure:

-  tool process runtime
-  process-exit → handler-return
-  handler-return → result-delivery
-  result-delivery → next sampling
-  final turn completion
-  final lifecycle state

That could identify the exact publish where the pathological behavior first appeared. Even if performance degraded gradually, you’ll see which change caused each jump.

Third, I would resist adding more watchdogs until the ownership/state bug is understood. Five publishes of trouble can happen when each fix handles a symptom—timeout, stale process, missed completion, slow delivery—while the underlying transition contract is still wrong. A watchdog can make those turns eventually recover while hiding the race that caused them to get stuck.

The pattern you have now makes me especially suspicious of a lifecycle sequence resembling:

`tool accepted → process runs → process exits → completion recorded somewhere → ownership/state not fully released → relay waits for an event that already happened → timeout/watchdog eventually wakes it`

That would neatly explain why actual process time can be tiny while handler/gate time explodes, why dead processes still appear “running,” and why some turns become active with no pending tool.

I’d also add one regression test that repeatedly executes a tiny immediate command hundreds or thousands of times through the real production orchestration path, not a mocked executor. Every iteration should end with the exact same clean state. Intermittent lifecycle races often won’t show up in a handful of tests.

Given the five-publish history, I’d now make the project goal something closer to: **prove the turn state machine has one owner and one deterministic path from tool completion back to model sampling**. Parallel tool calls and performance optimization should come after that. If single-tool turns cannot reliably close, concurrency will make the underlying problem harder to reason about.
