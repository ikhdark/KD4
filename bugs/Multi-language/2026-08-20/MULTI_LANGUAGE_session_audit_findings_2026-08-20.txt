A matching replay therefore calls `createPendingSubscriber` again and can create tokens or send email again ([route.ts:357](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/alert-signups/route.ts:357), [migration:1](C:/Users/kuh/Desktop/mdpwa-main/migrations/0007_alert_signup_idempotency.up.sql:1)).

   Consequences include:

   - Replaying an originally confirmed signup generates management links and invokes another email.
   - Replaying after unsubscribe changes the subscriber back to `pending`, clears unsubscribe state, and records a misleading `restored` consent event ([subscriberRepository.ts:190](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:190), [subscriberRepository.ts:217](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:217)).
   - The route can then return 503 because its deterministic confirmation token was already revoked.
   - This directly conflicts with the documented rule that a stored replay returns its durable outcome without repeating notification side effects ([SOURCEMAP.md:97](C:/Users/kuh/Desktop/mdpwa-main/SOURCEMAP.md:97)).

   The durable ledger should record the subscriber/outcome and delivery-acceptance state. Lifecycle mutation must never be reconstructed from an old POST replay.

2. **Expired or revoked sessions remain valid after unsubscribe.**

   The session lookup requires a live session for confirmed or suppressed subscribers, but the unconditional `OR subscriber.status = 'unsubscribed'` bypasses both expiry and revocation ([subscriberRepository.ts:481](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:481)).

   Anyone retaining an old session cookie can retrieve the unsubscribed resident’s name, email, locale, topics, and status until retention eventually deletes that session—despite the advertised 30-minute session lifetime. The same bypass exists in repeated-unsubscribe authorization ([subscriberRepository.ts:555](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:555)).

   GET access should always require an unexpired, unrevoked session. Idempotent DELETE replay needs a separately bounded mechanism.

3. **Suppression and administrative revocation leave consumed email links usable.**

   Consumed action tokens are intentionally replayable and mint a fresh management session ([subscriberRepository.ts:404](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:404)). However:

   - Resend bounce/complaint suppression revokes only tokens where `consumed_at IS NULL` ([resend route.ts:149](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/webhooks/resend/route.ts:149)).
   - Administrator suppression/unsubscribe has the same filter ([subscriberRepository.ts:690](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:690)).

   A previously opened link therefore survives the operation that claims to revoke the subscriber’s credentials and can continue producing sessions for up to its 24-hour or 7-day lifetime. Both revocation paths need to revoke every action token.

### Medium severity

4. **The public POST endpoint exposes whether an email is already confirmed.**

   The response contains `signupStatus` without proving ownership ([route.ts:418](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/alert-signups/route.ts:418)), and the UI explicitly reports that the address was already confirmed ([AlertSignupForm.tsx:132](C:/Users/kuh/Desktop/mdpwa-main/src/components/AlertSignupForm.tsx:132)). Confirmed, pending, and suppressed addresses also take observably different 201/503 paths.

   This enables subscriber enumeration and conflicts with the repository’s rule not to expose alert signups. Return a generic public result and perform state recovery only through email.

5. **A pending resident cannot request a replacement confirmation for up to 24 hours.**

   For an already-pending email submitted with a new key, the repository refuses to create another token while an active confirmation token exists, but it cannot recover the raw existing token ([subscriberRepository.ts:261](C:/Users/kuh/Desktop/mdpwa-main/src/lib/subscriberRepository.ts:261)). The route consequently returns 503 ([route.ts:412](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/alert-signups/route.ts:412)) and tells the resident to retry after 15 minutes, even though the blockage can last for the token’s full 24-hour lifetime.

   A controlled replacement flow should revoke/rotate the prior token and send a new one without revealing subscriber state.

6. **Deployment readiness permits production without required signup confirmation email.**

   Every email check is advisory ([deploymentReadiness.ts:632](C:/Users/kuh/Desktop/mdpwa-main/src/lib/deploymentReadiness.ts:632)), so `canDeploy` remains true when confirmation email is entirely unavailable. That contradicts the source-of-truth designation of resident signup confirmation as a required release capability ([SOURCEMAP.md:96](C:/Users/kuh/Desktop/mdpwa-main/SOURCEMAP.md:96)).

   The check also combines optional administrator notification settings with the required resident confirmation sender. These should be split into a production-blocking confirmation check and an advisory administrator-notification check.

7. **The signup idempotency ledger has no retention path.**

   The table has a `created_at` index but no deletion or redaction logic ([migration:9](C:/Users/kuh/Desktop/mdpwa-main/migrations/0007_alert_signup_idempotency.up.sql:9)). The retention job covers subscribers, tokens, sessions, and deliveries but not `subscriber_signup_requests` ([retention.mjs:216](C:/Users/kuh/Desktop/mdpwa-main/src/lib/retention.mjs:216)).

   Rows and deterministic hashes of names, emails, locale, phone presence, and topics accumulate indefinitely. Add a bounded retention period and corresponding candidate counts, deletion evidence, and tests.

- Confirmation GET is inert against automated mail scanners; state changes require POST.
- Tokens are stored as hashes, cookies are HttpOnly/SameSite, and sensitive responses use no-store headers.
- Broadcast selection is restricted to confirmed subscribers.
- English and Spanish signup paths are paired, and the form has solid accessibility behavior.
