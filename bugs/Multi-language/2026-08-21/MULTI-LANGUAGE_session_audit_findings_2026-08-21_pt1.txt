### 1. Cancellation and finalization closure

**Historical motivation:** TASK-03, TASK-06, TASK-08; EXEC-02, EXEC-03, EXEC-05, EXEC-06, EXEC-07 and EXEC-17; MCP-02 and MCP-05; TIME-02. Examples include blocking scans without cooperative cancellation, rollback launched from `Drop` using an ambient Tokio runtime, cancellation tokens not propagated through OAuth/config stages, cleanup loops abandoned by `?`, process registrations stranded during shutdown, and remote work reported as cancelled when only the local future was dropped ([TASK-03 onward](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:377), [EXEC-02 onward](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:610), [MCP-05](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1308)).

Later tests for bounded cancellation of non-cooperative callbacks, process-exit/delivery races, stalled commands, and terminal-output delivery show that this remained a substantial runtime-hardening concern in `37f7f9bf36`.

**Generalized invariant:** Once code acquires responsibility for work or a resource, every return, error, cancellation, panic boundary, shutdown path, and destructor must do exactly one of:

- finalize and confirm termination;
- transfer ownership to a recognized durable supervisor;
- persist enough state for deterministic recovery;
- return an explicit unknown or incomplete outcome.

Cancellation tokens must reach every downstream cancellable stage. Cleanup of a collection must attempt every item and aggregate errors instead of allowing the first `?` to abandon later obligations.

**Breadth:** Very broad across `codex-core`, unified execution, process management, MCP clients, task rollout, OAuth, hooks, code mode, callback registries, and background persistence.

**Detectability:** Acceptable with rust-analyzer HIR, resolved call identities, CFG exit analysis, type information, and configurable contracts for acquire/transfer/finalize/cancel operations. High-confidence cases include:

- `tokio::spawn` as the sole correctness mechanism inside `Drop`;
- a `CancellationToken` parameter that is not forwarded to a cancellable callee;
- `?` inside a cleanup loop following acquisition;
- process kill without a subsequent bounded reap;
- local future cancellation translated into remote cancellation success.

Recognizing opaque supervisors or external crate guarantees requires annotations.

**Would catch before runtime:** Orphaned tasks, leases, callbacks and process trees; shutdown hangs; partially cleaned process sets; false cancellation acknowledgement.

**Likely false positives:** Intentionally detached idempotent telemetry, resources whose cleanup is guaranteed inside an opaque dependency, and typed ownership transfers the analyzer has not yet been taught.

### 2. Shared-state linearization and publication protocols

**Historical motivation:** VAL-03 registered singleflight work against a stale epoch; VAL-04 removed the flight before publishing and notifying; VAL-06 allowed a losing key creator to observe a partially written file; EXEC-04 could evict live attempts; TIME-03 removed a callback after a later recipient failed even though an earlier recipient could still answer ([VAL-03/04](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:141), [EXEC-04](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:668), [TIME-03](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1715)).

The same theme reappears in `df89702c4d`, `4db08a95ce`, and `37f7f9bf36`: evidence staleness, terminal-authority selection, independent store commits, watcher wakeups, buffered output notification, and process-exit versus delivery ordering.

**Generalized invariant:** A coordination object must follow a linearizable state machine:

`register with current identity → produce terminal state → publish state → notify waiters → become evictable`

Freshness identities must be captured before deduplication. An active entry cannot be capacity-evicted. A multi-producer or multi-recipient entry remains live until no authorized producer can still complete it.

**Breadth:** Validation singleflight, task stores, process registries, callbacks, evidence watchers, mutation caches, terminal-output delivery, leases, and background attempt tracking.

**Detectability:** Acceptable for codex-rs with semantic contracts identifying register, publish, notify, invalidate and remove operations. CFG and field-sensitive analysis can detect incorrect intra-function ordering and removal on only some branches. Cross-function and cross-thread correctness needs summaries for the state-machine-owning types; a global name-based heuristic would be too noisy.

**Would catch before runtime:** Duplicate leaders, stale validation reuse, missed wakeups, live attempt eviction, partial key visibility, lost callbacks, and output races.

**Likely false positives:** Advisory notifications, stores whose transaction commit implicitly publishes and wakes, entries intentionally hidden during publication, or synchronization guarantees implemented by an unmodeled wrapper type.

### 3. Deadline closure and aggregate latency budgets

**Historical motivation:** TASK-05 awaited shutdown and rollout without deadlines; EXEC-02 and EXEC-05 could wait forever during finalization or draining; EXEC-15 killed after timeout but then waited without another bound; TUI-02 allowed roughly 50 sequential 30-second commands; MCP-01 had a graceful timeout followed by unbounded forced shutdown; MCP-04 serialized client latency; TIME-01 added unconditional polling delay ([TASK-05](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:436), [EXEC-15](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:989), [TUI-02](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1105), [MCP-01](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1192)).

**Generalized invariant:** A deadline must dominate the entire terminalization protocol, including forced fallback, kill, reap, drain, join and notification. A loop or fan-out operation also needs an aggregate deadline or concurrency bound; per-item timeouts do not establish an operation-wide bound.

**Breadth:** Process execution, task shutdown, MCP fan-out, diff generation, network calls, background workers and test orchestration.

**Detectability:** Good. Rust-analyzer semantics can resolve `timeout`, `select!`, cancellation futures, awaited calls and loop structure. An interprocedural deadline context can identify an awaited terminalization phase outside the protected scope and sequential loops whose worst-case duration is `item count × per-item timeout`.

KDA already recognizes direct missing timeout boundaries, but the current implementation treats visible ancestor timeout/select wrappers as protection ([lifecycle.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/lifecycle.rs:176)). The useful addition is protocol-wide and aggregate deadline reasoning, not another direct-call list.

**Would catch before runtime:** Shutdown hangs, post-kill hangs, minute-scale command stalls and multiplicative MCP/TUI latency.

**Likely false positives:** Tiny statically bounded collections, operations proven immediate after a successful kill, and shutdown APIs intentionally allowed to block indefinitely by documented policy.

### 4. Identity-preserving validation and use

**Historical motivation:** MCP-07 permitted out-of-root uploads through joined absolute or traversal paths; MCP-08 checked path metadata and later reopened the pathname; TUI-03 performed metadata/read TOCTOU; EXEC-09 retained one file handle but reopened the pathname for reading; PATCH-02 compared endpoint strings instead of filesystem identity; VAL-06 exposed a partially created key file ([MCP-07/08](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1366), [TUI-03](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1134), [EXEC-09](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:815)).

**Generalized invariant:** Security, size, type, freshness or confinement validation must be attached to the same opened object or immutable snapshot consumed by the sink. Reopening a pathname after validation requires revalidation. Path confinement must reject absolute escape, parent traversal and symlink/reparse escape according to the operation’s policy. Same-file questions require identity, not lexical equality.

**Breadth:** MCP uploads, artifacts, logs, patches, diffs, configuration, caches, credentials and validation evidence.

**Detectability:** Generally high precision. Semantic dataflow can distinguish `File` handles from `Path` values, trace `metadata(path) → read(path)`, resolve `join`, `canonicalize`, `open`, `rename` and upload sinks, and detect when validation facts are applied to a different value. OS-specific alias and reparse behavior requires platform-aware contracts.

**Would catch before runtime:** Arbitrary host-file upload, symlink swaps, size-check bypass, artifact substitution, inconsistent same-file handling and partially published files.

**Likely false positives:** Immutable deployment trees, paths protected by an exclusive directory lock, private temporary directories, or cases where content identity is explicitly irrelevant.

### 5. Atomic multi-effect and compensation protocols

**Historical motivation:** VAL-05 independently wrote and pruned related persistence stores; TASK-09 installed OAuth credentials before durable configuration; MCP-09 left earlier remote uploads behind when a later upload failed; EXEC-10 removed the protection marker before deleting logs; EXEC-14 deleted the destination before a fallible rename; TIME-03 rolled back shared callback state despite a partially successful send ([VAL-05](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:201), [TASK-09](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:552), [EXEC-10](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:844), [MCP-09](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1424)).

**Generalized invariant:** Related effects forming one logical operation must either commit together or retain explicit compensating state. Authority or protection markers change only after all fallible preparation succeeds. Every error after the first external effect must compensate all prior effects or return a typed partial-commit state.

**Breadth:** Persistent state, credentials/configuration, remote uploads, artifact publication, callback dispatch, log cleanup and destructive replacement.

**Detectability:** Acceptable only as a contract-driven analysis. Resolved calls should be classified as `prepare`, `effect`, `commit`, `protect`, `rollback` or `destructive replace`; CFG and postdominance analysis can then inspect all `Result` error edges. KDA’s existing durability pass deliberately restricts itself to linear statements in one lexical block ([durability.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/durability.rs:3)); branches, compensation and interprocedural effect groups are the important extension.

**Would catch before runtime:** Orphan credentials and remote files, split persistence state, unprotected logs, destructive replacement loss and invalid rollback of partially successful fan-out.

**Likely false positives:** APIs explicitly designed for partial success, externally reconciled idempotent effects, and stores providing an implicit transaction that the analyzer has not modeled.

### 6. Whole-cost bounds and persistent-state accounting

**Historical motivation:** VAL-01 silently truncated searches at 64 rows; TASK-01 recovered only 256 tasks; TASK-04 and EXEC-01 leaked keyed global state; EXEC-04 evicted live attempts; EXEC-11 rejected before reclaiming space; TUI-01 read untracked files without byte limits; MCP-03 allowed unbounded cursor cycles; MCP-06 repeatedly serialized a growing response; AGENTS-01/02 omitted rendered overhead and allowed each environment to consume the aggregate budget ([VAL-01](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:83), [TASK-01/04](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:318), [MCP-03/06](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1250), [AGENTS-01](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1598)).

Commit `7f08c056cd` subsequently added bounded TUI streaming and extensive boundary tests, reinforcing the recurrence.

**Generalized invariant:** Every persistent collection and externally driven traversal needs a declared cost domain and completion policy:

- bytes, rendered bytes, items, pages, active entries, completed entries, or elapsed time;
- bounded, evicted, paginated or explicitly process-lifetime;
- truncation surfaced to callers when completeness matters;
- reclamation performed before rejection;
- aggregate budgets shared rather than independently duplicated.

**Breadth:** Task stores, caches, attempt registries, command output, tool history, instructions, MCP pagination, diffs and recovery scans.

**Detectability:** Mixed. Strong useful cases include static `HashMap` insertion without removal/sweep, unbounded reads/collects, pagination loops without total/cycle bounds, and serialization of a growing collection inside its construction loop. Rust semantics alone cannot reliably infer SQL query completeness, statistical sufficiency, or whether a numeric cap matches a product requirement. Those require explicit cost-domain contracts or query-language support.

**Would catch before runtime:** Memory growth, incomplete recovery, active-entry eviction, runaway pagination, huge diff reads and quadratic response building.

**Likely false positives:** Naturally finite key spaces, deliberately process-lifetime registries, APIs that guarantee finite pagination, and small collections whose bound is maintained externally.

### 7. Fail-closed uncertainty and provenance continuity

**Historical motivation:** VAL-02 allowed unparseable “do not test” wrappers; TASK-02 discarded immutable validation evidence; SRC-01 mixed host `HOME` with a selected executor’s namespace; SRC-02 relied on an incomplete handwritten Git parser; SRC-03 collapsed I/O errors into absence; PATCH-01 interpreted PowerShell and Cmd text as Bash; TUI-04 corrupted non-UTF-8 Git paths ([VAL-02](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:112), [TASK-02](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:347), [SRC-01/03](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1453), [PATCH-01](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1540)).

Later tests in `df89702c4d` and `4db08a95ce` explicitly require unparseable or uncertain mutating commands to fail closed and preserve evidence identity.

**Generalized invariant:** At an authority or safety boundary, `Unknown`, parser failure and I/O failure cannot enter the permissive branch. The parser dialect, filesystem namespace, environment, path representation and evidence identity must remain consistent with the eventual sink. Conversion boundaries must preserve immutable authority fields.

**Breadth:** Validation admission, shell interception, local/remote execution, source discovery, evidence transport, generated protocols and filesystem paths.

**Detectability:** Acceptable with typed provenance tags and configured safety sinks. Strong cases are `Err | Unknown => allow`, a Bash parser selected despite a resolved non-Bash shell, host environment APIs mixed with executor filesystem operations, or accepted evidence fields dropped/defaulted during conversion. Proving that a handwritten Git parser is fully compatible with Git is outside normal Rust semantic analysis.

**Would catch before runtime:** Policy bypasses, wrong-shell interception, remote/local namespace confusion, discarded evidence and silent partial source discovery.

**Likely false positives:** Low-risk prediction paths where uncertainty is intentionally permissive, best-effort discovery, or environment equivalence established outside the analyzed function.

### 8. Outcome truthfulness and error aggregation

**Historical motivation:** VAL-07 globally suppressed unrelated warning classes; EXEC-08 logged finalization failure but still marked execution finished; MCP-05 claimed remote cancellation without acknowledgement; SRC-03 treated errors as absence; COMPACT-01 discarded the fallback failure and returned only the primary error ([VAL-07](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:260), [EXEC-08](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:784), [COMPACT-01](/C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1744)).

**Generalized invariant:** A failure, partial result or unknown outcome cannot be converted to success, completion, cancellation or absence without proof of recovery. When multiple attempts fail, the diagnostic outcome retains all causally relevant failures. Suppression keys must correspond to stable diagnostic classes, not one global bit.

**Breadth:** Tool results, process completion, shutdown, source scanning, compaction, validation and user-visible diagnostics.

**Detectability:** Acceptable when outcome types or contracts provide an ordering such as `Success > Partial > Unknown > Failed`. Semantic dataflow can find `Err` values that are only logged before returning a success discriminant, dropped secondary errors, and broad suppression state reused across different result classes. Names alone would not provide adequate precision.

**Would catch before runtime:** False successful completion, false cancellation acknowledgement, incomplete scans presented as complete and loss of the most useful fallback diagnostic.

**Likely false positives:** Explicit best-effort subsystems, privacy-driven error redaction, fallback paths that genuinely recover, and APIs intentionally designed to squash lower-level causes.

## Recommended analyzer shape

These should not become eight families of KD4-specific function-name checks. The reusable foundation is five semantic fact systems:

1. ownership obligations: acquire, transfer, finalize;
2. protocol phases: prepare, publish, notify, commit, compensate;
3. identity and provenance: object, revision, executor, shell, evidence;
4. budgets: deadline, bytes, items, active entries;
5. outcome lattices: success, partial, unknown, failed.

KDA already has useful seeds—lifecycle protocols, missing timeouts, effect ordering, unbounded-resource checks, conversion-field loss, freshness and structured-result collapse ([current lint inventory](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:723)). The historical evidence argues for making those analyses interprocedural, contract-aware and identity-sensitive rather than adding more lexical lint IDs.

I would not prioritize generic RA lints for VAL-08’s statistical validity, SRC-02’s Git grammar completeness, or product-specific choices such as an exact row cap. Those need domain validators, model tests or embedded-language analysis; pretending Rust semantics can prove them would create noise rather than prevent KD4 debugging.

## 1. Interprocedural operation-obligation closure

Historical motivation:

- TASK-03, TASK-05, TASK-06, and TASK-08: cancelled scans kept running, eviction waited indefinitely, rollback depended on a Tokio runtime, and cancellation was propagated through only one stage.
- EXEC-02, EXEC-03, EXEC-05–07, EXEC-15, and EXEC-17: unbounded finalization, leases stranded outside a runtime, missing notifications, cleanup stopped after the first error, unreaped children, and surviving descendants.
- MCP-01, MCP-02, MCP-05, and TIME-02: forced shutdown had no deadline, failed clients were not terminated, local future drop was reported as confirmed remote cancellation, and dropped requests left callbacks registered. See the [process/lifecycle cluster](C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:436).
- Later repairs repeated the pattern: overwritten process-root registrations in `0d1c726b`, untracked persistence in `4db08a95`, and connection/challenge ownership leaks in `52be9e924d`.

Generalized invariant:

> Every acquired operation obligation—child process, task, lease, callback, registry entry, reservation, notification, or remote request—must be consumed exactly once or explicitly transferred on every success, error, cancellation, timeout, unwind, and shutdown path.

A transferred obligation must remain owned. Cleanup of a collection must attempt every member and aggregate errors. A timeout followed by forced cleanup needs a bound on both phases.

Breadth across codex-rs: extremely broad. It applies to unified exec, shell hooks, MCP clients, multi-agent tasks, task residency, output watchers, callback registries, OAuth flows, and keyed state.

Rust-analyzer feasibility: acceptable with medium–high precision. rust-analyzer can resolve constructors, calls, types, `Drop` implementations, returned ownership, `?` exits, and async control flow. KDA would need effect declarations identifying acquisition, transfer, and terminal operations. This should strengthen the existing lifecycle, keyed-protocol, child-process, and timeout analyses rather than create per-resource lint names.

Caught before runtime: orphaned process trees, permanently held capacity, futures waiting on notifications that may never fire, local cancellation falsely presented as remote cancellation, and cleanup paths dependent on a runtime that may no longer exist.

Likely false positives: intentionally detached daemon work, cleanup guaranteed by an external supervisor, process-exit cleanup, deliberately permanent registries, and RAII guards whose terminal effect is hidden behind dynamic dispatch.

## 2. Transactional effect-set analysis

Historical motivation:

- VAL-04–06: an in-flight record was removed before publication, related history rows committed independently, and concurrent key creation exposed partial content.
- TASK-09 and MCP-09: credentials or remote files were created before later operations failed, leaving orphaned state.
- EXEC-10, EXEC-13, and EXEC-14: marker/log ordering, missing parent-directory durability, and delete-before-replace could expose or destroy artifacts.
- TIME-03: one recipient received a request, another failed, and the callback for both was removed.
- The root audit found backup publication before safe destination validation, while the scripts audit grouped at least six release/package partial-commit failures. See [transactional script failures](C:/Users/kuh/Desktop/bug/kd4_scripts_full_review_63dde623.txt:38).
- `52be9e924d` added a particularly revealing case: rollback restored an old whole-document snapshot and could overwrite a newer concurrent mutation.

Generalized invariant:

> Effects presented as one logical state transition must either commit atomically or have complete, version-safe compensation for every committed prefix.

Preparation and validation precede visible mutation; durable state precedes publication; rollback must not restore stale snapshots over newer versions.

Breadth: persistence, cache publication, credentials/configuration, remote uploads, callbacks, validation history, artifact replacement, live configuration, and generated mirrors.

Rust-analyzer feasibility: medium precision, provided KDA supports effect summaries such as `prepare`, `durable_write`, `publish`, `commit`, and `compensate`. It can detect `?`, returns, and awaits between effects, missing rollback guards, and stale snapshot restoration without an intervening version check. Arbitrary external transactions cannot be inferred from Rust types alone.

Caught before runtime: half-configured accounts, leaked uploads, duplicate singleflight leaders, partial database state, exposed logs, old destination loss, and rollback clobbering newer state.

False positives: intentionally resumable partial progress, idempotent eventually consistent operations, APIs that are internally transactional, and workflows where a durable repair queue is the documented compensation.

## 3. Canonical identity and key completeness

Historical motivation:

- VAL-03 used a turn-local mutation identity before merging the repository-wide epoch.
- PATCH-02 compared unresolved path strings rather than filesystem identity.
- `4db08a95` found three variants: `test(foo)` treated as exact, target selectors omitted from validation identity, and unrelated questions superseded because only request-local `question_id` was compared.
- `52be9e924d` found authentication cache keys that omitted credential mode or non-Authorization headers.
- `db5b812de2` found durable continuity identity missing `last_turn_id`.
- The script audit independently found incomplete build cache keys. See [F21](C:/Users/kuh/Desktop/bug/kd4_scripts_full_review_63dde623.txt:423).

Generalized invariant:

> A key used for reuse, deduplication, authorization, supersession, or freshness must distinguish every input that can change the authoritative result.

Normalization may remove representation differences, but it must not merge semantically different requests. Equality used for coverage may be directional; it should not automatically become symmetric cache identity.

Breadth: validation proofs, cache keys, singleflight, task continuity, artifact identity, authentication, prompt decisions, model selection, test targeting, and workspace mutation accounting.

Rust-analyzer feasibility: medium–high when key roles are configured. KDA can trace fields and arguments influencing an operation, compare them with fields entering `Hash`, `Eq`, key constructors, and canonicalization functions, and detect many-to-one normalizations. Pure heuristics would be noisier, so identity-bearing types or configuration should declare the authoritative operation.

Caught before runtime: cross-target test-proof reuse, stale singleflight joins, authentication reuse after a secret/header change, unrelated decision supersession, and incompatible build-cache hits.

False positives: intentionally coarse caches followed by exact validation, fields functionally determined by other key fields, invariants guaranteed by a caller, and secret values deliberately represented by a complete digest rather than stored directly.

## 4. Stable-object and snapshot-continuity analysis

Historical motivation:

- TUI-03 checked metadata and then reopened the path, permitting a symlink/reparse swap.
- MCP-08 checked file size and later reopened the path for upload.
- EXEC-09 retained a writer handle but reopened the pathname when reading, allowing different bytes under the same artifact ID.
- Watcher generation was repeatedly mistaken for authoritative content identity in later repair commits `cccad001c4` and `4db08a95`.
- The root audit found settings backup operations that followed symlinks/hardlinks and did not guarantee the backup matched the validated bytes. See [root F-02](C:/Users/kuh/Desktop/bug/WORKTREE_AUDIT_2026-08-01.txt:146).

Generalized invariant:

> A correctness or security decision made about an object must govern the same stable object or immutable snapshot that is later consumed or published.

Metadata on a pathname does not authorize a later reopen. Watcher delivery is advisory, not proof that bytes are unchanged.

Breadth: uploads, artifact reads, repository evidence, untracked diffs, settings/configuration, cache validation, and sandboxed path handling.

Rust-analyzer feasibility: high for standard APIs. It can recognize `metadata(path)`/`canonicalize(path)` followed by `read(path)` or `open(path)`, especially across an await, and distinguish a retained `File` handle from a reopened pathname. Wrapper summaries would cover project-specific filesystem abstractions.

Caught before runtime: path substitution, sandbox escapes, stale output registered as current, size-limit bypass, and artifact identity referring to different bytes.

False positives: immutable filesystems, paths protected by a proven exclusive directory lock, private temporary directories, and APIs providing stable snapshot semantics internally.

## 5. Compositional resource-budget analysis

Historical motivation:

- TUI-01 capped file count but not per-file or total bytes.
- TUI-02 allowed 50 sequential commands, each with its own 30-second timeout.
- MCP-03 had no aggregate page/item cap; MCP-04 serialized work unnecessarily; MCP-06 repeatedly serialized a growing response, producing quadratic work.
- AGENTS-01 excluded rendering overhead; AGENTS-02 allowed every concurrent loader to reserve the full aggregate budget.
- Later repairs found a nominally bounded artifact cache capable of retaining roughly 4 GiB and per-file 512 MiB limits with no aggregate limit. See the [resource cluster](C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1076).

Generalized invariant:

> A local bound is meaningful only if the aggregate bound across cardinality, nesting, concurrency, retries, and final encoding is also finite.

Count bounds, byte bounds, time bounds, and concurrency bounds must compose. Cache entry limits need value-size accounting.

Breadth: repository scans, TUI rendering, MCP aggregation, caches, logs, artifacts, project instructions, pagination, and concurrent environment loading.

Rust-analyzer feasibility: medium–high. Constants and standard iterator, collection, timeout, semaphore, and cache APIs are tractable. Symbolic cost expressions such as `N × per_item_limit` can be reported without pretending to know exact runtime sizes. Custom collection/cache summaries would improve precision.

Caught before runtime: multi-gigabyte caches, 25-minute fallback paths, quadratic serialization, aggregate memory oversubscription, and encoded output exceeding its declared cap.

False positives: low cardinality guaranteed outside the analyzed crate, lazy or compressed storage, offline batch utilities intentionally allowed large budgets, and pools whose global budget is enforced by an opaque dependency.

## 6. Semantic state/refinement preservation

Historical motivation:

- TASK-02 replaced immutable validation evidence with defaults.
- EXEC-08 logged finalization failure but returned `true`.
- MCP-05 collapsed “cancellation requested locally” into “cancelled remotely.”
- SRC-03 collapsed permission/I/O failure into absence.
- COMPACT-01 discarded the terminal fallback failure.
- `4db08a95` converted `CommandMutation::Uncertain` to `bool` and reconstructed it as `KnownMutation`.
- Later process changes lost deterministic validation classification when an operation transitioned into tracked/background execution.

Generalized invariant:

> A richer domain state must not be collapsed into a weaker scalar or default and later used to make a stronger authoritative claim.

Analyzer attention should focus on many-to-one mappings such as enum-to-bool, structured error-to-string, `Result` failure-to-absence, and default reconstruction of evidence-bearing fields.

Breadth: task outcomes, process completion, cancellation, errors, evidence receipts, mutation classification, retryability, partial results, and protocol adapters.

Rust-analyzer feasibility: high for local enum/struct flows and medium interprocedurally. Variant fan-in, defaulted fields, discarded causes, and later scalar-to-enum reconstruction are semantically visible. This should extend KDA’s existing structured-result, evidence-loss, and field-flow machinery.

Caught before runtime: false success, false cancellation confirmation, silent partial search results, incorrect mutation evidence, lost retry causes, and task completion rejection.

False positives: intentional public abstractions, telemetry-only projections, compatibility adapters with a documented mapping, and non-authoritative UI summaries.

## 7. Bounded-prefix treated as complete

Historical motivation:

- VAL-01 searched only the most recent 64 records for an exact reusable proof.
- TASK-01 restored only the first 256 persisted bindings.
- MCP-03 detected only immediate cursor repetition and had no complete pagination guarantee.
- EXEC-04 allowed a bounded cache to evict active state, turning a capacity mechanism into loss of authoritative accounting. See [VAL-01 and TASK-01](C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:83).

Generalized invariant:

> A capped or paginated collection cannot be consumed as an exhaustive inventory unless completeness is proved or incompleteness is represented in the type/result.

A bound should produce something conceptually like `Partial<T>`, not an ordinary complete collection.

Breadth: persistence recovery, validation history, MCP pagination, search, test discovery, task inventories, cache reconciliation, and source-owner enumeration.

Rust-analyzer feasibility: high for recognized `take`, `truncate`, `limit`, pagination, and bounded-query APIs when connected to configured “complete sink” operations such as exact lookup, restore, or reconciliation. SQL embedded as arbitrary strings needs adapters.

Caught before runtime: binding 257 disappearing after restart, exact proof misses despite retained evidence, cursor cycles, and active execution state silently evicted.

False positives: UI previews, best-effort diagnostics, caps that define the actual product contract, small domains independently proven below the cap, and callers that explicitly surface partial status.

## 8. Execution-domain and dialect provenance

Historical motivation:

- SRC-01 derived ignore paths from host configuration while reading through a selected executor filesystem.
- PATCH-01 classified PowerShell/Cmd commands and then parsed them using Bash grammar.
- TUI-04 converted Git’s byte-oriented paths into UTF-8 strings.
- Later fixes corrected unconditional Windows-style case folding on Unix and repository continuity state reused across a newly created nested repository. See [source and parser findings](C:/Users/kuh/Desktop/bug/KD4_codex-rs_full_bug_audit_2026-08-12.txt:1453).

Generalized invariant:

> Values carrying filesystem, platform, shell-dialect, encoding, repository, or executor provenance may only be interpreted by a compatible consumer unless an explicit conversion establishes new provenance.

Breadth: remote/local executors, shell parsing, paths, Git output, sandboxing, environment configuration, hooks, and cross-platform code.

Rust-analyzer feasibility: medium. Strong wrapper types would make it highly precise; existing `PathBuf` and `String` values require configured provenance sources and sinks. rust-analyzer can still detect branches that determine `ShellKind` followed by an unconditional Bash parser, or host path constructors passed to remote filesystem methods.

Caught before runtime: host configuration affecting remote searches, incorrect command classification, corrupt non-UTF-8 paths, Linux case errors, and cross-repository continuity reuse.

False positives: deliberate translators, portable normalized representations, platform-gated code not visible under the selected analysis profile, and intentionally inherited environment state.

## Recommended direction

The first implementation wave should not create eight unrelated lint IDs. It should add three reusable semantic substrates:

1. Obligation/effect graphs for lifecycle and transactional checks.
2. Identity/provenance graphs for keys, stable snapshots, and execution domains.
3. Abstract quantity/state propagation for budgets, partial completeness, and refinement loss.

The current KDA catalog already has useful foundations—lifecycle protocols, effect ordering, identity downgrade, structured-result collapse, and unbounded resource checks ([current lint catalog](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:709)). The historical corpus argues for making those analyses interprocedural and relational, not adding lints named after `nextest`, `WRITE_WARNING_EMITTED`, a 64-row limit, or a particular marker file.

Some findings should remain outside the generic semantic analyzer: VAL-08’s statistical formula, full Git-config grammar correctness, and exact third-party command grammar require domain specifications or dedicated protocol adapters. Treating those as ordinary Rust semantic lints would produce more noise than prevented debugging.

The highest-leverage improvement is not another large batch of lint names. It is a patch-scoped semantic fact layer that tells an agent what must remain true across ownership transfers, async boundaries, persistence paths, identity joins, and generated interfaces.

KDA already has strong foundations: resolved calls and references in [analysis_context.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:79), production reachability, typed async edges in [runtime_activation_graph.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/runtime_activation_graph.rs:47), field-flow checks, surface baselines, lifecycle contracts, and artifact provenance. The missing facts are mostly relational: “these two operations form one transaction,” “this ID is only half the key,” or “this await occurs while a value has no durable owner.”

I would ask whether `cargo kda` can automatically answer these questions for every changed symbol:

- What value or responsibility changed owners, and can cancellation occur between removal and installation?
- Does an awaited call guarantee its named effect, or is it conditional, best-effort, or error-swallowing?
- What is the full correlation key and its expected cardinality?
- Which state fields and counters form one atomic transition?
- Can a wire value mean “missing from an old payload” as well as its ordinary meaning?
- Which generated artifacts and runtime consumers are transitively affected?

## 1. Cancellation-safe ownership-transfer analysis

**Example change:** An agent simplifies task startup by draining pending input earlier, or removes `TasklessTurnStartupGuard` because the eventual task installation looks inevitable. KD4 currently drains input at [tasks/mod.rs:930](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:930), but protects the interval with the guard defined at [tasks/mod.rs:807](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:807). Its `Drop` path recovers a taskless placeholder, eventually restoring input through [input_queue.rs:136](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/input_queue.rs:136).

**Missed consequence:** `get_pending_input` is destructive—it drains several queues at [input_queue.rs:256](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/input_queue.rs:256). Cancellation during one of the subsequent awaits can leave the input owned by neither the queue nor a running task. It can also leave an `ActiveTurn` placeholder that makes the session appear busy.

**Analyzer report:** Something like:

> `cancellation-unsafe-ownership-handoff`: 3 `TurnInput` sources are drained before `RunningTask` becomes the committed owner. Cancellation points exist on the path. Rollback is provided only by `TasklessTurnStartupGuard`; this patch removes or bypasses that guard.

The report should identify the source container, destination owner, cancellation points, commit operation, and rollback path.

**Why actionable:** The agent knows exactly where to retain a guard, postpone the drain, or introduce an explicit commit/rollback operation. It also suggests the relevant cancellation test, rather than merely warning that “async code is risky.”

**Required infrastructure:** An async control-flow graph with suspension/cancellation points; move and container-drain facts; ownership states such as `queued → detached → installed/recovered`; and effect summaries for `Drop`. KDA’s activation graph already models spawn, cancellation, and abort-on-drop edges, so this is an extension rather than a separate system.

Find-references answers “where is this symbol mentioned?” Blast radius should answer “why might this location matter?”

## Reliability model

The report should expose an evidence level rather than flattening everything into certainty.

- **Resolved:** HIR-resolved calls, methods, definitions, trait/impl relationships, variant construction and patterns, field accesses, and conversions within the loaded Cargo graph.
- **Structural:** Serde attributes, public declarations, Cargo targets, `cfg` conditions, feature checks, registry construction, known event/channel idioms, and literal SQL column access.
- **Declared:** KD4’s owner roots, invariants, generated artifacts, tests, validation commands, and architectural relationships. KD4’s source map explicitly treats persistence and resume as one compatibility surface and provides cross-cutting change routes: [SOURCEMAP.md](C:/Users/kuh/Desktop/kd4/SOURCEMAP.md:352), [SOURCEMAP.md](C:/Users/kuh/Desktop/kd4/SOURCEMAP.md:471).
- **Possible/opaque:** Trait-object targets not narrowed by registration, callbacks stored in collections, data-dependent routing, macro-generated behavior without authored provenance, and external consumers.

It can reliably say that a test transitively depends on a symbol. It cannot reliably say the test asserts the changed behavior. Likewise, it can prove that a handler is registered under a condition, but not that a particular production request will exercise it.

Every report should include analyzed profiles/features/targets and explicit blind spots. Default-profile impact should be primary; inactive feature or platform consumers should be a separate section.

## Preventing noise

The analyzer should not emit arbitrary transitive closure. Instead:

- Classify the change facet first: body, signature, field, variant, wire representation, trait contract, or implementation behavior.
- Group results by behavioral surface, not file.
- Show one shortest evidence path per surface, plus a count of collapsed locations.
- Rank compatibility boundaries, production paths, owner invariants, and exhaustive consumers above generic callers.
- Separate `must inspect`, `likely affected`, and `possible/opaque`.
- Collapse generated files into one “regenerate/check this artifact” obligation.
- Group tests by suite or behavior and distinguish direct assertions from transitive dependency.
- Put feature-disabled, test-only, and platform-specific consumers below active production paths.
- Cap human output; retain the complete deterministic graph in JSON.

## Product shape

The primary interface should be a separate command, such as:

```text
cargo kda impact --base <revision>
cargo kda impact --symbol codex_protocol::protocol::EventMsg::TurnComplete
```

This is not naturally a diagnostic: a large blast radius is not a defect and should not affect gate exit status or baseline debt.

Internally, it should produce versioned, reusable `ImpactFacts` and a first-class `ImpactReport` containing:

- Changed semantic subjects and change facets.
- Categorized affected surfaces.
- Evidence paths, confidence, and activation conditions.
- Suggested focused tests and declared validation routes.
- Coverage and blind spots.

Existing diagnostics could reference those facts when a real violation exists—for example, a public API regression, dropped conversion field, or wildcard hiding a new variant. They should not embed the entire impact graph in `DiagnosticRecord.semantic_facts`; the current diagnostic model is finding-centric: [model.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/model.rs:50).

One practical constraint is latency and broken intermediate trees. The current analyzer deliberately performs a broad Cargo check before semantic analysis. An agent-facing impact command should be able to query a known-good base graph and overlay the current diff, or degrade to structural evidence with explicit confidence, so it remains useful while code is temporarily uncompilable.
