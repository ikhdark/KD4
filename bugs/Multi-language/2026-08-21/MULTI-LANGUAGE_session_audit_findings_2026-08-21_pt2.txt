## Recommendation

Build a shared, typed, path-sensitive control/data-flow IR—“KDA MIR,” but deliberately smaller than Rust MIR.

That is the next true capability jump. KDA already knows semantic identity: its `ProgramIndex` records resolved functions, calls, and references ([analysis_context.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:79)). Its current ceiling is that each lint must rediscover execution and value flow from syntax. The shared flow helper explicitly says it is not a complete CFG and only understands nearby guards ([flow.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/flow.rs:1)); lifecycle and reverse-wiring passes then build separate mini-interpreters such as `ReverseFlow` ([reverse_wiring.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/reverse_wiring.rs:527)).

The fundamental transition is:

> From “what definition is this?” to “what facts and obligations hold at this exact program point, on every feasible path?”

KD4’s deliberately faulty investigation cases are unusually good acceptance tests for this decision. They are fixtures, not claims that current production code is broken.

| Direction | New knowledge | KD4 payoff | Architecture impact |
|---|---|---|---|
| 1. Typed path/data-flow IR | Facts and obligations at each program point | Broadest; catches 3 major investigation fault classes | Large |
| 2. Closed-world dynamic-target analysis | Which concrete implementations and keyed handlers can reach a call | Excellent for tools, extensions, registries | Medium-large |
| 3. Finite relational ADT analysis | Whether conversions preserve semantic variants and fields | Excellent for protocol/config/schema boundaries | Medium |

## 1. Typed path-sensitive program IR

### What becomes possible

KDA could reason about:

- Dominance and post-dominance: whether validation or cleanup happens before every relevant use or exit.
- Loop invariants and exit conditions.
- Field-sensitive state: `state.phase`, `document.next_id`, and `child` as distinct semantic places.
- Reaching definitions across assignments, branches, matches, `?`, early returns, and loops.
- Resource obligations: acquired, transferred, terminalized, killed, awaited, persisted.
- Bounded interprocedural effects: “this helper terminalizes argument 0” or “return value is at least the maximum input ID plus one.”

Today, the analyzer can recognize selected local shapes or run purpose-built structured traversal, but it cannot expose these facts as one reusable substrate.

### KD4 problems it addresses

1. **Dropped final batches.** The bad loop uses `start.saturating_add(width) < items.len()` and skips exact-size or trailing partial batches ([local-logic-last-batch-dropped.patch](C:/Users/kuh/Desktop/kd4/scripts/investigation_eval/patches/local-logic-last-batch-dropped.patch:11)). Detecting this requires relating the loop condition, update, slice bounds, and unprocessed range—not merely identifying calls.

2. **Persistent-ID collisions.** The migration derives the next ID from collection length rather than the maximum existing identifier ([persistence-receipt-sequence-collision.patch](C:/Users/kuh/Desktop/kd4/scripts/investigation_eval/patches/persistence-receipt-sequence-collision.patch:13)). A value-domain analysis could verify invariants such as `next_id > every persisted id`.

3. **Cancellation leaks.** The fixture returns from a `tokio::select!` cancellation arm without killing and reaping its child ([lifecycle-cancelled-child-leak.patch](C:/Users/kuh/Desktop/kd4/scripts/investigation_eval/patches/lifecycle-cancelled-child-leak.patch:11)). Conversely, KDA could prove that KD4’s real process path kills and waits on cancellation ([exec.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/exec.rs:1145)).

4. **Tool lifecycle completeness.** KD4’s registry has numerous pre-handler failures, cancellation handling, hooks, projection, persistence, and terminal outcome paths ([registry.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/registry.rs:826)). A shared obligation analysis could prove that every successful start reaches exactly one terminal outcome across helpers and early returns.

5. **Durability boundaries.** KD4 explicitly requires committed plan updates to reach durable evidence before response emission ([architecture_index.json](C:/Users/kuh/Desktop/kd4/architecture_index.json:288)). That is naturally a post-dominance and effect-ordering contract.

### Minimum viable version

Build a KDA-owned IR from rust-analyzer’s typed HIR:

- Basic blocks for `if`, `match`, loops, `break`, `continue`, `return`, `?`, calls, and awaits.
- Typed semantic places: locals, parameters, fields, and conservative wildcard places for indexes and opaque dereferences.
- SSA-like value versions or reaching-definition sets.
- Correct normal and exceptional/control exits.
- Initial abstract domains:
  - enum/`Option`/`Result` state;
  - integer intervals plus simple affine/difference constraints;
  - initialized/moved/escaped state;
  - configurable resource and lifecycle obligations.
- Workspace-local function summaries for returns, mutations, transfers, and terminalization.
- Source mapping back to authored syntax, retaining KDA’s existing diagnostic format.

Do not migrate every lint initially. Prove the substrate with the bad/clean batching pair, cancellation leak, and one real KD4 lifecycle contract.

### Where complexity should stop

- No borrow-checker reimplementation.
- No general SMT solver; support intervals, equality, inequalities, and a small affine fragment.
- No precise arbitrary heap aliasing. Unknown mutable calls kill affected facts.
- No thread-interleaving or async schedule exploration. Model control transfer, cancellation, spawn/join, and ownership obligations only.
- No exact panic unwinding initially.
- No analysis of opaque dependency bodies except configured summaries.
- Cap recursive summary iterations and widen loops deterministically.

### Architecture change

**Large: roughly 35–50% of the analysis core over time.**

The workspace loader, semantic identity index, configuration, diagnostics, baselines, and reporting can remain. The major change is a new cached `BodyIr`/summary layer in `AnalysisContext`, followed by migration of perhaps 20–30 existing passes. `flow`, lifecycle, authority, taint, async, reverse-wiring, loop enforcement, and state provenance would become clients of shared facts instead of separate syntax interpreters.

KDA’s existing fixed-point taint summaries ([taint.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/taint.rs:71)) are a useful prototype for summary convergence, but not yet a shared execution model.

## 2. Closed-world dynamic-target and registry analysis

### What becomes possible

KDA could determine finite sets of concrete runtime targets behind:

- `Arc<dyn Trait>` and `Box<dyn Trait>`;
- closure and function-pointer values;
- builder and registry collections;
- keyed `insert`, `register`, `push`, and immutable `build` flows;
- trait method calls whose receiver originated at known construction sites.

Calls would resolve to `{target A, target B}`, empty, or explicitly unknown—not just “unresolved dynamic dispatch.”

### KD4 problems it addresses

1. **Advertised-but-undispatched operations.** KD4’s missing-handler fixture advertises both `inspect` and `repair`, but dispatches only `inspect` ([static-wiring-missing-handler.patch](C:/Users/kuh/Desktop/kd4/scripts/investigation_eval/patches/static-wiring-missing-handler.patch:6)).

2. **Tool-plan consistency.** KD4 accumulates `Arc<dyn CoreToolRuntime>` values, builds visible specs, and separately constructs a `ToolRegistry` ([spec_plan.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/spec_plan.rs:111), [spec_plan.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/spec_plan.rs:270)). The analyzer could prove key-by-key that every visible tool has a reachable compatible runtime and that dispatch-only tools remain hidden.

3. **Extension installation.** The extension registry stores many categories of trait objects—tool, lifecycle, context, config, approval, and turn contributors ([registry.rs](C:/Users/kuh/Desktop/kd4/codex-rs/ext/extension-api/src/registry.rs:21)). Target sets would show which concrete contributors are installed in each host and whether their trait entrypoints are ever invoked.

4. **Lifecycle attachment.** It could connect concrete `ToolLifecycleContributor` implementations to the iteration sites that invoke them, instead of merely seeing a trait-object boundary.

5. **Closure/task activation.** Spawned closure bodies and callback values could become real call-graph edges when their origins are workspace-local.

### Minimum viable version

- Allocation-site identities for concrete-to-trait coercions.
- Flow through locals, assignments, returns, `Arc`/`Box`, struct fields, and simple aggregates.
- Models for `Vec::push`, map insertion, builder registration, and build/freeze patterns.
- Literal enum/string keys tied to registered values.
- Workspace-local function summaries for passed-through or stored values.
- Trait method resolution from each concrete target set.
- A target-set cap with explicit `unknown` widening.

### Where complexity should stop

- Closed-world workspace analysis only.
- External plugins, MCP inventories, reflection-like discovery, and deserialized implementations remain unknown.
- No fully precise mutable heap graph or concurrency-sensitive container contents.
- Do not distinguish individual elements after arbitrary collection mutation.
- Do not attempt whole-program monomorphization.
- When target sets exceed the cap, retain sound “some compatible target may exist” evidence rather than exploding the graph.

### Architecture change

**Medium-large: approximately 20–30% of the analysis core.**

`ProgramIndex` would gain value origins, coercions, receiver target sets, registry membership, and keyed dispatch facts. The current activation graph already admits semantic, syntax, and heuristic edges and an `UnresolvedDynamicDispatch` result ([runtime_activation_graph.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/runtime_activation_graph.rs:51)); this direction would replace much of that heuristic layer rather than replace the whole analyzer.

## 3. Finite relational analysis for protocol and data transformations

### What becomes possible

KDA could understand a converter as a relation between two finite data models:

- which input variant maps to which output variant;
- where every output field came from;
- which fields are dropped, defaulted, widened, or narrowed;
- whether forward and reverse conversions round-trip;
- whether serialized names, internal variants, and generated schema identities agree.

The compiler proves that a match is exhaustive. It does not prove that `"read-only"` means `ReadOnly`.

### KD4 problems it addresses

1. **Protocol meaning swaps.** The investigation fixture maps `"read-only"` to `WorkspaceWrite` and vice versa ([protocol-sandbox-mode-swap.patch](C:/Users/kuh/Desktop/kd4/scripts/investigation_eval/patches/protocol-sandbox-mode-swap.patch:12)).

2. **Core/app-server conversion drift.** KD4 has explicit `SandboxMode` conversions in both directions ([shared.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/shared.rs:289)). The analyzer could verify semantic variant correspondence, not just exhaustiveness.

3. **Nested permission loss.** `SandboxPolicy` and permission-profile conversions copy nested fields and translate nested enums in both directions ([permissions.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/permissions.rs:621)). It could detect omitted roots, swapped access modes, dropped flags, or asymmetric round trips.

4. **Schema/source parity.** KD4 already declares that JSON Schema and TypeScript fixtures must match protocol source ([architecture_index.json](C:/Users/kuh/Desktop/kd4/architecture_index.json:25)). Relational analysis could check semantic field and discriminant parity before or alongside generator snapshots.

5. **Compatibility migrations.** For supported structural migrations, it could verify preservation of unchanged fields and explicitly account for each introduced or discarded field.

### Minimum viable version

- Build a semantic ADT graph for enums, structs, tuples, `Option`, and `Result`.
- Interpret pure, terminating conversion functions into normalized value-shape expressions.
- Support matches, constructors, field projection, literals, simple helper calls, and `map`/`transpose`-style combinators.
- Track field provenance and variant correspondence.
- Establish expected meaning from serde names, same-name identities, inverse conversions, generated declarations, or explicit KDA contracts.
- Check:
  - discriminant preservation;
  - field preservation;
  - forward/reverse round trips;
  - documented intentional loss;
  - wire-name-to-variant consistency.

### Where complexity should stop

- Only bounded, first-order data transformations.
- No loops, I/O, allocation-sensitive behavior, arbitrary collections, crypto, or general program equivalence.
- Helper calls must be analyzable pure conversions or configured opaque mappings.
- Intentional lossy conversions require an explicit contract rather than an attempted proof.
- Do not turn this into general symbolic execution.

### Architecture change

**Medium: approximately 15–25% of the analysis core.**

This needs a reusable type/field identity index, normalized symbolic values, and a relational contract engine. Existing semantic resolution, schema inspection, authority checks, and diagnostics remain useful. It would touch fewer current passes than direction 1, although its branch handling could later reuse the shared IR.

## Why direction 1 wins

Direction 1 changes KDA’s center of gravity. Directions 2 and 3 add powerful new verticals; direction 1 creates a horizontal substrate that improves a large fraction of the analyzer.

It also covers three of KD4’s five deliberately injected fault classes immediately:

- local loop boundary failure;
- persistent state invariant failure;
- cancellation/resource lifecycle failure.

More importantly, it reduces architectural duplication. KDA currently has semantic identity, interprocedural taint summaries, activation graphs, and several independent “all paths” interpreters. A shared body IR turns those into interoperable analyses: target analysis can propagate values over it, and relational conversion analysis can interpret its pure subset.

I would sequence the work as:

1. Typed CFG and semantic-place layer.
2. Resource/lifecycle obligations plus interval constraints.
3. Bounded function summaries.
4. Closed-world target sets.
5. Relational ADT checking.

I considered symbolic `cfg`-world formulas as another candidate, but did not rank them in the top three: KDA already evaluates configured profiles independently and reports profile registration gaps ([README.md](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:513)). Formula-level presence reasoning would be valuable, especially across KD4’s platform code, but its marginal knowledge gain is smaller than acquiring an actual reusable execution model.

### 1. `Feature` enum ↔ `FEATURES` metadata registry

The feature identity is declared in [`Feature`](</C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:82>), while its configuration key, lifecycle stage, and default are independently recorded in [`FEATURES`](</C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:784>). - Drift: adding an enum variant without a registry entry compiles, then panics when metadata is requested. Duplicate IDs or keys also compile; first-match lookup can hide the duplicate.
- Check: enum variants must equal registry `id` values; every ID and key must be unique; every registry ID must resolve to the same variant.
- General rule: yes. An `enum-registry-parity` rule could recognize a registry record containing an enum discriminator, especially when a lookup method establishes that the registry is total.

- Value: very high.
- False-positive risk: low once the total-registry relationship is inferred or configured.

The existing line-oriented [`relation` mechanism](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/relations.rs:1>) could approximate this, but multiline record initializers and attributes make a semantic AST/HIR rule substantially safer.

### 2. Tool JSON schema ↔ actual Serde parser

`update_plan` has a manually constructed schema in [`create_update_plan_tool`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/plan_spec.rs:7>), but arguments are parsed into [`PlanningUpdateInput`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/task_evidence.rs:216>) by [`parse_update_plan_arguments`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/plan.rs:347>). Nested plan-step fields and enum value lists are also repeated manually.

- Drift: a schema property can be renamed or added without the parser accepting it; a required parser field can be added without advertising it; an enum value can exist on only one side. Everything compiles, but model-generated calls fail or fields become unreachable.
- Check:
  - Every advertised property and enum value must be accepted by the deserializer.
  - Every non-defaulted parser field must be advertised and required.
  - Parser-only internal fields should remain allowed; the relationship is directional, not strict equality.
- General rule: yes. Associate a `ToolSpec` with the type passed to `serde_json::from_str`, then compare schema keys, requiredness, enum literals, Serde renames, aliases, and defaults.
- Current state: the model-visible fields inspected appear aligned. Parser-only values such as internal bookkeeping demonstrate why strict equality would be wrong.
- Value: very high.
- False-positive risk: low to medium, principally around custom `Deserialize` implementations and dynamically assembled schemas.

### 3. Persistence classifier ↔ history reducer coverage

[`should_persist_event_msg`](</C:/Users/kuh/Desktop/kd4/codex-rs/rollout/src/policy.rs:88>) decides which `EventMsg` variants can enter rollout files. [`ThreadHistoryBuilder::handle_event`](</C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/thread_history.rs:345>) says it handles all persistable variants, but ends with `_ => {}`.

- Drift: the persistence match is exhaustive, so adding a new event forces a persistence decision. Marking it persistent does not force the wildcard-based reducer to make a corresponding decision.
- Check: every variant whose classifier arm can return `true` must have a named consumer arm. An intentional ignore can be an explicit empty arm or configured exemption.
- General rule: yes. This is a reusable `classifier-consumer-coverage` relationship between a predicate match and a downstream consumer match.
- Value: high, particularly for persistence, replay, indexing, authorization, and capability classifiers.
- False-positive risk: low when the relationship is declared; medium if inferred globally.

The current [`protocol-adapter-parity`](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/protocol_parity.rs:1>) would complain about every unnamed `EventMsg`, including transient ones. Comparing only the classifier’s positive set would be much more precise.

### 4. Core plan DTO ↔ app-server plan DTO

[`PlanItemArg`](</C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/plan_tool.rs:136>) is projected into [`TurnPlanStep`](</C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/turn.rs:507>) through a manual [`From` implementation](</C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/turn.rs:541>).

- General rule: yes, but it should be opt-in or evidence-based. One-way `From` implementations are frequently intentional projections.
- Value: high.
- False-positive risk: medium to high without a “mirror” or “projection with exclusions” contract; low with one.

It cannot detect a new source field for which no destination field exists, which is exactly this case.

### 5. `ApprovalsReviewer` wire domain across Serde, schema, TypeScript, and mirrors

The core declaration repeats its accepted values in Serde attributes, a TS literal type, and a custom JSON Schema implementation in [`config_types.rs`](</C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/config_types.rs:159>). - Serde accepted-input values against schema/TS input domains.
- Serde canonical-output values against output representations.

Value is high and false-positive risk low to medium if input aliases are distinguished from canonical output. The current representation-parity rule only compares explicit metadata conflicts; it does not inspect custom schema bodies or literal-union contents.

### 6. `CodexErr` ↔ public error classification

[`CodexErr`](</C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/error.rs:68>) has an exhaustive retryability decision in [`is_retryable`](</C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/error.rs:173>), but [`to_codex_protocol_error`](</C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/error.rs:220>) and [`http_status_code_value`](</C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/error.rs:261>) use wildcard defaults.

1. Enum-to-registry completeness and uniqueness.
2. Tool-schema-to-deserializer compatibility.
3. Configured classifier-positive-set-to-consumer coverage.
4. Direction-aware Serde/schema/TS value-domain parity.

I would not prioritize KD4-specific hard-coding. All five relationships recur naturally in Rust systems, while configuration or lightweight annotations can express the few places where intent cannot be inferred.

### 2. Command-process retirement state machine

## Conclusion

The ideal KD4 quality gate is a **change-scoped contract-closure and proof-validity system**, not a larger collection of generic Rust lints.

Your analyzer already contains many of the necessary semantic primitives. Its biggest weakness is that KD4’s authoritative architecture—the source-owner graph, compatibility routes, generated outputs, and validation commands—is mostly advisory. The gate does not yet make “the change is architecturally complete and proved by exactly applicable evidence” its central decision.

I derived this design from:

- KD4’s required pre-edit ownership and consumer analysis in [AGENTS.md](C:/Users/kuh/Desktop/kd4/AGENTS.md:26).
- Its direct-test requirement in [AGENTS.md](C:/Users/kuh/Desktop/kd4/AGENTS.md:68).
- The persistence, generated-artifact, and cross-cutting routes in [SOURCEMAP.md](C:/Users/kuh/Desktop/kd4/SOURCEMAP.md:354) and [SOURCEMAP.md](C:/Users/kuh/Desktop/kd4/SOURCEMAP.md:475).
- The twelve confirmed defects recorded before commit `37f7f9bf36`: proof-scope collisions, lost enum state, unsafe PowerShell classification, detached persistence, stale watcher evidence, unbounded retained bytes, hidden output, scoped-ID collisions, and invalid parallel-time arithmetic.

## The ideal KD4 gate

It would provide these capabilities:

1. **Diff-to-contract closure**

   Every changed path resolves to an owner, entrypoint, direct callers and consumers, compatibility boundary, generated mirrors, focused tests, and validation route. Missing ownership or an unexamined affected route is a gate failure or explicit unknown.

2. **Production wiring and activation proof**

   New handlers, tools, contributors, variants, features, and config fields must be registered and reachable on every required production path—not merely compile.

3. **Wire, persistence, and generated-representation closure**

   Serde shapes, JSON Schema, TypeScript/Python projections, stored rollouts, migrations, defaults, aliases, and legacy round trips are treated as one compatibility surface.

4. **Lifecycle and durability contracts**

   Important KD4 flows are modeled as state machines: begin/terminal pairing, commit-before-response, await-before-observe, cancellation, process-tree shutdown, output drain, cache publication, and exactly-once completion.

5. **Identity and information-preservation checks**

   The gate rejects lossy state projections such as enum-to-boolean conversion, incomplete composite keys, reminted scope IDs, and claims of currentness based on advisory generations rather than content identity.

6. **Authority-aware command classification**

   Shell classification is dialect-specific and conservative. Unknown PowerShell constructs, method invocation, quoting loss, sandbox transitions, and approval boundaries cannot silently acquire read-only authority.

7. **Compositional quantitative contracts**

   Bounds must compose across nesting: per-entry and aggregate bytes, visible-yield latency, total deadline versus per-operation timeout, model-visible token budgets, and parallel elapsed time versus summed work.

8. **Exact validation-proof semantics**

   A proof identity includes package, target kind/name, feature set, profile, toolchain, filter semantics, working directory, candidate/content identity, and selected-test count. Equality and directional proof coverage are separate concepts.

9. **Static-to-runtime escalation**

   Static analysis should identify the smallest authoritative runtime test whenever scheduling, OS processes, persistence ordering, notification delivery, or output draining cannot be proved statically.

10. **Agent-oriented output**

    Diagnostics should state the violated contract, owner, affected route, counterexample path, unknowns, required proof, and the smallest next action.

### Important missing capabilities

1. **An authoritative change-closure decision**

   The gate does not currently fail a change because an owner, consumer, compatibility projection, generated mirror, or required validation route is missing from its closure.

2. **Canonical validation identity**

   The historical proof defects—contains versus equality filters and discarded `--test`/`--bin`/`--example`/`--bench` selectors—show that proof identity needs its own semantic model, not shell-string comparison.

3. **KD4 transaction-level state machines**

   The high-risk contracts are multi-function and asynchronous: persist before reuse, retire before publish, commit before terminal response, drain before completion, cancel without starting new work. Generic local lints are insufficient.

4. **First-class distinction between observed, possible, and unknown state**

   F4 and F7 both came from promoting weaker evidence into stronger claims. The gate needs an explicit evidence lattice and should reject authority gained through lossy conversion.

5. **Topology-aware quantitative reasoning**

   F11 demonstrates that summed child work and critical-path elapsed time are semantically different. The current quantitative checks do not model that distinction as a KD4 contract.

6. **Repository-specific direct-test validity**

   Reachability to a test is not enough. The gate needs proof that the precise test ran, selected at least one case, exercised the changed contract, and is bound to the current content identity.

### Unnecessary complexity

The unnecessary complexity is primarily **breadth on the default critical path**, not the existence of the machinery.

- The analyzer exposes roughly 279 built-in lint IDs and registers most passes with always-applicable activation. Many duplicate rustc/Clippy concerns or rely on broad naming and shape heuristics that are less valuable than KD4’s explicit owner contracts.
- Several overlapping generic families cover lifecycle, authority, identity, transitions, derivation, propagation, and optimization. Adding more such families would dilute confidence without addressing the confirmed failures.

## What KDA should avoid competing on

KDA will mostly duplicate stronger tools if it prioritizes:

- general syntax, style, idiom, or performance lints;
- borrow, lifetime, unsafe, exhaustiveness, or ordinary type errors;
- generic unused-code and dead-code detection;
- editor navigation, rename, completion, or per-symbol references;
- simply wrapping `cargo test`;
- checks that are only configurable `rg` patterns;
- large catalogs of name-based security heuristics without identity and flow semantics.

Those may be useful supporting checks, but they are not the product’s reason to exist.

## The clearest three reasons for cargo kda to exist

1. **Semantic change-to-proof closure:** derive the exact KD4 obligations and smallest credible validation plan for a change, then invalidate proofs when their semantic dependencies become stale.

2. **Production realization and profile parity:** prove that every declared capability is constructed, registered, reachable, dispatched, terminalized, and tested across the relevant entrypoints and configurations.

3. **Cross-representation compatibility closure:** trace Rust type evolution through Serde, wildcard consumers, conversions, persistence/replay/resume, generated schemas, and client projections—reporting both broken stages and explicit unknowns.

Those three form a coherent product: KDA tells an agent what a change means, whether it can actually happen in production, and whether the current evidence is sufficient to finish.

# Semantic-model review

## Bottom line

KDA’s main limitation is not a lack of semantic machinery. It already has credible primitives for identities, control flow, provenance, effects, resources, async relationships, predicates, boundary relations, and uncertainty.

The problem is that those primitives form several partially overlapping semantic universes:

- Legacy analyses use canonical strings.
- Newer dispatch analysis uses stable executable identities.
- Value provenance defines another callable identity.
- Runtime activation, dynamic targets, async protocols, and finite ADT relations are mostly outside the shared `AnalysisContext`.
- Many KD4-specific checks consequently reconstruct local approximations instead of composing shared facts.

The shared context currently exposes program calls, executable dispatch, local CFGs, body IR, value provenance, resource obligations, async relationships, and predicates ([analysis_context.rs:464](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:464)). It does not unify `DynamicTargetIndex`, `RuntimeActivationGraph`, `AsyncProtocolGraph`, boundary projections, or authority facts.

That fragmentation is the highest-leverage issue. A unified semantic substrate should rank ahead of more isolated lints.

## Recommended upgrade order

| Rank | Semantic-model upgrade | Why it comes first |
|---|---|---|
| P0.1 | Unified callable, executable, type, and subject identity | Every interprocedural analysis inherits current collisions and string matching. |
| P0.2 | One composed executable/activation graph | Unlocks effects and reachability through trait objects, registries, closures, spawns, and handlers. |
| P0.3 | CFG-sensitive value, place, alias, and key provenance | KD4 lifecycle correctness frequently depends on preserving the same composite key or resource instance. |
| P0.4 | Ordered temporal effects and ownership obligations | KD4 invariants depend on sequence, Drop, cancellation, and all-exit behavior—not unordered effect sets. |
| P1.1 | Structured async task and synchronization model | Needed for select cancellation, handle ownership, notifications, channels, and happens-before reasoning. |
| P1.2 | Unified outcome model | Panic, error, cancellation, timeout, abort, and task failure currently live in separate approximations. |
| P1.3 | Profile/predicate-aware semantics | KD4’s platform and feature structure makes all-features reachability materially misleading. |
| P1.4 | Boundary and representation graph | Protocol, serde, TS/schema generation, conversions, and persistence should be related semantically. |
| P1.5 | Typed blocking and unsafe effect models | Current API catalogs and comment checks cannot support reliable transitive reasoning. |
| P2.1 | Authority/security provenance lattice | Valuable, but should reuse the stronger identity, flow, and graph layers first. |
| P2.2 | Extensible semantic-domain algebra | Generalizes quantities, paths, dialects, identities, and wire domains. |
| P2.3 | Proof-bearing diagnostic schema | Important for agent use and baselines, but does not compensate for weak underlying semantics. |

## Concept-by-concept findings

### 1. Callable and executable identity — critically shallow

**Today.** `canonical_function` constructs an identity from crate, module, the simple self-type or trait name, and method name ([semantic.rs:388](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic.rs:388)). Newer executable identities additionally distinguish named functions, closures, async closures, and async blocks ([semantic_identity.rs:36](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic_identity.rs:36)). `ProgramIndex` also adds file and range to form a function instance.

**KD4 information loss.** KD4 contains many implementations such as `impl From<CollabAgentSpawnBeginEvent> for EventMsg` and adjacent `From<...>` implementations ([protocol.rs:1721](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:1721)). They all reduce to the equivalent of `EventMsg::from`: the trait identity and its source-type argument are absent. Trait implementations, generic instantiations, reexports, and same-named ADTs in different modules can therefore collide or become indistinguishable between analyses.

**Richer representation.** Introduce one `CallableId` shared by every model, carrying:

- crate/package/target and module identity;
- inherent versus trait implementation;
- canonical self type and full trait path;
- method signature, generic parameters, and relevant substitutions;
- ABI, safety, asyncness, and source anchor;
- stable lexical child identity for closures and async blocks.

Compiler identities can be used during a run, with a structural serialized identity for baselines.

**Checks unlocked.** Exact effect propagation through trait implementations; trait-implementation parity; correct panic/blocking/unsafe paths; per-implementation impact analysis; duplicate registration detection; implementation-specific suppressions and baselines.

### 2. Type identity — critically shallow

**Today.** Body IR strips references, then stores only an ADT’s simple name or a primitive name ([body_ir.rs:135](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/body_ir.rs:135)). `ValueExpr` and call facts retain that optional string.

**KD4 information loss.** Types such as `Arc<OnceCell<Arc<dyn AgentTaskStore>>>`, `Arc<RwLock<BindingIndex>>`, and `Arc<Mutex<HashMap<String, Arc<Notify>>>>` become merely `Arc` ([task_coordinator.rs:99](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/task_coordinator.rs:99)). `JoinHandle<io::Result<StreamOutput<Vec<u8>>>>` loses its task result and payload structure ([exec.rs:1246](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/exec.rs:1246)). Aliases such as `SharedValidationSingleflight` hide both lock and keyed-resource semantics ([validation_admission.rs:606](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/validation_admission.rs:606)).

**Richer representation.** Use a recursive type term containing nominal definition identity, generic and const arguments, references and mutability, raw pointers, trait-object bounds, associated types, function types, and both authored and normalized aliases. Add derived capabilities such as `Send`, `Sync`, lock kind, channel kind, task handle, and ownership wrapper.

**Checks unlocked.** Lock-kind-aware await checks; channel payload compatibility; join-result handling; `Send`/`Sync` boundary checks; alias-aware resource ownership; generic effect specialization; FFI layout validation; unsafe-contract checking.

### 3. Call graphs, dynamic dispatch, and runtime activation — strong pieces, insufficient composition

**Today.** `ProgramIndex` records semantically resolved direct calls and methods. The legacy graph remains keyed by canonical strings. `ExecutableDispatchGraph` is considerably richer: direct calls, callable references, closure invocation, registered handlers, trait-object dispatch, and explicit unknowns ([semantic_identity.rs:164](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic_identity.rs:164)). `DynamicTargetIndex` models bounded trait-object and keyed-registry targets ([dynamic_targets.rs:1](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/dynamic_targets.rs:1)), while `RuntimeActivationGraph` models registration, spawn, join, select, channels, watches, notification, and cancellation ([runtime_activation_graph.rs:55](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/runtime_activation_graph.rs:55)).

The shared context, however, builds the dispatch graph with default options and directs project registration rules to a separate graph ([analysis_context.rs:525](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:525)).

**KD4 information loss.** `ToolRegistry` stores `Arc<dyn CoreToolRuntime>` under keys returned by `tool_name()` and later retrieves the trait object by name ([registry.rs:743](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/registry.rs:743)). This combines value-derived keys, trait coercion, dynamic lookup, and method dispatch. No single shared KDA graph represents that entire path.

**Richer representation.** Compose the existing models into one typed multi-edge graph:

- direct call and method dispatch;
- function/closure/future values;
- finite trait-object target sets;
- keyed registration and lookup;
- spawn, join, abort, select, channel, notify, and cancellation edges;
- production root and test reachability;
- profile predicate, confidence, and explicit unknown frontier on every edge.

**Checks unlocked.** Panic/blocking/unsafe propagation through registered handlers; registered-but-unreachable tools; dispatched-without-registration; effect parity across handler implementations; spawned-task impact analysis; handler-specific test selection; production wiring gaps.

### 4. Control flow and expression semantics — too shallow for KD4’s macro-heavy async code

**Today.** `LocalCfg` provides bounded source-level branches, loops, exits, dominance, and common effects. It explicitly excludes macro expansion, unwinding, lexical drop order, and cross-call behavior ([local_cfg.rs:1](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/local_cfg.rs:1)). Body IR adds calls, assignments, comparisons, returns, and bounded affine expressions ([body_ir.rs:223](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/body_ir.rs:223)).

**KD4 information loss.** KD4 uses `tokio::select!` for cancellation, timeout, process exit, and notification races. For example, process supervision selects between cancellation and process completion inside a spawned task ([process_manager.rs:647](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/process_manager.rs:647)). Treating that macro as opaque loses branch cancellation, future-drop behavior, and cleanup ordering.

It also weakens reasoning about `join!`, `try_join!`, `let else`, match guards, destructuring, short-circuiting, `?`, and compiler-inserted drops.

**Richer representation.** Add targeted HIR/MIR-like lowering for important constructs, especially async macros:

- explicit suspension and cancellation edges;
- lexical and unwind drop scopes;
- `select!`, `join!`, and `try_join!` branch semantics;
- match guards, `let-else`, and short-circuit expressions;
- macro callsite plus expansion provenance;
- typed normal/error/unwind exits.

**Checks unlocked.** Select cancellation safety; cleanup on timeout/cancellation branches; guard lifetime across macro-generated awaits; panic/unwind cleanup; terminal notification on every branch; error-path resource discharge; publish/unlink order across expanded control flow.

## Practical roadmap

The best next architectural move is not “replace everything with MIR.” It is:

1. Define shared typed identities and predicate-bearing semantic nodes.
2. Promote existing dispatch, dynamic-target, runtime-activation, and async-protocol facts into one graph.
3. Make CFG-sensitive provenance and ordered temporal events the common interface consumed by effects, resources, authority, blocking, unsafe, and boundary analyses.
4. Migrate existing lints onto that substrate incrementally, retaining explicit unknowns and bounded analysis.
5. Upgrade diagnostics once the shared graph can emit real proof paths.

That path reuses much of KDA’s existing work. It primarily removes parallel identity systems and local semantic reconstructions.
