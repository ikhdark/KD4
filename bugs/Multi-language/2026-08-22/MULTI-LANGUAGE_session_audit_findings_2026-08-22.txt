DIRECTLY STATED HISTORICAL FINDING / FIX / VALIDATION
(Faithful final_answer conclusion from the source session.)

Yes. The current snapshot has four definite issues plus one durability risk:

1. **Build-breaking notification ID migration.** `RuntimeEvent::Notify.id` is `Option<String>`, but the producer supplies `String` and `spawn_notification` also expects `String`. The crate cannot compile until this migration is made consistent. See [runtime/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode/src/runtime/mod.rs:65), [runtime/callbacks.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode/src/runtime/callbacks.rs:286), and [cell_actor/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode/src/cell_actor/mod.rs:430).

2. **`notify()` recreates an unbounded hang path.** JavaScript now receives a promise that resolves only after host delivery, while `spawn_notification` awaits `host.notify` without a deadline. If that callback stalls, `await notify(...)` prevents the runtime from emitting its final result, so the later two-second cleanup bound never runs. See [callbacks.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode/src/cell_actor/callbacks.rs:23) and [runtime/callbacks.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode/src/runtime/callbacks.rs:273). Notification delivery needs its own timeout or a bounded enqueue acknowledgment.

3. **The 60-second default can silently become arbitrarily longer.** `runtime_request` derives the tool deadline from `yield_time_ms` and takes the maximum with 60 seconds. That contradicts the documentation saying `yield_time_ms` is compatibility-only and that nested calls default to 60 seconds. See [service.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode/src/service.rs:308) and [description.rs](C:/Users/kuh/Desktop/kd4/codex-rs/code-mode-protocol/src/description.rs:16). These controls should be independent.

4. **Exec projection drops recovery guidance.** Projection now includes only raw output and basic metadata, omitting `repair_notice`. The existing direct test still requires a `ProcessFinalStatus` fragment, so the implementation and test contract disagree. A model receiving a projected PowerShell failure can lose the instruction to retry using `powershell_script`. See [context.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/context.rs:642) and [unified_exec_tests.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/unified_exec_tests.rs:89).

5. **Durable missing-output persistence is cancellation-unsafe.** It mutates in-memory history before awaiting append and flush, while its caller cancels the future after one second. A timeout between those stages can leave live history containing synthetic aborted outputs that the rollout lacks. See [session/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:3310) and [tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:2458). This needs persist-first ordering or a cancellation-shielded write, plus a blocked-flush test.

I did not edit these because this was a review request. The one exact test attempt could not reach its assertion because the shared source changed during compilation and produced transient signature errors; repository policy precluded retrying while edits were ongoing.
