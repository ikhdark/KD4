MDPWA ALERT-BROADCAST AND NOTIFICATION DELIVERY AUDIT
Review date: 2026-08-07

SCOPE
=====

This review traces the resident alert-broadcast path from the final-send API
through PostgreSQL, Workflow, Resend, Web Push, and the service worker. It also
traces the adjacent resident-notification outbox because it is dispatched by
the same cron route. That second outbox sends administrative email about a
resident's community-input or map-feedback submission; it does not send a
message to the resident.

This is a source audit. No production data, provider account, or live workflow
run was inspected. In this report, "provider accepted" means the provider API
returned success. It does not prove inbox delivery, device display, or resident
receipt.


EXECUTIVE RESULT
================

The current queue architecture has strong creation, ownership, cancellation,
and failed-recipient retry fencing. It does not need replacement.

Six material issues or contract limitations remain:

  A-01  HIGH    Web Push may display an alert after the alert has expired.
  A-02  HIGH    A crash/timeout at the provider/DB boundary can cause a retry
                after the provider already accepted the message; Web Push can
                therefore be displayed twice. Email relies on Resend's external
                idempotency behavior to close the same ambiguity.
  A-03  HIGH    Repeated start/attach ambiguity can dead-letter an alert job
                while its broadcast remains "scheduled", after which neither
                alert retry path can recover it.
  A-04  MEDIUM  "sent" records provider acceptance, not final resident
                delivery. A provider-accepted email can bounce and an accepted
                push can expire without display while the database remains sent.
  A-05  MEDIUM  A workflow-owned job has no repository-level stale-run recovery.
                If the durable workflow engine never resumes or executes its
                failure handler, the alert can remain running forever.
  A-06  LOW     A broadcast with zero frozen recipients is finalized as "sent"
                even though no provider call occurred.

Cancellation, normal concurrent dispatch, target freezing, partial-result
finalization, and failed-recipient-only retry are correctly fenced in the
reviewed code. Duplicate Workflow invocation alone does not cause duplicate
delivery because only one run can acquire the database workflow lease.


END-TO-END TRACE
================

1. Final-send creation

  - POST /api/alert-broadcasts requires a final-send idempotency key and at
    least one configured delivery channel.
    Evidence: src/app/api/alert-broadcasts/route.ts:150-200.

  - createBroadcastAndOutbox inserts the alert_broadcasts row, its outbox_jobs
    row, and audit state in one PostgreSQL statement. The broadcast request hash
    is checked when the final-send idempotency key already exists. The outbox
    idempotency key is unique and available_at is the broadcast effective time.
    Evidence: src/lib/alertBroadcastRepository.ts:168-298.

  - An immediate alert is claimed and Workflow-started in the request when
    possible. A start failure is swallowed only after the durable outbox exists,
    so cron can recover it. A scheduled alert is not claimable before
    available_at and is later picked up by /api/cron/outbox.
    Evidence: src/app/api/alert-broadcasts/route.ts:201-245;
    src/lib/alertBroadcastRepository.ts:1085-1213;
    src/app/api/cron/outbox/route.ts:15-47.

2. Outbox claim and Workflow start

  - Claiming uses one UPDATE selected through FOR UPDATE SKIP LOCKED. Eligible
    states are queued/retry or an ownerless running claim older than ten
    minutes. The claim changes state to running, sets locked_at, and increments
    attempt_count atomically. Concurrent cron/request workers cannot claim the
    same current lease.
    Evidence: src/lib/alertBroadcastRepository.ts:1085-1213.

  - The dispatcher calls Workflow start, then attaches run.runId to the running
    outbox row. If start throws, the shared release function returns the job to
    bounded retry/backoff or dead state. If attaching the run ID throws, the
    ownerless running claim is left for stale-claim handling.
    Evidence: src/lib/alertBroadcastDispatcher.ts:18-60;
    migrations/0005_shared_outbox_retry_policy.up.sql:1-48.

3. Scheduled execution, cancellation, and expiration

  - Workflow reads effectiveAt, sleeps if needed, then calls
    markBroadcastSending. That database transition both acquires the exact
    workflow owner and changes the broadcast from scheduled to sending.
    Evidence: src/workflows/alertBroadcastDelivery.ts:327-365;
    src/lib/alertBroadcastRepository.ts:373-435.

  - If the alert has expired, markBroadcastSending atomically cancels and
    withdraws it and cancels the outbox job before any target/provider step.
    Evidence: src/lib/alertBroadcastRepository.ts:373-435.

  - Admin cancellation is allowed only while draft/scheduled. It atomically
    changes the broadcast to cancelled/withdrawn and changes its queued, retry,
    or running outbox job to cancelled. Once sending wins the race, cancellation
    returns conflict rather than claiming that a provider-bound alert was
    cancelled.
    Evidence: src/lib/alertBroadcastRepository.ts:869-919;
    src/app/api/alert-broadcasts/[id]/route.ts:84-98.

4. Recipient freeze

  - Before either provider is called, Workflow loads confirmed email signups
    and active push subscriptions, filters by topic and by readiness at the
    delivery-start instant, and snapshots both channel recipient IDs in one
    atomic repository operation.
    Evidence: src/workflows/alertBroadcastDelivery.ts:56-112;
    src/lib/alertBroadcastRepository.ts:521-560.

  - Later signups are not added to an old alert. A frozen target that has since
    unsubscribed or become ineligible is recorded suppressed, not sent. Failed,
    skipped, pending, or missing frozen targets remain incomplete; sent and
    suppressed targets do not.
    Evidence: src/workflows/alertBroadcastDelivery.ts:115-189,204-236;
    src/lib/alertBroadcastRepository.ts:1046-1084.

5. Email provider delivery

  - Incomplete eligible email targets are sent in batches. Each recipient gets
    a stable provider idempotency key of
    broadcast:<broadcast-id>/email/<subscriber-id>. Each provider operation is
    retried up to three times with the same key.
    Evidence: src/lib/alertBroadcastRetry.ts:1-5;
    src/lib/alertBroadcastNotifications.ts:589-614,615-769.

  - sendResendEmail passes the key to Resend and treats a non-empty provider
    message ID as sent. Provider outcomes are accumulated in memory; only after
    sendAlertBroadcastEmails returns does Workflow write all email attempts to
    PostgreSQL.
    Evidence: src/lib/resendEmail.ts:72-128;
    src/workflows/alertBroadcastDelivery.ts:115-187.

6. Web Push provider delivery

  - Each incomplete push target is first claimed in delivery_attempts. Failed,
    skipped, or pending attempts older than ten minutes may be reclaimed; sent
    and suppressed attempts cannot be reopened.
    Evidence: src/lib/alertBroadcastRepository.ts:561-682.

  - The provider call uses a 24-hour TTL and a topic derived from broadcast.id.
    On provider success, the exact still-pending attempt and subscription health
    are completed atomically. A superseded attempt cannot be completed by its
    old claimant.
    Evidence: src/lib/webPushSubscriptions.ts:688-731;
    src/lib/alertBroadcastRepository.ts:683-734.

  - The service worker displays every received payload with showNotification.
    The payload has no alert ID or expiration and showNotification supplies no
    notification tag or local already-displayed check.
    Evidence: src/lib/webPushSubscriptions.ts:635-685;
    public/sw.js:299-309.

7. Partial result and terminal state

  - Finalization computes the latest attempt for every frozen target in one SQL
    statement. All sent => sent. A resolved mixture => partial. No successes =>
    failed. Partial jobs complete; failed jobs become dead. Ownership is checked
    by exact workflow_run_id.
    Evidence: src/lib/alertBroadcastRepository.ts:770-868.

  - A thrown workflow/step failure calls the shared outbox release policy,
    which applies exponential backoff and a six-attempt maximum. The broadcast
    returns to scheduled for retry or becomes failed when the released job is
    dead.
    Evidence: src/workflows/alertBroadcastDelivery.ts:382-390;
    src/lib/alertBroadcastRepository.ts:735-769;
    migrations/0005_shared_outbox_retry_policy.up.sql:1-48.

8. Failed-recipient-only retry and dead letters

  - The admin retry action is accepted only for partial/failed broadcasts. A
    row lock serializes competing retry requests. Existing dead jobs are
    cancelled and one new queued outbox job is created with
    retryIncompleteOnly=true. Only frozen targets whose latest state is
    missing/pending/failed/skipped are selected; sent and suppressed recipients
    are not reopened.
    Evidence: src/app/api/alert-broadcasts/[id]/route.ts:99-120;
    src/lib/alertBroadcastRepository.ts:920-1084.

  - The operator dead-letter tool intentionally refuses dead alert-broadcast
    jobs; those must use the application failed-recipient retry. It can requeue
    or close resident-notification dead letters. Requeue/close of an ownerless
    stale-running job requires explicit acknowledgement of ambiguous delivery.
    Evidence: scripts/outbox-dead-letter.mjs:52-83,90-174.

9. Adjacent resident-notification outbox

  - Community-input/map-feedback creation inserts the submission and its
    resident-notification outbox row in the same statement. The notification is
    an admin email, with a stable outbox-based Resend idempotency key.
    Evidence: src/lib/communityInputStore.ts:730-799;
    src/lib/mapFeedbackStore.ts:1080-1143;
    src/workflows/residentSubmissionNotification.ts:22-53.

  - It uses the same SKIP LOCKED/ten-minute ownerless claim pattern, Workflow
    run attachment, owner-checked completion, bounded shared release policy,
    and dead-letter operator tool.
    Evidence: src/lib/residentNotificationRepository.ts:22-170,188-289;
    src/lib/residentNotificationDispatcher.ts:13-71.


DETAILED FINDINGS
=================

A-01  HIGH  WEB PUSH CAN ARRIVE AFTER ALERT EXPIRATION

Condition
  A push provider accepts an alert shortly before its expiresAt/expiresOn, or a
  device remains offline while the provider retains the push.

Why it happens
  sendAlertBroadcastPushToSubscription always sends TTL = 24 hours. The TTL is
  not capped by the alert's remaining validity. The payload does not carry an
  expiration, and the service worker does not reject stale payloads.

Resident impact
  A resident can receive/display an old alert after the application would no
  longer publish or start that alert.

Evidence
  src/lib/webPushSubscriptions.ts:635-685,688-720;
  public/sw.js:299-309;
  src/lib/alertBroadcastRepository.ts:373-435.

Repair within the current architecture
  Cap Web Push TTL at the alert's remaining lifetime, put the absolute expiry
  and broadcast ID in the payload, and have the service worker discard an
  expired payload. No queue replacement is needed.


A-02  HIGH  PROVIDER/DB CRASH WINDOW CAN DUPLICATE DELIVERY

Push sequence
  1. PostgreSQL records a pending push attempt.
  2. The push provider accepts it (and may immediately deliver it).
  3. The process dies or the Workflow step times out before
     completeClaimedPushDeliveryAttempt commits.
  4. After ten minutes the pending attempt is claimable again and the provider
     is called again.

  The Web Push topic may coalesce messages still waiting at a push service, but
  it cannot retract a notification already delivered. The service worker adds
  no display tag or durable broadcast-ID dedupe, so a second delivery can be
  displayed as a second notification.

Email sequence
  Email attempts are not written until the entire helper returns. A process
  death after one or more Resend accepts but before recordDeliveryAttempts
  commits leaves those targets incomplete and replays the provider calls. The
  stable Resend idempotency key is the intended mitigation, including across
  failed-recipient retry jobs, but its retention/guarantee is external and is
  not established by this repository. An ambiguous provider response after
  acceptance has the same shape.

Resident/database impact
  A resident can receive a push twice. Email duplication is provider-dependent
  rather than prevented by PostgreSQL. The database correctly remains
  pending/missing after the crash, but that state causes a potentially incorrect
  retry of an already accepted message.

Evidence
  src/lib/alertBroadcastRepository.ts:448-520,561-734;
  src/workflows/alertBroadcastDelivery.ts:115-187,204-270;
  src/lib/alertBroadcastNotifications.ts:720-769;
  src/lib/resendEmail.ts:72-128;
  src/lib/webPushSubscriptions.ts:688-731;
  public/sw.js:299-309.

Repair within the current architecture
  Preserve the current outbox. For push, include broadcast ID in the payload
  and deduplicate display durably in the service worker (a notification tag
  alone is weaker after dismissal). Review whether ten minutes can overlap a
  live provider call. For email, document and monitor Resend idempotency
  retention and ensure replay remains inside it; if that cannot be guaranteed,
  reconcile ambiguous provider outcomes before replay.

Exactly-once note
  Web Push does not expose a transactional commit shared with PostgreSQL. The
  queue alone therefore cannot guarantee exactly-once resident display across
  this boundary. End-client/provider idempotency is required; a different queue
  would not remove the ambiguity.


A-03  HIGH  EXHAUSTED OWNERLESS START CLAIM CAN STRAND A SCHEDULED ALERT

Condition
  Workflow start returns successfully, but attaching run.runId fails and the
  Workflow does not reach beginBroadcastDelivery before the ten-minute claim
  timeout. Repeated ownerless reclaims can consume max_attempts.

Why it happens
  The dispatcher comment says leaving the job running prevents duplicate
  enqueue, but claim SQL explicitly reclaims a running row with NULL
  workflow_run_id after ten minutes. Each reclaim increments attempt_count.
  martindale_expire_outbox_claims eventually changes only the outbox row to
  dead; it does not change alert_broadcasts.delivery_status from scheduled.

Recovery gap
  The application failed-recipient retry accepts only partial/failed
  broadcasts. The operator tool refuses source=dead for alert-broadcast. The
  result is a dead outbox job paired with a scheduled broadcast and no supported
  recovery path. A resident in the frozen/intended audience can be skipped
  permanently until code or direct database intervention repairs the state.

Duplicate-invocation qualification
  Before exhaustion, several Workflow runs may be enqueued, but the database
  begin transition allows only one workflow_run_id to own delivery. Late runs
  return unchanged/superseded. Duplicate invocation by itself is fenced; the
  defect is terminal-state synchronization and recovery after exhaustion.

Evidence
  src/lib/alertBroadcastDispatcher.ts:36-55;
  src/lib/alertBroadcastRepository.ts:299-315,373-435,1085-1213;
  migrations/0005_shared_outbox_retry_policy.up.sql:50-72;
  src/lib/alertBroadcastRepository.ts:920-1045;
  scripts/outbox-dead-letter.mjs:69-83.

Repair within the current architecture
  When expiring an alert-broadcast dispatch claim, atomically move its broadcast
  to failed (as releaseBroadcastDispatchClaim already does for normal start
  failure), or permit the audited alert dead-letter recovery path to reconcile
  both rows. Correct the dispatcher comment. No queue replacement is needed.


A-04  MEDIUM  SENT MEANS PROVIDER ACCEPTED, NOT RESIDENT DELIVERED

Condition
  Resend returns a message ID but the email later bounces, or a push service
  accepts a message that never reaches/displays on the device (including TTL
  expiry).

Why it happens
  Both provider wrappers map successful API response directly to sent. There is
  no delivery/bounce receipt reconciliation in the reviewed path.

Impact
  The database can claim sent even though resident delivery did not happen.
  This may be an intentional at-provider-acceptance contract, but it is not a
  final-delivery contract and should not be presented operationally as proof of
  resident receipt.

Evidence
  src/lib/resendEmail.ts:88-128;
  src/lib/webPushSubscriptions.ts:709-729;
  src/lib/alertBroadcastRepository.ts:770-868.

Repair within the current architecture
  Define and label sent as provider-accepted. If final provider outcome is a
  requirement, ingest/reconcile supported provider receipts and expose accepted
  separately from delivered/bounced/expired. This is state-semantic work, not a
  new queue architecture.


A-05  MEDIUM  ATTACHED WORKFLOW RUNS HAVE NO LOCAL STALE-RUN RECOVERY

Condition
  An outbox row successfully stores workflow_run_id, but its durable Workflow
  run never reaches completion or its catch/release step.

Why it happens
  Automatic stale claiming and the operator stale-running action both require
  workflow_run_id IS NULL. A non-NULL owned running row is excluded forever by
  repository recovery logic.

Impact
  Depending on where the run stopped, every resident may be skipped, some may
  have received while later targets are skipped, or an ambiguous provider
  acceptance may remain pending. The job can remain running indefinitely.

Qualification
  Ordinary process death should be resumed by the durable Workflow engine, so
  this is a dependency/liveness limitation rather than proof that a normal
  worker crash loses delivery. The repository has no independent reconciliation
  if that external durability guarantee fails.

Evidence
  src/lib/alertBroadcastRepository.ts:1085-1213;
  migrations/0005_shared_outbox_retry_policy.up.sql:50-72;
  scripts/outbox-dead-letter.mjs:120-135;
  src/workflows/alertBroadcastDelivery.ts:382-390.

Repair within the current architecture
  Add an audited reconciliation procedure for old owned runs that first checks
  Workflow run state and provider/attempt state. Do not blindly clear a run ID;
  delivery may be ambiguous.


A-06  LOW  ZERO-TARGET DELIVERY IS FINALIZED AS SENT

Condition
  The atomic target snapshot contains no eligible email or push recipients.

Why it happens
  finalizeBroadcastDelivery explicitly maps total_count = 0 to sent. The email
  helper uses the same zero-recipient sent convention.

Impact
  No eligible resident is incorrectly omitted, but the database claims a sent
  broadcast even though no provider call occurred. This can mislead operators
  reviewing reach or diagnosing an unexpectedly empty audience.

Evidence
  src/lib/alertBroadcastRepository.ts:770-868;
  src/lib/alertBroadcastNotifications.ts:628-640.

Repair within the current architecture
  Preserve terminal completion but report zero-target completion explicitly in
  API/admin presentation and metrics; avoid wording that implies delivery.


REQUESTED SCENARIO MATRIX
=========================

Immediate sends
  SAFE WITH RESIDUAL PROVIDER WINDOW. Creation/outbox is atomic. A request-time
  Workflow start failure leaves a recoverable queued/retry job. Once a provider
  accepts, A-02 applies.

Scheduled sends
  SAFE UNTIL PROVIDER ACCEPTANCE. available_at prevents early claim; Workflow
  rechecks cancellation/expiry at begin. A-01 allows late Web Push display after
  timely provider acceptance.

Cancellation
  SAFE. Cancellation and begin-delivery are competing fenced database updates.
  A cancellation that wins prevents provider steps. A cancellation request that
  loses returns conflict and does not falsely label the message cancelled.

Workflow execution
  SAFE UNDER THE DURABLE WORKFLOW LIVENESS CONTRACT. Step failures release to
  bounded retry. A-05 is the gap when an attached run never resumes/releases.

Outbox claiming and concurrent workers
  SAFE. UPDATE + FOR UPDATE SKIP LOCKED prevents simultaneous claim of the same
  current lease. Exact workflow_run_id ownership fences later transitions.

Stale claims
  PARTIAL. Ownerless claims are reclaimed after ten minutes, but A-03 can strand
  a scheduled alert on exhaustion. Owned claims have the A-05 liveness gap.

Partial delivery
  SAFE EXCEPT FOR AMBIGUOUS PROVIDER ACCEPTANCE. Frozen targets and latest
  attempts yield partial/failed correctly. Completed targets are not selected
  again. A-02 applies when acceptance was not committed as sent.

Provider failures
  SAFE FOR UNAMBIGUOUS FAILURES. Email retries three times with a stable key;
  push records failed/expired/skipped per target. Unambiguous failure remains an
  incomplete target. Ambiguous failure-after-acceptance is A-02.

Failed-recipient-only retry
  SAFE. A row lock serializes retry creation. The new job retains the original
  frozen audience and stable per-broadcast/per-recipient idempotency. Sent and
  suppressed targets are excluded; failed, skipped, pending, and missing targets
  are retried.

Dead-letter handling
  SAFE FOR NORMAL workflow failure and resident-notification jobs. Alert
  provider failures become partial/failed and use the application retry.
  A-03 is the unmatched alert dead-letter state.

Duplicate Workflow invocation
  DELIVERY-FENCED. Multiple enqueued runs can occur after start/attach ambiguity,
  but only one run can set/retain workflow ownership and enter provider steps.
  This does not independently duplicate resident delivery.

Process crashes between transitions
  - Before atomic creation commit: no broadcast/job exists.
  - After creation commit, before claim: cron can claim it.
  - After claim, before Workflow start: start failure releases; hard death leaves
    an ownerless stale claim for reclaim/A-03.
  - After Workflow start, before run-ID attach: ownerless reclaim may enqueue a
    duplicate run, but begin fencing selects one owner; repeated exhaustion is
    A-03.
  - After run-ID attach, before/during Workflow: durable Workflow must resume;
    otherwise A-05.
  - After target snapshot: snapshot is atomic and is reused.
  - After provider acceptance, before attempt commit: A-02.
  - After attempt commit, before finalization: retry reads the committed sent
    attempt and does not resend that target.
  - During finalization: broadcast and outbox terminal transitions are atomic.


RESIDENT-HARM ANSWERS
=====================

Receive a message twice
  YES: Web Push provider acceptance followed by a crash/timeout before the
  pending attempt is completed, then stale-attempt replay (A-02). Email is also
  ambiguous at this boundary but is mitigated by external Resend idempotency.

Receive a cancelled message
  NO confirmed path. A database cancellation that wins occurs before provider
  steps; after sending starts the cancel request is rejected rather than stored
  as cancelled. Providers cannot recall an already accepted message, but this
  implementation will not then label the broadcast cancelled.

Receive an old message
  YES: fixed 24-hour Web Push TTL can outlive alert expiry (A-01).

Be skipped permanently
  YES: ownerless dispatch-claim exhaustion can dead-letter the job while leaving
  the alert scheduled and unrecoverable through supported alert tools (A-03).
  Conditional: an attached Workflow run that never resumes/releases (A-05).

Be retried incorrectly
  YES: an accepted-but-uncommitted provider call remains missing/pending and is
  selected for retry (A-02). Normal failed-recipient retry selection is correct.

Database claims delivery that did not happen
  YES: sent means provider acceptance, not resident receipt (A-04), and a
  zero-target broadcast is also marked sent without any provider call (A-06).


PRIORITIZED REPAIR ORDER
========================

1. Fix push expiry at provider TTL and service-worker receipt (A-01).
2. Add push display dedupe keyed by broadcast ID and explicitly govern ambiguous
   email/push replay (A-02).
3. Make ownerless alert-claim exhaustion synchronize the broadcast terminal
   state and recovery path (A-03).
4. Define provider-accepted versus delivered semantics (A-04/A-06).
5. Add audited reconciliation for stale owned Workflow runs (A-05).

These repairs retain the existing transactional outbox and Workflow design.
