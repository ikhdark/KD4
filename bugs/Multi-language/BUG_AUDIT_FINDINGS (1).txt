METHOD AND LIMITATIONS

This was a file-by-file static audit of the current working tree. Findings were
retained only when the review established:

  1. a violated repository, API, persistence, UI, test, or content invariant;
  2. a reachable causal path;
  3. a practical consequence; and
  4. precise source evidence.

Every retained finding received a separate adversarial re-check for guards,
alternate call paths, storage differences, native browser behavior, tests, and
documented intent. Duplicate causes were consolidated.

Per repository policy, the audit did not run lint, typecheck, unit tests,
format checks, builds, package/dependency audits, generated-output checks,
development servers, local browser automation, database commands, or
application/provider remote-service calls. Runtime-only,
production-configuration-only, concurrency-only,
and current dependency-vulnerability defects can therefore exist beyond what
static source proves. Official City of Martindale web material was consulted
only to verify the civic fact in finding 9.

Severity meanings:

  Medium - a concrete operational, data-integrity, or admin-workflow failure
           under a bounded but plausible path.
  Low    - a concrete defect with limited reach, mitigation, or impact confined
           to local/admin UX, tests, documentation, stale metadata, or a past
           civic record.


CONFIRMED FINDINGS

1. [MEDIUM] Requeueing an exhausted stale-running outbox job does not make a
   replacement dispatch claimable

Invariant:
  A successful operator "requeue" action must return the selected outbox job to
  a state that a dispatcher can claim.

Causal path:
  A final allowed claim increments attempt_count from max_attempts - 1 to
  max_attempts before workflow launch. If the dispatcher then crashes before
  recording workflow_run_id, the row becomes an eligible stale-running claim.
  The operator script changes that row to retry, clears the lock and workflow
  ID, and reports success, but only resets attempt_count when source=dead.
  Both resident and broadcast dispatchers require attempt_count < max_attempts.
  Their exhausted-row cleanup only examines state=running, so the newly retry
  row is neither claimable nor converted to dead.

Consequence:
  A resident-notification job remains stuck until direct repair. A broadcast
  replacement claim is likewise stuck if no already-started orphan workflow
  survives. The script nevertheless prints that it requeued the claim.

Evidence:
  - scripts/outbox-dead-letter.mjs:93-112, 168-175
  - src/lib/residentNotificationRepository.ts:26-61, 77-116
  - src/lib/alertBroadcastRepository.ts:1093-1150, 1170-1212
  - src/lib/residentNotificationDispatcher.ts:45-68
  - src/lib/alertBroadcastDispatcher.ts:63-80

Qualification:
  An already-started alert workflow can still resume on its own, so this
  finding does not claim that every affected broadcast is impossible to
  deliver. The confirmed failure is that the operator action does not create a
  dispatchable replacement claim.


2. [MEDIUM] Changing an item out of a filtered community-input queue leaves a
   stale row and can skip the next eligible submission

Invariant:
  A filtered moderation queue must continue to contain only matching records,
  and pagination must not skip records after a local mutation changes the
  filtered server result set.

Causal path:
  The panel requests a page using statusFilter. After PATCH changes a matching
  item to a different status, updateStatus replaces that item in place rather
  than removing it when it no longer matches the active filter. It also keeps
  the old nextOffset. If a 20-item filtered page loses one record on the
  server, the record formerly at index 20 shifts to index 19; "Load more" still
  requests offset 20 and skips it.

Consequence:
  An administrator can see reviewed/closed work in a "new" queue and can miss
  one still-eligible resident submission until the queue is reloaded or
  refiltered.

Evidence:
  - src/components/CommunityInputAdminPanel.tsx:134-152, 160-183,
    215-245, 333-339
  - src/app/api/community-input/route.ts:108-150


3. [MEDIUM] Map moderation accepts text beyond the durable schema limits and
   behaves differently across storage backends

Invariant:
  Authenticated API input must be bounded before persistence and must have
  consistent meaning across supported stores.

Causal path:
  readOptionalText trims nonblank strings but has no length argument. Review
  PATCH passes reviewNote and publicAddress directly to updateReview. The
  PostgreSQL implementation writes them against CHECK constraints of 1000 and
  240 characters. The route rethrows that database error. The JSON
  implementation instead converts an overlength supplied value to undefined
  while continuing the review update.

Consequence:
  A direct/custom authenticated admin client can send 1001/241-character
  values. PostgreSQL returns an unhandled 500 with no update, while Blob/local
  JSON can report success after clearing the moderation reason or public
  address and applying the other review fields.

Evidence:
  - src/app/api/map-feedback/route.ts:102-105, 476-553, 603-617
  - src/lib/mapFeedbackStore.ts:502-531, 548-620, 1212-1235
  - migrations/0001_security_reliability_foundation.up.sql:161-170

Qualification:
  The shipped admin panel has matching maxLength attributes, so ordinary UI
  entry is bounded. The confirmed path is the public admin API contract used by
  a direct or custom authenticated client.


4. [MEDIUM] A failed backup-manifest transaction leaves scheduled backup blobs
   outside repository-managed retention

Invariant:
  A scheduled backup is not successful until its verified database manifest is
  recorded, and scheduled encrypted objects must be eligible for the configured
  7-365 day retention window.

Causal path:
  database-backup uploads the encrypted artifact and its sidecar before the
  backup_manifests/audit transaction. Its compensating Blob deletion is scoped
  only to failures inside the upload block. If the later database transaction
  or connection fails, both private objects remain while the command fails.
  Future pruning selects paths only from backup_manifests, so the unrecorded
  pair is never selected or marked deleted. No repository Blob-listing or
  reconciliation job discovers it.

Consequence:
  Repeated failed scheduled runs can create an unbounded set of encrypted
  artifact/sidecar pairs that are absent from the recovery audit inventory and
  retained beyond the repository's scheduled-backup policy. The data remains
  encrypted, but repository-managed retention and observability cannot see it.

Evidence:
  - scripts/database-backup.mjs:122-160, 163-241, 244-250
  - docs/security-data-operations.md:39-45
  - .github/workflows/data-backup.yml:36-42
  - src/app/api/health/operational/route.ts:53-58

Qualification:
  An external Blob lifecycle or manual dashboard cleanup could mitigate this,
  but no such policy or reconciliation path is established in the repository.


5. [MEDIUM] The example-data verification gate omits two tracked store fixtures

Invariant:
  Every tracked data/examples fixture must contain fake values and match its
  owning store schema envelope.

Causal path:

Consequence:
  A malformed schema envelope or non-fake/sensitive value in either omitted
  fixture can pass verify:fast and verify:full.

Omitted fixtures:
  - data/examples/alert-broadcasts.example.json
  - data/examples/web-push-subscriptions.example.json

Evidence:

  - scripts/data-report.mjs:33-90, 275-315, 418-477
  - scripts/check-local-data-files.mjs:45-81

Qualification:

6. [LOW] Map-abuse PATCH omits the database-unavailable response used by GET
   and POST

Invariant:
  Every database-only abuse-queue operation must fail closed with a controlled
  503 when transactional storage is unavailable.

Causal path:
  GET and POST explicitly check isTransactionalStoreConfigured. PATCH
  authenticates, validates its body, and calls getPostgres without the same
  guard or a matching catch. In nonproduction, configured legacy admin
  credentials can authenticate without DATABASE_URL, after which a valid UUID,
  action, and resolution reach getPostgres and
  TransactionalStoreUnavailableError.

Consequence:
  A valid direct local admin request receives an internal 500 instead of the
  documented no-store 503. No data mutation occurs.

Evidence:
  - src/app/api/map-feedback/abuse/route.ts:100-111, 176-182, 298-327
  - src/lib/adminIdentity.ts:124-132, 359-383
  - src/lib/postgres.ts:25-31

Qualification:
  The normal admin UI cannot first load an abuse queue without the database, so
  this is primarily a direct-API/misconfiguration path.


7. [LOW] Subscriber search can leave an enabled action button paired with a
   blank invalid selection

Invariant:
  Action enablement must reflect the visible, currently selectable subscriber.

Causal path:
  A replacement search load replaces items but preserves every nonempty
  selectedId. When the old subscriber is absent from the new results, the
  required controlled select has no matching option and displays its empty
  placeholder. The Apply button still tests the stale state string, so it
  remains enabled.

Consequence:
  An operator can fill the reason and click Apply only to be stopped by native
  required-field validation, then must explicitly select a current result.

Evidence:
  - src/components/AdminSubscriberPanel.tsx:97-103, 175-182, 251-270,
    302-305

Qualification:
  Native required-select validation blocks the ordinary submit before the
  PATCH path. This is not a silent destructive action against the hidden old
  subscriber.

9. [LOW] The directly downloadable July 16 council event still contains the
   wrong official location

Invariant:
  Meeting locations must follow the latest controlling official notice.

Causal path:
  The event record stores 409 Main Street and an inherited June 16 verification
  date. The later official City News notice, posted July 9, states that the
  July 16, 2026 regular council meeting was at 407 Main Street. The event is now
  expired from upcoming UI, but findEventByCalendarId searches all events and
  the calendar route emits the stored LOCATION for a direct matching query.

Consequence:
  /calendar.ics?event=city-council-2026-07-16 currently downloads an ICS file
  with the wrong address.

Evidence:
  - src/lib/events.ts:35-37, 161-173, 745-757, 801-810, 827-875
  - src/app/calendar.ics/route.ts:10-38
  - Official notice (accessed 2026-07-28):
    https://martindale.texas.gov/m/newsflash/Home/Detail/542

Qualification:
  The meeting is past, so current impact is limited to the still-reachable
  direct calendar download and any consumer of the stored historical event.
  This finding does not infer that the separate August 20 location is wrong.

UNCONFIRMED RISKS - NOT COUNTED AS BUGS

U1. The default public map panel selects the oldest fetched report, but intended
    product behavior is undocumented

Observed behavior:
  Both public stores return reports newest-first. With no focused URL or marker
  selection, MapFeedbackMap uses reports.at(-1), so the summary and abuse form
  display the oldest of up to 200 fetched reports.

Evidence:
  - src/app/api/map-feedback/route.ts:161-180, 248-260
  - src/lib/mapFeedbackStore.ts:972-990
  - src/components/MapFeedbackMap.tsx:587-590, 627-635, 766-806,
    1322-1335

Missing fact:
  No repository contract or resident copy states whether the default panel
  should show the newest, oldest, or another prioritized report. The ordering
  is therefore a plausible UX defect, not a safely confirmed bug.


U2. Alternate database aliases can evade restore URL identity, but the remaining
    guard blocks a normal populated primary

Observed behavior:
  database-restore compares lowercased hostname, port, and database name, with
  one "-pooler." normalization. A different DNS/routing alias for the same
  database compares unequal and enters the rehearsal branch, omitting the
  in-place confirmation and recent restore-point checks. That branch separately
  refuses any target with public tables.

Evidence:
  - scripts/database-restore.mjs:66-77, 142-184
  - docs/security-data-operations.md:49-59

Missing facts:
  The repository does not establish a usable alternate production endpoint,
  and a full bypass also requires the protected primary to have zero public
  tables. A normal populated primary is stopped by the non-empty rehearsal
  guard. DNS equivalence and production state cannot be proven from static
  source, so this is not a confirmed current bug.


IMPORTANT REJECTED OR CONSOLIDATED CANDIDATES

  - The stale subscriber selection cannot silently PATCH the hidden prior
    subscriber through ordinary UI interaction; native required-select
    validation blocks it. Only the residual UI-state bug is finding 7.
  - Service-worker push renewal saves a replacement before deleting the old
    endpoint. A failed save preserves the old record; a failed delete leaves a
    stale duplicate that later delivery handling can expire. No data-loss bug
    was confirmed.
  - The two omitted example fixtures are one verification-gate bug, not two.
  - The missing .codex harness pages, deleted skill, and stale source-map claim
    are one incomplete-removal bug, not separate counts.
  - No claim was made about the August 20 council location from evidence that
    only controls the July 16 event.
