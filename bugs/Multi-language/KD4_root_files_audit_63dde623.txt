1. COMMITTED RUNTIME EVIDENCE EXPOSES PRIVATE AND MACHINE-SPECIFIC STATE
-----------------------------------------------------------------------

File(s):
  task-evidence/
  WORKTREE_REVIEW.txt
  .gitignore

Severity: Critical
Confidence: Very high

Issue:
The current tracked tree contains the exact task-evidence material that
WORKTREE_REVIEW.txt classified as a privacy and publish blocker. The recursive
tree includes SQLite databases, logs databases, WAL/SHM companions,
validation-history.key files, installation_id files, and copied runtime skill
trees. The committed review itself states that the material can contain user
thread/log text, local filesystem paths, installation identifiers, raw
validation-history keys, and possible credential-like strings.

This is not a hypothetical warning. The warned-against material is present in
the child commit immediately after the review's frozen HEAD.

Why this is a real issue:
A person cloning the repository can receive local runtime history and
identifier/key-bearing state that has no legitimate role in source control.
Even when a particular token is no longer active, private conversation text,
local paths, identifiers, and validation material remain an exposure.

Real task example:
A contributor clones KD4 to review a Rust change. Before opening any source
file, the clone already contains another machine's state_5.sqlite,
logs_2.sqlite, validation-history.key, installation_id, and associated runtime
files.

Highest-confidence fix:
  1. Remove task-evidence/ from the Git index and current tree.
  2. Add an anchored /task-evidence/ ignore rule.
  3. Preserve only tiny, deterministic, hand-redacted test fixtures whose
     contents are intentionally public.
  4. Review the committed artifacts without printing their sensitive values.
  5. If the repository or commits were shared, purge the sensitive paths from
     reachable history where operationally appropriate.
  6. Rotate or revoke any credential, key, installation identifier, or other
     secret-like value found during that review.

Do not solve this by placing the existing databases in Git LFS. LFS changes
storage mechanics; it does not solve privacy, nondeterminism, or provenance.


2. TASK-EVIDENCE DATABASE CAPTURES CREATE LARGE, OPAQUE, NONDETERMINISTIC DIFFS
------------------------------------------------------------------------------

File(s):
  task-evidence/

Severity: High
Confidence: Very high

Issue:
The committed evidence contains multiple large mutable database captures. The
tracked tree includes state_5.sqlite files of approximately 37.9 MB and
logs_2.sqlite files of approximately 4.8 MB, in addition to WAL/SHM state and
duplicated runtime trees. WORKTREE_REVIEW.txt describes the overall evidence
set as approximately 134 MB.

SQLite and WAL snapshots are not stable source fixtures. Small runtime actions
can rewrite many binary pages, and reviewers cannot meaningfully inspect the
semantic difference in a normal pull request.

Why this is a real issue:
It increases clone/fetch size, slows repository operations, defeats ordinary
code review, and allows incidental runtime activity to generate massive binary
changes.

Real task example:
A developer records one additional validation event and then runs git status.
Instead of a small expected fixture update, Git reports tens of megabytes of
opaque database changes that cannot be reviewed line by line.

Highest-confidence fix:
Replace database-home captures with the smallest deterministic fixture that
proves the exact behavior:
  - a schema-only fixture;
  - a tiny migration fixture generated by a script;
  - a small SQL seed file with synthetic values; or
  - a test that creates its database in a temporary directory at runtime.

Document the generator and verify that regeneration is byte-stable where
possible.

29. THE GLOBAL JUST SHELL PROBES SCCACHE EVEN FOR NON-RUST COMMANDS
------------------------------------------------------------------

File:
  justfile

Verified owner:
  scripts/just-shell.py

Severity: Medium
Confidence: Very high

Issue:
Every recipe is routed through scripts/just-shell.py. The router performs an
sccache health probe before the command has been limited to Rust/Cargo work,
so documentation, source-map, schema, and other non-Rust recipes can pay for
sccache startup/health behavior.

Successful probe state is reusable, but failed/timed-out probes are not

create. The probe timeout can therefore be paid repeatedly when sccache is

commands.

starts several wrapper processes; each unrelated line can wait on the sccache
probe before executing.

Highest-confidence fix:
Classify the command first and probe sccache only for Cargo/rustc commands that
can use it. Cache both positive and negative health results for the duration of
the top-level just invocation, with an explicit reset/recheck path.
