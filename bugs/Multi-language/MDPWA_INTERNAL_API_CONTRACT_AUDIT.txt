MDPWA INTERNAL API CLIENT/ROUTE CONTRACT AUDIT
Date: 2026-08-07
Scope: Production MDPWA callers of internal /api routes under src/, public/,
       scripts/, and vercel.json. Tests were used only as corroboration and
       are not counted as clients.

RESULT
======

Three contract drifts can make a client show the wrong state. They do not
require an API redesign. The smallest fixes are client-side handling of
Retry-After, admin-session expiry, and request deadlines.


CONFIRMED MISMATCH 1 - Retry-After is emitted but every interactive client
ignores it
==========================================================================

Server contract:

1. POST /api/alert-signups returns 503 with Retry-After: 900 when required
   confirmation mail cannot be sent
   (src/app/api/alert-signups/route.ts:358-371).
2. POST /api/admin/session returns 401 or a submission-integrity status with
   Retry-After: 1
   (src/app/api/admin/session/route.ts:100-115, 149-160, 180-191,
   211-222).
3. POST /api/alert-broadcasts returns the submission-integrity status with
   Retry-After: 1
   (src/app/api/alert-broadcasts/route.ts:70-87).

Client assumption:

- AlertSignupForm submits through useResidentFormSubmission. Its finally block
  releases the submission lock immediately; neither residentSubmission.ts nor
  the hook reads Retry-After
  (src/components/AlertSignupForm.tsx:99-103;
  src/components/useResidentFormSubmission.ts:100-153;
  src/components/residentSubmission.ts:15-58).
- AdminLoginForm also releases isSubmitting immediately and does not inspect
  the header (src/components/AdminLoginForm.tsx:33-67).
- AlertBroadcastComposer releases its send lock immediately and does not
  inspect the header (src/components/AlertBroadcastComposer.tsx:218-264,
  268-304).

Wrong state:

The forms present themselves as ready to retry while the server has explicitly
said that an immediate retry should not occur. This is especially misleading
for alert signup, where the advertised wait is 15 minutes. The JSON error is
correctly treated as failure, but the retry state is wrong.

Smallest correction:

Add one client helper that parses a delta-seconds or HTTP-date Retry-After from
ApiResponseError.response. In these three submit paths, keep the action disabled
until that instant and show the remaining/retry-later state. Do not change the
route statuses or bodies.


CONFIRMED MISMATCH 2 - Expired admin authentication is displayed as an ordinary
load/action error while the dashboard remains authenticated
===============================================================================

Server contract:

requireAdminRequest returns JSON 401 { ok: false, error: "Not authorized.",
issues: [...] } whenever the admin cookie/token is absent, expired, or lacks the
required permission (src/lib/adminRoute.ts:20-55). It returns JSON 503 when the
identity system is not configured. The protected routes consistently return
that Response rather than redirecting.

Client assumption:

AdminDashboard checks GET /api/admin/session only on its initial effect and
stores the resulting authenticated state
(src/components/AdminDashboard.tsx:35-96). Later protected fetches pass every
401 through their ordinary generic-error path; they neither invalidate the
dashboard session nor navigate to login:

- AlertBroadcastComposer POST /api/alert-broadcasts
  (src/components/AlertBroadcastComposer.tsx:223-261, 284-299).
- AdminSubscriberPanel GET/PATCH /api/admin/subscribers
  (src/components/AdminSubscriberPanel.tsx:55-60, 84-114, 153-168).
- CommunityInputAdminPanel GET/PATCH /api/community-input
  (src/components/CommunityInputAdminPanel.tsx:62-97, 171-213).
- MapFeedbackAdminPanel GET/PATCH /api/map-feedback/abuse
  (src/components/MapFeedbackAdminPanel.tsx:100-117, 257-274).
- useMapFeedbackAdminActions PATCH /api/map-feedback
  (src/components/useMapFeedbackAdminActions.ts:80-164).
- The admin form of MapFeedbackMap GET /api/map-feedback
  (src/components/MapFeedbackMap.tsx:768-831).

The list clients also retain their existing records when a later load returns
401. The outer AdminDashboard therefore continues to render authenticated
controls and can display previously loaded admin data while each action merely
reports a generic load/action failure.

Wrong state:

The server says the actor is no longer authenticated, but the UI still says and
behaves as though an admin session exists. Repeated protected actions cannot
succeed until the user signs in again.

Smallest correction:

At the shared admin-client boundary, special-case ApiResponseError status 401:
clear protected list/detail state and notify AdminDashboard to set
authenticated=false (or navigate to the existing localized admin login URL).
Keep 403 available for any future permission-specific UI, and keep 503 as an
availability/configuration error. Do not add a server redirect; the existing
JSON API contract is appropriate.


CONFIRMED MISMATCH 3 - Interactive API calls have no elapsed-time deadline, so
loading/submitting states can remain permanent
==========================================================================

Observed contract:

- scripts/synthetic-check.mjs correctly aborts its internal health request at
  15 seconds (lines 40-57).
- Some browser load effects create AbortControllers, but they abort only on
  unmount/dependency cleanup. That is lifecycle cancellation, not a timeout.
- Mutation calls generally supply no AbortSignal at all.
- Server-side NWS and reverse-geocode upstream calls have their own deadlines,
  but those do not bound a stalled browser-to-MDPWA request.

Affected interactive clients include:

- WeatherPanel and HeaderWeather -> GET /api/weather.
- useSubmissionIntegrityToken -> GET /api/submission-integrity-token.
- MapFeedbackMap -> GET/POST /api/map-feedback and GET
  /api/reverse-geocode.
- CommunityInputForm/AdminPanel -> POST/GET/PATCH /api/community-input.
- AlertSignupForm/AlertSignupExperience -> POST/GET/PUT/DELETE
  /api/alert-signups.
- PushNotificationSignup -> GET/POST/PUT/DELETE /api/push-subscriptions.
- MapFeedbackAbuseForm/MapFeedbackAdminPanel -> POST/GET/PATCH
  /api/map-feedback/abuse.
- AdminDashboard/AdminLoginForm/AdminSignOutButton -> GET/POST/DELETE
  /api/admin/session.
- AdminSubscriberPanel -> GET/PATCH /api/admin/subscribers.
- AlertBroadcastComposer -> POST /api/alert-broadcasts.
- useMapFeedbackAdminActions -> PATCH /api/map-feedback.

Examples of permanent wrong state are submitting/pending locks whose finally
blocks never run, and loading/checking views whose catch branches never run.
The user cannot distinguish a slow request from a dead one and may be unable to
retry without reloading the page.

Smallest correction:

Compose every interactive fetch's lifecycle signal (when present) with one
shared elapsed-time deadline, and map timeout/abort separately: cleanup aborts
should be silent, while elapsed timeout should release the lock and show the
existing retry/error state. This is client request handling only; no route
contract change is needed. The synthetic check already demonstrates the
minimal pattern.


FULL ROUTE/CALLER INVENTORY AND CONTRACT RESULT
===============================================

/api/admin/session
  Clients: AdminDashboard GET; AdminLoginForm POST; AdminSignOutButton DELETE.
  Result: Status and JSON success/error bodies align. POST Retry-After and
  timeout handling drift as described above. DELETE is JSON 200, not a redirect;
  the client intentionally performs its own navigation.

/api/admin/subscribers
  Client: AdminSubscriberPanel GET/PATCH.
  Result: 200 list/update shapes, 400 validation, 401 auth, 404 not-found, and
  503 availability are rejected/parsed correctly. The 401 is not promoted to
  session expiry, and there is no request deadline.

/api/alert-broadcasts
  Client: AlertBroadcastComposer POST for preview, test, and final send.
  Result: dry-run 200 is validated; final 202 queued and replay 200 are
  distinguished by queued; partially successful test delivery stays HTTP 200
  and is shown as warning using delivery result counts. Error statuses are
  rejected. Retry-After, auth expiry, and timeout handling drift as above.

/api/alert-broadcasts/[id]
  Client: no production in-repo MDPWA caller found. The PATCH cancel/retry
  contract therefore has no client assumption to compare.

/api/alert-signups
  Clients: AlertSignupForm POST; AlertSignupExperience GET/PUT/DELETE.
  Result: 201 signup, 200 management/update/removal, 400 validation, 401
  preference access, 404 missing subscriber, 409 conflict, and 503 storage/mail
  errors are treated as success/failure on the correct side of response.ok.
  Known resident issueCodes are mapped. Retry-After and timeout handling drift
  as above. A management-session 401 becomes a generic failed-management view;
  it does not falsely report success.

/api/alert-signups/link
  Clients: action URLs generated by alertSignupNotifications.ts and
  alertBroadcastNotifications.ts; the route's returned HTML form POSTs back to
  the same route.
  Result: GET returns the confirmation HTML or redirects an invalid link; POST
  uses 303 redirects for invalid, unavailable, or completed exchanges. Browser
  method switching is correct. No fetch client expects JSON or an empty body.

/api/community-input
  Clients: CommunityInputForm POST; CommunityInputAdminPanel GET/PATCH.
  Result: 201 accepted/idempotent response, 200 list/update shapes, 400/413
  validation/body errors, 401 admin auth, 404 missing record, 409 idempotency
  conflict, and 503 storage errors align. notificationQueued=false is a partial
  notification outcome, not a failed submission; the resident UI's saved state
  is correct. Admin auth expiry and timeout handling drift as above.

/api/cron/outbox
  Client: Vercel cron declaration in vercel.json.
  Result: Vercel supplies the scheduled GET/auth context and uses HTTP success
  versus failure. No in-repo UI consumes its JSON body, redirect, or empty-body
  behavior.

/api/cron/retention
  Client: Vercel cron declaration in vercel.json.
  Result: Same as outbox; no in-repo stateful JSON consumer.

/api/health/operational
  Client: scripts/synthetic-check.mjs GET with bearer auth.
  Result: 200 healthy versus 401/503 failure and application/json content type
  align. The client follows redirects but also verifies content type, so a
  redirect to HTML cannot produce a false pass. It has a 15-second abort.

/api/map-feedback
  Clients: MapFeedbackMap GET/POST; useMapFeedbackAdminActions PATCH.
  Result: list/submission/update shapes and 200/201/400/401/404/409/503 outcomes
  align. Resend-alert returns 503 unless email.status is sent, so the client
  cannot announce a failed resend as success. Resident notificationQueued=false
  does not undo the saved report. Admin auth expiry and timeouts drift as above.
  DELETE has no production in-repo caller.

/api/map-feedback/abuse
  Clients: MapFeedbackAbuseForm POST; MapFeedbackAdminPanel GET/PATCH.
  Result: submission/list/resolution shapes and error statuses align. The
  idempotency conflict path rotates its key rather than showing success. Admin
  auth expiry and timeouts drift as above.

/api/map-feedback/agency
  Client: no production in-repo MDPWA caller found. Its signed agency-action
  browser contract has no in-repo client assumption to compare.

/api/push-subscriptions
  Clients: PushNotificationSignup and the generated public/sw.js; the canonical
  scripts/templates/service-worker.js mirrors the service-worker calls.
  Result: GET configuration, PUT saved-topic lookup, POST 201 save, and DELETE
  200 removal shapes/statuses align. Non-OK responses are checked before state
  changes. Replacement migration explicitly retains pending state across a
  save-new/delete-old partial failure. Interactive and service-worker fetches
  lack elapsed-time deadlines.

/api/reverse-geocode
  Client: MapFeedbackMap GET.
  Result: 200 address versus 400/429 validation/integrity and 502 upstream error
  are not confused with success. Server errors deliberately produce the
  resident-safe not-found/error state. The effect aborts on cleanup but has no
  browser request deadline.

/api/submission-integrity-token
  Client: useSubmissionIntegrityToken GET.
  Result: The success body intentionally has submissionIntegrityToken without
  ok; the hook correctly requires that field. 400 scope and 503 availability
  errors are rejected. Cleanup abort exists; elapsed timeout does not.

/api/weather
  Clients: WeatherPanel and HeaderWeather GET.
  Result: Both require 200 { ok: true, weather } and reject the route's 503
  { ok: false, error }. They preserve prior weather on refresh failure, which
  is correct. Cleanup/refresh cancellation exists but no browser request
  deadline.

/api/webhooks/resend
  Client: external Resend webhook sender, not an MDPWA client. No in-repo
  caller assumptions were found; it is listed so route coverage is explicit.


REQUESTED EDGE-CASE SUMMARY
===========================

- HTTP status codes: compared for every in-repo caller; 202 queued and 201
  creation paths are handled correctly. Confirmed drift is 401 meaning and
  Retry-After state, not response.ok classification.
- Success response shapes: aligned for actual route outputs. Where a client
  ignores optional delivery/notification detail, its displayed primary action
  (saved/queued) remains true.
- Error response shapes: all fetch clients reject non-2xx responses. Resident
  issueCodes are mapped where field-level guidance is supported. Several admin
  clients intentionally show generic fallback copy, but they do not report
  success; the wrong-state exception is expired authentication.
- Retry-After: present on three server paths and ignored by all three clients;
  confirmed mismatch 1.
- Empty responses: no internal route returns a successful 204/205 or other
  successful empty body. readJsonResponse tolerates an empty 2xx, but no actual
  route currently exercises that permissive assumption.
- Redirects: only /api/alert-signups/link redirects. GET keeps GET semantics;
  POST uses 303. No JSON fetch client calls it. The health script's redirect
  following is protected by its content-type check.
- Authentication failures: protected routes use JSON 401, not redirects.
  Alert preference 401 is a failed management state. Admin 401 is not promoted
  to dashboard session expiry; confirmed mismatch 2.
- Validation errors: 400/413/409 shapes are consistently non-OK and cannot be
  shown as success. Known resident issue codes are consumed; generic admin copy
  loses detail but not success/failure state.
- Partial successes: broadcast delivery counts drive warning state; final
  queued delivery is recognized; resident saved-with-notification-not-queued
  stays correctly saved; push key migration preserves retry state.
- Timeout/abort: only the synthetic health client has an elapsed deadline.
  Cleanup aborts are not deadlines; confirmed mismatch 3.


RECOMMENDED MINIMAL PATCH ORDER
===============================

1. Add Retry-After parsing and wire the three submit paths.
2. Add shared admin-401 invalidation/navigation and clear protected cached
   records on expiry.
3. Add one shared request-deadline signal to interactive fetches, preserving
   existing cleanup-abort behavior.

No API route status, schema, redirect, or persistence redesign is recommended.


IMPLEMENTED CORRECTIONS
=======================

Date: 2026-08-07

1. Retry-After
   - Added shared parsing for both delta-seconds and HTTP-date values.
   - Alert signup, admin login, and alert broadcast now keep their submit
     actions disabled until the advertised retry deadline passes.

2. Expired admin authentication
   - Protected admin requests now share a 401 boundary.
   - A protected 401 invalidates the dashboard session state and unmounts the
     protected panels, clearing their in-memory records without introducing a
     redirect or changing the API response.

3. Request deadlines
   - Interactive internal API requests now share a 15-second deadline.
   - Existing lifecycle abort signals are composed with the deadline; lifecycle
     cleanup remains silent while a deadline uses the caller's existing failure
     state and localized fallback message.

Scope and review
----------------

- This implementation does not change any API route status, response schema,
  redirect, authentication mechanism, validation rule, persistence behavior,
  or partial-success contract.
- Source review found no remaining direct production fetch calls under
  src/components; internal calls now pass through the shared request helper.
- Automated repository checks were not run because repository policy requires
  an explicit user request.
