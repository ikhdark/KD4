MDPWA DATA-OPERATIONS AUDIT — ACTIONABLE GAPS ONLY
Audit date: 2026-08-07

1. HIGH — A scheduled backup sidecar can claim verification before durable finalization.

Failure case:
After the artifact and sidecar uploads succeed, but before the database manifest is finalized, a process termination or lost database operation leaves the sidecar in private Blob with a populated verifiedAt value while backup_manifests.verified_at is still NULL. finalizeManifest is outside the publication cleanup catch, so a finalization failure also leaves the uploaded objects and their verification-looking sidecar in place. An operator or release record that treats the sidecar as proof can accept an interrupted backup that the authoritative manifest still considers unverified.

Implementation evidence:
- scripts/database-backup.mjs:101-120 uploads artifact, uploads sidecar, and only then calls finalizeManifest.
- scripts/database-backup.mjs:225-238 writes verifiedAt into that pre-finalization sidecar.
- scripts/database-backup.mjs:270-298 sets backup_manifests.verified_at and appends the audit event later.

Documented contract:
- docs/security-data-operations.md:43 says the manifest is reserved unverified, verified_at and the creation audit are finalized atomically, and a scheduled backup is not successful until verified_at exists.
- docs/release-assurance.md:43 and 93 require a recent verified manifest/fingerprint as release evidence.

Required enforcement:
Do not publish a field named verifiedAt before authoritative finalization. Represent pre-finalization verification as pending/local-only, or publish a distinct immutable completion marker only after the database finalization is known durable. Make consumers and release checks require the authoritative verified manifest. Add fault-injection tests for termination/failure after reservation, artifact upload, sidecar upload, finalization commit, and lost finalization response.

2. HIGH — Backup and restore select the current migration nondeterministically.

Failure case:
All migration rows inserted by one migration run receive the same transaction-stable now() timestamp. Backup and restore both use ORDER BY applied_at DESC LIMIT 1 without a tie-breaker. PostgreSQL may therefore return any migration from the batch, causing a backup to be labeled with an older version, a restore to fail unpredictably, or the metadata/dump comparison to agree on the wrong version by accident.

Implementation evidence:
- migrations/0001_security_reliability_foundation.up.sql:1-5 defines applied_at DEFAULT now().
- scripts/database-migrate.mjs:238-276 applies all pending migrations and inserts their schema_migrations rows in one transaction.
- scripts/database-backup.mjs:166-173 selects the version by applied_at only.
- scripts/database-restore.mjs:204-214 repeats the same unordered selection.

Documented contract:
- docs/release-assurance.md:44 and 91 require an exact database migration version and applied migration run.
- docs/security-data-operations.md:56 and 59 require migration-version comparison and app/database version alignment.

Required enforcement:
Derive the current version from the ordered repository manifest plus a contiguous applied set, or store an explicit monotonic migration sequence/run record. Never infer it from a non-unique timestamp. Add a regression test in which every applied row has the same applied_at value.

3. HIGH — Restore completion does not establish compatibility with the running application or repository migration catalog.

Failure case:
Restore only checks that the version found inside the restored database equals the version embedded in that same backup. It does not compare either value with the current repository manifest or an explicitly supported schema range. A cryptographically valid old backup—or a forward-version backup presented to an older checkout—can print “Restore completed” even though the current application must not be re-enabled against it.

Implementation evidence:
- scripts/database-restore.mjs:1-17 imports the backup-format helpers but no migration catalog.
- scripts/database-restore.mjs:196-215 compares restored state only with metadata.migrationVersion.
- scripts/database-restore.mjs:233-235 prints completion immediately after those database-local checks.

Documented contract:
- docs/security-data-operations.md:56-59 requires comparison of migration state and re-enablement only after application and database versions match.
- docs/release-assurance.md:89-91 requires the candidate revision and applied migration run to be part of the same production exit record.

Required enforcement:
Validate the restored migration set/checksums against the checkout’s manifest and classify the result as current, safely forward-migratable, recovery-only, or unsupported. Do not emit a ready/completed operational result for an incompatible state. Require and test the forward-migration/application-compatibility step before writes can be re-enabled.

4. HIGH — In-place restore does not enforce the required write outage.

Failure case:
The CLI requires an in-place flag, confirmation, and a recent restore-point backup, but it never proves that application writes are stopped. Concurrent requests can write while pg_restore is running or immediately after its transaction commits and before post-restore validation/audit completes. That can invalidate verification counts, mix pre- and post-restore state, or let the command report completion for a database already modified after the restored snapshot.

Implementation evidence:
- scripts/database-restore.mjs:130-183 implements target checks, recent restore-point lookup, and confirmation only.
- scripts/database-restore.mjs:184-235 runs pg_restore, queries counts, writes an audit event, and reports completion without acquiring a shared maintenance/write fence.
- No retention/restore-wide advisory lock or application maintenance-state check is present in this path.

Documented contract:
- docs/security-data-operations.md:51-59 requires stopping application writes, an approved outage for in-place restore, and re-enabling only after compatibility and audit checks.

Required enforcement:
Introduce a durable, target-bound maintenance state and a database lock/fence honored by every resident/admin write path; verify it before restore and keep it through post-restore checks. Bind the approval and restore-point evidence to the specific target and operation. Add a concurrency test proving writes are rejected for the full restore window and cannot land between restore commit and validation.

5. HIGH — Legal-hold placement can race past retention’s disposal snapshot.

Failure case:
Retention’s destructive statement tests NOT EXISTS against active holds, while hold placement/release executes independently. Under PostgreSQL READ COMMITTED, a hold committed after the retention statement snapshot is established can be invisible to that disposal statement. The retention transaction can therefore delete or redact the record even though the hold command successfully commits before the retention run completes.

Implementation evidence:
- src/lib/retention.mjs:154-334 performs disposal in a transaction whose destructive CTEs use repeated NOT EXISTS hold checks.
- scripts/retention-hold.mjs:55-154 places or releases a hold in a separate statement.
- Neither path acquires a shared advisory/per-record lock or uses a serializable retry protocol.

Documented contract:
- docs/security-data-operations.md:65 says active record_retention_holds always override disposal.
- docs/security-data-operations.md:82-84 requires hold review before apply and record-specific holds before scheduled disposal.

Required enforcement:
Serialize hold mutations and disposal for the same record (or all retention operations) with a shared advisory/per-record lock, or use SERIALIZABLE transactions with mandatory retries and a final locked hold check immediately before mutation. Define whether an in-flight hold request blocks disposal and enforce that rule. Add a real-PostgreSQL barrier test that interleaves hold placement with retention deletion/redaction.

6. MEDIUM — Backup provenance and PostgreSQL tool-version evidence are not authenticated or enforced at restore.

Failure case:
The backup command checks pg_dump compatibility but discards the returned client/server majors. The encrypted metadata and sidecar contain neither those versions nor a source database/environment identity. Restore does not preflight pg_restore/archive compatibility. As a result, the command cannot produce the required version evidence, cannot distinguish a valid backup from the wrong source environment when keys are shared or misconfigured, and discovers an incompatible restore tool only during the destructive apply attempt.

Implementation evidence:
- scripts/database-backup.mjs:70-89 calculates clientMajor/serverMajor, but verifyPgDumpCompatibility returns no retained result to the caller.
- scripts/lib/database-backup-format.mjs:31-66 authenticates format, timestamp, IV, migration version, and plaintext checksum only.
- scripts/database-backup.mjs:225-238 omits source identity and PostgreSQL versions from the sidecar.
- scripts/database-restore.mjs:33-63 invokes pg_restore directly without a version/archive preflight.

Documented contract:
- docs/release-assurance.md:93 requires pg_dump/server major versions in production exit evidence.
- docs/release-assurance.md:100 requires fingerprints to belong to the intended environment.
- docs/security-data-operations.md:21-23 requires intended-environment targeting and compatible PostgreSQL client tools.

Required enforcement:
Put normalized pg_dump and server majors plus a stable, non-secret source database/environment identifier into authenticated backup metadata and the authoritative manifest. Query and attest the actual target database identity rather than relying only on URL text. Preflight pg_restore/archive compatibility before --apply, and require an explicit source-to-target policy. Test wrong-environment artifacts, endpoint aliases, and newer-archive/older-pg_restore combinations.

7. MEDIUM — The required database failure-mode test track is mostly absent.

Failure case:
The current tests can remain green while transaction locking, interrupted/corrupt backup handling, wrong-target refusal, rollback ordering, or retention/hold serialization is broken. Migration tests exercise a mocked read-only planner, backup tests mock publication callbacks, and retention tests inspect mocked SQL text. No test invokes restore, decrypts a corrupt/truncated artifact, or interleaves real PostgreSQL sessions.

Implementation evidence:
- src/app/tests/database-migrate.test.ts:68-125 covers manifest alignment and in-memory planning/checksum rejection only.
- scripts/database-backup.test.ts:8-90 covers the version comparison helper and mocked publication ordering/one upload failure.
- src/lib/tests/retention.postgres.test.ts:1-128 uses a mocked transaction harness and asserts generated SQL fragments.
- Repository test search found no database-restore, database-backup-format, migration advisory-lock, rollback execution, or retention-hold concurrency test.

Documented contract:
- docs/release-assurance.md:25-34 explicitly requires automated coverage for concurrent migration attempts, encrypted backup verification, isolated-target restore, legal holds, and retention dry-run/apply.

Required enforcement:
Add an isolated real-PostgreSQL integration suite covering two concurrent up attempts; up/down contention; injected failure midway through a migration; manifest/file/checksum drift; latest-only rollback; corrupt, truncated, wrong-key, and unsupported-format backups; interrupted publication at every boundary; empty/wrong/in-place restore targets; old/new schema compatibility; retention against concurrent activation; and hold placement racing disposal. Keep these tests in the mandatory release track.

8. MEDIUM — Repository release automation does not enforce that data-operation proof belongs to one candidate and environment.

Failure case:
The scheduled backup workflow creates a backup independently, while migration, restore rehearsal, rollback rehearsal, and candidate revision evidence are not joined by a machine-checked release gate. A stale but valid backup record, a rehearsal from another environment, or a migration run from another revision can be copied into a release record and still reach promotion unless an external manual control catches it.

Implementation evidence:
- .github/workflows/data-backup.yml:1-70 schedules and dispatches the backup command but emits no candidate/environment-bound release attestation.
- package.json:46-52 exposes independent migration, backup, restore, retention, and hold commands; the repository contains no promotion check that joins their run IDs/fingerprints to a candidate revision and intended environment.

Documented contract:
- docs/release-assurance.md:81-100 says procedures/workflow definitions are not completion evidence and forbids promotion until every URL/fingerprint belongs to the same candidate revision and intended environment.

Required enforcement:
Create a signed or otherwise tamper-evident release attestation that binds candidate commit/deployment, target environment/database identity, migration run, verified backup manifest, restore/rollback rehearsal records, timestamps, and approvers. Make the production promotion/environment gate validate freshness and exact binding rather than relying on copied free-form evidence. If this enforcement exists outside the repository, document its control owner and immutable evidence source here.
