F01 - HIGH - CONFIRMED - Diagnostic false success
------------------------------------------------------------------------------------------------------------
File: scripts/git_doctor.py
Relevant code: timed_status(), build_report(), main()
Issue: A nonzero `git status --short --untracked-files=no` result is recorded exactly like a successful
       status check. `timed_status()` returns `(elapsed, False)` for both return code 0 and every nonzero
       return code, and `main()` fails only when the command times out.
Why this is an issue: The doctor can certify Git health while Git is unable to inspect the repository at
                      all. That is a false-success result on the diagnostic's primary probe.
Real task example: A developer runs the doctor after an index corruption, unsafe-repository ownership error,
                   or missing-object failure. `git status` exits 128, but the doctor prints a normal elapsed
                   time and exits 0, so an automated setup check proceeds as though Git is healthy.
Highest-confidence fix: Return a structured status result containing elapsed time, timeout state, return
                        code, and a bounded stderr message. Add a `status_failed`/`status_error` field to
                        `GitDoctorReport`; make `main()` return nonzero for timeout or command failure.
                        Never display a failed command as a normal timing sample.
Regression test to add: Mock `run_git()` to return code 128 with stderr and assert JSON reports the failure
                        and the CLI exits nonzero; retain separate success and timeout tests.

F02 - LOW - HIGH - Incorrect configuration diagnosis
------------------------------------------------------------------------------------------------------------
File: scripts/git_doctor.py
Relevant code: git_config(), recommendations()
Issue: `core.untrackedCache` is read as raw text but is considered enabled only when the text is exactly
       `true`. Valid Git boolean spellings such as `yes`, `on`, or `1` are therefore reported as disabled.
Why this is an issue: The same valid configuration can produce different doctor verdicts based only on
                      spelling, causing unnecessary configuration churn and misleading automated reports.
Real task example: A workstation has `git config core.untrackedCache yes`. Git treats the setting as
                   enabled, but the doctor recommends enabling it again.
Highest-confidence fix: Read boolean settings with `git config --type=bool --get <name>` and compare the
                        canonical result, or route both FSMonitor and untracked-cache values through one
                        Git-compatible boolean parser. Preserve non-boolean special values explicitly where
                        a setting supports them.
Regression test to add: Parameterize `true`, `yes`, `on`, `1`, `false`, `no`, `off`, and `0`; assert
                        equivalent spellings receive equivalent recommendations.

F03 - HIGH - CONFIRMED - Evidence/staging mismatch
------------------------------------------------------------------------------------------------------------
File: scripts/investigation_evidence_smoke.py
Relevant code: provider source fingerprinting and _copy_tracked_tree()
Issue: The provider fingerprint includes untracked provider files, but the staged provider copy is built
       from `git ls-files` tracked paths only. The evidence identity can therefore describe bytes that are
       not present in the provider actually exercised by the smoke run.
Why this is an issue: A passing smoke result can be bound to the wrong source tree. This defeats the purpose
                      of content-bound evidence and can hide missing new plugin modules or resources.
Real task example: A developer adds an untracked `provider/runtime.py`, updates a tracked import to use it,
                   and runs the smoke check before `git add`. The fingerprint changes because the new file
                   exists, but staging omits it; the smoke run tests a stale/incomplete provider copy.
Highest-confidence fix: Use one canonical file manifest for both fingerprinting and staging. Either include
                        tracked plus untracked non-ignored files with `git ls-files --cached --others
                        --exclude-standard -z`, or reject any untracked provider file before producing
                        evidence. Copy and hash the exact same manifest, and record that manifest in the
                        result.
Regression test to add: Create an untracked provider module required by a tracked file. Assert the smoke
                        tool either copies it and succeeds against matching evidence or fails before
                        execution with an explicit untracked-source error.

F04 - HIGH - CONFIRMED - Benchmark false success
------------------------------------------------------------------------------------------------------------
File: scripts/kd4_perf_snapshot.py
Relevant code: ScenarioResult.passed, main()
Issue: `ScenarioResult.passed` returns true for both `passed` and `skipped`. Consequently, a profile can
       omit unavailable executables and still produce `ok: true`, an empty `failedScenarios`, and exit code
       0.
Why this is an issue: A baseline is only useful when its required measurements actually ran. Treating
                      absence as success makes incomplete snapshots look comparable to complete snapshots.
Real task example: A `phase0` run has no installed local Codex binary and no `cargo-nextest`. The
                   installed-binary and test scenarios are skipped, but the command succeeds and the JSON
                   can be archived as a valid phase-zero baseline.
Highest-confidence fix: Give each profile an explicit required/optional scenario policy. A skipped required
                        scenario must make the profile incomplete and return nonzero (or a distinct exit
                        code). Add an explicit `--allow-skips`/`--allow-incomplete` escape hatch for
                        exploratory runs, and report skipped scenario names separately from failed names.
Regression test to add: Run a required scenario with a missing executable and assert `ok` is false and the
                        CLI is nonzero by default; assert the opt-in incomplete mode is clearly labeled.

F05 - HIGH - CONFIRMED - Validation fail-open
------------------------------------------------------------------------------------------------------------
File: scripts/root_maintenance.py
Relevant code: git_changed_paths(), expand_changed_paths(), format-python/lint-python/test-python routing
Issue: When either Git changed-path command cannot run or exits nonzero, `git_changed_paths()` prints an
       error and returns an empty list. In `--changed` auto-detection mode, that empty list is then treated
       as 'no matching changed files', and format/lint/test commands return success.
Why this is an issue: Failure to discover the validation scope must not be indistinguishable from an empty
                      scope. The current behavior silently bypasses validation precisely when repository
                      state is broken.
Real task example: A CI checkout lacks `HEAD`, or Git returns an index error. `python
                   scripts/root_maintenance.py test-python --changed` prints a Git error followed by 'No
                   matching changed Python files to test.' and exits 0.
Highest-confidence fix: Make changed-path discovery return a success/error result or raise a dedicated
                        exception. Auto-detected `--changed` commands must exit nonzero when discovery
                        fails. Keep an empty list only for a successfully inspected repository with no
                        changed paths.
Regression test to add: Stub the first and second Git commands to fail independently; assert format, lint,
                        and test subcommands all exit nonzero and never print a successful no-match verdict.

F06 - HIGH - CONFIRMED - Cargo lane isolation bypass
------------------------------------------------------------------------------------------------------------
File: scripts/rust_build_status.py
Relevant code: _cargo_command_with_target_dir(), run_in_cargo_lane()
Issue: Cargo-watch commands supplied with `-s`/`--shell` are not rewritten. At the same time,
       `run_in_cargo_lane()` removes `CARGO_TARGET_DIR`, so a watched shell command such as `cargo check`
       falls back to the shared target directory instead of the reserved lane.
Why this is an issue: The process holds a lane reservation that does not protect the directory actually
                      receiving artifacts. Concurrent jobs can contend in the shared target while
                      diagnostics falsely imply lane isolation.
Real task example: One terminal runs `run-lane --lane core -- cargo watch -s "cargo check"` while another
                   runs a shared build. The watch child compiles into `codex-rs/target`, causing lock
                   contention and cross-job artifact churn despite the `core` lane lock.
Highest-confidence fix: Set the child environment's `CARGO_TARGET_DIR` to the reserved lane as the universal
                        fallback; an explicit Cargo `--target-dir` can still override it. Also recognize
                        cargo-watch `-s`, `--shell`, and assignment forms and inject/propagate the lane into
                        their nested command.
Regression test to add: Cover `-s`, `--shell`, and `--shell=...`; execute a fake nested Cargo command and
                        assert its effective target directory is the reserved lane.

F07 - HIGH - CONFIRMED - Cargo lane parser bypass
------------------------------------------------------------------------------------------------------------
File: scripts/rust_build_status.py
Relevant code: _cargo_command_with_target_dir()
Issue: The Cargo argument scanner assumes the first non-dash token after `cargo` is the subcommand. It does
       not understand `+toolchain` selectors or global options whose values are separate tokens. Commands
       such as `cargo +nightly check` and `cargo -Z unstable-options check` are left unchanged.
Why this is an issue: Because the wrapper also removes `CARGO_TARGET_DIR`, these valid Cargo forms compile
                      into the shared target and escape the reserved lane.
Real task example: A nightly-only validation is launched through `run-lane -- cargo +nightly test -p
                   codex-core`. The lane directory remains mostly idle while the actual test writes to the
                   shared target.
Highest-confidence fix: Implement a small Cargo-prefix parser that consumes an optional `+toolchain` and all
                        supported global options with their values before identifying the subcommand. Keep
                        the reserved `CARGO_TARGET_DIR` environment fallback so unknown future Cargo
                        prefixes remain isolated.
Regression test to add: Parameterize `+nightly`, `-Z value`, `--config value`, and assignment forms; assert
                        the effective target remains the reserved lane.

F08 - MEDIUM - CONFIRMED - Misreported destructive maintenance
------------------------------------------------------------------------------------------------------------
File: scripts/rust_build_status.py
Relevant code: prune_stale_lanes(), prune_stale_lanes_report()
Issue: After a lane is renamed to a `.trash-*` path, a recursive-delete failure is described as 'deferred
       cleanup', but the original lane is still appended to the `removed` list. The report then says it was
       `pruned` even though its disk usage remains.
Why this is an issue: Storage maintenance can claim success without reclaiming space. This makes disk-budget

Highest-confidence fix: Track `removed`, `deferred`, and `failed` outcomes separately. Append to `removed`
                        only after successful deletion; include the actual trash path and remaining size for
                        deferred cleanup. Add a bounded cleanup pass for old `.trash-*` directories.
Regression test to add: Force `remove_tree_allow_readonly()` to raise after a successful rename and assert
                        the report does not claim reclaimed/pruned status.

F12 - HIGH - CONFIRMED - Batch release output is not transactional
------------------------------------------------------------------------------------------------------------
File: scripts/stage_npm_packages.py
Relevant code: stage_package(), stage_packages(), main()
Issue: Each package writes its tarball directly to the final output directory. If a later package in the
       same invocation fails, tarballs from earlier packages remain and look like a complete release set.
Why this is an issue: The CLI accepts multiple packages as one staging operation. Partial final outputs can
                      be mistakenly uploaded or reused after the command reports failure.
Real task example: A batch stages `codex` successfully and then fails while staging a platform package.
                   `dist/npm/codex-npm-<version>.tgz` remains, and a later upload glob publishes it without
                   the matching platform artifacts.
Highest-confidence fix: Write every tarball into a per-run temporary output directory. After all package
                        workers and the final source/native freshness check succeed, atomically replace
                        final outputs as one commit with backups and rollback on commit failure. At minimum,
                        track and remove outputs created by a failed invocation.
Regression test to add: Make package A succeed and package B fail; assert no new final tarball remains and
                        pre-existing outputs are unchanged.

F13 - HIGH - CONFIRMED - Remote cache destruction
------------------------------------------------------------------------------------------------------------
File: scripts/start-codex-exec.sh
Relevant code: rsync_opts
Issue: `rsync` uses `--delete-excluded` while excluding `codex-rs/target/`, top-level `target/`,
       `node_modules/`, and multiple cache directories. On the receiver, excluded content is therefore
       deleted rather than merely left unsynchronized.
Why this is an issue: The remote workflow is designed to reuse a remote build, yet every sync can erase the
                      very Cargo and dependency caches needed for fast iteration.
Real task example: A remote machine has a warm 80 GB `codex-rs/target`. Starting the exec-server helper
                   syncs a small source edit and deletes the remote target tree, forcing a full rebuild.
Highest-confidence fix: Remove `--delete-excluded`. Keep `--delete-delay` for in-scope source paths, or
                        place persistent build caches outside the synchronized root and point Cargo to them
                        explicitly. Add a deliberate separate cache-clean option if destructive cleanup is
                        needed.
Regression test to add: Run rsync against a fixture receiver containing an excluded target sentinel; assert
                        source deletions propagate while the excluded sentinel survives.

F14 - HIGH - CONFIRMED - Brittle remote readiness protocol
------------------------------------------------------------------------------------------------------------
File: scripts/start-codex-exec.sh
Relevant code: remote exec-server process substitution and FIFO readiness read
Issue: The first combined stdout/stderr line from `codex exec-server` is written to the readiness FIFO, and
       that one line must start with `ws://`. Any warning or informational line emitted before the listen
       URL makes startup fail even if the server reports a valid URL immediately afterward.
Why this is an issue: Normal diagnostic output becomes a protocol-breaking event. This is especially fragile
                      across new Codex versions that add startup warnings.
Real task example: The remote binary prints a deprecation warning and then `ws://127.0.0.1:43123`. The
                   script reads the warning, declares an invalid listen URL, kills the healthy server, and
                   aborts.
Highest-confidence fix: Read lines until a syntactically valid WebSocket listen URL appears or the
                        timeout/process exit occurs; log all other lines. Prefer a dedicated ready-file/JSON
                        readiness channel if the server supports one.
Regression test to add: Use a fake server that prints a warning, blank line, then a valid URL; assert
                        startup succeeds and preserves the warning in the log.

F19 - HIGH - CONFIRMED - Build cache integrity bypass
------------------------------------------------------------------------------------------------------------
File: scripts/codex_package/cargo.py
Relevant code: source_output_matches_fingerprint()
Issue: The fast reuse path accepts a binary when path, size, and `mtime_ns` match the stamp and merely
       checks that the stored SHA-256 field is a string. It does not hash the current bytes.
Why this is an issue: A same-size mutation with restored timestamp is treated as the stamped binary even
                      though the stored digest no longer describes it. Package output can therefore contain
                      corrupted or replaced code.

                   `--reuse-source-builds` skips Cargo and packages the modified binary as if its SHA-256
                   still matched.
Highest-confidence fix: For correctness, hash every candidate output before reuse and compare it to the
                        stored digest. If performance requires a fast path, use an immutable
                        content-addressed output or a trustworthy file-identity/change-journal mechanism -
                        not mutable size/mtime metadata.
Regression test to add: Change binary bytes while preserving size and `mtime_ns`; assert reuse is rejected
                        and the binary is rebuilt.
