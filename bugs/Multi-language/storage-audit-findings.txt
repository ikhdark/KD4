MDPWA PRODUCTION-LIKE STORAGE SELECTION AUDIT
Date: 2026-08-07

Scope
-----
Actual runtime selection and write execution paths for PostgreSQL, Vercel Blob,
and local JSON/compatibility storage. This ledger contains only confirmed
inconsistencies.

Production-like compatibility configuration used below
------------------------------------------------------
When DATABASE_URL is absent and BLOB_READ_WRITE_TOKEN is present, the generic
store resolver selects Blob (src/lib/storage.ts:95-125). Community input and map
feedback select PostgreSQL only when DATABASE_URL is present; otherwise they use
that generic store (src/lib/communityInputStore.ts:874-877 and
src/lib/mapFeedbackStore.ts:1370-1374). This path is reachable in a runtime that
is classified as production-like; local file paths remain blocked there
(src/lib/storage.ts:103-125 and src/lib/deploymentEnvironmentShared.mjs:20-28).

FINDING 1: Idempotency is enforced by deployment owner, not by write contract
-----------------------------------------------------------------------------
Affected paths:
- POST /api/community-input
- POST /api/map-feedback
- POST /api/map-feedback/agency

Execution evidence:
- The resident routes reject a missing idempotency key only when
  isTransactionalStoreConfigured() is true (src/app/api/community-input/route.ts:
  184-199 and src/app/api/map-feedback/route.ts:297-313). The verified-agency
  route uses the same conditional requirement (src/app/api/map-feedback/agency/
  route.ts:80-104).
- Without a key, community input assigns crypto.randomUUID()
  (src/lib/communityInput.ts:207-208), and map feedback assigns a new UUID
  (src/lib/mapFeedback.ts:466-467 and 581-587).
- The compatibility adapters already implement request-id idempotency: community
  input returns the existing record for the same id/hash and throws on a
  different hash (src/lib/communityInputStore.ts:441-469); map feedback does the
  same (src/lib/mapFeedbackStore.ts:414-433).

Inconsistency:
The same API request without an idempotency key is rejected with HTTP 400 when
PostgreSQL owns the store, but is accepted when production-like Blob owns it.
Because each keyless retry receives a new UUID, Blob stores the retry as a new
submission/report rather than recognizing it as a replay. The adapter is capable
of the same idempotency semantics; the route boundary disables them solely based
on which durable owner was selected.

FINDING 2: Verified-agency Blob writes succeed without their audit event or outbox
-------------------------------------------------------------------------------
Affected path:
- POST /api/map-feedback/agency when DATABASE_URL is absent and Blob is present

Execution evidence:
- The route supplies an audit event to store.add(), then unconditionally attempts
  resident-notification dispatch, catches any dispatch failure, and returns 201
  (src/app/api/map-feedback/agency/route.ts:91-131).
- The Blob implementation's add/addWithResult signatures omit the mutation
  options and write only the report array, so the supplied audit object is
  discarded (src/lib/mapFeedbackStore.ts:681-698). Its status, review, and remove
  methods likewise omit the audit options (src/lib/mapFeedbackStore.ts:701-742).
- The PostgreSQL add statement atomically creates the map report, a queued outbox
  job, and the requested audit event (src/lib/mapFeedbackStore.ts:1031-1134).
- Dispatch lookup is PostgreSQL-only: it calls getPostgres() through
  getResidentNotificationOutboxId (src/lib/residentNotificationDispatcher.ts:
  45-55 and src/lib/residentNotificationRepository.ts:117-122). With no
  DATABASE_URL, getPostgres() throws (src/lib/postgres.ts:19-35).

Inconsistency:
On the Blob compatibility path, the verified report is durably accepted but the
caller-supplied audit event is silently dropped and no durable notification job
exists. The subsequent PostgreSQL-only dispatch failure is logged as "deferred
to the outbox" even though this path created no outbox row, and the API still
returns HTTP 201. The corresponding PostgreSQL write couples all three state
changes in one statement.

FINDING 3: Alert-signup compatibility tokens have different lifetime and replay semantics
----------------------------------------------------------------------------------------
Affected paths:
- POST /api/alert-signups and subsequent confirmation/preferences/unsubscribe
  links when DATABASE_URL is absent and Blob is present

Execution evidence:
- The POST route uses createPendingSubscriber only with PostgreSQL. Otherwise it
  stores the compatibility signup, emails signup.preferenceToken, and returns the
  same 201 response shape (src/app/api/alert-signups/route.ts:259-328).
- The compatibility token is stored on the signup
  (src/lib/alerts.ts:111-124 and 198-207). Confirmation locates it by direct
  equality, performs no expiry check, and treats a replay against an already
  confirmed signup as a successful unchanged result
  (src/lib/alertSignupStore.ts:239-283). Preferences access also authorizes by
  comparing the stored token directly (src/app/api/alert-signups/route.ts:
  126-137).
- PostgreSQL instead stores only a hash of a confirmation token with a 24-hour
  expiry (src/lib/subscriberRepository.ts:79-85 and 165-184). Exchange marks the
  token consumed and requires it to be unconsumed, unrevoked, and unexpired
  (src/lib/subscriberRepository.ts:292-311), then issues a 30-minute management
  session (src/lib/subscriberRepository.ts:296-300).

Inconsistency:
Selecting Blob silently changes the signup state machine from expiring,
single-use confirmation plus a short-lived management session to a reusable
stored bearer token with no enforced expiry. Confirmation replays and later
preference or unsubscribe operations therefore have materially different
authorization and transition semantics even though the public signup response
does not identify the compatibility mode.
