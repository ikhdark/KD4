First, make “turn completes correctly” a release gate. A publish should fail validation if a basic tool-using turn can enter `active_without_pending_tool`, retain `running_process` after the process is gone, or exceed a reasonable orchestration budget after the tool itself has completed. Otherwise you can keep shipping local fixes while the underlying lifecycle remains broken.

Second, bisect the behavior historically instead of only debugging HEAD. If you have a known publish where turns worked well, run the same small deterministic workload against each publish between that version and now. Measure:

-  tool process runtime
-  process-exit → handler-return
-  handler-return → result-delivery
-  result-delivery → next sampling
-  final turn completion
-  final lifecycle state

That could identify the exact publish where the pathological behavior first appeared. Even if performance degraded gradually, you’ll see which change caused each jump.

Third, I would resist adding more watchdogs until the ownership/state bug is understood. Five publishes of trouble can happen when each fix handles a symptom—timeout, stale process, missed completion, slow delivery—while the underlying transition contract is still wrong. A watchdog can make those turns eventually recover while hiding the race that caused them to get stuck.

The pattern you have now makes me especially suspicious of a lifecycle sequence resembling:

`tool accepted → process runs → process exits → completion recorded somewhere → ownership/state not fully released → relay waits for an event that already happened → timeout/watchdog eventually wakes it`

That would neatly explain why actual process time can be tiny while handler/gate time explodes, why dead processes still appear “running,” and why some turns become active with no pending tool.

I’d also add one regression test that repeatedly executes a tiny immediate command hundreds or thousands of times through the real production orchestration path, not a mocked executor. Every iteration should end with the exact same clean state. Intermittent lifecycle races often won’t show up in a handful of tests.

Given the five-publish history, I’d now make the project goal something closer to: **prove the turn state machine has one owner and one deterministic path from tool completion back to model sampling**. Parallel tool calls and performance optimization should come after that. If single-tool turns cannot reliably close, concurrency will make the underlying problem harder to reason about.

I reviewed the full 783-line test file. It is moving in the right direction, but it still does not lock down the failures we just found in the real rollouts.

One important discrepancy first: your uploaded test now expects an open unresolved tool to be named unresolved\_tool\_call and exposes unresolvedToolCallTurns. Current KD4 main still calls that state running\_process and reports runningProcessTurns. So if this test file is meant to run against current GitHub main, that specific test is intentionally ahead of the implementation and should fail until the auditor rename is committed.

The larger issue is coverage. Your relay fixture already contains parallelGateWaitMs, process timestamps, persistence timestamps, and model-resumption timestamps, which is good. But the tests currently exercise queue time, process-exit-after-delivery, basic phase totals, and outer code-mode child-work estimation. They don't reproduce the pathological profile we actually saw.

I would add these four regression tests before relying on this auditor for the next publish:

test\_reports\_exclusive\_gate\_convoy\_between\_parallel\_nested\_reads: two exec\_command records in the same generation, accepted at effectively the same time; first has parallelGateWaitMs=0, second has \~114,000ms. Assert the report identifies that serialization rather than merely calling both tools slow.
test\_reports\_post\_tool\_hook\_as\_owner\_of\_post\_process\_stall: make a process run \~45ms but give it postToolHookMs=99\_000. Assert the report surfaces PostToolUse as the dominant delay and does not attribute that 99s to process execution.
test\_terminal\_turn\_with\_unresolved\_tool\_call\_is\_inconsistent: emit task\_started, a model-visible wait function call with no matching output, then task\_complete. This is essentially the 6f7f ending. The auditor should report an invariant violation even though the turn has a terminal event.
test\_blocked\_task\_complete\_is\_not\_successful\_completion: use the real shape from 6f7f, where task\_complete.completion.status == "blocked". Current terminal classification mainly distinguishes aborts and payload.error; a blocked terminal shouldn't silently land in the same semantic bucket as a normally completed turn.

That third one is the most important missing test. Your current terminal/open-state test only covers a genuinely open turn containing an unresolved call and a separate empty leaked turn. It does not cover the nastier condition we observed: a terminal turn that still has an unmatched accepted tool call.

I would also extend \_timing() itself with:

"preToolHookMs": 0,
"postToolHookMs": 0,
"workspaceEvidenceBeforeMs": 0,
"workspaceEvidenceAfterMs": 0,
"authorizationStateCoordinationMs": 0,

Those are now diagnostically important enough that the canonical fixture should carry them. Otherwise future changes can accidentally stop reporting one of those phases without most tests noticing.

Your existing test\_separates\_reported\_child\_runtime\_from\_tool\_orchestration\_gap is still useful, but it tests the older coarse inference—three seconds of outer wall time versus one second of reported child work. Now that schema 22/23 has detailed relay timing, I would make the detailed toolCalls telemetry authoritative whenever available and treat the wall-time parsing as fallback evidence.

So I would keep this file, but add those four tests. The auditor is already good at saying “there is a large gap.” What it needs now is the ability to say “this gap is 99s of PostToolUse holding an exclusive gate, which caused another supposedly parallel call to queue for 114s.” That's the level of diagnosis your current KD4 problem needs.
