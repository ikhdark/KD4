[01] VAL-01 — Exact focused-validation reuse searches only the 64 most recent successful calls for the workspace. A matching, still-fresh proof older than that window is treated as absent.
--------------------------------------------------------------------------------------------------------------
Severity:   Medium
Confidence: High
Class:      Workflow / redundant validation
File(s):
  - codex-rs/agent-task-store/src/local.rs
Owner/path: LocalAgentTaskStore::record_validation_call

Issue
~~~~~
Exact focused-validation reuse searches only the 64 most recent successful calls for the workspace. A matching, still-fresh proof older than that window is treated as absent.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
The reuse identity is already computed, but the SQL query applies ORDER BY recorded_at DESC LIMIT 64 before matching the evidence key in Rust. Correctness of reuse therefore depends on unrelated validation volume rather than evidence freshness.

Real task example
~~~~~~~~~~~~~~~~~
A long-running KD4 workspace executes 80 different focused checks after `cargo test -p codex-core target_test`. The source and manifest for `target_test` are unchanged. Repeating the same requested proof scans the newest 64 records, misses the older exact match, and runs the test again.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Persist the exact reusable evidence key in indexed columns and query it directly. The query should filter by workspace, successful status, non-stale evidence, start epoch/manifest identity, command/provenance identity, and then select the newest exact match. If schema work is deferred, paginate until a match or an explicit age/row budget is reached; do not impose a correctness-affecting fixed 64-row prefix.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Insert more than 64 newer nonmatching successful calls, retain one older exact match, and assert that a new call shares from the older proof without executing.

[02] VAL-02 — An explicit user prohibition such as “do not run tests” fails open for common wrappers. `make`, `just`, and `task` are classified as Opaque; Node script forms such as `npm run test` are not recognized as tests. Opaque/nonvalidation commands bypass the prohibition gate and execute.
--------------------------------------------------------------------------------------------------------------
Severity:   High
Confidence: High
Class:      User-instruction safety defect
File(s):
  - codex-rs/core/src/validation_admission.rs
Owner/path: classify_argv_at_depth / prohibited_skip_for

Issue
~~~~~
An explicit user prohibition such as “do not run tests” fails open for common wrappers. `make`, `just`, and `task` are classified as Opaque; Node script forms such as `npm run test` are not recognized as tests. Opaque/nonvalidation commands bypass the prohibition gate and execute.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
The code uses the same narrow classifier for cost prediction and hard user-denial enforcement. Uncertainty is acceptable for prediction, but it is not safe for a direct prohibition. The current `prohibited_skip_for` returns a skip only when classification is already `Validation`.

Real task example
~~~~~~~~~~~~~~~~~
The user says “Do not run tests while editing.” The model calls `just test` or `npm run test`. The validation classifier does not identify the wrapped test, so the shell handler proceeds despite the explicit instruction.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Separate hard-deny detection from the cost classifier. Under an active test/check/lint prohibition, recursively expand known wrappers using repository recipe metadata where possible; recognize `npm|pnpm|yarn run <script>` and common test script names; and fail closed with a model-visible “wrapped command may run prohibited validation” response when a wrapper is opaque. An explicit later user grant can override it through the existing authorization rules.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Add deny-contract tests for `just test`, `make test`, `task test`, `npm run test`, `pnpm run test`, nested shell wrappers, and an opaque wrapper whose body cannot be resolved.

[03] VAL-03 — The in-flight validation key is constructed from the turn-local mutation revision before that revision is merged into the shared repository epoch. Two turns can therefore join the same validation flight even when one turn has already observed mutations that the other has not.
--------------------------------------------------------------------------------------------------------------
Severity:   High
Confidence: High
Class:      Concurrency / stale-proof regression
File(s):
  - codex-rs/core/src/tools/handlers/shell/shell_command.rs
  - codex-rs/core/src/validation_admission.rs
  - codex-rs/core/src/tools/command_execution.rs
Owner/path: ShellCommandHandler validation registration

Issue
~~~~~
The in-flight validation key is constructed from the turn-local mutation revision before that revision is merged into the shared repository epoch. Two turns can therefore join the same validation flight even when one turn has already observed mutations that the other has not.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
`validation_identity(... observed_mutation_revision)` is registered first; `observe_repository_revision(turn_id, observed_mutation_revision)` runs afterward. The deduplication boundary is consequently weaker than the repository-wide freshness boundary used for normal command attempts.

Real task example
~~~~~~~~~~~~~~~~~
Turn A starts `cargo test -p core foo` at local revision 0. Turn B edits a source file, advances its tracker to revision 1, and nearly simultaneously requests the same test. Depending on turn-local counters, B can attach to A’s pre-edit validation instead of executing against the changed repository.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Observe and obtain the globally monotonic repository epoch before registering validation singleflight, then include that epoch—or a frozen changed-input manifest hash—in `InFlightValidationKey`. The registration and epoch observation should be ordered under one repository coordination primitive so a mutation cannot slip between identity capture and admission.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Race two turn IDs around a mutation and assert that post-mutation validation never joins a pre-mutation flight, while identical requests at the same global epoch still coalesce.

[04] VAL-04 — Completion removes the flight from the registry before storing the result and notifying waiters. A third caller entering in that gap sees no flight and starts a duplicate validation.
--------------------------------------------------------------------------------------------------------------
Severity:   Medium
Confidence: High
Class:      Singleflight race
File(s):
  - codex-rs/core/src/validation_admission.rs
Owner/path: ValidationLeaderOwnership::complete

Issue
~~~~~
Completion removes the flight from the registry before storing the result and notifying waiters. A third caller entering in that gap sees no flight and starts a duplicate validation.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
The registry removal, result publication, and notification are three separately awaited operations. Singleflight guarantees require the completed value to remain joinable until publication is visible.

Real task example
~~~~~~~~~~~~~~~~~
A 25-second package check completes. Existing followers are waiting. Immediately after the leader removes the map entry but before it stores the result, another model call requests the same check and becomes a new leader, launching a second process.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Publish the result first, mark the flight terminal, notify waiters, and only then remove it conditionally from the registry. Better, keep a short-lived terminal entry or perform state transition and registry removal under one lock so a new registration can reuse the completed value.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Pause completion between each boundary with barriers and assert that every concurrent registration either joins the original flight or reuses its terminal result; none becomes a second leader.

[05] VAL-05 — One validation observation is written independently for repository-exact, repository-family, and global-family scopes. Each call performs its own UPSERT, cache invalidation, and pruning query.
--------------------------------------------------------------------------------------------------------------
Severity:   Medium
Confidence: High
Class:      Persistence integrity / SQLite overhead
File(s):
  - codex-rs/core/src/validation_admission.rs
  - codex-rs/state/src/validation_history.rs
Owner/path: ValidationObservationRecorder::record / ValidationHistoryStore::record

Issue
~~~~~
One validation observation is written independently for repository-exact, repository-family, and global-family scopes. Each call performs its own UPSERT, cache invalidation, and pruning query.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
The three observations describe one event but are not atomic. A crash or timeout after one or two writes leaves internally inconsistent prediction tiers. The repeated prune also adds avoidable SQLite contention to every completed validation.

Real task example
~~~~~~~~~~~~~~~~~
A test finishes in 42 seconds. The exact and repository-family UPSERTs commit, but the global-family write times out. Future prediction behavior changes depending on which tier is queried, even though all three should represent the same run.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Add a batch-record API that derives all scope keys, executes the UPSERTs in one explicit SQLite transaction, invalidates the affected cache keys after commit, and runs pruning once. Preserve fail-open behavior if the whole batch cannot be stored.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Inject a failure between UPSERTs and assert all-or-none persistence; assert one prune per observation and equivalent aggregates to three successful scalar calls.

[06] VAL-06 — Concurrent first-time key creation can make the losing process read the key immediately after `create_new` reports AlreadyExists, while the winner is still writing the 32 bytes. The loser then treats a short read as an invalid key and disables validation history for that runtime.
--------------------------------------------------------------------------------------------------------------
Severity:   Medium
Confidence: High
Class:      Startup race
File(s):
  - codex-rs/state/src/validation_history.rs
Owner/path: load_or_create_key

Issue
~~~~~
Concurrent first-time key creation can make the losing process read the key immediately after `create_new` reports AlreadyExists, while the winner is still writing the 32 bytes. The loser then treats a short read as an invalid key and disables validation history for that runtime.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
File creation publishes the directory entry before `write_all` and `sync_all` complete. `AlreadyExists` is not proof that the contents are complete.

Real task example
~~~~~~~~~~~~~~~~~
Desktop and VS Code start the same fork at once with a fresh CODEX_HOME. One creates `validation-history.key`; the other observes the file between open and write, reads zero or partial bytes, logs that history is unavailable, and loses prediction/reuse for the session.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Create a fully written, synced temporary key and atomically install it with a no-clobber operation. If another writer wins, retry reading the installed file until it has exactly 32 bytes or a bounded deadline expires. Sync the parent directory after installation.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Use barriers to hold the winning writer before `write_all`; start a second initializer and assert both return the same valid key rather than one failing with invalid length.

[08] VAL-08 — The code reports 0.95 confidence while using a fixed normal critical value (1.645) with estimated variance and as few as eight completed samples. That lower predictive bound is too optimistic at small sample sizes and can skip a borderline validation prematurely.
--------------------------------------------------------------------------------------------------------------
Severity:   Medium
Confidence: Medium
Class:      Statistical gating defect
File(s):
  - codex-rs/core/src/validation_admission.rs
Owner/path: prediction_from_aggregate

Issue
~~~~~
The code reports 0.95 confidence while using a fixed normal critical value (1.645) with estimated variance and as few as eight completed samples. That lower predictive bound is too optimistic at small sample sizes and can skip a borderline validation prematurely.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
With unknown variance, the one-sided predictive bound requires a Student-t critical value or another calibrated method. At n=8, 1.645 materially understates uncertainty. Censored-above samples also count toward `effective` without contributing duration variance.

Real task example
~~~~~~~~~~~~~~~~~
Eight package checks cluster near 31–34 seconds with one variable run. The z-based lower bound can remain over the 30-second threshold and automatically skip the ninth check even though a correctly calibrated small-sample bound would not.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Use a one-sided Student-t predictive interval based on completed samples, conservatively incorporate censoring, and calibrate the minimum sample count with replay/backtesting. Do not label the output 0.95 unless empirical coverage meets that level.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Add deterministic datasets where z and t decisions differ, and a simulation/backtest asserting the configured false-skip rate.

[09] TASK-01 — Restart recovery loads at most 256 persisted task bindings and has no pagination or completeness signal.
--------------------------------------------------------------------------------------------------------------
Severity:   High
Confidence: High
Class:      Restart recovery defect
File(s):
  - codex-rs/core/src/agent/task_coordinator.rs
Owner/path: AgentTaskCoordinator::initialize

Issue
~~~~~
Restart recovery loads at most 256 persisted task bindings and has no pagination or completeness signal.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
Bindings outside the first page remain durable in SQLite but absent from the in-memory `by_agent_path` and `by_assignment` indexes. Source-based lookups do not fall back to the store, so behavior depends on row ordering and workload size.

Real task example
~~~~~~~~~~~~~~~~~
A large CSV agent job or long session creates 300 active typed assignments. After Desktop restarts, 44 bindings are not loaded. Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Page through all active bindings during initialization, or load a bounded hot set and make every miss perform an indexed store lookup followed by cache insertion. Persist and expose a recovery-complete flag; never silently truncate.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Persist 300 active bindings, restart the coordinator, and verify source and assignment lookup succeeds for every one.

[11] TASK-03 — Task location is run in `spawn_blocking` without a cooperative cancellation token. Dropping or aborting the async join does not stop the blocking traversal/parser/cache work.
--------------------------------------------------------------------------------------------------------------
Severity:   Medium

Class:      Cancellation / wasted I/O
File(s):
  - codex-rs/file-search/src/task_locator.rs

Owner/path: spawn_blocking task-location path

Issue
~~~~~
Task location is run in `spawn_blocking` without a cooperative cancellation token. Dropping or aborting the async join does not stop the blocking traversal/parser/cache work.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
Tokio cannot forcibly cancel work already executing on the blocking pool. A user cancellation can return control while the expensive repository scan continues consuming disk and CPU and may still publish cache state.

Real task example
~~~~~~~~~~~~~~~~~
The model calls task location on a monorepo containing large generated trees, then the user cancels after one second. The turn ends, but the blocking scan continues for minutes and competes with the next task.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Pass a cancellation token into the locator and check it at directory, file-read, parse, render, and cache-publication boundaries. On cancellation, stop traversal and do not publish a partial cache entry. Await bounded worker quiescence before reporting cancellation.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Cancel during each phase of a deliberately slow scan and assert bounded exit time, no subsequent cache write, and no continuing filesystem reads.

[14] TASK-06 — Rollback of a partially committed agent spawn is delegated to a detached `tokio::spawn` from Drop. If no runtime is available, or the runtime is shutting down/aborts the task, the child and its typed-task binding can survive without being committed to the parent registry.
--------------------------------------------------------------------------------------------------------------
Severity:   High
Confidence: High
Class:      Orphaned-agent lifecycle defect
File(s):
  - codex-rs/core/src/agent/control/spawn.rs
Owner/path: PendingSpawnCleanup::drop

Issue
~~~~~
Rollback of a partially committed agent spawn is delegated to a detached `tokio::spawn` from Drop. If no runtime is available, or the runtime is shutting down/aborts the task, the child and its typed-task binding can survive without being committed to the parent registry.

Why this is a real issue
~~~~~~~~~~~~~~~~~~~~~~~~
Drop-based cleanup is the last correctness boundary after the child exists. Best-effort detached work is not a durable ownership transfer and gives the caller no proof that cleanup completed.

Real task example
~~~~~~~~~~~~~~~~~
The spawn future creates a child thread, then is cancelled before registry commit while Desktop is closing. The cleanup task never runs, leaving a live or persisted child that the parent does not know how to manage.

Highest-confidence fix
~~~~~~~~~~~~~~~~~~~~~~
Use an explicit awaited rollback on every error/cancellation branch. Back it with a runtime-owned cleanup supervisor or durable pending-spawn journal that survives task drop and startup-reconciles orphans. Drop should only enqueue into an always-owned supervisor and synchronously mark a tombstone if enqueueing fails.

Required regression proof
~~~~~~~~~~~~~~~~~~~~~~~~~
Cancel at every post-child/pre-commit boundary, including runtime shutdown, and assert no live child, binding, subscription, or capacity slot remains.
