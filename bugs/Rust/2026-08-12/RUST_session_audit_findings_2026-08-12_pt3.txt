## Top 10 inefficiencies and gating opportunities

1. **Gate on result utilization, not merely assignment creation.**
   Only 4 of 36 assignments supplied unique material value; 28 were unused. Require each result to be referenced by a decision, edit, test, or review before spawning another lane.

2. **Require a clean independent decomposition before fan-out.**
   Streaming used nine child threads but obtained one child-only path and no consumed result. Focused tasks should follow KD4’s existing one-turn/light-workflow policy.

3. **Check thread capacity before dispatch.**
   Across all streams, 59 spawn calls mapped to only 31 retained bound threads. Latency alone used 14 spawn calls for five threads. Fail admission synchronously instead of producing assignments that immediately need retry or abandonment.

4. **Add an early liveness deadline.**
   Multiple agents remained nonproductive for roughly 7–22 minutes before abandonment. Require a first evidence/progress checkpoint; recover or serialize when it is missed.

5. **Make waits critical-path only.**
   Root agents spent 34.9 minutes in explicit waits. Streaming accumulated 15.7 minutes across all streams; mutation guard spent six minutes waiting on a task the root ultimately completed itself. Root should continue disjoint work and wait only when its next decision depends on the result.

6. **Make receipt requirements capability-aware.**
   Token and SKILL read-only audits completed substantive investigation but remained `needs_main` because their role could not provide the required validation-class evidence. Read-only assignments need a receipt schema they can actually satisfy.

7. **Bound completion dossiers before sealing.**
   Streaming architect retries failed because completion material exceeded private bounds. Enforce concise evidence manifests, bounded excerpts, and incremental receipts before the final sealing call.

8. **Reject high-overlap investigation assignments.**
   Main agents reread 58% of distinct child source paths. In six tasks, at least 75% of child paths overlapped the main. Assign children to explicit unknowns or disjoint owner surfaces.

9. **Use the architect lane only when the downstream lane is ready.**
   Terminal, lease, and streaming work stalled at architect or receipt gates without a ready coder/validation path. Before spawning an architect, verify that its contract can be copied, the worker can acquire capacity, and the required validator is admissible.

10. **Reserve integration and validation capacity before parallel implementation.**
    The latency task received seven useful agent-written files but then required substantial root reconciliation, validation retries, and gate cleanup. Multi-writer dispatch should require a named integration owner, available validation lane, and bounded post-agent review budget.

## Where multi-agent helps

Multi-agent clearly provides engineering value when work has independent ownership and independently checkable outputs:

- separate implementation surfaces such as startup prewarm versus typed output projection;
- read-only mapping of disjoint runtime domains;
- adversarial review after a concrete implementation exists;
- validation that can run independently without sharing a contested Cargo or mutation lane.

The latency task is the cohort’s positive example. Agents broadened contract coverage and produced real implementation work the main agent would otherwise have had to perform serially. It still lacked the validation needed to demonstrate an improved final outcome.

## Where one agent was likely sufficient

The historical evidence favors one agent for:

- focused mutation-guard fixes;
- mutation-lease deadlock fixes after the owner was known;
- SKILL.md debloat/reinstall work;
- terminal lifecycle fixes once the owner path was mapped;
- review-ledger work without independent implementation surfaces.

Resource and token audits were broad enough to justify delegation in principle, but their actual assignments overlapped the main investigation too heavily to pay off.

## Early spawning and blocking waits

Spawning happened too early in:

- streaming behavior;
- long-tail latency;
- KDSB architecture;
- review-file fixes;
- terminal finalization.

The main agent had not yet stabilized owner boundaries, evidence questions, or downstream validation readiness.

Waiting most clearly blocked direct progress in:

- streaming: 940 seconds across agent streams;
- orchestration latency: 488 seconds;
- mutation guard: 359 seconds;
- long-tail latency: 264 seconds;
- terminal finalization: 172 seconds.

## Recommended operating rule

Keep multi-agent capability, but admit a child only when all five conditions hold:

1. The workstream is independent and bounded.
2. Its expected evidence is materially different from the root’s current scope.
3. Capacity and role capabilities are available.
4. A compatible receipt and validation path exist.
5. The root has useful disjoint work or truly requires the result before proceeding.

This would retain the correctness gains seen in the latency task while eliminating most of the abandoned streams, duplicated reads, retries, and blocking waits observed here.

Limitations: this is an observational cohort, not an A/B test; timing sums overlap because agents ran concurrently; exact prompt tokens and monetary cost were unavailable; and tracked-read overlap omits unregistered shell-level reads. No repository files were changed, no agents were started, and KD4 was not rebuilt.

### Why they exist and the smallest safe change

1. **Source discovery:** Reading and searching were frequently serialized into overlapping or adjacent spans. Initial file selection was decision-critical; most redundant paging was not. Batch independent reads in one execution, track covered byte/line intervals, and preserve that coverage across compaction.

2. **Wait-only continuation:** The model repeatedly emitted a predetermined wait call for running jobs. The eventual result is critical; choosing to wait again generally is not. Let the host await the known cell until completion or state change, then resume the model once.

3. **Tool continuation:** Mostly `read_tool_output` pagination. The next page request was normally known before invoking the model. Automatically drain bounded output pages and present one combined result.

4. **Agent coordination:** Spawn, instruction, and receipt decisions were useful; unchanged status/list/wait polling was not. Use event-driven completion notifications and wake the coordinator only when agent state changes.

5. **Compaction recovery:** Re-establishing state after compaction is necessary, but some reads and status checks repeated known state. Inject a structured checkpoint containing covered sources, pending jobs, current plan, and last validation result.

6. **Validation interpretation:** Most interpretations selected a meaningful next action. A few merely launched a predeclared next gate after success. Launch independent validations together and return one structured combined result.

7. **Edit planning:** The plan itself can be critical; generations whose sole action updated the plan tracker are not. Commit the tracker update in the same generation as the first planned tool action.

8. **Initial reasoning:** Almost entirely decision-critical. The one avoidable case immediately emitted a known wait. Route an existing wait/status state through the host without starting a fresh reasoning generation.

9. **Repair:** No entire repair generation was conservatively removable. Repairs changed code or task state; leave them model-mediated.

10. **Other:** No repeatable zero-value signature was established. Do not optimize this bucket without subdividing it first.
