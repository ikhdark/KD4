# KD4 Source-Discovery Token Waste Audit

The dominant waste is not the size of filenames or even the returned source text. It is the repeated model continuation after each small search or read.

Across telemetry-covered turns, discovery results were allocated:

- 350.35M input tokens, including 339.19M cached input.
- 1.063M output tokens, of which 380.3K were reasoning tokens.
- 301.64M input tokens specifically between one discovery operation and the next.
- 5,939 metered discovery-to-discovery continuations; 9,764 observed across the full readable archive.

Removing whole continuations is therefore much more valuable than shortening individual results.

## Scope and method

Audited read-only:

- 115 readable active and archived rollout JSONLs, 156.3 MB.
- Activity from July 28 through August 12, 2026.
- 211 distinct historical task/turn IDs.
- 81 rollouts contained token telemetry; source/result repetition was measurable in all 115.
- Two corrupt backup rollouts were excluded.

Captured token totals:

| Token category | Tokens |
|---|---:|
| Input | 525,751,324 |
| Cached input | 508,606,592 |
| Uncached input | 17,144,732 |
| Output | 1,694,265 |
| Reasoning output, included in output | 606,594 |
| Total | 527,445,589 |

Cached input was 96.7% of input. Caching reduces billing/computation impact, but the context still repeatedly passed through model generations.

Direct tool-result sizes were estimated using KD4’s own `approx_token_count` logic from `codex-rs/utils/string/src/truncate.rs`. Per-generation costs were attributed by dividing each turn’s exact cumulative telemetry among its result-fed continuations plus its initial generation. Thus aggregate telemetry is exact, while per-tool attribution is an estimate.

The public documentation was used only to confirm the standard input/cached-input/output accounting taxonomy; local JSONLs supplied the actual measurements. [OpenAI model documentation](https://developers.openai.com/api/docs/models/codex-mini-latest)

## Necessary discovery versus repetition

Necessary architecture work included:

- The first locator for a task.
- The first applicable `AGENTS.md`, `SOURCEMAP.md`, `do-not-code.md`, or skill instruction read.
- First reads of the owning implementation, important callers, focused tests, and affected contracts.
- Adaptive follow-up where a result genuinely changed the next question.

The strongest definite repetition signals were:

- 232 exact same-span rereads within a task and without an intervening patch epoch.
- 270 exact repeated source queries.
- 339 repeated ownership/instruction paths after owner resolution.
- Six literal-equivalent locator repeats.
- 103 metered recovery→recovery transitions, consuming 5.13M input.
- 366 recovery outputs that truncated again.

The 4,988 overlapping reads are only an upper bound: adjacent function context, deliberate verification, and reads following source changes may be legitimate. Cross-task repeats were also excluded from the waste ranking because separate tasks cannot necessarily share model context safely.

## Bottom line

The best target is the 9,764 observed discovery-to-discovery continuations. In the telemetry-covered subset alone, 5,939 such transitions account for an estimated 301.64M input tokens and 898.1K output tokens, including 322.0K reasoning tokens.

The most effective design change would be a reusable “owner plus scoped evidence bundle” containing:

1. Owner and governing instructions.
2. Relevant implementation spans.
3. Callers and dependents.
4. Focused tests.
5. Contract/generated-output implications.

That, combined with per-repository query/span caching and cursor-based truncation recovery, removes entire tool/model cycles rather than merely making each cycle marginally shorter.
