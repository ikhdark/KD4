I found four concrete identity problems. Two cause severe miss/churn behavior, one creates cross-provider false hits, and one unnecessarily fragments a small serialization cache.

| Mechanism | Insertion identity | Lookup identity | Problem |
|---|---|---|---|
| Known Delta immutable Git reads | Project + cwd position + requested commit SHA/path + resolved blob | Reconstructs the same full fingerprint | Requested commit SHA and cwd are redundant once the blob is resolved, so identical content gets new entries |
| Task locator syntax cache | File path under canonical-root cache, plus stored repository identity containing Git HEAD | Rejects the entire cache if current HEAD-derived identity differs | Commit/checkout invalidates every independently fingerprinted file |
| Models disk cache | One `models_cache.json` containing version, TTL, ETag, models | Same file; checks only version and TTL | Provider identity is never persisted or checked |
| Request-schema serialization | Tools/schema/verbosity plus `use_responses_lite` | Same composite key | Lite mode does not affect the cached value, so it needlessly splits entries |

### 1. Known Delta requires repeated identical commit-specific commands

This is the clearest “stores plenty, almost never hits” mechanism.

The identity builder accepts only a 40/64-character resolved object, resolves the requested `SHA:path` to a blob, but hashes both the original commit-specific request and the resolved blob. It also hashes the caller’s repository-relative cwd. [known_delta_store.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/known_delta_store.rs:159) [known_delta_store.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/known_delta_store.rs:189) [known_delta_store.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/known_delta_store.rs:530)

Conceptually:

```text
insert/lookup fingerprint =
    project
  + cwd_position
  + requested "<commit-sha>:<path>"
  + resolved_blob_sha
```

For `git show SHA:path`, the output is determined by the resolved blob. Therefore:

- A new commit SHA pointing to the same unchanged blob creates a different cache entry.
- Running from another subdirectory creates another entry, despite identical output.
- A newly stored entry starts with `reusable = false`.
- It needs a second identical execution for shadow validation and only a third identical request can actually hit. [known_delta_store.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/known_delta_store.rs:247) [known_delta_store.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/known_delta_store.rs:270) [known_delta_store.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/known_delta_store.rs:282)

The active fork cache corroborates the effect: 86 stored evidence records, 83 never shadow-validated, and only 2 marked reusable. That runtime snapshot is corroborating evidence rather than proof of which source revision created every record.

The unnecessarily changing components are `requested` and `cwd_position`; `project_namespace + resolved_blob` already identifies the immutable output.

### 2. Task locator conflates repository snapshot identity with parse-cache eligibility

The cache filename is stable per canonical repository root. Each cached file already stores its own content fingerprint and parser version, and lookup checks both before reusing its syntax IR. [task_locator.rs](C:/Users/kuh/Desktop/kd4/codex-rs/file-search/src/task_locator.rs:1007)

But the cache layer also stores:

```text
repository_identity =
    SHA256(canonical_root + .git/HEAD + referenced branch contents)
```

On load, any repository-identity mismatch returns an entirely empty cache. [task_locator.rs](C:/Users/kuh/Desktop/kd4/codex-rs/file-search/src/task_locator.rs:2919) [task_locator.rs](C:/Users/kuh/Desktop/kd4/codex-rs/file-search/src/task_locator.rs:2979)

Thus every commit, branch checkout, or ref movement discards all entries—even files whose content fingerprints and parser versions are unchanged. In this checkout, the current task-locator artifact contains 182 cached files and is about 15.4 MB, so the invalidation is material.

Git HEAD is valid as an output snapshot identity, but unnecessarily volatile as a gate for loading independently content-addressed parse entries. Those two identities should be separated.

### 3. Models cache omits provider identity entirely

All providers use the same `$CODEX_HOME/models_cache.json`. Network results are persisted with:

```text
fetched_at + etag + client_version + models
```

The provider or endpoint identity used to fetch them is not stored. [manager.rs](C:/Users/kuh/Desktop/kd4/codex-rs/models-manager/src/manager.rs:250) [cache.rs](C:/Users/kuh/Desktop/kd4/codex-rs/models-manager/src/cache.rs:77)

Lookup checks only client version and TTL before applying the cached models and ETag to the current endpoint client. [cache.rs](C:/Users/kuh/Desktop/kd4/codex-rs/models-manager/src/cache.rs:31) [manager.rs](C:/Users/kuh/Desktop/kd4/codex-rs/models-manager/src/manager.rs:560)

There is already an explicit TODO acknowledging this omission. The result is a false hit rather than a miss: switching providers can reuse another provider’s fresh model catalog and ETag. The active `LOCAL-KD/models_cache.json` likewise contains only `fetched_at`, `etag`, `client_version`, and `models`.

### 4. Request-schema cache includes a field that cannot affect its value

The cache key hashes tools, output schema, strictness, verbosity, and `use_responses_lite`. [client.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1759)

The cached value, however, is constructed solely from:

```text
serialize(prompt.tools)
create_text(verbosity, output_schema, strictness)
```

`use_responses_lite` is not consumed. It only changes where the already-serialized tools are placed later in the request. [client.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1778) [client.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1888)

Consequently, changing between otherwise equivalent Lite and regular model modes creates duplicate entries and extra misses in an eight-entry cache. This is lower impact than the first two but is a clean over-keying defect.

I found no comparable insertion/lookup mismatch in the Git workspace manifest cache, Codex Apps cache, connector directory cache, route-aware HTTP pool, image cache, or orchestrator skill-resource cache. I made no source changes and ran no build because this was a read-only identity audit.
