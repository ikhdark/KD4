# 8/15 vs 8/16 binary audit

## Verdict

The 8/16 binary is substantially better at source-discovery throughput and initial responsiveness, but it has four important non-terminal regressions:

1. Prompt-cache effectiveness collapsed.
2. Typical model-request latency increased.
3. Tool-output truncation/projection became much more frequent.
4. Context compaction happens more often relative to requests and input tokens.

The strongest controlled evidence is an exact same-prompt comparison: the 8/16 binary used about half the requests, tools, and tokens, while reducing tool time by 98.6% and elapsed time by 61.5%. Both matched turns were interrupted, so this measures work performed before interruption, not completed-result quality.

I excluded the 8/16 terminal-state bug from regression scoring: 13 interrupted turns and three partial/error terminalizations were not counted as evidence of reduced quality or completion reliability.

## Top 10 improvements to apply

1. **Restore prompt-cache reuse.** Investigate byte-level prefix stability, cache keys, request serialization, and stable-fragment ordering. Reducing 17,462 uncached tokens/request toward the old 4,085 level is the largest cost opportunity.

2. **Reduce tool-output projection loss.** Preserve summaries, matched lines, source identities, errors, and continuation locators before dropping bulk content. A 33.7% canonical-to-visible loss is too high.

3. **Improve typical model-request TTFT.** Median TTFT regressed 53%. Instrument request construction, queueing, connection reuse, and transport timing separately so the new source-discovery gains are not consumed by slower inference starts.

4. **Retune compaction thresholds and reuse.** Compactions are 60% more frequent per request and 78% more frequent per input token. Reuse stable compacted checkpoints and avoid compacting again when only tool evidence changed.

5. **Make the dynamic tool manifest mechanically safe.** Validate generated calls against the active manifest and provide stable aliases for batch reads, Repo Atlas, skills, and process control. This should eliminate the observed namespace `TypeError`s and invalid locator.

6. **Add existence/routing preflight for source reads.** Resolve candidate paths through `rg --files`, Repo Atlas, or the source map before batch reads; cache negative path results so the same missing file is not retried.

7. **Add bounded audit convergence.** The new corpus still averaged approximately 25 requests and 68 tools per timed turn. Stop when the requested finding count has sufficient producer-to-consumer evidence instead of continuing broad searches.

8. **Standardize the fast read-only discovery lane.** The matched task’s 98.6% tool-time reduction is the strongest success. Make batched search, targeted source reads, and indexed architecture lookup the default across comparable repository-analysis tasks.

9. **Complete the v13 telemetry contract.** One terminal event lacked duration/timing, two lacked first-agent timing, and 34/401 requests lacked token usage. Record explicit “unavailable because interrupted” states rather than absent fields.

10. **Create a matched binary canary suite containing coding tasks.** Run identical prompts for source discovery, small edits, multi-file changes, compiler-error repair, focused tests, and validation. Track patch churn, clean compile rate, exact test selection, user-visible result quality, and wall-clock completion. The current 8/16 corpus cannot answer whether coding regressed.

Overall: the 8/16 binary is a meaningful throughput improvement, especially in repository discovery and redundant-loop suppression. Cache efficiency, request latency, projection loss, and compaction frequency are the main areas preventing it from converting those gains into consistently cheaper and faster completed work.

## Top 10 improvements to apply

1. **Restore stable prefix/cache reuse.** Canonicalize prompt ordering, isolate volatile manifests and telemetry after the cacheable prefix, and reuse unchanged instruction/tool/history digests. This addresses the 3.4× uncached-token regression.

2. **Activate the non-progress governor.** Reconcile `decision_bearing` classification with observational progress, enable deterministic continuation or early convergence, and trigger loop controls when non-progress exceeds a bounded threshold.

3. **Reduce compaction churn.** Preserve cacheable prefixes through compaction, use incremental summaries, and compact only when projected context pressure justifies it. Initial-turn compactions/request rose 31%.

4. **Fix tool-output projection recovery loops.** Improve semantic section selection and targeted range retrieval. A one-third model-token saving is good, but four truncations per turn and roughly one recovery/reread per three artifacts is too expensive.

5. **Make architecture slices complete and reusable.** Cache slices across parallel sessions, surface exactly which relationships are missing, and do not count an attempt without binding tool results into the completion contract. Current result: 13 attempts, zero completions.

6. **Cache and narrow Repo Atlas queries.** Reuse identical repository/index results between concurrent audits, validate index freshness once, and split broad `task` calls into cheaper owner-specific queries. Ten task calls consumed 173 seconds.

7. **Add path-aware native source discovery.** Have batch reads validate or resolve moved paths from the index before execution, return structured alternatives, and avoid process launches for simple repository reads.

8. **Recover request first-output latency.** Keep the improved executor readiness and completion tail, but profile transport readiness, request transformation, and server queueing responsible for the 27% dispatch-to-first-output regression.

9. **Replace fragile raw-JavaScript orchestration paths with typed helpers.** Preflight tool arguments, paths, skill locators, and command policies. New orchestration failure density doubled despite fewer overall failures.
