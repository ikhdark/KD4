## Recommended design

Add two related checks:

1. `production-unreachable-telemetry`

   Reports a telemetry recording site whose enclosing function has no reverse call path to a production root.

2. `incomplete-optimization-activation`

   Reports an optimization state that exists and may even be recorded, but is never produced, propagated, consumed, or dispatched on a production path.

The analysis should construct this chain:

```text
production root
  → activation/dispatcher
  → optimizer or cache operation
  → receipt/disposition/state
  → state consumer
  → telemetry recording point
```

A missing edge anywhere in that chain becomes the diagnostic.

### What to trace

| Evidence | Forward/backward trace |
|---|---|
| Counter | `inc`, `fetch_add`, metric macro, or configured recorder → enclosing callable → production callers |
| Disposition | Enum construction → return/assignment → match arm → telemetry recorder |
| Receipt | Producer return value → bindings and fields → consumer/dispatcher |
| Cache hit | `Some`, `Occupied`, `Hit`, successful lookup branch → hit/reuse result |
| Reuse | Reused artifact/value construction → selected fast-path return |
| Owner drain | `drain`, `take`, `finish`, owner-drop state → production owner lifecycle |
| Suppression | Suppression predicate → suppressed disposition → counter or receipt |
| Fast path | Guard condition → fast branch → early return and associated telemetry |

This requires a bounded interprocedural backward slice, not merely identifier-name matching.

## Foundations KDA needs

First, extract `CallGraph` into a shared semantic module and enrich each callable with:

- Cargo target kind;
- `cfg(test)` ancestry;
- feature and target profile;
- visibility and export status;
- entry-point classification;
- closure ownership;
- callback/function-pointer registrations;
- trait implementation edges where resolution is possible.

Production roots should include binary `main`, exported ABI functions, proc-macro entry points, and configured service/worker roots. Public library functions should be treated as “externally reachable but unproven,” unless the project supplies explicit roots.

A proposed configuration could look like:

```toml
[[activation-check]]
id = "query-cache-reuse"
roots = ["server::serve", "worker::run"]
activators = ["query_cache::lookup", "optimizer::try_reuse"]
recorders = ["telemetry::record_cache_disposition"]
states = ["hit", "reuse", "owner-drain", "suppressed", "fast-path"]
exclude-targets = ["test", "bench", "example", "build-script"]
severity = "deny"
```

Recorder configuration should support canonical function selectors, method selectors, and macro-plus-key extraction. That matters because a generic `counter!` macro alone does not identify which optimization it describes.

- `no-production-caller`
- `test-only-callers`
- `unregistered-callback`
- `state-never-constructed`

### New lint design

Add `unenforced-work-decision`, initially limited to high-confidence intraprocedural cases:

```rust
let hit = cache.contains(key);
if hit {
    tracing::debug!("cached");
}
model.generate(key).await; // diagnostic: cache decision does not bypass generation
```

It should recognize:

- Cache hit followed by unconditional recomputation.
- `validated`, `complete`, `blocked`, `stale`, or `already_exists` states that only affect logging or metrics.
- Convergence/change flags that do not dominate `break`, `return`, or `continue`.
- Retry loops that repeat the same resolved call with unchanged inputs after a terminal result.
- Equivalent validation/tool calls with no relevant mutation between them.

The essential proof is:

> A terminal decision is known, but the expensive effect remains reachable under both outcomes with the same receiver and inputs.

KDA’s current flow helper deliberately supports only nearby guards, not a complete CFG: [flow.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/flow.rs:1). This lint therefore needs:

- Basic-block CFG construction.
- Definition/use tracking for decision values.
- Dominance and post-dominance.
- A conservative mutation barrier.
- Normalized call identity using resolved callee, receiver, and equivalent arguments.
- Loop-carried progress detection for retries and fixed points.

Because names such as “cached” or “blocked” are application-specific, add configurable contracts alongside built-in heuristics:

```toml
[[work-contract]]
id = "cached-generation-must-bypass"
decision = "project::Cache::get"
terminal-outcomes = ["Some", "Hit"]
effects = ["project::Model::generate"]
same-key-args = [0]
severity = "deny"
```

Diagnostics should include `decision_kind`, decision and effect ranges, canonical effect callee, matched key arguments, and whether the effect post-dominates the decision.

My recommended order is:

1. Add a centralized, validated `ExecutionPlan` and pass-level `allow` short-circuiting.
2. Wire `unmatched-config-selector` and real implementation-registration validation.
3. Add the intraprocedural `unenforced-work-decision` MVP.
4. Extend it to retry loops and interprocedural wrapper functions.

That gives KDA immediate self-improvement while creating the machinery needed to detect the same waste in analyzed projects.

## Conclusion

The highest-value direction is a new class of analysis: **cross-function, identity-correlated protocol checking**.

KD4 is effectively a set of durable distributed systems inside one Rust process. Your analyzer already covers an unusually broad surface, including cancellation, task ownership, lifecycle balance, durability ordering, retry behavior, authority, event pairing, field flow, and identity freshness ([built-in registry](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/config.rs:57>)). - Lifecycle protocols are local to a lexical scope ([lifecycle_protocol.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/lifecycle_protocol.rs:1>)).
- Event balance only needs a later local terminal event ([event_lifecycle.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/event_lifecycle.rs:1>)).

## Ranked proposals

### 1. Turn-terminal linearizability and replay safety

Model terminalization as one correlated transaction keyed by `turn_id` and terminal fingerprint:

```text
open
  → optionally interrupt-fenced
  → claimed
  → exact authority established
  → active turn detached
  → delivery attempted
  → delivered/retried
  → acknowledged
  → interaction released and cleanup complete
```

The analysis should prove:

- At most one exact terminal outcome becomes authoritative.
- A conflicting outcome cannot replace it during failure recovery.
- An interrupt cannot admit terminal completion until interrupted output is durable.
- No new sampling is admitted after the interrupt fence.
- Detachment happens before the terminal becomes externally observable.
- Redelivery always reuses the exact authoritative event and fingerprint.
- Acknowledgment, cleanup, receipts, and app-server state reduction refer to the same turn and fingerprint.
- Failed or indeterminate delivery does not prematurely release the interaction fence.

KD4 evidence:

- `TurnTerminalCoordinator` maintains separate claim, durability, delivery, interaction, cleanup, interrupt, and sampling-admission state ([turn.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/state/turn.rs:100>)).
- Interrupt readiness is generation-checked and sampling is fenced ([turn.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/state/turn.rs:269>)).
- Conflicting terminal candidates preserve the first authoritative event ([tasks/mod.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1399>)).
- If foreground persistence times out, KD4 preserves the exact candidate and schedules recovery rather than synthesizing a replacement ([tasks/mod.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1497>)).
- The old turn must be detached before terminal delivery, or the next user turn can be mistaken for steering and dropped ([tasks/mod.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1526>)).
- App-server independently deduplicates, rejects conflicts and stale terminals, projects notifications, and acknowledges by fingerprint ([thread_state.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/thread_state.rs:306>)).
- Restart reconstructs state reduction from rollout but intentionally requires exact-event replay for notification delivery ([thread_state.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/thread_state.rs:372>)).

Why this matters: a local “every path emits complete or abort” check cannot detect double terminal events, mismatched recovery events, early turn release, or state applied once but notification lost. These are among the most damaging agent-runtime failures because they can lose user input, duplicate completion, or leave a session permanently fenced.

### 2. Tool-call conservation across model, runtime, persistence, and lifecycle

For every composite tool identity—at minimum `(turn_id, call_id, source)`, including code-mode carrier IDs—prove a conservation law:

- One model call item is persisted before execution begins.
- Exactly one matching output eventually exists, including cancellation and malformed calls.
- Output is durable before an interrupted turn is terminalized.
- Output is incorporated before the next model sample.
- Exactly one lifecycle terminal outcome is issued.
- No output is orphaned, duplicated, or attached to a different call generation.
- Synthetic cancellation outputs have stable identities across replay/resume.

KD4 evidence:

- Model-emitted calls are persisted immediately before being queued for execution ([stream_events_utils.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/stream_events_utils.rs:377>)).
- Context normalization synthesizes deterministic aborted outputs for missing call results ([normalize.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/context_manager/normalize.rs:18>)) and removes orphan outputs ([normalize.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/context_manager/normalize.rs:146>)).
- Tool completion uses an atomic claimant so cancellation, hooks, and normal completion cannot all emit terminal lifecycle outcomes ([registry.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/registry.rs:1230>)).
- Lifecycle start and finish carry the same turn, call, tool, and source identity ([lifecycle.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/lifecycle.rs:20>)).
- Interrupted tool output crosses a durability barrier before terminal readiness ([session/turn.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/turn.rs:3982>)).

Why this matters: tool execution is the primary model/runtime handoff. Missing or duplicated results corrupt future prompts, while mismatched lifecycle notifications confuse extensions, telemetry, and app-server state. Existing event-balance and field-flow checks do not establish a bijection over the same correlated identity.

### 3. Attempt-scoped approval and sandbox authority binding

Treat an approval as authority over a specific effective attempt, not as a Boolean attached to a call.

The approval receipt should be bound to a tuple such as:

```text
turn + call + attempt
+ normalized command/tool payload
+ cwd/environment
+ filesystem policy
+ network policy
+ sandbox mode
+ requested permissions
```

Flag execution when any authority-bearing part changes without an approval that dominates that exact attempt. Retrying with broader privileges must invalidate narrower approval; retrying unchanged work may reuse authority only where policy explicitly permits it.

KD4 evidence:

- Approval is obtained before selecting and running the first attempt ([orchestrator.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/orchestrator.rs:162>)).
- An unsandboxed retry has materially different authority semantics; strict auto-review therefore requires fresh review and a distinct `:retry` request identity ([orchestrator.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/orchestrator.rs:399>)).
- Returned permissions are intersected with the requested profile, and strict auto-review cannot become session-scoped ([session/mod.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:3072>)).

Why this matters: the existing `retry-context-drift` compares security-looking arguments between repeated calls ([security_contracts.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/security_contracts.rs:404>)). KD4 needs a stronger and more nuanced property: some retry changes are valid only because they trigger new authorization. Merely requiring unchanged arguments would both miss approval reuse and reject intentional escalation protocols.

### 4. Delayed-completion ownership and ABA protection

Detect asynchronous completions that mutate shared state using a reusable or insufficient identity.

For every spawned future, watcher, callback, or background recovery task that later updates a registry, require one of:

- A generation/execution ID checked against the current owner.
- An unforgeable reservation or permit.
- Exact object identity comparison.
- A ledger transition that rejects stale ownership.

The check must follow the identity across function boundaries, not merely notice a local ID used after an `await`.

KD4 evidence:

- Tool relay completion is rejected when its execution ID no longer matches the timing owner ([session/turn.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/turn.rs:3960>)).
- Process completion carries `process_id`, `command_execution_id`, and parent tool execution identity ([async_watcher.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/async_watcher.rs:229>)).
- Process removal compares the exact `Arc` owner before touching a reused numeric ID ([process_manager.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/process_manager.rs:1425>)).
- Cached WebSocket publication is protected by an epoch permit ([client.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1213>)).

Why this matters: long-running agents constantly outlive the operation that spawned a task. A stale completion can otherwise finish a newer command, overwrite a newer cache, acknowledge the wrong terminal event, or remove an ID that has already been reused. `stale-observation-after-await` is useful but does not prove ownership of a remote registry entry.

### 5. Turn-boundary routing and late-event quarantine

Model which turn is legally allowed to consume every user input, child-agent message, tool result, and mailbox delivery.

Required properties:

- Late child messages after visible final output remain queued for the next turn.

### 6. Subprocess supervision topology and teardown closure

Go beyond “child must be waited on.” Model the complete managed-process ownership graph:

