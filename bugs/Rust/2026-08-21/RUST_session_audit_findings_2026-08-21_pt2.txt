### 3. Place/value provenance with callable summaries

What KDA cannot understand now:

Calls do not retain receiver or argument-to-parameter relationships. The primitive should track abstract places—parameters, locals, fields, tuple elements, enum payloads, dereferences—and edges such as assign, project, borrow, move, clone, wrap, unwrap, call argument, and return. Callable summaries should describe input-to-output and input-to-effect flow.

KD4 evidence:

In tool dispatch, `invocation` can be replaced by hook-produced input ([registry.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/registry.rs:937)), cloned for the handler, moved into an async closure, stored through `response_cell`, and later projected into hooks and lifecycle outcomes ([registry.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/registry.rs:985)). Today those are disconnected syntactic observations.

Checks enabled:

- Structured results collapsed after being forwarded through locals or wrappers.
- Call IDs, tool names, execution IDs, sandbox contexts, or cancellation tokens replaced or crossed.
- A field populated from one identity but consumed with another.
- Security and trust data reaching a sink through helper functions.
- Returned status or evidence derived from stale rather than updated input.
- Channel/token pairs constructed together but later mixed.
- Fields that are syntactically read but whose produced value never reaches an effect.

Determinism:

Use finite provenance sets keyed by stable place and entity IDs. Summaries should be monotone and canonicalized; ambiguous aliasing joins to `Unknown` or `MayFlow`.

Boundedness:

Track locals and field projections flow-sensitively inside a callable, then use context-insensitive summaries across calls. Treat heap aliases, raw pointers, escaped references, and unknown external calls as escape boundaries. This is sparse dataflow, not general alias analysis.

### 4. Resource ownership and obligation facts

What KDA cannot understand now:

Lifecycle reasoning is resource-specific. Child-process analysis explicitly suppresses a finding when a value is returned, passed to an unknown function, or moved into a closure ([lifecycle.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/lifecycle.rs:23)). KDA has no reusable representation of who owns a resource, what operation disarms an obligation, or what `Drop` guarantees.

The primitive should represent:

- Resource creation and current abstract owner.
- Transfers into locals, fields, closures, tasks, and return values.
- Obligations such as commit, finish, reap, abort, release, or cancel.
- Explicit disarm operations and compensating `Drop` effects.
- Forget/leak and unknown-escape boundaries.

KD4 evidence:

`PendingProcessRegistration` owns cleanup state, is disarmed by `commit`, and performs fallback cleanup when dropped uncommitted ([process_manager.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/process_manager.rs:262), [process_manager.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/process_manager.rs:365)). `StdioTransportHandle` owns a termination signal and calls it from `Drop` ([connection.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/connection.rs:76)).

Checks enabled:

- Pending registrations or transactions escaping without commit or compensating cleanup.
- Guards disarmed too early, forgotten, leaked, or dropped before the protected operation.
- A compensating `Drop` implementation acting on a different resource identity.
- Resources moved into tasks without transferring the corresponding shutdown obligation.
- Owner structs that store a resource but not its required handle/token.
- Exactly-once terminal claims implemented through explicit action plus fallback `Drop`.

Determinism:

Derive candidate protocols from canonical type and method identities, with configuration for project-specific verbs. Apply them over the deterministic CFG and provenance facts.

Boundedness:

Model only explicit resource types and finite obligation states. Rust already supplies move legality; KDA only needs abstract ownership changes visible in source. Unknown calls transfer or obscure ownership rather than triggering speculative findings.

### 5. Async task, channel, and cancellation topology

What KDA cannot understand now:

KDA already recognizes useful async concepts, but the relationships are mostly textual. KD4 evidence:

Checks enabled:

- Critical spawned work whose handle is detached or silently dropped.
- Task sets that are neither drained nor aborted on some owner exit.
- Cancellation tokens that are signalled but never observed, or observed without a reachable signal.
- Shutdown select branches that do not terminate their owned task/resource.
- Channel producers and consumers whose lifetime prevents shutdown.
- Spawn loops whose apparent budget does not actually dominate task creation.
- Abort-on-drop intent lost when a handle is unwrapped or moved elsewhere.

Determinism:

Recognize async APIs by resolved canonical identity and configurable project adapters. Derive clone families and ownership from value-flow facts; never infer runtime scheduling order.

Boundedness:

Support known task/channel/token families and workspace wrappers summarized in terms of those families. No executor simulation, interleaving exploration, or deadlock model checking.

### 7. Predicate and configuration contexts

What KDA cannot understand now:

The shared call index exposes only `cfg(test)` and “potential production path” booleans ([analysis_context.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:90)). A richer `PredicateFact` already exists in activation semantics, but it is pass-local and stores mostly textual expressions ([activation_semantics.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/activation_semantics.rs:100)).

The primitive should attach normalized predicates to entities, edges, value producers, and effects:

- Cargo feature, target, test, and platform predicates.
- Simple runtime capability and feature gates.
- Branch polarity and conjunction.
- Known contradiction, implication, or unknown relationship.

KD4 evidence:

Tool availability depends on combinations such as ToolSuggest + Apps + Plugins ([spec_plan.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/spec_plan.rs:365)), provider namespace support, model capabilities, collaboration mode, and environment count. Registration, model visibility, and runtime dispatch can therefore exist under different predicate sets.

Checks enabled:

- Specifications visible under configurations where their runtime is absent.
- Handlers registered under a broader or narrower gate than their dependencies.
- Production paths that exist only for incompatible feature combinations.
- Platform-specific cleanup or terminal behavior missing on one target.
- Tests exercising a branch under predicates different from production.
- Capability checks performed after rather than before constructing or exposing a component.

Determinism:

Canonicalize predicates into ordered atoms with polarity. Implement only finite conjunction, direct implication, and contradiction rules; preserve opaque runtime expressions as stable atoms.

Boundedness:

No SAT/SMT solver is necessary. Avoid arbitrary boolean simplification and runtime value prediction. The result can remain a conservative predicate-label algebra.

## Architectural conclusion

The first three primitives are the core investment: semantic identity/dispatch, local CFG, and value provenance. Ownership, async topology, and type-state should consume those facts rather than build new AST walkers. Predicate context ranks lower by direct leverage, but it should be present in the fact schema from the beginning because retrofitting predicates onto every node and edge would be expensive.

KDA’s existing planner already has a generic artifact concept, but its shared semantic inputs currently stop at `AnalysisContext` and `ProgramIndex` ([analyzer_plan.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analyzer_plan.rs:21)). The target architecture should be one immutable semantic-facts artifact with stable identities, evidence provenance, confidence, and explicit unknown boundaries.

I would specifically avoid growing `RuntimeActivationGraph` through additional source-text patterns. It is a valuable prototype of the relationships KDA needs, but the KD4 review shows that its next gains will come from semantic identities and shared flow facts, not a larger vocabulary of registration or async method names.

## Assessment

KDA is HIR-informed, but not yet MIR-like. It has strong symbol/type resolution, direct-call indexing, interprocedural summaries, and several narrow flow engines. What it lacks is a shared semantic middle layer representing:

- The identity of values and places over time.
- Control-flow joins, loops, early exits, moves, drops, and unwinding.
- Callable values flowing through closures, fields, collections, and trait objects.
- Resource effects and temporal relationships between asynchronous tasks.

That missing middle explains most of the current blind spots. Individual passes repeatedly reconstruct partial versions of it using names, source order, or bespoke statement walkers.

I reviewed the current working tree, including its uncommitted files. I found 496 test declarations, but did not run them because KD4 already had active Cargo/rustc work and the repository instructions prohibit overlapping repeated validation.

## Current semantic boundary

| Layer | What KDA can currently establish | Important boundary |
|---|---|---|
| Symbol/type identity | Resolve function and method calls, canonical types, reference roles | [`IndexedCall`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:79) records caller/callee but not arguments, results, or places |
| Direct interprocedural reasoning | Fixed-point summaries for direct resolved calls | Taint state is keyed by textual binding names and merged monotonically ([taint.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/taint.rs:222)) |
| Local flow proofs | Recognize enclosing branches and immediate guards | Explicitly not a CFG ([flow.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/flow.rs:1)) |
| Runtime topology | Model registration, spawn, join, channels, select, and dynamic boundaries | A topology graph, not a value-flow or call-target proof ([runtime_activation_graph.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/runtime_activation_graph.rs:1)) |
| Lifecycle/protocol checks | Handwritten analyses for child processes, tasks, keyed cleanup, and durability | Each has its own limited path and receiver-name model |
| Closures/dynamic calls | Some specialized registration and spawn recognition | The ordinary caller index deliberately excludes closure-nested calls ([analysis_context.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:561)); tests explicitly suppress dynamic targets ([capability_parity.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/tests/capability_parity.rs:286)) |

The highest-leverage direction is therefore not more method-name lists. It is to build reusable value, effect, and control-flow semantics that existing passes can consume.

# 1. New lint buildable with capabilities already present

### Cancellation loss under timeout

Generalize the existing cancellation-safety check from `tokio::select!` to resolved timeout combinators such as:

- `tokio::time::timeout`
- `tokio::time::timeout_at`

KDA already has a curated resolved-call classification containing `mpsc::Sender::send`, async writes, semaphore acquisition, and locks as cancellation-sensitive operations ([async_lints.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/async_lints.rs:32)). It currently applies that reasoning primarily to select branches.

KD4 has a direct adversarial example:

```rust
tokio::time::timeout_at(deadline, incoming_tx.send(event)).await
```

in [`send_incoming_event`](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/noise_relay/harness.rs:597). If the timeout wins, the send future is dropped and its queue position/work is abandoned. That may be intentional here, but it is exactly the kind of cancellation decision that deserves an explicit diagnostic or allowance.

Implementation policy should be narrow:

- Emit only when the inner awaited operation resolves to `KnownUnsafe`.
- Treat safe operations such as oneshot receive as safe.
- Do not flag arbitrary methods textually named `send`.
- Allow an annotation/configured suppression for deliberate backpressure policies.

This requires no new fundamental analysis—only recognizing timeout combinators and feeding their future argument into the existing classifier.

# 2. Small semantic primitives that unlock several valuable lints

## A. `PlaceId` plus ordered reaching definitions — highest priority

Introduce a stable identity for:

- Parameters and local bindings.
- Field projections.
- Dereferences.
- Constant-index projections where practical.
- Values related by move, borrow, clone, and assignment.

Then provide a conservative “origins of this place at this program point” query with strong updates for unaliased locals and conservative merges elsewhere.

Why it matters in KD4:

- RPC cleanup is keyed by cloned `request_id` values across insertion and several removals ([rpc.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:442)).
- Turn submission coordinates `turn_id`, an in-flight claim, and an `origin_reservation` across an awaited failure path ([turn_processor.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/request_processors/turn_processor.rs:732)).
- Current name-based maps cannot reliably distinguish reassignment, shadowing, projections, aliases, or matching cloned keys.

This primitive would improve multiple existing families:

- Taint and sanitizer precision.
- Stale-after-await checks.
- Keyed acquire/release matching.
- Authority provenance.
- Durability ordering.
- Lock/channel/resource identity.
- Lifecycle ownership transfer.

It should precede a full CFG. Even a structured, statement-ordered version would remove substantial duplicated heuristics.

## B. A reusable resource/effect contract vocabulary

Add semantic summaries such as:

- `acquires(resource)`
- `terminalizes(resource)`
- `commits(resource)`
- `rolls_back_on_drop(resource)`
- `transfers(resource, argument)`
- `returns_alias(argument)`
- `publishes(path)`
- `durability_barrier(resource)`
- `cancellation_safe` / `cancellation_sensitive`

Initially, these can be configured for external APIs and inferred only for simple local wrappers.

KD4 exercises the same underlying obligation through very different APIs:

- An execution registration is created, an async submission occurs, and then it is committed; failure relies on drop behavior ([codex_thread.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/codex_thread.rs:552)).
- A residency claim must be restored, discarded, or transferred into a late-shutdown task ([residency.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/control/residency.rs:180)).
- A temporary shell snapshot must be deleted on validation/rename failure or atomically published on success ([shell_snapshot.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/shell_snapshot.rs:168)).

One effect vocabulary could support:

- Unfinished reservation/transaction checks.
- Missing rollback or cleanup.
- Use-after-commit.
- Double terminal action.
- Transfer into spawned work.
- Temporary-file publish protocols.
- Interprocedural lifecycle summaries.

This is much more valuable than teaching each pass that `commit`, `restore`, `discard`, or `remove` has a particular spelling.

## C. Callable-value identities and transfer edges

Represent function items and closures as values, including captures, and track straightforward transfers through arguments, fields, and collection insertion.

KD4’s RPC router stores generic handlers inside boxed closures in a `HashMap`:

- Callable types: [`RequestRoute` and `NotificationRoute`](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:51)
- Registration and capture of `handler`: [`RpcRouter::request`](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:144)

The activation graph already knows that registration and dynamic boundaries exist, but it cannot connect the eventual `route(...)` invocation to the captured handler’s summaries.

A modest callable-flow primitive would immediately improve:

- Runtime reachability.
- Taint through callbacks.
- Cancellation summaries.
- Authority checks.
- Panic propagation.
- Lifecycle transfer into asynchronous callbacks.

Keep this bounded to syntactically visible transfers. Full trait-object/points-to resolution belongs in the larger-capability category.

# 3. Larger analysis capabilities worth adding later

## A. Shared CFG plus ownership-aware typestate analysis

This is the most valuable larger investment.

The CFG should model:

- `?`, `return`, `break`, and `continue`.
- `if`, `match`, and loop joins.
- Moves into closures and async blocks.
- Normal drop at scope exits.
- Conservative panic/unwind exits.
- Call effects supplied by the resource contract layer.

KD4’s RPC request protocol demonstrates why linear statement inspection is inadequate. A pending entry is inserted, removed on serialization failure, send failure, and timeout, and otherwise completed indirectly by the reader ([rpc.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:432)).

The residency claim is even more adversarial: it crosses a loop, multiple `continue`/`return` paths, awaits, and an ownership transfer into `tokio::spawn` ([residency.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/control/residency.rs:187)).

A common typestate engine would subsume much of the bespoke logic in lifecycle, owned-lifecycle, keyed-protocol, durability, and authority passes.

## B. Bounded points-to and dynamic-dispatch resolution

Build on callable-value tracking to compute conservative candidate sets for:

- `dyn Fn` and boxed closures.
- Trait-object method calls.
- `Arc<dyn Trait>`.
- Callbacks stored in maps or structs.
- Generic implementations where the concrete set is closed within the workspace.

KD4 uses both major adversarial patterns:

- RPC handlers stored as `Box<dyn Fn>` in route maps ([rpc.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:122)).
- Execution environment services stored as `Arc<dyn ExecBackend>`, `Arc<dyn ExecutorFileSystem>`, and `Arc<dyn HttpClient>` ([environment.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/environment.rs:409)).

Without candidate targets, every existing interprocedural analysis loses visibility at precisely the abstraction boundaries used by application architecture.

The result must be set-valued and allowed to return `Indeterminate`; pretending to resolve a unique target would make security and lifecycle checks unsound.

## C. Async happens-before and protocol-state reasoning

The activation graph already inventories tasks, channels, select edges, joins, and synchronization objects. A later layer could attach resource identities and temporal facts:

- A lock protects a check-plus-mutation region.
- A channel send precedes a receive.
- A watch observation is marked seen before waiting.
- Shutdown prevents later registration.
- Exactly one completion path wins.
- A task transfer preserves an obligation.

KD4’s RPC client explicitly requires the disconnect check and pending insertion to be atomic with the reader’s drain operation; otherwise a caller can wait forever ([rpc.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:445)). That invariant cannot be expressed by a local lock lint or call graph.

KD4 also demonstrates careful watch usage by cloning the current value from `borrow_and_update()` before awaiting `changed()` ([spawn.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/control/spawn.rs:659)).

This capability could eventually detect:

- Lost wakeups.
- Check-then-act races.
- Double completion.
- Shutdown/registration races.
- Channel protocol violations.
- Stale watch observations.

It should follow `PlaceId`, effect summaries, and CFG work; otherwise resource matching would remain textual.

# 4. Ideas not worth implementing

## Generic Clippy/rustc duplicates

Do not expand KDA into another style, unwrap, lock-across-await, or ordinary panic checker. KD4 already denies `await_holding_lock`, `expect_used`, `unwrap_used`, redundant clones, and numerous mechanical lints ([workspace lints](/C:/Users/kuh/Desktop/kd4/codex-rs/Cargo.toml:475)).

Likewise, `tokio::sync::watch::Ref` held across await is better handled by adding the type to Clippy’s `await-holding-invalid-types` configuration, which KD4 already uses for Tokio lock guards ([clippy.toml](/C:/Users/kuh/Desktop/kd4/codex-rs/clippy.toml:3)). KDA should focus on cross-operation protocol mistakes that Clippy cannot express.

## Generic atomic-ordering or unsafe-code judgments

A rule such as “Acquire is suspicious” or “use SeqCst” would be mostly noise. KD4’s RPC protocol uses `SeqCst` for request IDs and `Acquire` for shutdown state as part of a larger lock/drain invariant ([rpc.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/rpc.rs:442)). Correctness depends on the full protocol, not the spelling of an ordering.

Rustc, Miri, Loom, sanitizers, and targeted concurrency tests are better tools until KDA has an actual happens-before model.

## Name-based authorization or security inference

Inferring that methods named `authorize`, `validate`, or `check` dominate sensitive operations will remain fragile across wrappers, aliases, callbacks, and trait-object backends. KD4’s dynamically selected environment services demonstrate the problem.

Security checks should be built on explicit authority/effect contracts and dataflow, not a larger vocabulary of method names.

## Blanket warnings for timeout, send, or cancellation

The KD4 timeout around `incoming_tx.send(event)` deliberately implements an application-backpressure deadline. A blanket “timeout around send is wrong” rule would be noisy.

The worthwhile version is the narrow category-1 lint: resolve the exact inner operation, explain the cancellation consequence, and permit deliberate acknowledgment.

## Attempting to infer domain protocols automatically

For example, Noise relay ciphertext ordering and nonce progression are critical but domain-specific. Inferring such invariants from method names or neighboring statements would have poor precision. KDA should provide generic protocol/typestate machinery and let KD4 express the contract explicitly.

## Test-suite implication

The current suite is broad and good at deterministic plumbing and synthetic cases, including branch cleanup and interprocedural taint. Its largest gap is that there is no real KD4 precision/recall corpus; dynamic targets are explicitly tested as suppressed.

Before the larger investments, I would add an adversarial KD4 fixture set with seeded mutations:

- Remove one `pending.remove`.
- Drop one `claim.restore`.
- Omit `registration.commit`.
- Change a safe watch-observation sequence.
- Put a known cancellation-sensitive operation under a timeout.

Each should have the unmodified KD4 code as a negative control. That will measure whether a new semantic layer genuinely increases reasoning power rather than just increasing diagnostic volume.

- Resolve `std::env::vars`, environment-map mutations, `std`/Tokio `Command::envs`, and process-launch calls by identity.

- Perform bounded map-taint propagation from ambient environment and overlays to spawn.
- Require a recognized final `retain`/`env_remove` sanitizer to dominate every launch path.

The analyzer does not need to know whether a secret happens to be present at runtime. It diagnoses that the program permits a forbidden information flow. ## 2. Timed-out Git commands leave descendants running

Invariant: timing out a command known to spawn helpers must terminate the contained process tree, not merely the immediate child.

Current violations occur in:

- [git-utils/src/info.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/git-utils/src/info.rs:480), with another at line 607.
- [core/src/git_workspace.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/git_workspace.rs:419), with further instances at lines 1193 and 1268.

```rust

```

Dropping the output future kills the direct Git process, but Git credential helpers, filters, SSH processes, and other descendants can survive. The later fix `3149fa4b99` adds Unix process-group and Windows Job Object containment.

Static proof:

- Resolve the Tokio `Command`, `kill_on_drop`, `output`, and `tokio::time::timeout` calls.
- Attach `may_spawn_descendants` to resolved Git-launch functions or a configured executable boundary.

- Look for a containment proof on that value: a process group, Job Object, `ManagedRootProcess`, or an approved wrapper.

## 3. A task owning the sole child reaper is aborted

Invariant: a spawned task that exclusively owns `Child` and performs the only `Child::wait` must be awaited or detached, never aborted during cleanup.

Producer:

- [pipe.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/pipe.rs:310) moves `child` into a spawned task.
- The task performs `child.wait().await` at line 311, records the exit code, and signals completion.
- Its `JoinHandle` becomes `ProcessHandle::wait_handle`.

Reachable consumer:

- [process.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/process.rs:253) takes cleanup handles.
- It aborts `wait_handle` at [line 275](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/process.rs:275).
- `Drop` invokes termination at [line 289](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/process.rs:289).

1. Resolve `tokio::process::Child::wait` inside an `async move` closure passed to `tokio::spawn`.
2. Prove the child is moved into that closure and has no alternate owner.
3. Record the task effect as `owns_must_complete_child_reaper`.
4. Follow the returned `JoinHandle` through the constructor into a specific struct field.
5. Find a reachable `JoinHandle::abort` from `Drop` or cleanup.

KDA currently classifies moving a child into a closure or record as an ownership transfer in [lifecycle.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/lifecycle.rs:941) and stops there. A one-hop owner summary would unlock this check without requiring whole-program analysis.

## Ideas I would not promote

- Generic “mutex guard across await”: statically visible, but deadlock depends heavily on lock topology and intent.

- General RAII-derived-value checking: only compelling for explicitly modeled types such as `TempDir`.

The first three are the strongest immediate additions: they are live, high-consequence, and supported by concrete later fixes. The remaining three are excellent regression-grade semantic checks with real historical failures and tight static proofs.

Its semantic core is already capable of supporting higher-level questions: `ProgramIndex` tracks canonical definitions, calls, and references ([analysis_context.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:131)), while the runtime activation graph models registrations and asynchronous activation beyond a conventional call graph ([runtime_activation_graph.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/runtime_activation_graph.rs:136)). ## 1. Semantic change dossier

A revision-aware report answering: “What behavior did this patch change, what else is implicated, and what remains unverified?”

- **User workflow:** An agent runs `cargo kda impact --base <ref>` before editing to scope a task, then again after editing. The output is a bounded JSON or human report containing changed semantic units, affected production roots, boundary obligations, relevant tests, required generated artifacts, and unresolved edges. Every relationship should include a short witness path—not merely a list of files.
- **KD4 scenario:** The current turn-timing/tool-lifecycle work introduces protocol identities and boundaries around [protocol.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:2124), execution bookkeeping in [command_execution.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/command_execution.rs:36), process/output-drain handling in [async_watcher.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/async_watcher.rs:233), and an app-server re-export at [turn.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/turn.rs:19). A dossier should connect those changes and identify schema, persistence, compatibility, and validation obligations automatically.
- **Semantic information required:** Cross-revision HIR item matching; typed classification of body, signature, enum, field, trait-implementation, and serialization changes; reverse production activation; field flow; Cargo target/cfg awareness; generated-boundary metadata; test reachability; and declared ownership/validation routes.
- **Why ordinary tools cannot provide it:** Grep sees coincident names, rustc sees broken compilation, and rust-analyzer exposes individual references. None produces a typed, transitive, revision-aware completion report across runtime activation, wire representations, persistence, and tests.
- **Placement:** An opt-in `cargo kda impact` subcommand. It should not run in default `cargo kda`, because it depends on a base revision and can be expensive.
- **Complexity:** High, roughly 8–12 engineer-weeks for a robust first version. Much of the single-revision machinery already exists; cross-revision identity and useful obligation classification are the hard parts.

## 2. Focused semantic slice

A query that creates the smallest useful semantic context around a symbol, field, type, capability, or diagnostic.

- **User workflow:** An agent asks something like `cargo kda slice codex_protocol::protocol::ToolExecutionId --to production,boundary,test --budget 80`. It receives a bounded subgraph: definitions, constructors, callers, trait dispatch, registrations, async handoffs, external boundaries, production roots, tests, and explicitly unresolved edges.
- **KD4 scenario:** Slicing `ToolExecutionId` should reveal where it is allocated, correlated with `CommandExecutionId`, carried through background execution, written into timing lifecycle records, serialized, and observed by tests. Slicing `read_turn_timing` should connect its tool specification ([read_turn_timing_spec.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/read_turn_timing_spec.rs:6)), handler ([read_turn_timing.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/read_turn_timing.rs:57)), registry/dispatch, rollout persistence, and response projection.
- **Semantic information required:** Canonical HIR identities, impl and trait resolution, type aliases and re-exports, construction and field flow, function-pointer/registry references, spawn/channel activation, cfg/features, serialization boundaries, and production-versus-test roots.
- **Why ordinary tools cannot provide it:** Rust-analyzer can find references or show a conventional call hierarchy, but it does not normally produce a bounded slice spanning registry dispatch, task spawning, channel handoff, stored representations, and test roots.
- **Placement:** A separate query command backed by KDA’s index. For repeated agent queries on KD4, a cache or long-lived query process would be worthwhile; it should not be part of the default gate.
- **Complexity:** Medium–high, around 4–8 weeks. The central challenge is relevance ranking and graph reduction, not collecting more edges.

## 3. Proof and explanation mode

Turn KDA’s internal reasoning into an inspectable proof or counterexample.

- **User workflow:** After receiving a diagnostic, an agent runs `cargo kda explain <diagnostic-id>`. It gets an ordered witness showing why the result was produced, which assumptions were used, the first missing boundary, and alternative paths considered. It should also support `cargo kda prove <contract>` for passing invariants.
- **KD4 scenario:** For command completion, the explanation could show execution allocation → process exit → output drain → completion application, including why duplicate or stale completion is safe. The relevant implementation distinguishes stale completions in [command_execution.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/command_execution.rs:997), while the watcher coordinates exit and delivery in [async_watcher.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/async_watcher.rs:239).
- **Semantic information required:** Retained proof DAGs from analysis passes, CFG dominance/post-dominance, early-return and `?` paths, async activation edges, state/effect facts, canonical identities, and precise source spans. Unknown dynamic edges must be represented rather than silently ignored.
- **Why ordinary tools cannot provide it:** Compiler errors explain type failures; they do not explain a successful or failed project-specific, interprocedural invariant. KDA already has some structured evidence types ([evidence.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/evidence.rs:50)), but its top-level report remains diagnostic-oriented ([model.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/model.rs:699)).
- **Placement:** `cargo kda explain` over a saved report artifact, with optional compact proof references in normal JSON output. Default diagnostics should remain concise.
- **Complexity:** Medium, around 3–6 weeks for selected high-value passes. Retrofitting every pass immediately would be unnecessary.

## 4. Semantic test-and-validation planner

Select tests based on affected behavior and observable assertions, not file proximity or call reachability alone.

- **User workflow:** `cargo kda test-plan --base <ref>` emits a minimal ordered set of commands. For each test it states whether the test merely reaches changed code or whether an assertion/snapshot actually depends on the changed value or effect. It also lists uncovered changed behaviors.
- **KD4 scenario:** For the lifecycle patch, it should choose turn-timing aggregation tests, stale/duplicate completion tests, protocol backward-deserialization tests, app-server thread-history tests, and schema checks. It should separately report if cancellation or output-drain ordering reaches tests but is never meaningfully asserted.
- **Semantic information required:** Cross-revision change mapping, test entry points, call and async activation, data/control dependence from changed values to assertions and snapshots, Result/error-path coverage, cfg/features, Cargo targets, and KD4’s declared validation recipes. KD4’s source map already describes cross-cutting validation routes such as app-server API and tool behavior ([SOURCEMAP.md](C:/Users/kuh/Desktop/kd4/SOURCEMAP.md:479)).
- **Why ordinary tools cannot provide it:** Existing KDA test history is a strong start, but it explicitly limits proof to authored Rust functions and does not prove generated or dynamic-dispatch edges ([test_history.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/test_history.rs:535)). Reachability alone also cannot distinguish execution from observation.
- **Placement:** Separate `cargo kda test-plan`; the impact dossier could embed its summary. It should never execute commands without an explicit flag.
- **Complexity:** High, approximately 8–12 weeks. Assertion influence and snapshot/effect modeling are the major additions.

## 5. Boundary evolution report

A semantic comparison of how a type or value crosses wire, persistence, generated-schema, and crate boundaries.

- **User workflow:** An agent runs `cargo kda boundary-diff --base <ref> --type TurnTiming`. The output is a projection matrix showing Rust fields and variants, wire names, defaults, custom serialization, conversions, persisted readers/writers, re-exports, generated representations, compatibility status, and missing regeneration.
- **KD4 scenario:** New `TurnTimingToolLifecycleEvent` fields must remain compatible with older rollout records, appear in app-server representations, and propagate through schema generation. The report should explain the effect of `serde(default)`, manual serialization, wildcard handling, or missing conversion code—not simply report that a field changed.
- **Semantic information required:** ADT layouts, derive and serde attributes, manual `Serialize`/`Deserialize`, `Default`, `From`/`TryFrom`, type aliases/re-exports, match exhaustiveness and wildcard behavior, field construction/read flow, persistence roots, and schema-generator entry points.
- **Why ordinary tools cannot provide it:** Rustc catches missing fields in direct constructors but not compatibility semantics, silent defaults, stale generated outputs, or loss through intermediate representations. KDA’s existing surface snapshots and protocol-parity lints provide ingredients, but not this end-to-end projection.
- **Placement:** An opt-in `cargo kda boundary-diff`. Stable individual boundary rules can later graduate into ordinary lints.
- **Complexity:** High, around 6–10 weeks for serde plus known KD4 generators; arbitrary serialization frameworks should remain out of scope initially.

## 6. Bounded lifecycle scenario verifier

Verify a declared asynchronous lifecycle as a small temporal contract.

- **User workflow:** A project contract defines identities, start events, allowed transitions, terminal states, and exceptional exits. `cargo kda scenario exec-command-completion` returns `proved`, `violated`, or `unknown`, together with the shortest counterexample or unresolved activation boundary.
- **KD4 scenario:** Check the lifecycle from request creation through admission, handler entry, process spawn, process exit, output collection, relay delivery, and next sampling. It should cover background sessions, cancellation, stale completion, and output-drain ordering. KD4 already exposes these as semantic lifecycle boundaries ([protocol.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:2135)) and consumes them in timing aggregation ([turn_timing.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/turn_timing.rs:1480)).
- **Semantic information required:** Interprocedural CFGs, enum/state transitions, branch predicates, `Result` and cancellation paths, RAII/drop behavior, spawn/join/channel edges, identity correlation, and terminal-state reachability.
- **Why ordinary tools cannot provide it:** Compilers verify local typing and ownership, not that every asynchronous identity eventually reaches exactly one acceptable terminal state.
- **Placement:** A separate, opt-in verification mode. Selected scenarios could run in CI, but never as an implicit analysis of every enum that resembles a state machine.
- **Complexity:** Very high—likely 3–6 months for a trustworthy bounded engine. A generic Rust model checker would be unjustified; only explicitly declared, narrowly modeled scenarios are realistic.

## What I would not build

I would avoid:

- A workspace-wide DOT call graph. KD4 is too large, and KDA’s activation graph is already richer than a conventional call graph. Agents need reduced slices and witness paths.
- A natural-language architecture chatbot inside KDA. It can be a consumer of structured outputs, but should not become the semantic authority.
- Automatic temporal inference over every async function. The unknown and false-positive rate would overwhelm the value.
- Replacing stable diagnostics with reports. Rules such as “registered handler lacks a production installation path” remain best expressed as anchored, suppressible lints.

My suggested development order would be proof/explanation infrastructure first, then focused slices, then the change dossier. Although the dossier ranks highest in end-user usefulness, the first two provide the evidence representation and graph-reduction machinery it needs.

Implemented [durable_state.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/durable_state.rs).

A contract-specific analysis can:

- Resolve the exact `HashMap<RequestId, PendingCallbackEntry>` field rather than any receiver containing “request”.

Declare or infer value-level invariants such as:

```text
by_assignment[b.assignment_id] = b
    iff
by_agent_path[b.agent_path] = b
```

and:

```text
thread ∈ thread_ids_by_connection[connection]
    iff

```

For every mutator of the owning structure, the analyzer can prove that:

- Both relation projections are inserted under the same lock.
- Both are removed on every applicable path.
- Keys are derived from the same source values.

### 3. RAII reservation rollback and commit transfer

**Pair or family**

Every acquired spawn resource must either be rolled back when the reservation is dropped or transferred into committed registry state. Commit itself must release temporary gates without releasing resources now owned by the live agent.

**How KD4 establishes it**

[`SpawnReservation`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry.rs:460>) owns several temporary obligations:

- spawn-slot count;
- reserved agent path;
- parent spawn reservation;
- nickname reservation with intentionally different semantics.

[`commit`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry.rs:496>) registers the spawned thread, releases the temporary parent reservation, clears transferred tokens, and disarms rollback.

[`Drop`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry.rs:512>) releases the parent reservation and path and decrements the spawn count if commit did not succeed.

Tests explicitly establish both sides:

- [dropping releases a slot](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry_tests.rs:74>)
- [commit retains the slot until live-thread release](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry_tests.rs:84>)
- [failed spawn releases a reserved path](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry_tests.rs:324>)
- [committed path remains indexed until thread release](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry_tests.rs:343>)

`AgentTreeClosingGuard` provides another compact instance: [`mark_threads`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry.rs:442>) records newly marked threads, and [`Drop`](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/registry.rs:454>) releases precisely that set.

**Realistic one-sided edit**

Add another quota, reserved key, or parent gate to `SpawnReservation::reserve_*`, store its token, but forget to add rollback to `Drop` or ownership transfer to `commit`.

The program compiles, yet failed spawns permanently consume capacity or successful commits accidentally release resources still needed by live agents.

**Static proof**

For each side effect acquired while a guard is active:

- Associate the effect with the guard field holding its token.
- Require `Drop` to invoke an inverse effect using the same state object and token.
- Require `commit` either to release the temporary obligation or transfer it into committed state.
- Check that rollback remains armed across every fallible `?`.
- Check that disarming happens only after successful transfer.

This contract needs an exception facility: KD4 deliberately keeps used nicknames consumed after some failed spawns, so blindly requiring every `reserve_*` to roll back would be wrong.

**Why this is not text matching**

The spawn slot uses `fetch_add`/`fetch_sub`, paths use registry helpers, parent reservations use another helper pair, and commit represents ownership transfer rather than a simple inverse call. The proof depends on guard fields, `Drop`, result propagation, and effect identity.

Current [`lifecycle_protocol.rs`](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/lifecycle_protocol.rs:1>) explicitly avoids treating RAII guards as ordinary close protocols because it lacks type-level `Drop` analysis. This would be a new semantic feature.

## 1. Cache keys must cover the value’s semantic dependencies

Concrete KD4 patterns:

- Historical fix `4aa950d` changed prompt caching from a thread ID to a session ID. Different threads belonging to one session were incorrectly treated as different cache identities.
- The same risk surface is visible around [`ModelClient::prompt_cache_key`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1760). The request path has both session and thread identity available in [`build_session_headers`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1941).
- Other caches show how many identity dimensions can matter:
  - Workspace settings use base URL plus account ID in [`WorkspaceSettingsCacheKey`](/C:/Users/kuh/Desktop/kd4/codex-rs/chatgpt/src/workspace_settings.rs:27).
  - Connector directories additionally distinguish user and workspace-account state in [`ConnectorDirectoryCacheKey`](/C:/Users/kuh/Desktop/kd4/codex-rs/connectors/src/lib.rs:44).

Invariant:

> Two computations may share a cached value only if every input capable of changing that value is equivalent at the cache’s intended scope.

Producer and effect:

- The producer reads account, URL, user, workspace, session, configuration, or discovery-root state.
- The cache-hit branch returns an earlier result without executing that producer.
- A missing dimension can leak or reuse data across accounts/workspaces. A needlessly narrow dimension can silently defeat caching and create inconsistent behavior between root agents and subagents.

Why Rust accepts it:

Every candidate identity is a valid `String`, `ThreadId`, tuple, or `Eq` key. The type system cannot know whether “thread” or “session” is the correct equivalence relation.

Why ordinary tooling misses it:

Clippy sees a well-formed `HashMap` key. It has no specification connecting the value-producing operation’s inputs to the key. KDA’s existing identity/freshness checks cover identities that are dropped or collapsed, but not general functional-dependency completeness.

Needed analyzer capability:

- Summarize semantic inputs read by the cache-miss computation.
- Compare them with fields flowing into the cache key.
- Model identity scope: request → thread → session → account → workspace → deployment/base URL.
- Flag missing dependencies and suspiciously narrower sibling identities.
- Learn contracts from adjacent caches and isolation tests.
- Permit annotations for inputs intentionally irrelevant to the value.

Reliability:

About 85–95% for explicit key structs and nearby cache-miss calls. Generic wrapper caches would initially be closer to 60–75%.

Invariant:

> A completion or close event may become observable only after every causal producer that can affect the result has settled, and every lower sequence event has been delivered exactly once.

Producer and effect:

- PTY readers produce output.
- Exit watchers produce status.
- sandbox/network classifiers can revise failure meaning.
- interaction handlers produce externally visible input events.

Why Rust accepts it:

Tasks, atomics, channels, and notifications are independently type-correct. Rust guarantees memory safety, not that the chosen synchronization establishes the application’s intended happens-before relation.

Why ordinary tooling misses it:

A lifecycle checker can verify “started implies finished” while still missing “finished must occur after output drained and classification settled.” Clippy has no cross-task event protocol.

Needed analyzer capability:

- Infer event-state machines from enums, sequence fields, publish calls, and terminal variants.
- Build a cross-task causal graph.
- Treat `Notify`, mutexes, joins, channel closure, and Acquire/Release pairs as ordering evidence.
- Require terminal publication to be dominated by quiescence of all contributing producers.
- Verify recovery and normal delivery implement compatible transition rules.
- Detect resource/route removal before terminal publication is causally complete.

Reliability:

Approximately 80–90% where sequence numbers and terminal variants are explicit; 60–75% for loosely structured channel-based protocols.

Concrete KD4 patterns:

- Historical fix `7790524` preserved JSON number precision in exec-server RPC. The bounded custom decoder accepted `serde_json::Value`, but did not preserve arbitrary decimals, exponent-form numbers, or integers beyond native 64-bit ranges.

Invariant:

> An intermediary promising transparent storage, inspection, or forwarding must accept and preserve the entire source representation needed by downstream consumers.

Producer and effect:

- JSON-RPC peers and rollout files produce legal JSON values.
- Custom visitors or typed intermediate structures narrow the domain.
- Consumers receive rounded data, rejected messages, or an incomplete history after a valid-but-unexpected value.

Why Rust accepts it:

`serde_json::Value`, custom `Visitor` implementations, and derived deserializers all satisfy their Rust signatures. Cargo feature choices and accepted number grammars are not represented in those types.

Why ordinary tooling misses it:

There need not be an `as` cast or overflow. Existing numeric-cast checks would not see a narrowing performed by deserialization configuration or visitor coverage.

Needed analyzer capability:

- Represent serialization domains: bounded integers, floating-point approximation, arbitrary JSON numeric lexemes, and raw values.
- Inspect serde feature flags and custom visitor methods.
- Check whether “generic JSON” boundaries are implemented through narrower intermediates.
- Follow decode → transform → encode paths and compare accepted/preserved domains.
- Treat silent record skipping as a reachable semantic effect.

Reliability:

Around 90% for generic JSON boundaries with obvious domain narrowing; 65–80% for custom application formats whose domain is undocumented.

## 4. Shell source strings are not ordinary argv elements

Concrete KD4 pattern:

- Historical fix `3ac476b` repaired quoted hook commands on Windows.
- Passing a command string through ordinary `Command::arg` caused Rust’s Windows argument encoder to escape outer quoting before `cmd.exe /C` parsed it.
- Current code deliberately uses `raw_arg` when the downstream shell is `cmd.exe /C`, but ordinary `.arg` elsewhere in [`build_command`](/C:/Users/kuh/Desktop/kd4/codex-rs/hooks/src/engine/command_runner.rs:415).
- The failure was observable with a quoted `.cmd` path containing spaces, for both the default shell and explicitly configured `COMSPEC /c`.

Invariant:

> Data following a shell execution switch must be encoded as source text in that shell’s grammar, not automatically encoded as one ordinary argv atom.

Producer and effect:

- Configuration produces a complete hook command string.
- `Command` serializes it for process creation.
- `cmd.exe` reparses the resulting command line.
- A mismatch changes the executable or arguments, typically producing “file not found” or executing unintended syntax.

Why Rust accepts it:

Both `.arg` and `.raw_arg` accept valid strings. Their difference is about the next parser, not Rust validity.

Why ordinary tooling misses it:

This can involve fully trusted input and therefore is not necessarily command injection. Generic taint analysis will miss correctness failures caused purely by double quoting.

Needed analyzer capability:

- Track command values as either structured argv or shell source.
- Attach a shell dialect and invocation mode: `cmd /C`, PowerShell command text, POSIX `-c`/`-lc`, or direct execution.
- Model Rust’s Windows argument serialization separately from shell parsing.
- Flag `.arg(source_string)` at known shell-source positions and `raw_arg` outside justified Windows-shell cases.
- Recognize tested quoting helpers and explicit wrapper contracts.

Reliability:

Roughly 90–95% for known shells and execution switches; 65–80% for arbitrary shell wrappers.

## 5. Same primitive type does not mean same semantic quantity

Concrete KD4 patterns:

- [`retry.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/codex-client/src/retry.rs:23) documents a zero-based `attempt`, while [`backoff`](/C:/Users/kuh/Desktop/kd4/codex-rs/codex-client/src/retry.rs:40) consumes a one-based retry number.

- Historical fix `8b8fa72` corrected rollout-budget accounting: code always derived a weighted token estimate even when the provider supplied authoritative `codex_rollout_budget_units`. That changed reminder and compaction thresholds despite all values being valid numbers.

Invariant:

> Arithmetic and argument passing must preserve the quantity’s unit, origin, and ordinal convention; authoritative measurements must dominate derived fallbacks when present.

Why Rust accepts it:

Attempts, retry numbers, token counts, provider units, seconds, and milliseconds commonly share `u64`, `i64`, or `f64`.

Why ordinary tooling misses it:

There is no invalid cast and frequently no suspicious arithmetic. The error is that the number means the wrong thing.

Needed analyzer capability:

- Infer semantic quantity tags from parameter names, field names, documentation, and APIs such as `Duration::from_secs`.
- Distinguish zero-based attempt, one-based retry, cumulative count, delta count, wall-clock units, tokens, and provider-defined budget units.
- Propagate tags through arithmetic.
- Require an explicit conversion where conventions change.
- Model precedence contracts such as authoritative value → derived fallback.
- Optionally allow lightweight annotations when inference is ambiguous.

Reliability:

90–95% for clear suffixes, constructors, and documented ordinals. About 65–80% for domain-specific units such as provider budget accounting unless schemas or annotations supply the contract.

## 6. Byte offsets, graphemes, and terminal columns are different coordinate systems

Concrete KD4 patterns:

- Historical fix `3725f02` repaired TUI layout for half-width Japanese sound marks by replacing character-width assumptions with grapheme boundaries and terminal-compatible display width. It touched wrapping, truncation, cursor placement, masking, and alignment.
- Historical fix `cef3910` handled OSC 8 hyperlinks. Escape bytes are present in strings but consume no screen columns; wide cells can also leave styled trailing cells during terminal diffing.

Invariant:

> A position measured in UTF-8 bytes, Unicode scalars, grapheme clusters, terminal cells, or escape-stripped visible columns may only be consumed in the same coordinate space or after an explicit conversion.

Producer and effect:

- String APIs produce byte or character positions.
- Grapheme segmentation produces user-perceived boundaries.
- width APIs produce terminal columns.
- Layout and buffer-diff consumers can split graphemes, misplace cursors, truncate incorrectly, or leave stale cells.

Why Rust accepts it:

All coordinate values are normally `usize`. UTF-8 safety does not imply grapheme safety or correct terminal geometry.

Why ordinary tooling misses it:

Clippy can sometimes identify unsafe string indexing, but it cannot tell whether a valid `usize` represents bytes, characters, graphemes, or cells.

Needed analyzer capability:

- Assign coordinate-domain qualifiers to results of `.len()`, `char_indices`, grapheme iterators, Unicode-width functions, and Ratatui cell-width APIs.
- Propagate those qualifiers through ranges and arithmetic.
- Flag cross-domain slicing, cursor positioning, wrapping, and padding.
- Treat terminal control sequences as zero-width annotations.
- Recognize explicit conversion helpers as semantic boundaries.

Reliability:

Approximately 85–95% around known Unicode and terminal APIs; 65–80% for application-specific width helpers.

## 1. Foreign-retained pointer lifetime analysis

**Risk:** use-after-free, relocation, reallocation, or conflicting access while an asynchronous OS operation still retains Rust-owned pointers.

**KD4 evidence:** `codex-rs/tui/src/ide_context/windows_pipe.rs`

- `175-206`: `OverlappedOperation` pins a buffer, `OVERLAPPED`, event, and pipe handle together.
- `221-235`: returns raw buffer and `OVERLAPPED` pointers; comments require pinning and forbid resizing.
- `237-280`: completion is established through `GetOverlappedResult`.
- `283-293`: `CancelIoEx` is followed by transfer to a reaper because cancellation is not terminal.
- `296-305`: `Pin::into_inner_unchecked` is used only after observed completion.
- `309-312`: the unsafe `Send` implementation depends on exactly one ownership transfer.
- `372-385`, `389-453`: reaper failure deliberately uses `mem::forget` because freeing pending storage would be a UAF.
- `474-494`: the pipe handle remains shared through `Arc` and is closed exactly once.

The current code carefully preserves the invariant, but an innocuous future move, resize, early return, or “cleanup” of a `mem::forget` can create immediate memory unsafety. Rust borrowing ends at the FFI call and cannot express that the kernel retains the pointers.

**Analysis design:**

- Define configurable foreign-call contracts for issuing calls, retained pointer arguments, pending-result predicates, cancellation calls, terminal completion calls, and ownership-transfer sinks.
- Track a flow-sensitive foreign loan: `issued → pending → terminal`, or `pending → reaper-owned`.
- While pending, require the pointed allocation and enclosing pinned object to remain address-stable; reject drop, move, resize/reallocation, conflicting mutation, or premature handle release.
- Do not treat `CancelIoEx` as terminal until completion is observed.
- Permit an explicit retain/leak sink only when the foreign-loan contract says retaining memory is the safe fallback.
- Summarize helper functions interprocedurally.

**Why KDA:** KDA already has semantic call resolution, call graphs, lifecycle checks, and project contracts. Windows overlapped-I/O semantics are precisely the kind of workspace-specific fact rustc should not hard-code.

## 4. Async-signal-safe call-closure analysis

**Risk:** deadlock, allocator corruption, reentrancy failure, or process corruption when a signal handler calls logging, formatting, allocation, locking, TLS/lazy initialization, panic paths, or non-signal-safe foreign functions.

**KD4 evidence:** `linux-sandbox/src/linux_run_main.rs`

- `800-817`: installs a handler through `libc::sigaction`; callback assignment is at `806`.
- `820-826`: `extern "C" fn forward_signal_to_bwrap_child` currently performs atomic access and calls a helper.
- `835-839`: the helper currently limits its effects to two `libc::kill` calls.

The current closure is deliberately small. The danger is that an ordinary helper refactor—especially adding diagnostics—remains type-correct and may pass the existing panic-across-FFI check while becoming illegal in signal context.

**Analysis design:**

- Discover handler roots passed to `sigaction`, `signal`, and configured wrappers rather than treating every `extern "C"` function as a handler.
- Compute transitive effects over the call graph.
- Allow a target-aware whitelist of async-signal-safe libc calls, primitive operations, and proven lock-free atomic accesses.
- Reject allocation, formatting/logging, locks, TLS/lazy initialization, blocking APIs, panic, unsafe drop glue, and unapproved local/foreign calls.
- Include the shortest offending call path in the diagnostic.
- Treat unresolved dynamic calls as requiring an explicit contract rather than pretending they are safe.

**Why KDA:** signal-handler status is established at the registration site and must be propagated through helpers. KDA already has the call graph used by `panic-across-ffi`, and project contracts can encode the intended libc subset.

**Overlap check:** KDA’s existing FFI-panic analysis checks unwinding only. rustc checks ABI and type correctness, not POSIX signal safety. The current stable [Clippy lint index](https://rust-lang.github.io/rust-clippy/stable/index.html) has no signal-handler-context call-closure lint.

**Risk:** complementary target implementations silently drift in signature, visibility, generic bounds, representation, or promised effects even though each target compiles independently.

**Analysis design:**

- Materialize KDA’s semantic surface independently for each configured target/feature analysis profile.
- Automatically pair the same canonical path under complementary `cfg` predicates; support explicit parity groups for adapter functions with different names.
- Compare normalized signatures, visibility, generic and trait obligations, relevant auto-traits, serde representation, and selected effect contracts such as `Result`-returning or no-panic behavior.

**Why KDA:** `src/config.rs:382-439` already models target/feature analysis profiles, and `src/surface.rs` already extracts syntax-level public/serde surfaces. **Overlap check:** rustc and Clippy analyze one active `cfg` world at a time. ## 1. `notify-state-check-order` — detect level-triggered waits that can miss a wake

Concrete KD4 risk: `wait_for_validation_call_terminal` appears to contain a real missed-wakeup window.

- `core/src/agent/task_coordinator.rs:475-484` signals with `Notify::notify_waiters()`.
- `core/src/agent/task_coordinator.rs:487-491` claims installing the notifier before the read prevents missed transitions.
- `core/src/agent/task_coordinator.rs:498-507` installs only the `Arc<Notify>`.
- `core/src/agent/task_coordinator.rs:509-519` reads and tests authoritative state.
- The `Notified` future is not created until `core/src/agent/task_coordinator.rs:523-525`.

A terminal transition and `notify_waiters()` between the state check and line 524 is lost. Tokio 1.52.3 explicitly states that `notify_waiters()` stores no permit and only wakes already registered `Notified` futures (`tokio-1.52.3/src/sync/notify.rs:711-717`).

KD4 already contains the correct pattern at `core/src/validation_admission.rs:522-532`: create `notified` first, then inspect authoritative state, then await it.

Analysis design:

- Identify loops combining an authoritative predicate read with `Notify::notified()`.
- Link signal sites using `notify_waiters` or `notify_one`.
- Require registration before the state read; for multi-consumer `notify_one` protocols, also model `Notified::enable`.
- Accept level-triggered alternatives such as `watch`, condition-and-notification protected by the same lock, or durable queued permits.
- Report both the read and signal sites as a temporal counterexample.

Why kda: this needs interprocedural call resolution plus path/order reasoning across a project-specific state predicate and notification channel.

Overlap check: accepted. rustc and Clippy do not analyze wakeup protocols. kda’s existing `uncorrelated-async-wake` work is epoch-correlation-specific and explicitly ignores non-epoch latches; it does not check state/read registration order.

## 2. `critical-channel-delivery-contract` — prevent semantically critical events from reaching lossy sends

KD4 treats bounded-channel delivery as a protocol, not merely a capacity choice:

- `app-server-client/src/lib.rs:138-148` classifies lossless events, with a wildcard `_ => false`.
- Its comment at `:139-142` says dropping transcript/terminal events can corrupt markdown or leave surfaces waiting forever.
- `app-server-client/src/lib.rs:167-176` defines lossless versus best-effort delivery and requires dropped `ServerRequest`s to be rejected.

- The remote equivalent is split between classification at `app-server-client/src/remote.rs:1046-1053` and delivery at `:1056-1114`.

The high-risk regression is adding a new enum variant that silently inherits `_ => false`, or adding another `try_send` path that drops a terminal/request event without lag accounting or request resolution.

Analysis design:

- Track enum variants through `try_send`, `send_timeout`, broadcast lag, bounded queues, and intermediate forwarding helpers.
- Let project contracts classify variants as required, best-effort, coalescible, or request/response.
- For required variants, demand awaited send, durable pending delivery, or bounded retry.
- For intentionally lossy variants, require explicit drop classification plus observable accounting/coalescing.
- For request-bearing variants, require rejection/completion of the upstream obligation on every full/closed/drop path.
- Flag wildcard classification arms when enum growth can default new variants to lossy handling.

Why kda: it can relate protocol enums, producer/consumer call chains, and project-specific terminal semantics across crates.

Overlap check: accepted. rustc can enforce handling a `Result`; Clippy can flag some discarded results. Neither knows that a particular event variant is terminal, transcript-bearing, or owns a pending response. kda’s current `unbounded-channel` and producer-topology lints address memory/backpressure, not bounded-channel message loss.

- Extend lock identity/guard recognition to Tokio `MutexGuard`, owned guards, `RwLock` guards, and optionally semaphore permits.
- Treat an awaited lock acquisition while another async lock is live as a lock-order edge.
- Summarize helper methods interprocedurally.
- Canonicalize structural identities such as `Session.active_turn` and `ActiveTurn.turn_state`.
- Report only a proven cycle/SCC with two concrete opposing acquisition paths.

Why kda: its existing workspace lock graph is the right foundation; this is a semantic extension to the async primitives KD4 actually uses.

## 5. `repeatable-poll-side-effect` — detect unguarded resource creation on every `Future::poll`

KD4 has a production Windows example:

- `WinChild` has only `proc` and `job` state at `utils/pty/src/win/mod.rs:57-61`.
- Its `Future::poll` checks process completion at `:207-211`.
- Every pending poll clones the handle and creates a new OS thread at `:212-219`.
- Each thread blocks indefinitely in `WaitForSingleObject`, after which poll returns `Pending` at `:220`.

The Future contract permits repeated polling. Any extra poll before process exit creates another blocked OS thread because no state records that a waiter has already been installed. Repeated/spurious polling can therefore amplify one child wait into unbounded threads.

Analysis design:

- Analyze `Future::poll`, `Stream::poll_next`, and `poll_fn` bodies under implicit repeated invocation.
- On paths returning `Pending`, detect task/thread spawn, registration, durable mutation, I/O initiation, or other non-idempotent effects.
- Require a one-time state transition, stored waiter/handle, idempotent registration, or a bounded replacement protocol.
- Pair the finding with the `Pending` path and absent state guard.
- Optionally add a sibling check ensuring every `Pending` path arranges a wake.

Why kda: its effect summaries and CFG can model “poll may repeat” as an implicit loop, something ordinary source-loop analysis misses.

Overlap check: accepted. kda’s `unbounded-task-fanout` requires a syntactic enclosing loop (`src/async_topology.rs:85-89,420-430`), so it misses repetition caused by the Future protocol. Clippy’s `waker-clone-wake`, `future-not-send`, and `zombie-processes` do not detect spawn-on-each-poll resource amplification.
