## Overlap and disagreement

Three substantial overlaps should become shared analyzer families:

- **Lost-update analysis:** concurrent `ArcSwap` RMW and persistent SQL RMW share the same abstract obligation: a snapshot-derived write needs serialization, CAS/versioning, or a commutative merge.
- **Projection-relation analysis:** full-versus-delta context and canonical-versus-bounded tool output both require semantic source/field completeness across independently implemented projections.
- **Protocol-item conservation:** critical channel events and accepted agent input both need exactly-once transfer, explicit loss classification, and obligation resolution.
- **Capability coherence:** tool-name/exposure parity and prompt availability/revocation should share one capability manifest, while retaining separate diagnostics.

The disagreements are mainly about risk weighting:

- The compiler perspective preferred narrow but catastrophic memory-safety boundaries, even where current code appears correct.
- The concurrency perspective preferred temporal counterexamples and surfaced the two strongest probable current defects.
- The static-analysis perspective favored reusable relational analyses, accepting more configuration and implementation complexity.
- The agent-tooling perspective valued model-visible truth: a safe runtime is still incorrect if the model sees the wrong tools, loses input, or receives a misleading projection.

## Final ranked top 10

1. **`notify-state-check-order`** — likely finds a current missed-wakeup defect; precise and broadly reusable.
2. **`repeatable-poll-side-effect`** — likely finds current unbounded OS-thread amplification hidden by the `Future` protocol.
3. **Foreign-retained pointer lifetime** — protects a catastrophic, rustc-inexpressible Windows overlapped-I/O invariant.
4. **Unified RMW lost-update analysis** — merge ArcSwap and persistent whole-row cases under serialization/CAS/version proofs.
5. **Protocol-item conservation** — merge terminal channel delivery and accepted-input exactly-once handling.
6. **Relational projection completeness** — cover both full/delta context and canonical/model tool-output projections.
7. **Cross-route effect-policy equivalence** — ensure alternate tool routes cannot lose approval, sandbox, hooks, or cancellation semantics.
8. **Cross-resource failure atomicity** — expose partial commits across KD4’s multiple durability domains.
9. **Cache-key semantic completeness** — catch silent stale reuse when value dependencies outgrow manually maintained keys.
10. **Model-visible capability coherence** — detect transformed-name collisions and divergence among runtime registration, exposed specs, deferred activation, and prompt instructions.

Just below the cutoff: FFI out-parameter initialization, linear raw-handle ownership, cancellation-token lineage, async-signal safety, Tokio lock-order extension, and cross-`cfg` parity.

## Recommended additions

### 1. Semantic clone-family drift

Detect independently declared types or modules representing the same concept, even when they lack a direct `From` implementation or use different names.

KD4 examples:

- Nearly parallel JSON-RPC families in [app-server-protocol/src/rpc.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/rpc.rs:17) and [exec-server-protocol/src/rpc.rs](C:/Users/kuh/Desktop/kd4/codex-rs/exec-server-protocol/src/rpc.rs:16), plus another compatible `RequestId` in [protocol/src/mcp.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/mcp.rs:14).
- `SortDirection` is independently defined in the app-server protocol, thread store, state, and rollout crates.
- `ThreadSortKey` appears in three layers, while state calls the related concept `SortKey`.

The analyzer should cluster types by resolved field/variant shape, Serde representation, conversions, and common consumers. When one member changes, it should identify siblings whose variants, fields, defaults, wire names, or behavior no longer match.

Why growth matters: duplicated representations accumulate with every new transport and storage layer. Name-based search misses renamed equivalents, while ordinary type checking cannot relate independent types.

### 2. Implementation-cohort outliers

Compare implementations of the same trait as a family rather than checking each implementation in isolation.

Useful diagnostics would include:

- a defaulted trait method overridden by only part of an otherwise equivalent cohort;
- one tool implementation missing the lifecycle, approval, cancellation, accounting, or output-bounding effects common to its peers;
- one provider or filesystem implementation returning a weaker error/status classification;
- a new implementation registered correctly but behaviorally incomplete.

This is particularly relevant to KD4’s 45 `CoreToolRuntime` implementations and 53 `ToolExecutor` implementations. The existing [kda.toml](C:/Users/kuh/Desktop/kd4/codex-rs/kda.toml:1) proves registration, but registration does not prove behavioral parity.

Why growth matters: Rust catches missing required trait methods, but default methods and semantically optional behavior compile successfully. The probability of one outlier rises with the number of implementations.

### 3. Wrapper-envelope preservation

Build a semantic wrapper graph and verify that forwarding layers preserve the operation’s “envelope”:

- deadline and cancellation;
- trace and correlation identity;
- authentication/account scope;
- approval or permission context;
- retry classification and idempotency;
- redaction and error detail;
- request metadata and routing decisions.

KD4 has several deep wrapper stacks: shared HTTP clients and route-aware pools, generic `codex-api` endpoint clients, provider adapters, `ModelClient`, websocket paths, RMCP HTTP/OAuth adapters, and local-versus-remote app-server clients. Representative boundaries include [http-client/src/client.rs](C:/Users/kuh/Desktop/kd4/codex-rs/http-client/src/client.rs:25), [http-client/src/route_aware_client_pool.rs](C:/Users/kuh/Desktop/kd4/codex-rs/http-client/src/route_aware_client_pool.rs:50), and [core/src/client.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:1324).

KDA already has checks for individual properties such as deadline or trace loss. This addition would prove coverage across every method and bypass route in a wrapper family.

Why growth matters: a wrapper may be correct while one convenience method bypasses it. The number of possible bypasses grows with both chain depth and API surface.

### 4. Equivalent-entrypoint parity

Group entrypoints that expose the same underlying capability and compare their complete paths to the shared sink.

KD4 exposes behavior through the CLI, TUI, headless exec, app server, MCP server, code mode, extensions, and remote transports. A useful check would detect when one route has a different:

- feature or capability gate;
- approval/security guard;
- default value;
- request conversion;
- lifecycle event;
- persistence/update step;
- terminal error mapping.

The thread-listing path illustrates the shape: app-server types are manually converted into thread-store types, which are then converted again into rollout and state representations in [thread_processor.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/request_processors/thread_processor.rs:2247) and [list_threads.rs](C:/Users/kuh/Desktop/kd4/codex-rs/thread-store/src/local/list_threads.rs:299).

Why growth matters: each new frontend multiplies the routes to shared behavior. Local analysis can validate a route, but only a workspace graph can compare sibling routes and show the first semantic divergence.

### 5. Feature/configuration constraint graph

Model relationships among features, rather than only checking whether individual feature names are declared and consumed.

The feature registry already contains semantic relationships:

- `SpawnCsv` implies `Collab`.
- `CodeModeOnly` implies `CodeMode`.
- `UnifiedExecZshFork` is explicitly only a composition gate.
- cached web search has precedence over request web search.
- several browser capabilities are requirements-controlled rather than user-controlled.

The first two are normalized in [features/src/lib.rs](C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:554); the unified-exec composition semantics are implemented separately in [tools/src/tool_config.rs](C:/Users/kuh/Desktop/kd4/codex-rs/tools/src/tool_config.rs:61).

An analyzer addition should construct implications, exclusions, precedence, authority-source restrictions, and platform/model prerequisites. It could then report:

- a consumer assuming an implication that normalization does not establish;
- two equivalent consumers using different predicates;
- an impossible or behaviorally empty combination;
- a removed feature still influencing production behavior;
- a supported combination with neither a production path nor a test witness;
- replay/config-lock materialization that changes the effective relationship.

Why growth matters: risk grows combinatorially with the number of switches. Per-flag checks grow linearly and miss interactions.

### 6. Semantic dependency-boundary drift

Classify workspace dependency edges by their actual semantic role:

- public-signature exposure;
- runtime call;
- trait implementation;
- registration only;
- configuration only;
- test-only;
- feature- or platform-conditional.

Then enforce architectural direction and report new high-coupling edges, facade bypasses, or transitive leaks.

This matters in a graph where `codex-protocol` has 66 consumers, `codex-config` has 24, and `codex-core` itself depends on 66 internal crates. Cargo can show manifest edges, but it cannot explain whether an edge exposes a type publicly, calls runtime behavior, or exists only for tests.

Why growth matters: architecture erosion is rarely one obvious cycle. It happens through individually reasonable dependencies that gradually turn a low-level crate into a high-level coupling point.

### 7. General path-property contracts

Add a configurable interprocedural contract of the form:

> Every production path from sources S to sinks T must pass through semantic operation D and must preserve properties P.

Examples for KD4:

- every external request reaching model dispatch preserves trace and request identity;
- every privileged execution path is dominated by the effective approval/authority decision;
- every terminal response follows output drainage and state publication;
- every persisted mutation crosses the required durability barrier;
- every retry path preserves the original deadline and idempotency classification.

Diagnostics should include the shortest counterexample path and mark unresolved dynamic-dispatch or macro boundaries as unknown rather than safe.

Why growth matters: long call chains distribute one invariant across many owners. Each function can look locally correct while the composed path is wrong. This is the clearest area where a full-workspace semantic index has an advantage over Clippy, compiler checks, and editor navigation.

## Priority

I would prioritize them in this order:

1. Semantic clone-family drift.
2. Implementation-cohort outliers.
3. Equivalent-entrypoint parity.
4. Wrapper-envelope preservation.
5. Feature/configuration constraints.
6. General path-property contracts.
7. Semantic dependency-boundary drift.

The first three fit visible KD4 structure immediately and generalize several existing hand-written contracts. I would not prioritize more hard-coded registration checks: KDA already has strong registration, variant-flow, public-boundary, producer/consumer, feature-drift, and compatibility coverage. The next leverage comes from automatically discovering related families and comparing their behavior.

## 1. Sandbox requests carry parallel security representations

Risk: critical.

`SandboxExecRequest` carries both a command cwd and a sandbox-policy cwd, plus a `PermissionProfile` and derived filesystem/network policies. `SandboxTransformRequest` repeats much of that context in another form. See [manager.rs](C:/Users/kuh/Desktop/kd4/codex-rs/sandboxing/src/manager.rs:112) and the transformation logic at [manager.rs](C:/Users/kuh/Desktop/kd4/codex-rs/sandboxing/src/manager.rs:321).

The core-side wrapper adds another important distinction:

- `sandbox`: whether the host command is locally wrapped.
- `sandbox_requested`: whether the remote exec server should enforce a sandbox.
- `permissions`: host-materialized permissions.
- `exec_server_permissions`: canonical permissions from which the remote profile is derived.

That split is visible in [sandboxing.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/sandboxing.rs:429). Remote execution deliberately transforms a native command with `sandbox: None`, then attaches remote sandbox metadata only when `sandbox_requested` is true at [sandboxing.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/sandboxing.rs:489).

- Applying `additional_permissions` to one representation but not another.
- Sending a compatibility projection—potentially lossy, as shown in [manager.rs](C:/Users/kuh/Desktop/kd4/codex-rs/sandboxing/src/manager.rs:627)—to an enforcement sink.

- Reading `turn_context.environments` where the refreshed step environments are required.

## 3. Rollback-on-drop reservations require commit at exactly the right point

Risk: high.

Two different subsystems use the same transaction shape.

`TurnOriginReservation` inserts routing state immediately, removes it in `Drop`, and preserves it only when consuming `commit` is called: [thread_state.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/thread_state.rs:63). - Forgetting `commit`, causing successfully submitted work to lose routing or reserved capacity.

- every failure exit remains armed;

- Classifying a mutation as `GlobalSharedRead`.
- Extracting the wrong identity field, so operations on one thread/process do not serialize together.

- reads may use shared access;
- the key must originate from the same entity identifier used at state-access sinks;

## 7. `RolloutRecorder` has three different completion meanings

Risk: medium-high.

`RolloutRecorder` is cloneable and actor-backed [recorder.rs](C:/Users/kuh/Desktop/kd4/codex-rs/rollout/src/recorder.rs:89). Its operations mean different things:

- `record_canonical_items`: accepted into the actor queue [recorder.rs](C:/Users/kuh/Desktop/kd4/codex-rs/rollout/src/recorder.rs:877).

## Recommended analyzer features

I would prioritize these:

1. **Semantic-owner query**

   Given a type, trait method, constructor, or effect, rank candidate behavioral owners using:

   - trait declarations and implementations;
   - unique constructors/factories;
   - registration and dispatch;
   - production call dominance;
   - runtime consumers;
   - dependency direction;
   - values retained by long-lived types.

   The output should identify separate owners by concern, not declare one owner for an entire type.

2. **Required-mediation contracts**

   Require every production route to an effect or constructor to pass through named semantic callables, optionally in order. This handles shell execution and storage façade bypass.

3. **Trait-role/effect envelopes**

   Describe whether a trait is a producer, adapter, observer, policy authority, backend, or coordinator. Check implementation bodies and their transitive calls for permitted or forbidden effect families.

4. **Co-provenance constructor contracts**

   Require multiple constructor arguments to derive from the same resolution result, identity, epoch, or session event. This targets permission snapshots and similar proof-carrying aggregates.

5. **Lifetime and retention ownership**

   Infer session-, turn-, request-, and attempt-scoped types from constructors and runtime consumers. Flag longer-lived containers retaining narrower-scoped state.

6. **Generic-hub specialization detection**

   Flag concrete name/type/variant discrimination in registries, dispatchers, adapters, and planners when an existing registered implementation can own the branch.

For Codex, inferred ownership should initially be advisory: “the likely owner is X because it defines the trait, constructs the value, is registered at Y, and dominates effect Z.” Deny-level prevention should require a reviewed contract. Unique call structure is strong evidence, but not sufficient by itself to establish architectural authority.

## Ideal design

I would build six cooperating layers:

1. **Change discovery**

   Resolve the Git diff into changed functions, fields, variants, impls, manifests, configuration keys, generated inputs, and non-Rust contracts.

2. **Repository architecture closure**

   Consume `source_owners.toml` and `architecture_index.json` as authoritative routing data. Map each changed subject to owners, facets, incoming/outgoing relationships, generated outputs, invariants, tests, and validation commands. A changed known owner with incomplete routing should produce an unknown/deny result, not silently degrade.

3. **Compiler-backed semantic obligations**

   Use Cargo and rust-analyzer facts for identity, types, traits, cfg predicates, references, and call edges. Add narrow path/effect analysis for KD4’s dominant contracts:

   - lifecycle, cancellation, terminal delivery, and RAII;
   - wire/persistence conversions and legacy compatibility;
   - activation and execution-route parity;
   - authority, sandbox, path, and environment propagation;
   - context quantities, bounds, determinism, and telemetry noninterference.

4. **Profile-aware consequence analysis**

   Determine whether a change affects Windows, Unix, default features, all features, mutually exclusive feature combinations, tests, build scripts, schemas, SDKs, or installed Desktop behavior.

5. **Proof planning and admission**

   Select the smallest owning tests and generated checks, then admit their results only when receipts match the exact source snapshot, Cargo profile, command, working directory, architecture-index digest, and relevant dependency state. Exact test filters must prove that at least one test ran.

6. **Agent-facing evidence**

   Emit deterministic findings with a counterexample path, assumptions, unresolved boundaries, required next proof, source identity, and baseline status. Distinguish:

   - proved violation;
   - proved safe;
   - unknown requiring runtime proof;
   - advisory impact.

### 2. Commit-on-success, rollback-on-Drop guards

These are not ordinary “must discharge on every exit” resources.

- WFP [`Transaction`](</C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/wfp.rs:144>) explicitly aborts unless committed. Its production path commits only after all mutations succeed ([usage](</C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/wfp.rs:79>)).

2. `Session::send_event` is also persistence and state management.

3. `AppEventSender::send(UpdateFeatureFlags { … })` crosses into persistent configuration and potentially permission policy.

5. `FrameRequester::new(draw_tx)` creates a background actor.

6. `ToolEmitter::finish(...)` is not just result formatting.

   Required machinery: RAII typestate—`armed` versus `committed`—plus implicit drops on normal, error, cancellation, and unwind paths.

## How KDA could surface this

KDA already has useful foundations:

- [`EffectSummary`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/effects.rs:55) supports must/may effects, incompleteness, remapping, and cancellation sensitivity.
- The async index records direct spawns, channels, awaits, and token operations.
- Callable flow, value provenance, local CFGs, and the runtime activation graph already exist.
- Semantic queries already provide agent-oriented facts and paths.

The missing piece is composition. In this checkout, `EffectContracts` is not wired into the production analysis/query path, and `infer_local_wrapper` only composes a caller-supplied flat sequence. The async classifier intentionally recognizes direct runtime primitives, not wrappers—the test at [`async_relationships.rs:378`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/async_relationships.rs:378) explicitly rejects `my_spawn_helper`. Channel edges in the activation graph are largely inferred from method spelling and local receiver syntax, so payload dispatch through stored sender fields remains unresolved.

I would add an agent-facing `query effects` before adding a lint. Each fact should carry:

- `kind`: state-write, persist, spawn-task, spawn-thread, protocol-emit, cancel-signal, process-terminate, external-network, blocking-wait, suspend.
- `certainty`: must, may, or unknown.
- `phase`: inline, awaited, enqueued, background, callback, or on-drop.
- `condition`: enum variant, payload predicate, success/error path, or typestate.
- `strength`: attempted, best-effort, acknowledged, or durable.
- `completion`: what returning from the wrapper actually establishes.
- `target`: field, channel, process, endpoint, file/store, or protocol item.
- `provenance`: the complete call/channel/drop chain with source spans.
- `incomplete`: unresolved dynamic calls or aliases that prevent absence claims.

The semantic implementation would need:

1. Workspace-wide effect-summary fixed-point inference over resolved calls and recursive SCCs.
2. Variant- and payload-sensitive propagation through channels and match arms.
3. Alias flow connecting channel endpoints stored in structs or passed through wrappers.
4. Closure execution modeling for callbacks, UI actions, `get_or_init`, and spawned bodies.
5. Drop-aware CFG/ownership analysis with typestate transitions such as `armed → committed`.
6. A richer effect algebra than the current lifecycle-oriented `Acquire`, `Commit`, `Publish`, and related variants.
7. Query and diagnostic-metadata integration that reports only positive facts when analysis is incomplete.

I would avoid a general “harmless-looking wrapper” lint initially: harmlessness is naming-policy-dependent, and several examples are deliberately designed abstractions. Structured semantic facts would give a coding agent the important consequences without treating the wrappers themselves as defects.

## Bottom line

Freeze new leaf-lint development for now.

The analyzer has exceptional nominal breadth—257 documented lint entries across roughly 159K lines—but its portfolio is unbalanced:

- It is overinvested in registration, projection, enum, schema, and narrowly differentiated lifecycle rules.
- It is underinvested in the semantic machinery needed for KD4’s most serious failures: concurrent ordering, reused identity, cross-environment execution, and crash-consistent state.
- Many checks are different labels over the same shallow proof.
- The next additions should be capabilities that strengthen dozens of existing diagnostics, even if the visible lint count stays flat or decreases.

Recent KD4 fixes repeatedly involve generation-aware wakeups, stale process completion, watcher-registration races, independent-store notification, cancellation of non-cooperative work, durable authority, and bounded output. Examples are preserved in [task lifecycle tests](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod_tests.rs:382), [command execution tests](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/command_execution.rs:2077), [process watcher tests](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/async_watcher_tests.rs:27), and [cross-store wake tests](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/tests.rs:2497).

## Areas covered too heavily

1. **Registration and representation continuity**

   Registration, reverse wiring, capability closure, enum disposition, persistence continuity, adapter parity, generated artifacts, registry drift, projection drift, and producer/consumer checks form a dense cluster. These are valuable, but another variant would mostly re-detect the same omission through another representation.

2. **Lifecycle rule fragmentation**

   Owned lifecycle, lifecycle protocol, operation obligation, keyed obligation, keyed protocol, RAII transfer, transactional closure, terminal ordering, process retirement, and causal completion are separate analyses of acquisition, ownership, discharge, and publication.

   Lifecycle is not overimportant—KD4 proves that it is critical—but it is overfragmented. The portfolio has many lifecycle names without one sufficiently strong interprocedural lifecycle proof.

3. **Narrow historical KD4 checks**

   Exact guards for prior failures are useful regression tripwires. Continuing to encode each repaired bug as a bespoke lint will produce excellent coverage of yesterday’s defects and poor diversification against tomorrow’s.

4. **Analyzer meta-integrity and source-shape rules**

   Receipts, transition metadata, stale fixtures, test reachability, source registration, and architecture freshness are useful quality controls. They should not consume capacity that could address execution correctness.

## Important bug classes barely covered

- **True happens-before failures:** wake-before-subscribe, exit-before-watcher-registration, notification-before-visible-state, lock-domain splits, cancellation during ownership transfer, and ABA-style reuse of process IDs or generation keys.
- **Cross-process and crash consistency:** SQLite transactions, file replacement and `fsync`, rollout persistence, task-store commits, publication to another task, and recovery after failure between those operations.
- **Environment-qualified identity:** host path versus executor path, selected remote environment, native cwd, Windows versus POSIX shell semantics, sandbox target, and process namespace. The ongoing `PathUri` migration crosses protocol, app server, core execution, sandboxing, approvals, and tools; see [protocol.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:136), [exec.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/exec.rs:538), and [sandbox manager](C:/Users/kuh/Desktop/kd4/codex-rs/sandboxing/src/manager.rs:509).
- **Configuration-product behavior:** mutually exclusive features, target-specific code, test-only profiles, Windows/Unix differences, and build-script/generated behavior. A single resolved workspace profile cannot establish parity across these worlds.
- **Observed runtime behavior:** operating-system process behavior, scheduling, drain completion, notification delivery, and real timing. The analyzer already acknowledges these limits in [README.md](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:1184).

## Redundant analyses

The clearest candidates for consolidation are:

- `consumer-without-producer` with `consumed-but-never-produced`;
- `producer-without-consumer` with `produced-but-never-consumed`;
- registration, production wiring, reverse wiring, capability closure, and activation reachability;
- the shared-enum disposition, persistence, mapping, registry, and projection families;
- owned lifecycle, operation obligation, keyed obligation, protocol, RAII, and transaction closure;
- cache-key, freshness, correlation, causal identity, dependency identity, snapshot continuity, and execution provenance.

The user-facing diagnostics may remain distinct. The redundant part is independently reconstructing call flow, identity, ownership, and effects for each one.

## Missing semantic foundation

The analyzer is moving in the right direction: it declares shared control-flow, provenance, resource, async, typestate, and predicate inputs in [analyzer_plan.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analyzer_plan.rs:21).

But the common effect model remains small and local. It currently represents eight effect kinds, must/may sets, cancellation classification, and local wrapper summaries; unresolved calls make a summary incomplete ([effects.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/effects.rs:22), [effects.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/effects.rs:241)). It does not yet provide a dependable model of:

- aliases and partial moves;
- closure capture and dynamic dispatch;
- spawned-task ownership;
- happens-before edges;
- process and watcher generations;
- persistent transaction boundaries;
- execution-domain-qualified identity;
- crash and replay states.

That shared model—not another pattern recognizer—is the missing foundation.
