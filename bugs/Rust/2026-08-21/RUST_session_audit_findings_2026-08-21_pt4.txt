## Strongest candidate: the managed async component

KD4 repeatedly treats a collection of Rust values as one logical runtime component:

> an owner or registry entry + one or more tasks + command/event channels + a stop mechanism + a completion boundary.

KDA models each ingredient, but not their membership in the same component instance. This is more than an ordinary task lifecycle: the logical component may have several tasks, expose a façade, live in a keyed registry, be replaced, and become unusable or quiescent as a unit.

### Recurring KD4 locations

These are occurrences of the concept, not claims that each contains a bug.

- [ModelsRefreshWorker](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/models_refresh_worker.rs:13) bundles a cancellation token and retained `JoinHandle`; construction spawns a periodic loop, while shutdown and `Drop` signal cancellation.

- [FsWatchManager](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/fs_watch.rs:31) represents every `(connection_id, watch_id)` as a registry entry, registration guards, a spawned notification loop, and a termination handshake. Its `unwatch` method explicitly promises quiescence—no notification after the response—by waiting for the task to destroy a completion sender at [line 162](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/fs_watch.rs:162).

- [ConversationState](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/realtime_conversation.rs:248) is a replaceable realtime component containing input channels, primary and fanout tasks, an active marker, handoff state, and a stop token. Replacement stops the preceding instance at [line 305](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/realtime_conversation.rs:305), while late fanout registration is admitted only if it still belongs to the active instance at [line 434](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/realtime_conversation.rs:434).

- [CommandExecManager](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/command_exec.rs:56) treats each connection/process key as one component: registry membership, control and stdin channels, a child process, a coordinator task, stdout/stderr tasks, a delivery relay, and eventual registry removal. - [CodeModeDispatchWorker](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/code_mode/delegate.rs:465) is the lifetime handle for a spawned dispatcher created at [start_turn_worker](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/code_mode/delegate.rs:140). These subsystems are otherwise unrelated: model refresh, filesystem subscriptions, realtime audio, process execution, and nested tool dispatch.

### What KDA currently loses

KDA already extracts high-quality atomic facts:

- `TaskSpawn` knows a body, handle state, and optional structured owner.
- `ChannelRelationship` knows its sender and receiver.
- `CancellationRelationship` knows token creation, triggering, and observation.
- `AsyncRelationshipIndex` stores those as separate collections in [async_relationships.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/async_relationships.rs:88).
- `owned_lifecycle` checks locally retained handles beginning from `let` bindings and their enclosing lexical scope in [owned_lifecycle.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/owned_lifecycle.rs:27).
- Keyed protocols model registry entries as obligations, while deadline and terminal-order passes model other individual dimensions.

What disappears is:

- Which façade, registry entry, task, channels, token, and external resource are members of the same logical instance.
- Which task is the primary run loop and which tasks are dependents that must stop with it.
- Whether an action merely requests shutdown or proves that the component is quiescent.
- Which key or generation makes late work belong to the current instance.
- Whether the public façade remains usable after the run task fails.
- Whether removal from a registry means “stop requested,” “no longer addressable,” or “fully finished.”

Each primitive can therefore look locally correct while the component-wide contract is incomplete.

## Minimum semantic representation

This should be a small relational layer over existing facts, not a second async graph:

```text
ManagedComponentInstance
  id
  anchor                 // constructor, returned façade, field, or registry entry
  instance_key?          // registry key, generation token, or identity witness
  parent?                // optional component for cascade ownership

ComponentMember
  component
  entity                 // reference to an existing task/channel/token/resource fact
  role                   // owner, primary_task, dependent_task, ingress,
                         // output, stop_signal, completion_signal

ComponentTransition
  component
  kind                   // publish, request_stop, quiesce, retire, replace
  site
```

The essential new information is the `component ↔ member` relation. Everything else should reuse KDA’s existing task, channel, cancellation, resource, CFG, provenance, and keyed-identity facts.

High-confidence discovery could require a strong anchor, such as:

- a constructor returning a struct that retains a spawn handle or stop endpoint;
- a spawn closure consuming one channel end while the returned façade retains the other;
- a keyed registry entry sharing its key with a spawned coordinator;
- a shutdown method that signals members and joins or acknowledges completion;
- an explicit project contract where helper abstraction prevents structural inference.

A component would need at least an owner/addressability anchor, background execution, and a control or completion relationship. A bare spawned future would not qualify.

## Analyses this representation enables

1. **Stop request without quiescence**

   Diagnose an async `shutdown`, `unwatch`, or replacement path that promises completion but only cancels or sends a stop message without joining the primary task or observing a completion acknowledgement.

2. **Incomplete cascading shutdown**

   Detect a component whose primary task stops while dependent tasks, output relays, sideband tasks, or child processes remain live. This is particularly relevant to the realtime and command-exec shapes.

3. **Stale-instance publication**

   Detect a task from an old component instance that can register itself, publish an event, remove a registry entry, or mutate shared state after replacement without checking the instance key or generation. The `Arc::ptr_eq` checks in realtime become recognizable semantic witnesses rather than incidental pointer comparisons.

4. **Addressability/liveness drift**

   Report a façade or registry entry that remains available after its primary task can terminate unexpectedly, or an entry that is removed while senders and externally reachable handles can still accept work.

5. **Orphaned component**

   Distinguish an intentional, durably owned background service from a task whose only component owner is lost. This is more precise than treating every non-awaited spawn as suspicious.

6. **Incorrect retirement of a keyed instance**

   Detect cleanup that removes an entry by key without proving it is removing the same generation that spawned the cleanup task. Conversely, detect failure paths that leave an addressable entry for a component that never started.

7. **Readiness and publication ordering**

   Where a readiness contract exists, check that the façade or registry entry is not published before the primary task reaches readiness, and that startup failure is reflected back into component state.

### Why these checks are difficult without the abstraction

Without component identity, KDA must approximate using names and local syntax:

- Cancellation does not prove termination.
- Awaiting one handle does not prove that subordinate tasks are finished.
- A detached spawn may be an intentional service or an accidental orphan.
- Map removal may be correct cleanup or a stale task deleting its successor.
- A oneshot may carry a result, request cancellation, or act as a quiescence acknowledgement.
- A channel sender surviving shutdown may be a harmless clone or the component’s still-public API.

The missing membership and role information is what turns those ambiguous constructs into high-confidence relationships.

## Where the abstraction should stop

This should not become actor-model verification or general temporal analysis.

- Use a fixed lifecycle vocabulary: published, stop requested, quiescent, retired, replaced.
- Do not infer arbitrary business states from enums, booleans, or message payloads.
- Do not simulate Tokio scheduling or task interleavings.
- Do not prove arbitrary message ordering or protocol correctness.
- Follow workspace-local, statically traceable construction and ownership only.
- Treat dynamic dispatch, externally spawned work, and ambiguous membership as unknown.
- Require explicit contracts for strong promises such as readiness or “no output after shutdown.”
- Model dependent tasks only when ownership is structurally evident—spawned inside the primary task, stored in the same state object, or explicitly registered.

That keeps the model at the same bounded semantic level as KDA’s existing async relationship graph.

## Runner-up 1: time-bounded validity lease

This is not the acquire/release resource notion KDA already recognizes. It is a relationship among a subject, holder or generation, expiry, renewal, and revocation.

Examples include:

- Detached exec sessions retain a reconnectable attachment until a TTL expires, and the expiry task verifies the original connection identity before shutdown in [session_registry.rs](C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/server/session_registry.rs:132).
- Focused validation calls expose a lease expiry and support heartbeat renewal in [task_coordinator.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/task_coordinator.rs:52).
- Connector cache entries combine an identity key, payload, and validity deadline in [connectors.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/connectors.rs:55).

KDA’s deadline model concerns one operation budget, while resource obligations concern eventual release. Neither explicitly represents renewable or identity-scoped validity. Such a model could find use after expiry, stale expiry jobs revoking renewed state, renewal without durable update, and revocation of the wrong holder. It ranks second because “lease” conventions vary substantially and would likely need more contracts.

## Runner-up 2: observable state projection

KD4 often maintains authoritative facts, derives a public status, stores the latest projection, and emits only meaningful changes:

- `RuntimeFacts` is reduced into `ThreadStatus` in [thread_status.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/thread_status.rs:420).
- Remote control maintains a watch-backed current status and publishes field-preserving changes in [websocket.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-transport/src/transport/remote_control/websocket.rs:317).

KDA models record projections, monotonic state, notification ordering, and status-family parity separately, but not the higher-level relationship:

```text
authoritative facts → canonical reducer → current snapshot → change stream
```

That representation could detect mutations that fail to republish, initial-snapshot/update disagreement, partial updates that erase unrelated dimensions, incorrect change suppression, and multiple drifting reducers. It ranks below managed components because discovering the authoritative fact set and canonical reducer is more domain-dependent.

### 1. Typed-store key and scope integrity

`ExtensionData` is a `TypeId → Arc<dyn Any>` map. Its generic parameter is effectively a runtime key, while session, thread, and turn stores all have the same Rust type: [`state.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/ext/extension-api/src/state.rs:8).

Concrete contracts include:

- Core inserts `McpResourceClient`; the skills extension retrieves that exact type.
- Turn setup inserts `HostSkillsSnapshot`; consumers expect it specifically from the turn store.
- Types such as `SkillsThreadState`, `GoalRuntimeHandle`, and `Vec<SelectedCapabilityRoot>` act as implicit cross-crate registry keys.
- Contributor inputs contain `session_store`, `thread_store`, and `turn_store`, all typed `&ExtensionData`: [`contributors.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/ext/extension-api/src/contributors.rs:82).

Proposed analysis:

- Index operations by `(scope role, resolved generic argument)`.
- Report a production `get::<T>` or `remove::<T>` with no reachable producer in that role.
- Report producer/consumer role disagreements.
- Report multiple independent producers of the same `T` in the same role when insertion silently replaces an earlier value.
- Detect session/thread/turn store permutations at struct construction and forwarding boundaries.

The relationship should be inferred from generic type identity and store provenance. Parameter names can support confidence but should not define the rule.

This is distinct from KDA’s current [`scope_identity.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/scope_identity.rs:1), which checks whether a context mints or preserves `ExtensionData`; it does not model the contents of the typemap or distinguish same-typed store roles.

### 2. Production lowering for representation relations

KD4 has extensive paired runtime/wire types in [`payload.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/code-mode-protocol/src/host/payload.rs:19):

- `CellId ↔ WireCellId`
- `ToolName ↔ WireToolName`
- `ToolKind ↔ WireToolKind`
- `ToolDefinition ↔ WireToolDefinition`
- `ExecuteRequest ↔ WireExecuteRequest`
- Corresponding response, content, wait, and nested-call types

`ExecuteRequest` is particularly useful: runtime `Option<usize>` becomes wire `Option<i32>`, and both directions use checked conversions. Merely knowing that `From` or `TryFrom` was called misses the important property: the two entire transformations are intended to compose correctly over a bounded domain.

KDA already has the right proof substrate in [`relational_adt.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/relational_adt.rs:1), but its own documentation describes it as waiting for HIR lowering.

The addition should therefore be production lowering, not another proof engine:

- Discover reciprocal `From`/`TryFrom` implementations.
- Normalize enum cases, struct fields, field provenance, and fallibility.
- Feed them into `RelationalAdtIndex`.
- Check round-trip variant and field preservation.
- Detect changed fallibility or replacement of checked narrowing with casts.
- Treat guards, opaque helpers, and mutation as unknown rather than guessing.

A related target is the core `AgentStatus` enum in [`protocol.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:1787) projected into the independently deserializable `CollabAgentState` struct in [`item.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/item.rs:1181). The conversion establishes correlations between `status`, `message`, and `surfaced_result`, but the target product type admits combinations that no source enum variant produces. A `representation-image-gap` diagnostic could report that expanded state space unless a validator or explicit compatibility annotation accepts it.

### 3. Erased semantic-domain collision

Rollout trace declares numerous semantically distinct identifiers as aliases of `String`: [`model/mod.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/rollout-trace/src/model/mod.rs:22).

Examples include:

- `AgentThreadId`
- `CodexTurnId`
- `ConversationItemId`
- `InferenceCallId`
- `ToolCallId`
- `CodeCellId`
- `TerminalId`
- `CompactionId`
- `EdgeId`
- `CorrelationId`

They occur together as map keys and references within one graph, yet Rust permits all of them to be interchanged. Some APIs widen this further through `impl Into<Alias>`.

There is also a sharper cross-representation example: protocol `AgentPath` is a validated newtype with fallible string construction in [`agent_path.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/agent_path.rs:15), while rollout trace redeclares `AgentPath = String`.

An `erased-semantic-domain` analysis should not simply ban aliases. It could infer likely distinct domains when:

- Separate aliases over the same primitive coexist as keys and references in one aggregate graph.
- They occupy different ends of foreign-key-like relationships.
- Values cross from a validated nominal wrapper into a primitive representation.
- A function can accept multiple erased domains through the same broad conversion bound.

Diagnostics should identify the domain family and the unsafe interchange point, not complain at every alias declaration.

### 4. Owner-bound capability tokens

The readiness crate defines `Token(i32)` as `Copy`, while every `ReadinessFlag` starts its own token counter at one: [`lib.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/readiness/src/lib.rs:16).

Consequently:

1. The first subscription to flags A and B can both return `Token(1)`.
2. Passing A’s token to `B.mark_ready` removes B’s subscription.
3. The type contains no owner identity, lifetime, or brand that distinguishes the two authorities.

This is a concrete correctness defect, although current production use of the utility appears limited.

An `unbound-capability-token` analysis could infer:

- A token is minted through `&self`.
- It is registered in per-instance state.
- Another `&self` method consumes it as authority.
- Equality depends only on token-local data that can collide between owner instances.
- The token carries no owner key, borrow, brand parameter, or owner-bound wrapper.

That analysis is fundamentally about the relationship between an ownership-bearing object and its capability type.

### 5. Ambient guard ownership

`AbsolutePathBufGuard` establishes thread-local deserialization context, but it is a public unit struct: [`lib.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/absolute-path/src/lib.rs:327).

Its constructor installs a base path, while `Drop` always resets the thread-local state to `None`. Because the guard stores neither the installed value nor the previous value:

- External code can construct and drop the unit struct without acquiring the state, clearing another active guard.
- Nested guards do not restore the outer base; dropping the inner guard leaves no base at all.

This guard protects many configuration and tool-argument deserialization paths, so the relationship is operationally important.

A `forgeable-ambient-guard` or `ambient-guard-without-owned-state` analysis could report a `Drop` type when:

- Construction mutates parameterized ambient state.
- The guard stores no acquisition identity or prior-state token.
- It is externally constructible independently of acquisition.
- Drop unconditionally clears shared state.

A companion containment analysis could compute which `Deserialize` targets transitively contain `AbsolutePathBuf`, then require an active compatible context at generic deserialization boundaries. That depends on what the target type contains, not which parser function happens to be called.

### 6. Generic parameters as representation stages

Several permission types use their generic parameter to distinguish runtime paths from portable protocol paths:

- `PermissionProfile<PathType = AbsolutePathBuf>`
- `FileSystemPermissions<PathType>`
- `ManagedFileSystemPermissions<PathType>`

These are defined with paired `AbsolutePathBuf ↔ PathUri` conversions in [`models.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/models.rs:69). `FileSystemSandboxContext` deliberately stores `PermissionProfile<PathUri>` for serialization and converts back before execution: [`file-system/lib.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/file-system/src/lib.rs:138).

A `representation-instantiation-leak` analysis could infer that `Family<A>` and `Family<B>` represent different stages from:

- Reciprocal conversions between instantiations.
- One instantiation appearing in serialization or protocol types.
- The other appearing at host execution and filesystem boundaries.
- Fallible materialization at the boundary.

It could then flag:

- Persisted or public types accidentally relying on the default runtime instantiation.
- Execution code using the portable instantiation without successful materialization.
- Nested fields whose instantiation disagrees with their enclosing representation.

This should be inferred per generic family; it should not hardcode `PathUri` or `AbsolutePathBuf`.

### 7. Persisted projections and sentinel collisions

`ThreadMetadata` is a typed runtime model, while `ThreadRow` is a database representation using strings and integers: [`thread_metadata.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/state/src/model/thread_metadata.rs:80).

The write/read relationship is intentionally not fieldwise:

- `first_user_message: None` and `Some("")` are both persisted as `""`, then read back as `None`.
- A missing preview can be populated from `first_user_message` before persistence.
- Therefore the database `preview` column is partly a derived projection, not a round-trip mirror of the runtime field.

The writes are visible in [`threads.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/state/src/runtime/threads.rs:639).

A `persisted-projection-noninjective` analysis could:

- Relate row extraction, domain conversion, and SQL bind expressions.
- Detect sentinel collisions such as `None` versus `Some(default)`.
- Detect persisted fields derived from multiple runtime fields.
- Distinguish accepted normalization from accidental information loss using annotations or round-trip tests.
- Check enum/string mappings without assuming the runtime and row structures must have identical fields.

This complements schema-compatibility checks: the schema may remain perfectly compatible while the semantic projection becomes more lossy.

## Lower-priority possibilities

I would not prioritize ordinary trait or generic-implementor coherence. Relationships such as `ToolExecutor<Invocation>` and `AgentSpawner<R>` retain their type parameters and associated types, so the compiler already protects most substitutions.

Likewise, `ThreadId` and `SessionId` have reciprocal wrapper conversions. An equivalence-class check could detect future validation or serde drift between them, but there is no current mismatch and its expected yield is lower than the cases above.

My suggested implementation order would be typed-store integrity, relational-ADT lowering, semantic-domain erasure, then the two ownership analyses. Those combine broad architectural coverage with several findings that can be demonstrated against KD4 today.

### 1. Treat `Command::pre_exec` as a transitive post-`fork` safety boundary — P0

Rust requires extreme care in `pre_exec`: the closure runs after `fork`, where allocation, locking, environment access, and many library operations may be unsafe. The obligation applies to every transitively called function, not just the closure body. [Rust documents these restrictions explicitly.](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html#method.pre_exec)

Repository evidence:

- [`pty.rs`](C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/pty.rs:315) installs a `pre_exec` closure that calls `close_inherited_fds_except`.
- That helper uses `std::fs::read_dir`, creates a `Vec`, converts names to strings, and parses them in [`pty.rs`](C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/pty.rs:548).
- [`pipe.rs`](C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/pipe.rs:178) calls the same helper from another `pre_exec`.
- In contrast, other KD4 sites keep their closures syscall-shaped—for example `setsid()` in [`pid.rs`](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-daemon/src/backend/pid.rs:173).

This deserves immediate manual review: the high-level filesystem and allocation work in `close_inherited_fds_except` is precisely the kind of transitive operation that `pre_exec` makes dangerous.

Analyzer encoding:

- Make every `pre_exec` closure a semantic signal-safety root.
- Compute its transitive call closure.
- Allow known syscall-only operations and explicitly audited helpers.
- Flag allocation, formatting, locks, environment access, high-level filesystem APIs, unwinding, and unresolved calls.
- Require an annotation or configuration entry for audited wrappers instead of trusting an `unsafe` block or comment.

Your [`signal_safety.rs`](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/signal_safety.rs:1) already contains much of the needed transitive machinery, but it currently targets registered signal handlers rather than `pre_exec`.

## 4. Counted buffers need pointer/length/layout coherence

A notable locally unproven case is [`windows-sandbox-rs/src/token.rs:206`](/C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/token.rs:206).

**Unsafe operation:** Reading `group_count`, aligning a pointer to a trailing `SID_AND_ATTRIBUTES` array, and iterating `0..group_count` with pointer arithmetic.

**Safety assumption:** The returned buffer contains:

```text
aligned header offset + group_count * element size <= initialized buffer length
```

with valid alignment and no arithmetic overflow.

**Semantic evidence:** KD4 has `needed`, the allocated buffer length, the count, alignment calculation, and element size. It checks only a small minimum size; it does not locally prove that the count-derived traversal remains inside the buffer. Validity is therefore inherited from the Windows API contract.

A related case is [`windows-sandbox-rs/src/dpapi.rs:44`](/C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/dpapi.rs:44), where `from_raw_parts(out_blob.pbData, cbData)` relies on the API guaranteeing an acceptable non-null pointer on success. Rust requires a non-null aligned pointer even for a zero-length slice.

**General lint:** Yes—high value. For raw slices and count-derived pointer traversal, require dominating proofs for non-nullness, checked arithmetic, alignment, and allocation extent. Foreign metadata may discharge a condition that is guaranteed by the API; otherwise the proof should be visible in Rust.

## 5. Foreign resource ownership is a linear contract

KD4 uses many ownership families:

- `HANDLE` / `CloseHandle`
- `LocalAlloc` / `LocalFree`
- `GlobalAlloc` / `GlobalFree`
- `CoTaskMem` / `CoTaskMemFree`
- Core Foundation create/get ownership rules
- raw file descriptors / `OwnedFd` / `File::from_raw_fd`

Most RAII wrappers encode these contracts well. For example, [`http-client/src/outbound_proxy/windows.rs:241`](/C:/Users/kuh/Desktop/kd4/codex-rs/http-client/src/outbound_proxy/windows.rs:241) pairs an owned global string with `GlobalFree`, although its safe raw constructor still has the boundary problem described above.

There are concrete leak paths in [`windows-sandbox-rs/src/bin/setup_main/win.rs:532`](/C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/bin/setup_main/win.rs:532):

- SIDs allocated for users/authenticated users/everyone can be bypassed by `?` before cleanup.
- `sandbox_group_psid`, allocated around [`win.rs:777`](/C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/bin/setup_main/win.rs:777), has numerous error exits before its eventual `LocalFree`.
- The same pattern affects `root_cap_psid`, `deny_psid`, and partially constructed vectors of SIDs.

These are resource leaks, not necessarily immediate memory-safety bugs, but they violate exactly the ownership assumptions surrounding the unsafe allocation.

**General lint:** Yes. Model resources with semantic contracts:

- producer and invalid sentinel;
- allocator/releaser family;
- borrowed versus transferred ownership;
- terminal operation;
- destructor-backed adoption.

Then perform path-sensitive linearity analysis for leaks, double release, use after transfer, and allocator mismatch. Rust’s standard raw-owner conversions can be recognized by resolved definitions; foreign pairs require declarative binding metadata. Function-name conventions such as `Create*`/`Close*` are insufficient.

## 6. Foreign-retained pointers and asynchronous I/O

[`tui/src/ide_context/windows_pipe.rs:120`](/C:/Users/kuh/Desktop/kd4/codex-rs/tui/src/ide_context/windows_pipe.rs:120) is a strong positive example.

**Unsafe operation:** `ReadFile` and `WriteFile` receive buffer and `OVERLAPPED` pointers that may remain in use after the function returns. Later code uses `Pin::into_inner_unchecked` and an unsafe `Send` implementation.

**Safety assumption:** The operation state and buffer remain at stable addresses until terminal completion; neither is reallocated or dropped during cancellation; ownership moves to a reaper when completion is uncertain.

**Semantic evidence:** `OverlappedOperation` owns the buffer, `OVERLAPPED`, event, handle and permit; it is heap-pinned; the buffer is not resized; and ambiguous cancellation retains the allocation until the operation becomes terminal.

Other good encodings include:

- [`windows-sandbox-rs/src/proc_thread_attr.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/windows-sandbox-rs/src/proc_thread_attr.rs), whose retained handle/job arrays outlive the foreign attribute list.

**General lint:** Yes, provided FFI metadata marks a pointer as retained until completion, unregister, or another terminal operation. The analyzer can then verify stable ownership, absence of reallocating mutation, lifetime of associated handles, and terminalization or explicit ownership transfer on every path.

## 7. Callback context lifetime and aliasing

[`http-client/src/outbound_proxy/macos.rs:253`](/C:/Users/kuh/Desktop/kd4/codex-rs/http-client/src/outbound_proxy/macos.rs:253) passes a stack `PacRunLoopState` through an untyped Core Foundation callback context.

**Unsafe operation:** The callback casts the client pointer back to `&mut PacRunLoopState`.

**Safety assumption:** The pointer remains live and correctly typed, the callback is serialized sufficiently for an exclusive borrow, and no callback occurs after the state leaves scope.

**Semantic evidence:** Registration, synchronous run-loop execution, timeout invalidation, and source removal all occur within the state’s lexical lifetime. The missing part is the external guarantee about when Core Foundation has stopped retaining or invoking the callback.

**General lint:** Yes, as another retained-borrow contract. Registration creates a foreign loan; synchronous completion, unregister, removal, or join terminates it. The analyzer can check owner lifetime and exclusivity once those foreign lifecycle effects are represented semantically.

Positive examples include:

**General lint:** Yes. Model relationships of the form “tag of place `p` equals variant `T`” and require that fact to dominate a cast/projection of `p` as `T`. `ioctl` request-to-union-field relationships would need binding metadata.

Unsafe environment mutation appears in:

## 11. Required FFI structure headers

Several Windows calls initialize fields such as `cb`, `dwOSVersionInfoSize`, or `nLength` from `size_of::<T>()` before passing a structure to FFI, for example [`utils/pty/src/win/psuedocon.rs:111`](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/pty/src/win/psuedocon.rs:111).

**Safety assumption:** The structure’s size/version header exactly matches the layout expected by the callee.

**Semantic evidence:** A dominating assignment from `size_of::<the same type>()` with no intervening mutation.

**General lint:** Useful only with foreign-signature metadata declaring the required field and value. Matching field names such as `cb` or `dwSize` would be too brittle.

## Rules I would reject

I would not add:

- A generic warning for every unsafe block, FFI call, `zeroed`, or raw pointer.
- Function-name inference such as `Create*` owns and `Close*` releases.
- KD4-specific file, crate, function, or API allowlists.
- Textual searches for size checks, safety comments, `#[serial]`, or `Pending` markers.
- A hand-maintained whitelist of signal-safe call names.
- A blanket prohibition on unsafe `Send`/`Sync`.
- A special lint for `mem::zeroed` on FFI structures; Rust bit-validity and required foreign header fields are separate questions.
