## Findings

1. High — `IntegrationPlan` is computed but never affects launch behavior.

Admission returns `SingleWriter`, `RootOwned`, or `TypedIntegratorRequired` in [model.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/model.rs:213). The producer in [local.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/local.rs:6110) only:

- Counts whether any active writer exists.
- Does not compare candidate and existing write scopes.
- Does not compare contract claims for ordinary workers.

The spawning consumer records overlap telemetry, then extracts only `assignment` and `attempt`; it never reads the typed integration plan ([spawn.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs:394)). Consequently, all three plans launch identically. `TypedIntegratorRequired` neither creates nor routes work to an integrator.

Whole-repository uses of `.integration_plan` are test assertions such as [tests.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/tests.rs:913); production otherwise retains it only in an admission observation string. 2. Medium — duplicate-explorer detection rejects work but cannot reuse the existing result.

The explorer contract explicitly says “Reuse existing explorers” in [role.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/role.rs:390). Admission hashes an explorer’s scope, claims, objective, and criteria in [model.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/model.rs:380), then rejects an exact active duplicate in [local.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/local.rs:6154).

3. Medium — parent completion notifications can disagree with the durable receipt.

Receipt submission maps `NeedsMain`, `Blocked`, and `Failed` to durable `AttemptState::NeedsMain` ([model.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/model.rs:894), [local.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/local.rs:1797)).

V2 parent notification, however:

- Derives status from the runtime `TurnComplete` event.
- Seals a receipt only if one is missing.
- Does not hydrate an already submitted receipt before formatting the parent result.

See [session/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:2181) and [status.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/status.rs:6). Thus an agent may submit a `NeedsMain` receipt, finish its turn normally, and send the parent a `FINAL_ANSWER` based on `AgentStatus::Completed`, while durable state says `NeedsMain`.

Existing tests cover completion-gate preservation and missing-receipt sealing, but not an existing non-success receipt overriding the runtime completion envelope.

4. Medium — wait terminality ignores pending gates that the completion system considers unresolved.

Task hydration explicitly computes `pending_gates` and `next_required_action = "resolve pending gates before completion"` in [local.rs](C:/Users/kuh/Desktop/kd4/codex-rs/agent-task-store/src/local.rs:713). I found five reverse-wiring gaps in the current `codex-rs` working tree.

1. **High — Durable terminal receipts can remain permanently pending after a CLI/TUI restart.**

   The terminal decision is committed to the evidence ledger before its rollout event is appended ([tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1487), [tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1552)). A crash between those operations leaves an authoritative receipt whose rollout, notification, and cleanup flags are still false ([task_evidence.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/task_evidence.rs:3720)).

   Restart recovery sees the authoritative event and returns immediately instead of completing those pending effects ([tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:2236)). The correct replay routine exists—it mirrors the rollout, notifies the parent, releases the interaction, and persists recovery ([tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:2113))—but its only caller is gated on attaching an app-server client ([codex_thread.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/codex_thread.rs:409)). CLI/TUI resumes therefore never converge this crash state.

   Effect: the resumed rollout can retain an open turn while the ledger permanently reports pending delivery/cleanup.

2. **High — Memory phase 2 accepts `Partial` and `Blocked` completion as success and deletes the retryable workspace.**

   `AgentStatus::TerminalWithCompletion` correctly retains the completion gate ([protocol.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:1811)), whose valid statuses are `Passed`, `Partial`, and `Blocked` ([protocol.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:3320)). Error-free partial completion is explicitly legal ([protocol.rs](C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/protocol.rs:6120)), and rollout recovery recognizes only `Passed` as a passed completion boundary ([rollout_reconstruction.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/rollout_reconstruction.rs:275)).

   Memory phase 2 instead treats every `TerminalWithCompletion { error: None, .. }` as successful without inspecting `completion.status` ([phase2.rs](C:/Users/kuh/Desktop/kd4/codex-rs/memories/write/src/phase2.rs:391)). It then resets the memory-workspace baseline and marks the job successful ([phase2.rs](C:/Users/kuh/Desktop/kd4/codex-rs/memories/write/src/phase2.rs:430)).

   Effect: incomplete or blocked consolidation advances as successful and its generated diff is destroyed, preventing a faithful retry.

3. **High — Remote user-shell read failures lose the only cleanup handle without terminating the process.**

   Cancellation and timeout explicitly terminate a started remote process ([user_shell.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/user_shell.rs:483)), but a `read()` error or `ReadResponse.failure` returns directly from collection without termination ([user_shell.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/user_shell.rs:496)).

A disconnected server session deliberately retains its process for a 30-second resume window before shutdown ([session_registry.rs](C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/server/session_registry.rs:20), [session_registry.rs](C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/server/session_registry.rs:132)).

   Effect: after the tool reports failure, a side-effecting command can continue remotely until session expiry.

4. **Medium — App-server collaboration projections discard the new completion gate.**

   Core produces `TerminalWithCompletion` with the full gate ([status.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/status.rs:9)). The v2 projection ignores that field and maps every error-free terminal status—including `Partial` and `Blocked`—to plain `CollabAgentStatus::Completed` ([item.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/v2/item.rs:1236)).

Existing coverage tests interrupted tools and failed turns separately, but not a failed turn with an active tool ([analytics_client_tests.rs](C:/Users/kuh/Desktop/kd4/codex-rs/analytics/src/analytics_client_tests.rs:2515), [analytics_client_tests.rs](C:/Users/kuh/Desktop/kd4/codex-rs/analytics/src/analytics_client_tests.rs:5036)).

## Conclusion

Yes—cargo-kda could detect meaningful semantic drift between independently valid Rust implementations. KD4 contains several strong candidates.

The right abstraction is not “duplicated code detection,” but comparison of normalized semantic summaries under a declared relation:

- equivalence: both routes expose the same result;
- refinement: recovery preserves mandatory guarantees while using conservative values;
- round trip: `decode(encode(x)) ≡ x` modulo normalization;
- commuting classification: two conversion paths assign the same semantic class;
- capability parity: platform or backend implementations provide the same required capabilities.

Most cases can be checked structurally using finite decision tables, field provenance, must-effects, partial ordering, and abstract state transitions. Full path enumeration would usually be unnecessary and undesirable.

I found no basis for calling the current differences bugs; several are clearly intentional asymmetries that the analysis would need to model explicitly.

## Smallest useful analysis

Use one protocol-driven, finite-state analysis over the existing local CFG and place identities.

An obligation instance needs only:

```text
(specification, abstract identity, current owner, state, aggregate parent/key?)
```

Minimum common states:

```text
Absent
Outstanding
Discharged
Abandoned(reason)
Transferred(destination)
Unknown
```

A protocol can optionally supply a small finite automaton when a plain outstanding/terminal bit is insufficient. For example:

```text
WFP transaction:
  create -> Armed
  protected operation succeeds -> SuccessPending
  commit -> Discharged
  rollback/drop before success -> Abandoned
  rollback/drop after protected success -> invalid on normal exit
```

That small extension covers premature commit and success-preserving transactions without creating a general typestate language.

### Protocol contents

Each declared protocol should identify:

- Exact resolved constructors.
- Discharge operations.
- Explicit abandonment operations.
- Permitted exit outcomes: normal, error, cancellation, owner drop.
- Transfer rules for return values and particular parameters.
- Optional aggregate insertion/removal/drain rules.
- Optional ordering transitions such as `persist → publish`.
- Whether a terminal operation consumes one member, a keyed member, or the entire aggregate.

Avoid generic defaults such as matching every `::begin`, `::transaction`, or name containing `release`. Those may be useful in a candidate-discovery report, but not as production proof.

### Transfer summaries

Use narrow callee summaries rather than full interprocedural analysis:

```text
parameter 0:
  discharge
  abandon
  return_as(result.field)
  store_in(self.field, key=parameter 1)
  forward_to(parameter 2)
  unchanged
  unknown
```

A Rust move alone should not prove semantic transfer. Transfer occurs only when the protocol or callee summary says the destination assumes responsibility.

Similarly, passing `&mut obligation` may let the callee discharge the caller’s obligation without transferring Rust ownership.

### Aggregation

Aggregation needs only two representations:

- Bounded named/keyed members when identity can be retained.
- A summarized collection state: `Empty`, `NonEmpty`, or `Unknown`.

Examples:

- Inserting a request ID into a pending map transfers its obligation into that map.
- Removing the same ID transfers or discharges that member.
- Draining proves closure only if the called cleanup is total.
- A cleanup loop containing `?` does not prove all members discharged; later members remain outstanding.
- Moving a reservation into an enum or result wrapper transfers it to that aggregate rather than becoming `Unknown`.

This is sufficient for KD4’s keyed registries, process-cleanup payloads, startup-server sets, and returned wrapper values.

### Unknown

Unknown must remain a first-class result, triggered by:

- Unresolved calls or dynamic dispatch.
- Opaque macros such as an unmodeled `tokio::select!`.
- Unmodeled FFI or dependency bodies.
- Aliases or aggregate stores without summaries.
- State-space or recursion limits.
- Task/channel handoff without a declared receiving contract.

Production diagnostics should require a proved violation. Unknown paths should produce coverage information or a contract-authoring suggestion, not a leak accusation.

## Interaction with the requested domains

- Resource handles: ownership of a `Child` or `OwnedHandle` does not establish whether its OS resource, process group, or descendants are terminated.
- Tasks: dropping a `JoinHandle` detaches a task. Transferring an obligation into a spawned task must identify how task completion, cancellation, and detachment affect it.
- Transactions: distinguish commit, rollback, successful-operation boundary, and return transfer.
- State transitions: entering states such as “running,” “registered,” or “complete” can create follow-up obligations.
- Event publication: a state transition can create an obligation to publish one terminal event with the same identity.
- Persistence: publication may depend on a prior append/flush obligation.
- Cleanup: distinguish synchronous discharge, explicit cancellation, best-effort abandonment, and runtime-dependent asynchronous cleanup.

Persistence and publication are best expressed as a small aggregate with ordering:

```text
terminal transition
  ├─ persist terminal record
  └─ publish terminal event, permitted only after persistence
```

KD4’s plan handler demonstrates this contract directly: it persists the update, refuses to acknowledge failed persistence, and then publishes the event in [plan.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/plan.rs:224).

## Real KD4 bugs this could represent

With explicit protocols and a few curated boundary summaries, this model could catch these historical failures:

- `451b386442`: a cancelled filesystem-helper future dropped its child handle without killing the process. `kill_on_drop(true)` was added. Rust guaranteed memory cleanup, not process termination.
- `9152ebd289`: interruption dropped shell dispatch before `SIGTERM` cleanup completed, leaving Linux sandbox mount bookkeeping behind. This requires a modeled cancellation edge or known dispatch-race summary.
- `9daa491f7c`: terminating the MCP server process did not terminate its descendants. A root `Child` obligation was discharged, but the aggregated process-tree obligation was not.
- `f5f812389e`: `TurnComplete`/`TurnAborted` was appended and published without the final persistence flush. Rust cannot express “terminal event must become durable.”
- `c55ce3b51b`: submission-channel closure skipped `LiveThread::shutdown`, leaving a live writer registered and preventing resume.
- `4ffeddcbcc`: subagents treated deferred configured MCP servers as outstanding startup members forever. The expected-set aggregate needed explicit abandonment/removal for servers that would never start.

These are semantic completeness, identity, ordering, and external-effect bugs. Rust’s ownership system intentionally does not prove them.

## What this could unify

A shared engine could underpin several current bug classes:

- Incomplete success/lifecycle protocols.
- Missing or premature transaction commit.
- Incomplete RAII rollback or commit transfer.
- Unclosed keyed entries and key-identity drift.
- Runtime-dependent `Drop` cleanup.
- Short-circuiting batch cleanup.
- Missing terminal publication or persistence.
- Task cancellation that abandons externally owned work.

I would unify the semantic representation and proof engine, but retain protocol-specific diagnostic IDs. “Unclosed request key,” “premature transaction commit,” and “terminal event not durable” need different explanations even if they are all proved as obligation failures.

## Recommendation

Proceed with an obligation abstraction, but make it:

- Explicitly protocol-declared.
- Path-sensitive and three-valued.
- Place- and identity-aware.
- Compositional through narrow function summaries.
- Capable of small all-of/keyed aggregates.
- Aware of normal, error, cancellation, and drop exits.
- Strictly bounded in states and interprocedural depth.

Do not infer production obligations from vocabulary alone, and do not treat Rust moves or `Drop` as automatic semantic discharge. That boundary is what keeps the analysis small, explainable, and complementary to Rust ownership.

## What cargo-kda can already support

KDA has much of the proving infrastructure already:

- Semantically resolved test-to-production call relationships.
- A source-mapped local CFG with comparisons, affine expressions, calls, and assignments.
- Event, lifecycle, field-flow, identity, persistence, and state-transition analyses.
- Explicit exact/ambiguous/unknown classifications.
- Bounded scenario verification.
- Runtime evidence that can corroborate or refute but does not treat absence as proof.
- A fixture-to-production derivation analysis.
- A deterministic paired before/after regression corpus.

The missing layer is semantic interpretation of test oracles.

Currently, test history hashes selected assertions as compact source text in [test_history.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/test_history.rs:641). Test planning calls any recognized assertion macro “strong” without understanding what it asserts in [test_plan.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/test_plan.rs:405). The local body IR also deliberately treats macro bodies as opaque in [body_ir.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/body_ir.rs:1).

Therefore, mining would need a dedicated test-evidence representation, approximately:

- setup and triggering action;
- resolved production subjects;
- preconditions supplied by the fixture;
- observed equality, order, transition, presence, absence, or event trace;
- scenario, finite-domain, or proposed-universal scope;
- temporal assumptions such as before/after or timeout window;
- source provenance and supporting tests;
- production proof status: proven, refuted, ambiguous, unsupported, or runtime-only.

Custom `assert_*` helpers must be summarized or inlined semantically. Merely recognizing more macro names will miss some of KD4’s best contracts.

## Where inference becomes unsafe

The main overfitting risks are concrete in KD4:

- `assert_eq!(x, 3)` may describe one fixture, not a general invariant.
- Receiving event A before event B does not always prove production emits A before B; buffering and the test reader matter.
- A timeout proves no observation during a window, not impossibility.
- Test-only hooks can create boundaries that do not exist in normal production APIs.
- Whole snapshots combine semantic, compatibility, formatting, and incidental details.
- Repeated tests may share the same helper or fixture, so repetition is not necessarily independent evidence.
- Mocks can inject states production cannot create—something KDA’s existing fixture-derivation lint already recognizes.
- Some production proofs cross languages. Generic Rust analysis cannot prove the revision example without understanding the SQL trigger; KDA’s current SQL support is narrower and centered on enum/schema relationships.
- Parity assertions often compare projections, not full objects.
- Feature loops quantify over the current finite registry, not every conceivable future value.

These should lead to `unknown` or a suggestion, never a silently strengthened universal rule.

## Assessment of the four levels

| Level | Assessment |
|---|---|
| 1. Developer-visible suggestions | Feasible and low risk. Show the normalized relationship, supporting tests, likely production subjects, and why it was not promoted. Good broad starting point. |
| 2. Generated rules requiring approval | Best overall design. A developer chooses the quantifier, scope, exceptions, severity, and owning subsystem. Production analysis then treats the approved rule exactly like a handwritten contract. |
| 3. Automatically usable semantic facts | Safe only for narrow structural facts: resolved identity forwarding, enum variants, field presence, finite registry implications, simple arithmetic, and direct event construction. These facts can strengthen other analyses automatically, but should not become blocking policy solely because a test asserted them. |
| 4. Regression checks from stable patterns | Feasible after approval or strong corroboration. Store the normalized semantic relationship—not the assertion text—and verify it against future production snapshots. This fits KDA’s existing deterministic before/after regression model in [README.md](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:2304). |

A candidate should become a regression contract only when:

- multiple independent scenarios express the same normalized relation;
- production analysis can identify stable semantic subjects;
- no contradictory witnesses exist;
- the relationship survives source history rather than only duplicated tests;
- runtime-only assumptions are explicitly recorded;
- an owner approves any policy-level interpretation.

## Precision, determinism, and maintenance

Precision can be high if KDA mines relationships rather than literals and refuses to erase fixture conditions. Production proof should be stronger than test frequency.

Determinism is achievable: operate on the pinned rust-analyzer snapshot, sort evidence by stable semantic identity, hash normalized contract IR, and never require executing tests during extraction. Historical base revisions and configuration profiles must remain explicit inputs.

Maintenance burden is moderate. The generic relation library should stay small; KD4-specific knowledge will mostly be adapters for assertion helpers, event collectors, fixture builders, snapshots, and cross-language boundaries. Every generated candidate should retain its supporting and contradicting evidence so stale rules can be retired rather than fossilized.

## Recommendation

Treat tests as a contract-discovery corpus and corroborating semantic evidence, not as a rule generator with automatic authority.

The practical hierarchy should be:

1. Automatically extract narrow facts.
2. Produce suggestions for broader relationships.
3. Let developers approve policy-bearing candidates.
4. Promote approved, historically stable candidates into deterministic regression checks.
5. Preserve runtime tests wherever scheduling, delivery, OS behavior, timing, or non-occurrence cannot be statically proved.

That would materially reduce manual invariant discovery and rule authoring while keeping the key safety property: a test suggests what may be true; production evidence determines what KDA can actually claim.

## Conclusion

A genuinely useful `cargo kda diff` should compare two revision-scoped behavioral graphs, not diff syntax trees or lists of changed functions.

Its central question should be:

> From the same production entrypoints and configuration, which observable behaviors, obligations, classifications, and architectural relationships became reachable, unreachable, reordered, or uncertain?

KDA already contains much of the necessary single-revision vocabulary: rich effect summaries, implicit `Drop` behavior, ownership handoffs, lifecycle protocols, runtime activation, trait matrices, failure-fate graphs, and project contracts. The missing capability is a stable, whole-revision semantic model and a comparison engine tying these facts together.

Today:

- `impact --base` starts with changed lines and walks the current graph; it cannot faithfully describe deleted behavior or compare two resolved programs ([change_impact.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/change_impact.rs:1>)).
- `consequence-diff` compares one function’s local CFG and observations, but does not yet compose workspace call, ownership, dispatch, or protocol relationships ([counterfactual_behavior.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/counterfactual_behavior.rs:424>)).
- The effect vocabulary is already close to what semantic diff needs, including phase, completion, condition, target, must/may, and provenance ([effects.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/effects.rs:82>)).

## Most useful semantic deltas

I would prioritize the following nine delta families for reviewing Codex-generated patches.

### 1. Production-reachable effect-envelope changes

This asks whether an entrypoint can now reach a new observable effect, or can no longer reach one:

```diff
- registry.dispatch_any_with_terminal_outcome(invocation, terminal).await
+ handler.handle(invocation).await
```

Both sides execute the handler. The replacement silently bypasses registry-owned cancellation, lifecycle notification, telemetry, projection, and terminal-outcome behavior. KD4 already declares this mediation requirement explicitly in [kda.toml](</C:/Users/kuh/Desktop/kd4/codex-rs/kda.toml:267>).

Compute it by:

- Establishing production roots for each target/profile.
- Combining resolved calls, dynamic target sets, runtime registrations and effect summaries.
- Comparing normalized tuples such as:

  `root → effect kind → target → condition → phase → completion`

- Retaining a shortest before/after witness path.
- Treating unresolved calls as uncertainty, never as proof of effect removal.

Meaningful changes include new network, process, persistence, publication, blocking, spawn or termination effects; `must → may`; awaited work becoming detached; or a changed effect target. Harmless churn includes helper extraction or call-path substitution when the reachable normalized effect envelope remains identical.

Agent surface:

```text
HIGH  request_permissions gained an unmediated execution path
root: ToolRouter::dispatch_tool_call_with_terminal_outcome
new path: router -> RequestPermissionsHandler::handle
lost guarantees: cancellation notification, terminal-outcome accounting
```

Incremental requirement: medium. Recompute changed body summaries and the affected reverse-call SCCs. Registration, root, feature or dynamic-target changes require a wider slice.

### 2. Effect ordering and dominance changes

Ordering is frequently more important than presence. KD4’s plan update is a real example: cancellation must precede durable commit, which must precede publication and success ([kda.toml](</C:/Users/kuh/Desktop/kd4/codex-rs/kda.toml:226>)).

A tiny patch could violate that:

```diff
- let outcome = ledger.record_planning_update(update.clone()).await;
- ensure_durable(outcome)?;
  session.send_event(turn, EventMsg::PlanUpdate(update)).await;
+ let outcome = ledger.record_planning_update(update.clone()).await;
+ ensure_durable(outcome)?;
```

All the same calls remain, so call and reference tools show almost nothing useful.

Compute it with MIR control flow:

- Lower contract-relevant operations to semantic events.
- Calculate dominance, post-dominance and all-path precedence.
- Include normal, `?`, early-return, cancellation, coroutine-drop and unwind exits.
- Compare the partial order rather than statement offsets.

Meaningful changes are lost dominance, new paths that invert operations, or completion changing from “completed before return” to “enqueued only.” Reordering independent logging, local computation or commutative reads is harmless.

Agent surface:

```text
DENY  durable plan commit no longer dominates PlanUpdate publication
new counterexample:
  handle_call -> send_event -> record_planning_update
contract: kd4-plan-commit-before-publish
```

Incremental requirement: low for a local callable; medium if wrappers or transitive effects participate.

### 3. Cleanup and all-exit obligation changes

KD4’s `PendingProcessRegistration` has meaningful `Drop` behavior: it terminates processes and schedules confirmed cleanup through either a Tokio runtime or a cleanup worker ([process_manager.rs](</C:/Users/kuh/Desktop/kd4/codex-rs/core/src/unified_exec/process_manager.rs:371>)).

A small patch could weaken the guarantee:

```diff
- pending_process.process.terminate_confirmed().await?;
+ pending_process.process.terminate();
```

Or move guard construction after a fallible partial spawn, creating an unguarded `?` exit.

Compute it by:

- Using MIR cleanup, unwind and coroutine-drop edges.
- Modeling resource acquisition, typestate, ownership transfer, commit/disarm and `Drop`.
- Checking discharge on normal, error, cancellation and unwind exits.
- Comparing the obligation coverage matrix, not merely the presence of a cleanup call.

Meaningful change is a newly uncovered exit, confirmed cleanup becoming best-effort, cleanup moving to detached work, or ownership escaping without a responsible owner. Explicit cleanup becoming equivalent RAII cleanup is harmless if every exit retains the same guarantee.

Agent surface:

```text
CRITICAL  process cleanup weakened on cancellation
before: termination confirmed before deregistration
after: termination requested; confirmation continues outside the owner
witness: start_process -> cancellation -> PendingProcessRegistration::drop
```

Incremental requirement: medium-to-high. Changed async bodies and affected `Drop` implementations need MIR regeneration; carrier/constructor users need reverse type-use invalidation.

The current KD4 patch adding `AgentStatus::TerminalWithCompletion` is exactly the kind of semantic ripple this mode should explain. Meaningful change is a new reachable state, changed terminal classification, swallowed event, or a field reaching live state but not persistence/replay. Renames and one-to-one wrapper conversions are harmless when the disposition vector stays equal.

### 5. Error identity and failure-fate changes

- Resolving `?` through the actual `From`/`Try` implementation.
- Tracking variants through `map_err`, wrappers, matches, classifiers and retry loops.
- Comparing terminal fates: returned, retry, model-visible, protocol-visible, suppressed, abort, panic or process exit.
- Reporting identity collapse where distinct errors become a string or common variant.

Meaningful change is a fate change, loss of identity needed by a classifier, retry becoming fatal, or suppression becoming externally visible. Helper extraction and equivalent `From` chains are harmless.

### 6. Trait and dynamic-dispatch target changes

A default method change can affect many implementations without editing any of them:

- Resolving static monomorphized trait calls exactly.
- Recording inherited default versus override per implementation.
- Using allocation/coercion/field/container/argument flow to derive per-callsite dynamic target sets.
- Marking public/downstream-open traits as open world.
- Comparing effective target sets and their behavioral summaries, not the global list of impls.

Meaningful change is a newly reachable implementation, default-body change inherited by reachable impls, target-set widening to a more powerful effect, or closed-world becoming open/unknown. An unreachable new impl or behaviorally equivalent override is harmless.

Meaningful change is loss or replacement of authoritative provenance, transfer without rollback, short-lived state escaping to a longer scope, or same-typed arguments coming from different resolution roots. Agent surface:

### 9. Dependency-direction and public-boundary changes

A generated patch may “reuse” an implementation type across a boundary:

```diff

-    pub permission_profile: ProtocolPermissionProfile,
+    pub permission_profile: codex_core::config::PermissionProfile,
```

This creates a protocol-to-core dependency and leaks implementation ownership through a public or serialized surface. KD4 explicitly forbids such directions in [kda.toml](</C:/Users/kuh/Desktop/kd4/codex-rs/kda.toml:371>).

Compute it by:

- Comparing Cargo dependency edges per normal/dev/build target and feature profile.
- Computing public-signature type reachability, including aliases, generics and associated types.
- Connecting serialized fields to live producers and replay consumers.
- Distinguishing dependency existence from dependency leakage into an owned boundary.

Meaningful change is a new production dependency in the wrong direction, a cycle, public type leakage, or live/persist/replay continuity loss. Test-only dependencies, private implementation reuse within an allowed layer, and dependency moves that preserve the condensation DAG are usually harmless.

Agent surface:

```text

affected surfaces: JSON schema, rollout persistence, app-server protocol
```

Incremental requirement: high. Manifest, feature or public-surface changes invalidate crate graph and downstream metadata, though unchanged body analyses can remain cached.

## What `cargo kda diff` needs

### 1. Two real semantic revisions

KDA must analyze both sides independently: merge base/tree and working tree or two explicit refs. Loading only the current rust-analyzer database cannot represent deleted functions, removed impls, old resolution, or old feature wiring.

Each revision artifact must record:

- Git tree/worktree identity.
- `Cargo.lock`, manifests and target graph.
- Rust toolchain.
- target triple, enabled features and relevant `cfg`.
- KDA configuration and semantic contracts.
- proc-macro, build-script and relevant environment fingerprints.

Mismatched profiles should produce a provenance error or an explicit cross-profile comparison, not a normal delta.

### 2. Stable cross-revision identities

The current `FunctionInstanceKey` includes `FileId` and byte range ([analysis_context.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:57>)); that is excellent within one database but unsuitable as a revision identity.

A diff identity should primarily use semantic ownership:

- package/target/crate;
- module path;
- item kind and name;
- trait plus self type for impl items;
- normalized signature and generic role.

Moves and renames can use structural matching as secondary evidence, but ambiguous matches must remain “removed plus added” rather than being guessed.

### 3. A revision-wide semantic relation store

The artifact should store normalized relations rather than whole ASTs:

- call and dynamic-target edges;
- rooted runtime activation;
- effects with condition, certainty, phase and completion;
- effect ordering;
- states and transitions;
- protocol transformations and dispositions;
- ownership, lifetime, authority and obligation edges;
- error transforms and fates;
- Cargo/public/schema dependencies;
- explicit precision boundaries.

The diff engine then compares relation sets and their reachable closures.

### 4. Semantic equivalence as a first-class result

A major advantage over textual review is confidently saying:

> This patch changed 42 lines and three direct callees, but no production-rooted effect, state, failure, ownership or protocol relationship changed.

The current `exec-server` consolidation from three explicit spawn branches to `prepared.spawn(tty, pipe_stdin)` is an ideal test case. If the helper preserves the same conditions and spawn semantics, KDA should suppress the call churn and report equivalence. If it introduces `spawn_blocking`, detachment or different stdin ownership, it should report exactly that delta.

### 5. Explicit uncertainty semantics

Every result should be one of:

- `proved_added`
- `proved_removed`
- `changed`
- `possibly_added`
- `possibly_removed`
- `newly_unknown`
- `precision_improved`
- `equivalent_under_profile`

Most importantly, if the after revision introduces an unresolved call, KDA must not claim that an old effect was removed. It can only say that the effect is no longer provably reachable because precision was lost.

### 6. Rooted, witness-backed agent output

JSON should be the authoritative format. Each delta needs:

- stable identity;
- category and severity;
- before and after relation;
- production profile/root;
- shortest witness on each side;
- source evidence;
- certainty and precision boundaries;
- violated or affected KDA contracts;
- affected tests or suggested validation target;
- a concise review question.

The default human output should be a prioritized digest, not a graph dump:

```text
cargo kda diff --base origin/main

2 high-confidence behavioral changes
1. permission acceptance expanded for foreign network-only environments
2. TerminalWithCompletion is newly unloadable and failure-classified

1 semantic-equivalence group
- LocalProcess spawn refactor preserves process, tty and stdin effects

1 unresolved risk
- dyn ToolLifecycleContributor target set widened across a public trait boundary
```

### 7. Dependency-aware incremental analysis

Use content-addressed per-revision artifacts:

- Reuse unchanged crate metadata and unchanged body summaries.
- Recompute changed MIR/HIR bodies.
- Propagate summary changes through reverse dependency SCCs until hashes stabilize.
- Invalidate dynamic dispatch selectively for affected traits, coercion sites and value-flow carriers.
- Invalidate public consumers for signature/schema changes.
- Rebuild the profile graph for manifest, feature, build-script or proc-macro changes.

Most patches should cost approximately “changed bodies plus affected semantic cone,” not two cold whole-workspace analyses. A cold two-revision run will still be necessary when provenance artifacts are absent.

## The threshold for being substantially better

`cargo kda diff` becomes substantially more useful than git diff plus rust-analyzer references when it can reliably do all of these:

1. Compare before and after resolution, including deleted behavior.
2. Report only production-rooted behavioral deltas by default.
3. See implicit behavior: `Drop`, unwind, cancellation and coroutine-drop paths.
4. Compare conditions, effect phase, completion guarantees and ordering—not merely callees.
5. Resolve trait defaults and useful per-callsite dynamic target sets.
6. Track error identity, ownership, authority and protocol disposition across functions and crates.
7. Collapse refactors into semantic-equivalence results.
8. Preserve uncertainty and never turn missing analysis into proof of absence.
9. Give a coding agent a short witness and a precise validation question.

Without those properties, `cargo kda diff` would mostly be a more elaborate impact report. With them, it becomes a behavioral review instrument: the reviewer sees the small textual patch in Git, while KDA explains which system guarantees actually changed.

### 1. Windows `PathUri` identity

Historical fix: `4cb8676d3a`, “Make Windows path URI comparisons ASCII-case-insensitive.”

Violated contract: Windows file URI identity is ASCII-case-insensitive, while POSIX identity is case-sensitive. Derived `Url` equality and hashing represented URI spelling rather than native path identity.

Smallest counterexample:

```rust
#[derive(PartialEq, Eq, Hash)]
struct PathUri(Url);

let a = PathUri(parse("file:///C:/Users/Alice"));
let b = PathUri(parse("file:///c:/users/ALICE"));

assert_eq!(a, b); // Required by Windows path identity; actually false.
```

Minimum missing fact:

```text
equivalent(a, b) =
    same_authority(a, b)
    ∧ convention(a) = Windows
    ∧ ascii_fold(safe_decode(path(a))) =
      ascii_fold(safe_decode(path(b)))
```

`Eq`, `Hash`, containment, and relative-path operations must all use that same equivalence.

Weakest capable analysis: a configurable, context-indexed equivalence-key contract. It would require `PartialEq` and `Hash` to factor through the same declared identity key and reject the derived implementations because they use the raw representation.

Nearby valid patterns:

- POSIX paths remain case-sensitive.
- Unicode case folding is not implied by ASCII folding.
- Percent-equivalent safe segments may compare equal.
- Encoded separators and opaque fallback URIs fail closed.
- A wrapper whose constructor already canonicalizes the representation may validly derive `Eq` and `Hash`.

Refinement: activate the contract only when the value is proven to represent a normal Windows URI. On uncertain, opaque, or unsafe-decode paths, require exact representation equality. This avoids a global “path strings must ignore case” rule.

### 2. Symlinked skill identity versus discovery locator

Historical fix: `72d937ed4d`, “Preserve discovery paths for symlinked skills.”

Violated contract: canonical paths identify and deduplicate a skill, but discovery paths are the user-visible locator and must round-trip through explicit selection.

Smallest counterexample:

```rust
let discovered = "/repo/.agents/skills/demo/SKILL.md";
let canonical = "/shared/skills/demo/SKILL.md";

let skill = Skill { path: canonical };
catalog.emit_link(skill.path);       // Advertises canonical representation.
select_by_path(discovered, &skill);  // Fails to find the same skill.
```

Minimum missing fact: `canonical` and `discovery` are projections of one entity with different roles:

```text
identity(skill)   = canonical_path
locator(skill)    = discovery_path
resolves(locator(skill)) = identity(skill)
```

Weakest capable analysis: semantic role labels plus a declared alias/projection relation. Deduplication and storage require `identity`; catalog output and user-input round-tripping require `locator` or a resolver accepting both.

Nearby valid patterns:

- With no symlink, both projections may contain the same bytes.
- Internal logs and diagnostics may intentionally show canonical identity.
- Deduplication by discovery path would be wrong when two aliases reach one skill.
- Explicit canonical paths may remain accepted for compatibility.

Refinement: diagnose only at boundaries declared as user-visible or round-trippable, and only when an alias-capable discovery source reaches that boundary without its locator projection.

This and `PathUri` are the same underlying problem: raw Rust equality is not necessarily application identity, and one entity can have multiple non-interchangeable representations.

### 3. Buffered turns absent from prompt editing

Historical fix: `266c6920d9`, “Include buffered turns when editing prompts.”

Violated contract: the current transcript is the loaded snapshot with ordered buffered notifications applied. Prompt editing read only the snapshot.

Smallest counterexample:

```rust

let buffer = vec![
    TurnStarted(t),
    ItemCompleted(t, user_prompt),
];

find_prompt(&snapshot, user_prompt.id); // None
```

Minimum missing fact:

```text
current_turns = fold(apply_notification, snapshot_turns, replay_buffer)
```

Weakest capable analysis: a declared materialized-view contract. Consumers requiring the current transcript must depend on the composed view rather than only its base component.

Nearby valid patterns:

- Persisted-history inspection may intentionally read only the snapshot.
- Snapshot-only access is valid when the buffer is proven empty or fully incorporated.
- A helper such as `current_turns()` may discharge the obligation.
- Duplicate item events may be intentionally idempotent.
- Status events update an existing turn rather than append another turn.

### 4. Full permission instructions re-emitted for an additive approval

Historical fix: `1bbfb5cfad`, “Avoid reinjecting permissions after command approvals.”

Violated contract: world-state updates were patches, but a changed hash caused the full permission block to be re-emitted after adding one approved prefix.

Smallest counterexample:


Weakest capable analysis: a delta-view contract with two laws:

```text

unchanged dimensions are absent from a patch
```

Nearby valid patterns:

- A replace-all protocol may validly emit the full new state.
- Changed base permissions require a full refresh.

### 5. Ranking named sessions before eligibility filtering

Historical fix: `c38a60ded2`, “Harden named session lookup in the TUI.”

Violated contract: lookup should return the newest eligible session, but an ineligible newer duplicate could hide an older valid one.

Smallest counterexample:

```rust
let candidates = [
    Candidate { mtime: 2, provider: B },
    Candidate { mtime: 1, provider: A },
];

// Wrong:
candidates.max_by_key(mtime).filter(|c| c.provider == A) // None

// Required:
candidates
    .filter(|c| c.provider == A)
    .max_by_key(mtime) // Older candidate
```

Minimum missing fact:

```text
result = argmax(mtime, { c ∈ candidates | eligible(c) })
```

Filtering and ranking do not commute unless all candidates are already eligibility-homogeneous.

Weakest capable analysis: a normalized collection-query IR for operations such as `filter`, `find`, `sort`, `max`, `take`, and `next`, checked against a declared selector contract.

Nearby valid patterns:

- Rank-then-filter is valid when an earlier proof establishes that every candidate is eligible.
- “Choose newest and reject it if unusable” is a valid but different specification.
- Server-side filtering may discharge the local obligation if its API summary guarantees the same predicate.
- `top_k(filter(xs))` differs from filtering only the first `k` ranked items.

Refinement: do not warn on operator ordering in isolation. Require a selector contract such as `newest-eligible`, and suppress when an upstream invariant proves the candidate universe already satisfies the predicate.

### 6. Textarea cursor and rendering escaping the viewport

Historical fix: `ad6e48ddd3`, “Keep textarea cursors and rendering inside the viewport.”

Violated contracts:

```text
Some(x, y) ⇒ width > 0 ∧ height > 0
              ∧ area.x ≤ x < area.x + width
```

Weakest capable analysis: lightweight affine/interval refinement over `BodyIr`, supplemented with summaries for `min`, `max`, `clamp`, `saturating_sub`, `Rect::contains`, and bounded rendering APIs.

Nearby valid patterns:

- `x == width` is valid as a half-open slice endpoint, but not as a cursor coordinate.
- An empty viewport is valid when the function returns `None`.
- `set_stringn(..., width - x_offset)` is safe when `x_offset ≤ width`.

Refinement: attach boundary roles—`index`, `exclusive-end`, `length`, `terminal-cell`—to numeric facts. Prove definite violations under path guards; treat opaque helpers as unknown rather than unsafe.

## Smallest high-leverage capability set

I would build two engine-level capabilities, backed by three small theories.

1. **Declarative relational contracts**

   Contracts should name semantic roles and laws rather than KD4 functions:

   - equivalence key and projection roles;
   - materialized view and pending delta;
   - patch versus replacement semantics;
   - collection selection specification;
   - function preconditions and postconditions.

   Rust annotations, configuration, and trusted function summaries can all feed the same representation. Intent must be declared where Rust’s types do not express it.

2. **Path-sensitive relational abstract interpretation**

   Extend the existing CFG and `BodyIr` facts with:

   - environments propagated through branches and joins;
   - interprocedural summaries for small helpers;
   - definite-proof/unknown separation;
   - contract checking at returns, calls, equality/hash implementations, and external boundaries.

The theory packs should remain deliberately bounded:

- **Affine refinements:** inequalities, discriminants, `Option` presence, `min/max/clamp/saturating_*`.
- **Finite collection algebra:** membership, subset, union/difference, filter, ranking, and ordered fold.
- **Equivalence/projection lineage:** uninterpreted normalizers, congruence, representation roles, and alias witnesses.

This gives direct coverage of all six counterexamples without introducing `windows-path-uri-equality`, `buffered-prompt-edit`, or similarly narrow lints. The key noise rule should be: report only when the contract is known and its negation is provable; missing intent or opaque behavior remains unknown.

## 3. Ideas whose complexity is not justified

### Full async deadlock or schedule model checking

A product of task CFGs, Tokio scheduling, cancellation, select branches, external futures, and channel state would grow rapidly and still be incomplete. Resource interval summaries expose the most actionable deadlock and serialization mistakes at a fraction of the cost.

### Whole-program heap alias analysis or arbitrary interprocedural dataflow

Rust traits, macros, unsafe code, dependency bodies, smart pointers, and generated code would force aggressive approximation. Identity recipes and receiver/argument-relative resources cover the useful KD4 cases without pretending to solve general aliasing.

### A general inferred effect/type system

KDA already has a good finite effect vocabulary in [effects.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/effects.rs:82). Expanding it into a universal inferred effect system would add annotation and false-confidence costs without preserving the more important relations: *which resource*, *which key*, *under which mode*, and *at what point*.

### Automatic arbitrary invariant discovery or SMT verification

Discovering meaningful invariants across every struct and proving them over arbitrary Rust is disproportionate to a deterministic local quality gate. Declared finite schemas are reasonable; unconstrained invariant mining is not.

### “Build a full call graph” as the capability

The analyzer already has a useful resolved-call index. A larger call graph would improve transport of facts but would not create the missing facts. Open dynamic dispatch would also remain unresolved. The graph should remain supporting infrastructure, not the deliverable.

## Conclusion

Yes—`kda` should model semantic obligations, but as a small, configurable typestate layer, not as linear typing.

The useful abstraction is:

```text
Absent ──create──> Live(owner)
Live(owner A) ──transfer──> Live(owner B)
Live ──discharge──> Satisfied
Live ──abandon──> Abandoned
any ──unsupported effect──> Unknown
```

Transfer must preserve liveness; it changes who is responsible. Whether `Satisfied`, `Abandoned`, or transfer is acceptable depends on the exit kind and the declared protocol.

## Smallest viable analysis

Use an explicit protocol registry. Do not infer obligations from names such as `begin`, `spawn`, `commit`, or `finish`.

Each reviewed protocol needs only:

```text
family
creation operations
logical subject
discharge operations
abandonment operations
transfer positions
allowed fates by exit kind
optional prerequisite edges
```

For example:

```text
family: wfp-transaction
create: Engine::begin_transaction -> return
discharge: Transaction::commit
abandon: Transaction::drop/abort
normal return permits: discharge, transfer
error/cancellation permits: abandon, transfer
```

The abstract state for each logical instance should be a small set of:

```text
Absent
Live(owner)
Satisfied(action)
Abandoned(action)
Unknown(reason)
```

Important details:

- Do not make `Transferred` globally terminal. It should be an interprocedural summary effect; the obligation remains live under its destination owner.
- Keep discharge and abandonment distinct. Aborting an I/O helper may be permitted while aborting the process waiter is a violation.
- Parameter summaries should state whether a parameter is discharged, abandoned, transferred to another parameter/receiver, or placed into the return value.
- Returning `Option<T>`, `Result<T, E>`, tuples, structs, and enum variants should transparently transfer contained obligations.
- Passing an obligation to an external or unresolved callee without a summary produces `Unknown`, not “transferred successfully.”
- Dynamic aggregates need only a summary such as `NoLiveMembers`, `MayHaveLiveMembers`, or `Unknown`. A loop containing a short-circuiting exit before the remaining members are terminalized leaves `MayHaveLiveMembers`.
- Distinguish normal, error, cancellation, unwind, and Drop exits. KD4 frequently permits rollback on failure but requires commit or transfer on success.
- Attach provenance to `Unknown`: unresolved call, unsupported alias, aggregate overflow, dynamic dispatch, unsafe escape, or analysis budget.

Keep it bounded:

- Intraprocedural CFG fixed point with cached function summaries.
- Transparent summary composition across one local call boundary or SCC fixed point.
- A fixed instance/aggregate cap per function; overflow becomes `Unknown`.
- Use Rust’s existing move/place facts. Do not independently decide whether a move, borrow, or lifetime is legal.
- Arbitrary aliasing, `Arc` cloning, unsafe storage, trait-object dispatch, and unknown containers stop proof for the affected obligation only.
- Report a violation only when there is a concrete live path with no unsupported step on that path. Report uncertainty separately or suppress it by default.

## Could this unify existing bug classes?

Yes, as a shared substrate—not as one mega-lint.

The core state machine can unify:

- `incomplete-operation-obligation`
- `incomplete-success-obligation`
- `missing-raii-rollback`
- `incomplete-raii-commit-transfer`
- `unclosed-keyed-obligation`
- `incomplete-transactional-token-commit`
- resource and owned-lifecycle closure checks

The following remain thin extensions over the substrate:

- `short-circuiting-batch-cleanup`: aggregate universal closure
- `runtime-dependent-drop-cleanup`: whether an abandonment/transfer action is actually available in the current environment
- `keyed-obligation-identity-drift`: logical identity equality
- premature commit, persistence-before-publication, and terminal event order: prerequisite edges between obligation actions

It should not attempt to subsume deadlock analysis, transaction atomicity, arbitrary temporal logic, Rust aliasing, or borrow checking.
