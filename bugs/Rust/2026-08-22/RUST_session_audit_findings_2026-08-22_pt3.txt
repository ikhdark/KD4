## 1. Permission grants are a keyed authorization transaction

KD4 creates a pending request keyed by `call_id`, capturing the requested permissions, environment, originating turn, and response sender in [session/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:2846). On response it removes that exact entry, normalizes the response against the captured request, records the grant in the selected scope, and only then wakes the waiter in [session/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:3018). Normalization intersects requested and granted authority in [session/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:3063), while consumers retrieve session and turn grants using the same environment identity in [tools/handlers/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/handlers/mod.rs:293).

Compiling violations include:

- Sending the oneshot response before storing the grant.
- Merging instead of intersecting requested permissions.
- Storing `Session` scope in turn state, or `Turn` scope in session state.
- Indexing the grant under a different environment.
- Applying a late response after cancellation consumed the pending key.

All use ordinary, type-compatible permissions, IDs, maps, and senders.

`kda` already has a dedicated permission continuity pass and query in [authority_path.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/authority_path.rs:199). It can recognize narrowing and several correlation/environment stages, but it does not fully prove storage-before-wakeup, scope-to-owner agreement, or cancellation consuming the response authority.

Required representation:

```text
request(call_id) owns {
    requested_authority,
    environment,
    originating_turn
}

effective_authority ⊆ requested_authority
storage_owner = owner(selected_scope)
store(call_id, effective_authority) happens-before wake(call_id)
cancel(call_id) consumes the right to grant
```

This could unlock:

- `permission-grant-widening`
- `permission-scope-storage-mismatch`
- `permission-wake-before-commit`
- `late-permission-response`
- A query showing each request’s captured authority, narrowing step, storage lifetime, consumer, and cancellation path.

## 4. The old turn must be detached before terminal delivery becomes observable

KD4 documents the reason directly: once the client observes completion, it may immediately submit the next input. If the completed turn is still attached, that input can appear steerable and then be discarded when detachment clears the old turn. Accordingly, detachment precedes live terminal dispatch in [tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1621).

Moving `detach_terminal_turn` after `dispatch_terminal_event_live` compiles cleanly. The failure requires an external re-entry between the two awaits, which Rust’s types do not expose.

This is already encoded as `terminal-authority-detach-delivery` in [terminal_order.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/terminal_order.rs:60). That is useful direct coverage, but it is tied to known function and stage names.

A general representation would make terminal publication an external-observation barrier:

```text
settle active_turn(turn)
    happens-before
publish terminal(turn)

publish terminal(turn)
    enables external operation submit_next_turn
```

This enables a generic `observable-terminal-before-detach` diagnostic and a query answering: “What internal state must settle before this event permits client re-entry?”

## 6. Replay and live process events share a linearization transaction

`ExecProcessEventLog::publish` appends to retained history and sends to the live broadcast channel while holding the history lock in [process.rs](C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/process.rs:103). `subscribe` creates its live receiver and snapshots retained history under that same lock in [process.rs](C:/Users/kuh/Desktop/kd4/codex-rs/exec-server/src/process.rs:125).

This partitions events at one frontier: an event is either already in the snapshot or is delivered live after subscription. Taking the snapshot, unlocking, and then subscribing creates a loss window. Publishing to the channel before acquiring the history lock can similarly create duplication or order disagreement. Both changes compile.

The current channel and cross-resource checks do not model this publisher/subscriber interleaving. This requires an explicit linearization-domain representation:

```text
publisher transaction:
    append history(seq)
    publish live(seq)

subscriber transaction:
    establish live cursor
    snapshot history through frontier

both transactions use the same synchronization domain
each seq crosses the replay/live frontier exactly once
```

Potential results:

- `replay-live-subscription-gap`
- `publication-outside-event-log-lock`
- `split-handoff-synchronization-domain`
- A query showing the lock, event sequence, replay frontier, and live cursor establishment.

## Overall analyzer direction

The existing analyzer is strongest when the invariant is “resolved operation A dominates resolved operation B in one callable.” KD4’s most consequential remaining relationships need four additional semantic concepts:

1. **Keyed protocol instances** — `call_id`, terminal identity, interrupt generation, process ID.
2. **Value agreement and monotone transformations** — equality by fingerprint, authority narrowing, scope-derived ownership.
3. **Activation and observation boundaries** — first future poll and externally visible event publication.
4. **Concurrency facts** — shared linearization domains and multi-input joins.

A declarative representation combining those concepts could express most of the findings without hardcoding more KD4 names.

## Conclusion

It should not become a general invariant-learning system, and evidence frequency should never directly become enforcement policy. That would introduce too much uncertainty and research complexity for a deterministic quality gate.

## Concrete KD4 findings

### 1. Status projection before client-visible event delivery

This is the strongest apparently unconfigured local candidate I found.

Several `Session` delivery paths perform the same semantic operation:

1. Derive an `AgentStatus` with `agent_status_from_event(&event.msg)`.
2. If a status exists, update the status watch channel.
3. Only then send the event through the client-visible event channel.

This occurs in `dispatch_terminal_event_live`, `try_send_live_event_accepted`, `deliver_event_raw`, and `try_send_live_event` in [session/mod.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:2011). The conversion itself is defined in [status.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/agent/status.rs:4).

A candidate invariant would be:

> For an event crossing a designated `Session` event-delivery boundary, if that event projects to an `AgentStatus`, the projected status must be published before the event is delivered.

This is stronger than “these two calls tend to occur together” because it includes:

- The same event value.
- A conditional projection.
- A specific delivery boundary.
- Dominance of the status update over the send.
- A required order.

It should remain scoped to the reviewed `Session` boundary. Other `send` calls can represent unrelated channels, so a workspace-wide rule would be accidental.

### 2. Canonical `TurnItem` lifecycle projection

`TurnItem` is systematically converted into legacy lifecycle events through `HasLegacyEvent` in [legacy_events.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/protocol/src/legacy_events.rs:65).

Its implementations map typed variants into corresponding start and completion events, preserve correlation identifiers, and suppress completion events for incomplete states. The session then uses that interface before sending legacy events in [session/mod.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:2151).

A possible invariant is:

> Typed turn items crossing the legacy-event boundary must be projected through the canonical `HasLegacyEvent` mechanism, preserve the item correlation identity, and emit an end event only from a terminal item state.

This is preferable to mining “every begin event is followed by an end event.” That broader proposition is false: thread-history reconstruction intentionally accepts end-only events and late terminal events, as shown in [thread_history.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/app-server-protocol/src/protocol/thread_history.rs:679).

The legitimate invariant is about canonical projection and terminal-state gating, not universal temporal pairing.

### 3. Terminal-ledger guarded transitions

The app-server terminal ledger appears to implement a small state machine in [thread_state.rs](/C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/thread_state.rs:209):

- Terminal events are identified by turn ID and fingerprint.
- State reduction precedes notification projection.
- Notification acceptance is recorded for the same ledger entry.
- Acknowledgement clears several replay-related fields together.
- History-seeded entries follow an intentional alternate path.

A plausible candidate is:

> Notification projection or acceptance for a terminal event is enabled only after state reduction for the same `(turn_id, fingerprint)`.

This is potentially valuable, but it is not a good first mining template. Pairwise field-mutation counts would be misleading because some fields legitimately change independently. Mining it correctly requires:

- Field identities and place provenance.
- Guard predicates.
- Key equality.
- Method summaries.
- State-transition reconstruction.

This is a medium-confidence discovery candidate and a high-complexity analyzer feature.

### 4. Registration and durable-plan ordering

KD4 already declares several strong invariants in [kda.toml](/C:/Users/kuh/Desktop/kd4/codex-rs/kda.toml:50), including:

- Core tool and extension registration.
- Declassification before sensitive sinks.
- Cancellation before durable commit.
- Commit before publication and success.
- Registry-mediated tool handling.
- Cross-crate provenance and lifetime rules.

These should be used as calibration data, not rediscovered as novel findings. A miner should be able to reconstruct them from resolved semantics and then recognize that they overlap existing contracts.

If it cannot recover these known patterns without producing many false candidates, broader invariant mining is not ready.

## Candidate mining strategies

### Resolved temporal protocols

This finds relationships such as “A must precede B” or “after A, B must occur on every successful path.”

Semantic representation:

- Canonical callable identities, not names.
- Local CFG and call-site placement.
- Dominance and post-dominance.
- Return, cancellation, and error-path classification.
- Value/place provenance so A and B can be tied to the same resource.
- Interprocedural effect summaries for thin wrappers.
- Production/test and feature-profile information.

Strong evidence should mean:

- At least several independent opportunities—approximately five is a reasonable discovery floor.
- Evidence from at least three callable owners and preferably two modules or crates.
- No proven production counterexample.
- Opaque paths reported separately as unknown.
- The relationship survives collapsing loops, macros, wrappers, and duplicated call sites into independent activations.

Coincidence is controlled by requiring the same subject or key, consistent path conditions, and a meaningful boundary or state change. Lexical adjacency alone provides no evidence.

Discovery mode would report the candidate, witnesses, counterexamples, unknown paths, and inferred scope. After approval, it becomes an exact ordering or path-obligation rule with named callables, scope, exceptions, and unknown handling.

### Typed mediation funnels

This finds relationships such as “values of X pass through Y before reaching Z.”

Semantic representation:

- Canonical type identities, including generic substitutions.
- Def-use and place provenance.
- Exact resolved conversion/declassification functions.
- Boundary sink identities and argument positions.
- Trait coercions, serialization, and wrapper construction.
- Escape and unresolved-dispatch facts.

Strong evidence should mean that every analyzable production flow from X to the scoped Z passes through Y, across multiple callers or owners. Unknown or externally escaping flows cannot be treated as compliant.

To avoid coincidence:

- Y must operate on the same value that reaches Z.
- Merely calling Y in the same function is insufficient.
- The miner should compare other values and boundaries as negative controls.
- It should distinguish ordinary representation conversion from a meaningful validation, redaction, declassification, or capability transition.

Approval would freeze the discovered relation as a required-mediation or sensitive-sink rule. The learned percentage would disappear; enforcement would use an exact semantic contract.

### Guarded aggregate transitions

This finds coupled field changes or typestate transitions.

Semantic representation:

- Fields identified by definitions, not strings.
- Versioned places and assignments.
- Guard predicates and enum/`Option` states.
- Receiver identity and key provenance.
- Method-level transition summaries.
- Construction, reset, rollback, and destruction paths.

Strong evidence should include multiple independent transitions through the aggregate’s public mutation surface, no contradictory transition, and sufficient coverage of alternate outcomes.

A pair such as “field A and B usually change together” is not enough. The candidate should instead be stated conditionally:

> When an object transitions from semantic state S to T under guard G, fields A and B receive related values.

Constructors, recovery paths, history replay, and cleanup must be modeled as potential legitimate exceptions.

Discovery should initially produce a proposed transition table. Approval would require an owner to name the semantic states, validate exceptions, and select the operations that constitute the mutation boundary. This may require a new kda contract family; it should not be shoehorned into a generic co-mutation warning.

### Registration closure

This finds types or constructors that consistently enter the program through a registry, builder, inventory, or dispatcher.

Semantic representation:

- Resolved trait implementations.
- Constructor and factory identities.
- Generic obligations and trait coercions.
- Registry method and macro identities.
- Production-root reachability.
- Registration key extraction and multiplicity.
- Feature and test configuration.

Strong evidence should require a closed candidate universe. For example, all production implementations of a workspace-owned trait must be enumerable, and all registered instances must be traceable from configured production roots. Enforcement normally requires exact coverage, exact multiplicity, and key uniqueness—not a majority.

Coincidence is avoided by proving that registered values satisfy the relevant trait or generic obligation and flow into the actual registry. Similar method names or a nearby constructor do not count.

Approval maps naturally into kda’s existing registration configuration. The generated proposal would identify the trait, registry APIs, roots, multiplicity, and any reviewed exemptions.

### Event/state and variant projection

This finds relationships between a state transition and its externally visible event, or between corresponding variants across representations.

Semantic representation:

- Canonical enum and variant identities.
- Payload-field provenance.
- Correlation IDs.
- Event construction and sink calls.
- State mutation operations.
- Dominance and guarded terminal-state conditions.
- Producer mode: live execution, replay, recovery, or import.

Strong evidence should cover every in-scope transition or every variant of a closed enum, with no unexplained production omission. Start/end symmetry is only evidence when the execution domain requires it.

Coincidence is controlled by preserving keys and payload provenance and by separating live execution from replay and retry domains. KD4’s end-only history behavior demonstrates why this separation is essential.

Following approval, this could become a variant-flow rule, a canonical-projection rule, or a more specialized keyed-lifecycle contract.

## Evidence model

Kda should count semantic opportunities, not source matches.

Every candidate should classify relevant opportunities as:

- Witness: the proposed relationship is proven.
- Counterexample: it is proven absent or violated.
- Unknown: macros, dynamic dispatch, external code, aliasing, or incomplete analysis prevent a conclusion.
- Out of scope: excluded by an explicit semantic profile.

A high-confidence discovery candidate should normally have:

- Exact resolved identities.
- Several independent production witnesses.
- More than one owner where the invariant purports to be architectural.
- Zero unexplained counterexamples.
- Explicit unknown coverage.
- A stable semantic fingerprint across more than one revision or baseline.

A single subsystem can still produce a useful local candidate, such as the `Session` status projection, but its report must say that the evidence is local rather than architecture-wide.

No support threshold should auto-promote a candidate. Developer intent remains necessary even when evidence is perfect: uniform behavior can reflect an incidental implementation technique rather than a required property.

## Discovery and enforcement must be separate

Discovery output should not be a normal CI diagnostic. It should be a review artifact containing:

- Proposed invariant kind and wording.
- Canonical semantic selectors.
- Suggested scope and feature profile.
- Independent witness count.
- Counterexamples and unknown paths.
- Production/test split.
- Representative semantic paths and locations.
- Overlap with existing `kda.toml` rules.
- A stable semantic fingerprint.

Developer approval would then:

1. Confirm that the relationship expresses intent.
2. Narrow or edit its scope.
3. Name the rule and responsible subsystem.
4. Choose exact exceptions and unknown behavior.
5. Check in an explicit kda contract.
6. Add compliant, violating, and unknown test cases.
7. Initially run it as informational or warning-level enforcement.
8. Promote severity only after a clean observation period.

Once approved, the rule is deterministic. It no longer depends on what is “usual” in the current source tree.

## Fit with kda’s existing implementation

Much of the necessary foundation already exists:

- [analysis_context.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/analysis_context.rs:96) indexes resolved calls, callers, references, CFG profiles, provenance, effects, predicates, and optional MIR facts.
- [body_ir.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/body_ir.rs:264) places resolved calls, assignments, comparisons, and returns on a shared local CFG.
- [place_flow.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/place_flow.rs:34) provides binding-rooted places and projections.
- [field_flow.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/field_flow.rs:38) already demonstrates versioned semantic inventories and stable fingerprints.
- [registration.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/registration.rs:1) already performs much of the required closed-world registration reasoning.
- [semantic_effect_policy.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic_effect_policy.rs:193) has a suitable resolved ordering model and explicit unknown handling.

Important gaps remain:

- `BodyIr` type identity is currently too coarse for mining: ADTs are represented largely by simple names rather than canonical definitions and substitutions.
- Field projections need canonical field identities rather than textual field names.
- Independent activations need to be deduplicated so loops, wrappers, and macro expansions do not inflate evidence.
- Cross-function summaries would need careful composition.
- Async suspension, implicit drops, unwinding, and complex aliasing may require MIR-backed proof for enforcement.
- Boundary and execution-domain scopes must be explicit.

The existing [semantic_invariants.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic_invariants.rs:195) is not a basis for this work: it uses syntax-local and textual matching. Likewise, the current implementation-cohort outlier analysis mixes resolved trait identity with word-category matching, so it does not meet the semantic-only standard posed here.

## Engineering recommendation

This is useful engineering if bounded as follows:

- Offline and advisory only.
- A small fixed catalog of invariant shapes.
- Exact resolved semantic facts.
- Explicit production roots and profiles.
- Known KD4 contracts used as calibration.
- No automatic policy changes.
- No generic pair mining, embeddings, probabilistic models, or source-text similarity.

A sensible initial catalog would contain registration closure, temporal dominance, typed mediation, and variant/event projection. Guarded aggregate transitions should wait until those demonstrate value.

The go/no-go test should be practical:

- Can it rediscover KD4’s existing registration, mediation, and durable-order contracts without false “novel” findings?
- Can it produce the status-before-delivery and legacy-projection candidates with their scopes and counterexamples clearly exposed?
- Does a KD4 owner consider at least one proposed candidate worth converting into a checked-in rule?

If not, stop. A broad invariant-induction program would be unnecessary research complexity for kda. If it succeeds, the constrained discovery layer would be a natural extension of kda’s existing role: helping developers discover contracts, while leaving humans firmly responsible for declaring them.

## What KDA would need

The current architecture should evolve toward a single canonical preservation model rather than separate, partly overlapping `change-analysis`, `consequence-diff`, and semantic snapshot relation families.

The important additions are:

1. **Baseline-derived obligations.** Preserve proved relations, not raw diagnostics or syntax. Absence is only an obligation when coverage is complete.

2. **Impact closure.** Start from changed definitions, variants, fields, and dependency edges, then analyze unchanged consumers reachable through reverse dependencies. Conversion bugs often live in a consumer the patch forgot to edit.

3. **Refactor-resistant alignment.** Align entities using types, trait roles, event variants, resource protocols, effect summaries, and graph neighborhoods. Names and ordinal call positions should be fallback evidence, not primary identity.

4. **Relational properties.** Support equivalence under a projection: old representation versus new representation, live versus recovery path, local versus executor path, legacy versus paginated history.

5. **Intent envelopes.** KDA cannot safely infer that every semantic difference near edited code is intended. A review should distinguish:

```text
expected change
preservation obligation
newly proved property
suspicious change
proof lost / unknown
```

Intent could come from project contracts or a small patch-specific declaration. Without one, KDA should report candidate changes rather than silently bless them.

6. **Honest proof levels.** “Proved” should be reserved for closed domains. Unknown dispatch, macros, FFI, async scheduling, missing MIR unwind facts, and open-world trait calls must appear as proof boundaries.

## Strategic assessment

Preservation checking could become one of KDA’s strongest advantages—especially for autonomous-agent patches.

Agents are generally good at making the requested behavior appear and adding tests for it. The harder review problem is unintended erosion of a neighboring contract: an override loses precedence, a converter misses one consumer, cleanup disappears on an error path, a recovery route diverges from the live route, or a dependency migration bypasses the intended effect boundary.

The existing repository is the richest available implicit specification for those contracts. KDA can turn that baseline into independent review obligations without requiring humans to predict every failure mode in advance.

The defensible positioning is not “general proof that the patch is behaviorally equivalent.” It is:

> A compact, uncertainty-aware proof delta over project-relevant semantic relations, with intended changes separated from preserved contracts.

If KDA focuses first on finite and stable domains—Cargo dependency direction, enum/consumer completeness, configuration precedence, resource typestate, event automata, and source-to-sink continuity—preservation review could be more valuable than another lint collection and substantially stronger than diagnostic snapshot regression.

## Cases where polymorphism is not the primary missing feature

Two KD4 examples are useful controls.

[`with_cached_approval`](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/sandboxing.rs:72) invokes its approval callback only on an empty-key case or cache miss. ## Design assessment

The evidence supports the following staging:

1. Keep the initial effect vocabulary and ordinary concrete summaries simple.
2. Make the internal summary representation `fixed effects + formal invocation dependencies`.
3. Initially substitute only statically recoverable closures, function items, and generic trait implementations.
4. Preserve activation, argument remapping, must/may execution, and an explicit open-world alternative.
5. Add cardinality, guards, concurrency, and outcome ordering incrementally as retry, race, cache, and transactional checks require them.
6. Treat boxed closures, trait objects, and registry lookups conservatively until points-to or explicit capability metadata exists.

What is not justified yet:

- effect-row syntax;
- inferred effect parameters in Rust types;
- whole-program monomorphized effect types;
- pretending that polymorphism resolves arbitrary trait objects or registry keys;
- making the first effect-analysis release depend on path-sensitive callback reasoning.

The representation should be designed now because kda is still at version 0.1 and already has overlapping concrete, callback, and unified-summary machinery. If concrete `CallableKey -> closed EffectSummary` becomes embedded in caches and query schemas, adding latent invocation dependencies later will require a disruptive model change.

So the answer is: **yes, reserve and implement the summary seam before entrenchment; no, do not make a full effect-polymorphic system a prerequisite for the simpler effect analyzer.**

## Conclusion

Yes—semantic slicing should become a first-class, agent-facing `cargo kda` mode.

It should not be an extension of ordinary bidirectional call-graph expansion. The current implementation in [semantic_slice.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic_slice.rs:232>) is useful as a symbol-neighborhood primitive, but its stopping condition is essentially a symbol budget. That makes the output bounded, not semantically complete.

A review slice should instead be defined as:

> The smallest deterministic set of source evidence and semantic summaries that closes every review obligation created by a change, under stated build profiles and assumptions.

The unit should be an entity, span, relationship, or summary—not necessarily a whole file.

## What “semantically complete” means

Completeness is relative to four inputs:

1. The changed entities or runtime concept.
2. The claimed purpose of the change, inferred from the diff or supplied by the agent.
3. The relevant Cargo features, targets, and operating systems.
4. The revision pair being reviewed.

A slice is semantically complete when:

- The behavioral delta has been identified.
- Every applicable review obligation has evidence:
  - the authoritative state or policy owner;
  - producers and mutations;
  - transformations and projections;
  - consumers or terminal effects;
  - lifecycle inverses such as acquire/release, start/finish, persist/restore, enqueue/deliver;
  - relevant protocol or persistence representations;
  - feature and platform variants;
  - tests that express distinct invariants.
- Every relationship leaving the slice has an explicit frontier reason:
  - unchanged abstraction contract;
  - irrelevant relationship;
  - excluded build profile;
  - external or opaque behavior;
  - unresolved dynamic target;
  - traversal truncation.

An unresolved frontier means the result is honestly marked incomplete or conditional. Merely listing it does not make the slice complete.

“Smallest” should mean deterministically minimized against those obligations. It should not mean the fewest reachable nodes, and kda should not claim to have found a globally optimal mathematical minimum.

## Necessary relationships versus noise

A relationship is necessary when removing it would leave a review claim unproved. It is noise when it merely demonstrates reachability or repeats already-dominant evidence.

This leads to several rules:

- Callers are not automatically relevant.
- A distant `Drop`, persistence decoder, feature gate, or invariant test can be essential.
- Generic dispatch hubs should normally be collapsed.
- Unchanged adapters should be represented by verified summaries.
- Only tests contributing a distinct invariant or profile should be selected.
- Generated artifacts should be collapsed behind their generation provenance.
- Repeated witnesses should be minimized using deterministic dominance rules.

A practical minimizer could treat slice selection as weighted obligation coverage:

- Prefer compiler-resolved and changed evidence.
- Prefer authoritative owners over incidental consumers.
- Preserve distinct build profiles and lifecycle phases.
- Penalize generic hubs and repeated transitive witnesses.
- Never remove the only witness for an obligation.

## Stopping rules

Traversal should stop by semantic rule, never merely by radius.

1. Classify the delta: new state, changed projection, resource lifecycle, protocol change, selector/ranker, trait contract, persistence change, and so on.
2. Instantiate obligations appropriate to that delta.
3. Expand only relationships capable of closing an open obligation.
4. Stop at a verified semantic barrier:
   - unchanged API contract;
   - ownership transfer into an already-summarized component;
   - external boundary with a declared contract;
   - excluded configuration;
   - irrelevant producer or consumer.
5. Collapse transparent wrappers, strongly connected implementation clusters, generic hubs, and generated artifacts.
6. Minimize redundant evidence after all obligations are closed.
7. If a traversal or output budget is reached, report truncation. A budget must never silently redefine completeness.

An output budget may omit evidence only when a retained summary or frontier certificate accounts for it.

## Confidence and incompleteness

A single percentage such as “83% complete” would be misleading. Kda should report two orthogonal dimensions.

Evidence certainty:

- compiler-resolved;
- statically derived;
- declared project contract;
- test witness;
- historical association;
- heuristic.

Obligation state:

- closed;
- closed under stated assumption;
- contradicted;
- open/unknown;
- not applicable;
- truncated.

The overall result can then be:

- `complete`
- `conditional`
- `incomplete`
- `ambiguous`

`complete` should require every applicable obligation to be closed with no unresolved profile, dynamic-target, external, or traversal gap.

The output should include a coverage ledger such as:

```text
resource reservation balance       closed              statically derived
Windows descendant cleanup         conditional         declared OS contract
dynamic reclaimer target set        open/unknown         unresolved callback
Unix spawn/reap path                closed              compiler-resolved + tests
```

## Proposed first-class mode

I would introduce a review-oriented mode rather than silently changing today’s symbol slice:

```text
cargo kda review-slice --base <revision> [--target <symbol-or-concept>]
                       [--question <review-intent>] [--all-profiles]
```

The intent may be omitted, but if the diff supports multiple plausible behavioral theses, kda should report the ambiguity instead of choosing invisibly.

The result should be JSON-first and contain:

1. Change thesis and semantic subjects.
2. Review obligations and their status.
3. Selected evidence grouped by role:
   - owner;
   - producer;
   - transformation;
   - consumer;
   - lifecycle counterpart;
   - protocol or persistence boundary;
   - test.
4. Frontier certificates and stopping reasons.
5. Suppressed relationships, with counts and noise reasons.
6. Assumptions, profiles, unknowns, and expansion handles.

The existing `slice` mode can remain a lower-level neighborhood/evidence command.

## Infrastructure required

The main additions would be:

- A revision-paired semantic entity and delta index.
- A unified heterogeneous graph over functions, types, traits, fields, variants, configuration, protocols, persistence, runtime concepts, tests, and generated artifacts.
- Relationship providers for state lineage, lifecycle inverses, protocol projection, persistence, feature parity, resource conservation, selector/ranking order, and test invariants.
- Review-obligation templates keyed by change shape.
- Cross-function ownership, drop, cancellation, and effect summaries, using MIR where source analysis is insufficient.
- Test-contract extraction that distinguishes invariant strength rather than merely associating tests by reachability.
- Generated-artifact provenance and multi-profile analysis.
- Deterministic closure, hub collapsing, evidence minimization, and frontier certification.
- A coverage ledger that makes all incompleteness machine-readable.

## Recommendation

Build it as a first-class advisory mode.

KD4 changes repeatedly require review context that is neither lexical locality nor transitive dependency closure. The existing kda infrastructure is strong enough to support a useful first version, particularly for traits, ADTs, calls, configuration, runtime activation, ownership, protocols, and tests.

The key architectural move is to make review obligations—not graph edges—the organizing abstraction. Without that, semantic slicing will become a better dependency browser. With it, kda can produce compact, auditable packets that tell an agent both what it must understand and exactly where the analyzer could not prove completeness.

# Conclusion

Yes—cargo kda should track semantic provenance, but selectively.

The useful abstraction is not a universal taint graph. It is a bounded, typed, contract-backed explanation of how an important semantic fact was derived. KD4 contains several cases where two values have the same Rust representation but different correctness implications because of their causal history.

Kda already has most of the substrate:

- [`value_provenance.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/value_provenance.rs:1) tracks bounded structural origins such as parameters, calls, projections, constants, and unknowns.
- [`semantic_summary.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/semantic_summary.rs:503) composes effects, flows, phases, outcomes, and precision across calls.
- [`execution_provenance.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/execution_provenance.rs:27) already adds domain meaning for path projections and execution realms.
- [`identity_lineage.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/identity_lineage.rs:1) and [`authority_provenance.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/authority_provenance.rs:1) deliberately remain descriptive because names alone cannot establish semantic authority.

The missing layer is a compact derivation algebra that can say “selected by precedence,” “implied by another feature,” “accepted from this attempt,” “converted using this convention,” or “scoped by this owner.”

## Real KD4 cases

### 1. Effective configuration and feature decisions

KD4 retains the winning layer for ordinary configuration leaves. [`ConfigLayerSource`](/C:/Users/kuh/Desktop/kd4/codex-rs/config/src/config_layer_source.rs:4) distinguishes MDM, system, enterprise, user/profile, project, session flags, and legacy sources, while [`effective_config()` and `origins()`](/C:/Users/kuh/Desktop/kd4/codex-rs/config/src/state.rs:569) merge layers and record the winning leaf origin.

That provenance is lost as configuration becomes a feature decision:

- [`Features::from_sources`](/C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:522) applies defaults, base config, profile config, runtime overrides, and dependency normalization.
- [`normalize_dependencies`](/C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:550) can enable `Collab` because `SpawnCsv` is enabled, or `CodeMode` because `CodeModeOnly` is enabled.
- [`apps_enabled_for_auth`](/C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:374) combines the feature result with a runtime authentication predicate.
- The final [`Features`](/C:/Users/kuh/Desktop/kd4/codex-rs/features/src/lib.rs:324) retains only the enabled set and legacy usages.

Thus `true` may mean default-enabled, explicitly configured, supplied by a legacy alias, overridden by a profile, forced by a session override, implied by another feature, or enabled only after an authentication conjunction.

A compact representation would be one decision recipe per feature:

```text
AppsAvailable =
  And(
    OverrideWinner(Apps, profile layer, shadowed=2),
    RuntimePredicate(ChatGptAuthenticated)
  )

CollabEnabled =
  ImpliedBy(SpawnCsvEnabled)
```

Only the winner, required operands, legacy/normalization step, and a summary of shadowed candidates need be retained.

Useful output:

- “`Collab` is enabled solely because `SpawnCsv` implies it.”
- “The profile setting overrides the user layer; two lower-precedence values were shadowed.”
- “Apps are unavailable even though the feature is enabled because ChatGPT authentication is absent.”
- “This config leaf reaches deserialization but no behavior-affecting decision.”

### 2. Context authority derived from an accepted physical attempt

This is the clearest proof that semantic provenance is a correctness property in KD4.

A response carries a composite [`ResponseAttemptIdentity`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client_common.rs:235) containing a logical sampling request and a physical attempt. A logical request ID is reused while each retry gets a new physical attempt ID in [`new_attempt_identity`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/client.rs:686).

The identity composes as:

```text
logical request
  + fresh physical attempt
  → ResponseStream
  → durable SamplingBoundary
  → bind ContextBaselineCandidate
  → provider response event
  → equality check against bound pair
  → authoritative TurnContextProvenance
```

The binding is visible before provider dispatch in [`turn.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/turn.rs:4447). The commit rejects either component being different, then persists the accepted pair and fragment digests in [`session/mod.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/mod.rs:4142). The regression test explicitly proves that attempt 1 cannot commit after the candidate is rebound to attempt 2 in [`turn_tests.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/turn_tests.rs:1547).

The compact provenance is already close to optimal:

```text
AttemptKey(logical, physical)
State: staged → bound → accepted
PayloadEvidence: bounded fragment digests
```

Kda should symbolically track the identity roles and equality constraints, not concrete UUID values or every stream event.

Useful diagnostics:

- “A context candidate bound to physical attempt B may be committed using attempt A.”
- “This wrapper preserves the logical request but drops the physical-attempt component.”
- “Authoritative context is persisted without the event identity that accepted it.”
- “The first provenance-losing edge is the conversion from `ResponseAttemptIdentity` to a bare request ID.”

### 3. Path representation, execution realm, and fallback substitution

[`PathUri`](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/path-uri/src/lib.rs:32) is deliberately host-independent. Converting it to `AbsolutePathBuf` requires its inferred convention to match the current host; foreign paths are rejected rather than reinterpreted under unrelated host rules in [`to_abs_path`](/C:/Users/kuh/Desktop/kd4/codex-rs/utils/path-uri/src/lib.rs:372).

KD4 currently contains a recognized hazard in [`TurnContext` construction](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/session/turn_context.rs:893):

```text
foreign environment PathUri
  → to_abs_path under host convention
  → conversion failure becomes None
  → fallback selects session host cwd
  → per-turn config receives host AbsolutePathBuf
```

A plain origin trace reports two possible producers. Semantic provenance explains why the host cwd was selected and that it is not a representation of the foreign cwd.

The compact fact should be:

```text
PathMeaning {
  realm: host | executor | remote,
  convention: posix | windows | unknown,
  representation: uri | native,
  derivation: exact | inferred | lossy | fallback-substitution
}
```

It need not retain path contents. Kda’s existing execution-domain model already defines realms and projections in [`execution_provenance.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/execution_provenance.rs:47); the missing feature is composition through failed conversion and fallback selection.

Useful output:

- “Remote Windows cwd could not be projected to this POSIX host; `unwrap_or_else` substituted the session host cwd.”
- “An executor-bound value is host-native because its portable representation was discarded here.”
- “This legacy string was rendered by inferred convention; a later parser assumes an explicit different convention.”

### 4. Owner-scoped elicitation lease identity

An out-of-band lease is not identified by its string token alone. [`OutOfBandElicitationLeaseId`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/elicitation.rs:33) defines exact identity as:

```text
stable transport connection owner + server-issued lease token
```

The registry is keyed by the composite identity. App-server preserves both components when converting its key to the core identity in [`thread_state.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/thread_state.rs:833).

Compact provenance should model this as an atomic scoped identity:

```text
ScopedIdentity {
  owner: ConnectionId,
  local_token: LeaseId,
  implicit_scope: target thread
}
```

Calls such as acquire, release, map insertion, and adapter conversion should preserve the tuple relation. Kda should avoid expanding the possible owner/token cross-product.

Useful diagnostics:

- “The app-server key is composite, but this adapter forwards only `lease_id`.”
- “A lease acquired under connection A may be released under connection B.”
- “The map key no longer contains the owner that established token uniqueness.”
- Reviewer output could show every transformation that preserved or erased the owner component.

### 5. Shell approval decisions with different semantic causes

In shell escalation, `Decision::Prompt` is insufficient to determine whether prompting is permitted. [`DecisionSource`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/runtimes/shell/unix_escalation.rs:370) distinguishes a prefix-rule decision from the unmatched-command fallback.

The source changes which granular policy flag controls the result:

- A prefix-rule prompt requires `rules`.
- An unmatched fallback prompt requires `sandbox_approval`.

That distinction is enforced by [`execve_prompt_is_rejected_by_policy`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/runtimes/shell/unix_escalation.rs:383), and the decision source also selects the escalation execution route around [lines 663–685](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/runtimes/shell/unix_escalation.rs:663). Tests verify the two source-dependent policy checks in [`unix_escalation_tests.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tools/runtimes/shell/unix_escalation_tests.rs:99).

Compact representation:

```text
DecisionProof {
  result: Prompt,
  cause: PrefixRule(rule witness) | UnmatchedFallback,
  governing_capability: RulesApproval | SandboxApproval,
  execution: Unsandboxed | TurnDefault | AdditionalPermissions
}
```

Only the matched witness or fallback classification is necessary, not every rule considered.

Useful output:

- “This prompt is rejected because it came from a prefix rule and granular `rules` approval is disabled.”
- “Refactoring erased `DecisionSource`; the same `Prompt` value can now be checked against the wrong capability.”
- “Unsandboxed execution was selected because the policy rule, rather than the fallback classifier, produced the decision.”

### 6. Prompt contribution meaning

KD4 already demonstrates a compact runtime provenance pattern in [`prompt_provenance.rs`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/context/prompt_provenance.rs:18). Prompt fragments are assigned one of fifteen semantic categories, and a sidecar maps canonical response-item fingerprints to ordered category contributions at [lines 142–150](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/context/prompt_provenance.rs:142).

The composition is:

```text
assembly source
  → semantic category
  → content hash / item fingerprint
  → normalization and mixed-message projection
  → measurement attribution
```

This matters because identical response-item representations can mean repository instructions, task input, history, memory, permissions, or tool schemas. The sidecar avoids parsing prompt prose and preserves mixed-message attribution.

This is also a good explosion and privacy model:

- fixed category vocabulary;
- hashes rather than raw text;
- per-item contribution vectors;
- explicit fallback categories;
- no full causal history.

The test at [`prompt_provenance.rs:606`](/C:/Users/kuh/Desktop/kd4/codex-rs/core/src/context/prompt_provenance.rs:606) verifies that measurements contain hashes and token estimates but not secret prompt text.

A kda consumer could report that a prompt transformation dropped or invalidated its provenance sidecar without ever printing prompt contents.

## Recommended kda model

Semantic provenance should be a sparse typed overlay on existing value flow, not an expansion of `OriginSource`.

A sufficient internal concept is:

```text
Semantic atom:
  domain + role + canonical source

Derivation edge:
  override | alias | implication | conjunction | conversion
  | fallback | bind | accept | owner-scope | projection

Proof quality:
  must | may | unknown | truncated
```

Across a call, the callee summary would describe a recipe over symbolic parameters. At the call site, kda would remap those parameters to caller provenance, as its semantic summaries already remap symbolic places. A conversion adds one typed edge; a conditional records the selected or possible branch; a join retains must/may distinctions.

To prevent provenance explosion:

- Activate semantic tracking only for contract-selected types, fields, calls, and sinks.
- Intern identical derivation nodes as a DAG.
- Retain the winning cause and required operands; summarize shadowed alternatives by class and count.
- Treat composite identities as relations, not Cartesian products of origin sets.
- Cap depth, nodes, alternatives, and fixed-point iterations.
- Widen loops and recursion to a typed `Unknown` or `Truncated` fact.
- Preserve only event identities needed by a protocol transition, not an event log.
- Never infer authority or identity correctness solely from names.
- Emit a shortest sufficient causal slice rather than the complete graph.

## Would this explain causality?

Yes, within a precise boundary.

Today kda can often say “this argument came from that call” or “these two values have different roots.” Semantic provenance could instead say:

> The remote cwd was replaced because host conversion rejected its convention, the fallback selected session cwd, and that host-derived path then reached a remote execution consumer.

Or:

> The context became authoritative because the first response event carried the same logical/physical attempt pair that had bound the candidate; the stale retry failed that equality check.

That is genuine causal explanation, not merely suspicious-code reporting.

However, static kda can normally explain a conditional causal recipe—what must or may cause a value under the program—not which runtime alternative actually occurred. Actual historical causality requires a runtime receipt such as KD4’s accepted-attempt IDs, configuration-layer metadata, or prompt fingerprints. Kda should keep those two claims distinct.

My recommendation is to prioritize three semantic-provenance families:

1. Decision provenance: configuration, feature, and policy resolution.
2. Scoped identity provenance: attempts, leases, approvals, and owner-bound tokens.
3. Representation provenance: path realms, conventions, conversions, and fallbacks.

The prompt sidecar is a strong bounded-design exemplar. A universal provenance vocabulary would be too expensive and too speculative; a shared bounded engine with domain-specific contracts would materially improve both diagnostics and reviewer explanations.
