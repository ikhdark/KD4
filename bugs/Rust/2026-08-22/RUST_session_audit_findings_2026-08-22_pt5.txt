# “What async correctness properties are left to human reasoning after Rust has accepted the program?”

Most of the important ones are temporal.

Rust establishes that a suspended future is memory-safe, that its stored references remain valid, and—when required by its use—that it is `Send`. It does not establish that:

- cancellation leaves the operation logically consistent or restartable;
- child tasks terminate with their owner;
- task failures are observed;
- a resource or decision remains logically valid after suspension;
- waits are deadlock-free, fair, or eventually wake;
- a timeout bounds the whole operation;
- shutdown reaches quiescence;
- independent work actually runs concurrently.

An `await` polls a pinned future and suspends when it returns `Pending`; the suspended state becomes part of the enclosing future. [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html) specifies polling and output, but has no cancellation, deadline, supervision, or atomicity contract. Dropping the future normally cancels it, running ordinary synchronous destructors for initialized state; stable async cleanup cannot be assumed because [`AsyncDrop` remains experimental](https://doc.rust-lang.org/stable/core/future/trait.AsyncDrop.html). The official [async cancellation discussion](https://rust-lang.github.io/async-book/part-guide/more-async-await.html) therefore correctly treats every suspension as a possible logical interruption point.

That is the useful boundary for KDA: not “async syntax that looks suspicious,” but properties of obligations, ownership, observation, and ordering at suspension and task-lifetime boundaries.

## Recommended priority

| Problem class | Analyzer disposition |
|---|---|
| Cancellation leaves an acquired/consumed obligation open | Strong default or contract-backed diagnostic |
| Task ownership, error observation, and termination | Strong, with runtime lifecycle contracts |
| Shutdown fails to close admission, drain, or join | Strong for declared managed components |
| Definite lock-order or wait-for cycle | Strong default diagnostic |
| Lost-notification or freshness protocol violation | Strong with exact primitive/project contracts |
| Known blocking operation in executor polling domain | Strong default diagnostic |
| Deadline reset or timeout without containment | Strong contract-backed diagnostic |
| `select` cancellation and proven biased starvation | Derived checks, not a generic `select` lint |
| Reliable stream item not acknowledged or requeued | Contract-backed protocol diagnostic |
| Sequential awaits that could be concurrent | Query or advisory only |
| “Stream not fully consumed,” “guard held across await,” “spawn not joined” in isolation | Too intent-dependent for a general error |

## 1. Cancellation-cut obligation integrity

This is the highest-value general analysis.

### Semantics and compiler gap

An async function is a state machine. At a source-level `await`—more precisely, whenever polling returns `Pending`—control returns to its owner. The owner may then drop it. Memory is cleaned up, but Rust does not undo dequeues, external writes, registrations, reservations, or partial protocol transitions.

Typical failures include:

- remove an item, then await before transferring or requeuing it;
- reserve capacity or register interest, then abandon it without rollback;
- mutate durable or external state before an await and publish completion afterward;
- consume part of a framed input and lose the partial operation;
- start background work and assume dropping its initiating future stops that work.

The compiler permits these because all involved states and drops are type-correct. There is no language-level declaration saying “this resource must be committed, transferred, or restored before cancellation.”

### Provable facts

KDA can prove:

- which coroutine states are reachable at each suspension;
- which places are initialized, moved, or live there;
- which semantic obligations were acquired or consumed;
- whether the coroutine-drop path commits, rolls back, releases, transfers, or merely destroys them;
- whether every normal, error, unwind, and cancellation exit closes the obligation.

This should use the generated coroutine and coroutine-drop CFG, not source `.await` counting. Hand-written `Future` implementations need separate `poll` analysis or explicit contracts.

### Required summaries

Cross-function analysis needs parameter-, receiver-, and return-relative effects such as:

- `acquire(resource)`;
- `consume(item)`;
- `transfer(resource, destination)`;
- `commit`, `rollback`, `release`, `requeue`;
- effects performed by `Drop`;
- cancellation outcome of an awaited operation.

Cancellation cannot remain binary. Useful outcomes include:

- no observable change;
- restart-safe;
- progress lost but data retained;
- data/item lost;
- fairness queue position lost;
- external/background work continues;
- unknown.

Tokio itself distinguishes data loss from queue-position loss in its [`select!` cancellation documentation](https://docs.rs/tokio/latest/tokio/macro.select.html).

### Precise bounded analysis

For each exact MIR suspension cut:

1. Compute the finite set of open semantic obligations.
2. Follow the corresponding coroutine-drop paths.
3. Diagnose only when every feasible cancellation cleanup path leaves a required obligation open.
4. Bound place projections, local call depth/SCC iterations, and summary size.
5. Treat alias escape, unresolved dispatch, dependency bodies, unsafe code, and missing contracts as `Unknown`.

This is runtime-independent at its core. Runtime adapters only identify additional discard sites such as `select` losers, timeout expiration, task abort, and task-group teardown.

## 2. Resource ownership and logical authority across suspension

“Resource held across await” is not itself an error. Async mutexes are explicitly designed for it, and futures often must retain permits, transactions, buffers, or stream items while suspended.

The valuable properties are narrower.

### Open terminal obligations

A permit, transaction, message, lease, or owned item may require exactly one terminal action. This is the surrounding-future version of cancellation integrity:

```text
acquire → await* → commit | rollback | transfer
```

KDA can prove a violation when an exact resource identity remains open on a normal, error, or cancellation exit. Helper summaries are required when terminalization occurs across function boundaries.

### Freshness and authority

A borrow can remain memory-valid while becoming logically stale. Examples include:

- authorize using configuration, await, then perform the privileged action;
- read a generation or ownership state, await, then mutate without revalidation;
- borrow watched state across an await, preventing its producer from updating.

The compiler cannot reject these because logical freshness is not a lifetime. Tokio explicitly warns that a `watch::Ref` held across an await in a `!Send` environment can deadlock the producer; `borrow_and_update` also has distinct observation semantics. See [`watch::Receiver`](https://docs.rs/tokio/latest/tokio/sync/watch/struct.Receiver.html).

A precise checker needs configured effects:

- snapshot or authority source;
- invalidation/mutation event;
- generation or lease identity;
- freshness-sensitive sink;
- refresh/revalidation event.

Bound it to exact configured sources and sinks and require a proven path from snapshot through suspension to sensitive use without refresh. This semantic core is runtime-independent.

## 3. Task lifetime and supervision

### Semantics and compiler gap

Spawning creates an independently scheduled computation. Rust may enforce `'static` and `Send` at a particular spawn API, but that establishes memory safety—not parent/child lifetime, failure propagation, or observation.

Handle semantics are library-specific:

- Tokio starts the task immediately and dropping its [`JoinHandle`](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html) detaches it.
- [`async-std::JoinHandle`](https://docs.rs/async-std/latest/async_std/task/struct.JoinHandle.html) also detaches on drop.
- Dropping a [`smol::Task`](https://docs.rs/smol/latest/smol/struct.Task.html) cancels it; explicit `detach` keeps it running.

A generic “dropped task handle” rule would therefore be wrong.

### Provable facts

KDA can track:

- the spawned task identity;
- the handle or task-set receiving ownership;
- whether ownership is awaited, returned, transferred, detached, aborted, or dropped;
- whether its output is `Result`-like and whether both join failure and inner failure are observed;
- whether the owner may exit while the child still accesses owner-scoped logical resources;
- whether cancellation is followed by confirmed termination.

`abort` is not equivalent to quiescence. In Tokio it requests cancellation, but completion may take time, and `spawn_blocking` generally cannot be aborted after starting.

### Summaries and bounded rule

Runtime/project contracts need to describe:

- spawn lifecycle;
- handle-drop behavior;
- detach and abort effects;
- join/wait completion guarantees;
- task-set insertion and draining;
- error-observation projections.

For a declared task owner or managed component, require every exit to do one of:

1. join the child;
2. transfer ownership to another declared supervisor;
3. cancel and then await confirmed termination;
4. perform an explicitly allowed detach.

This is a finite ownership-flow problem. Unknown wrapper behavior suppresses the diagnostic rather than assuming detachment.

## 4. Shutdown and quiescence

Shutdown is not a single cancellation call. It is usually a protocol:

```text
stop admission
  → signal producers/tasks
  → close channels or trackers
  → drain accepted work
  → join/corroborate termination
  → release shared resources
```

Tokio’s mpsc documentation, for example, says clean shutdown requires closing the receiver and then consuming it to completion; simply dropping it can discard queued messages. [`TaskTracker::wait`](https://docs.rs/tokio-util/latest/tokio_util/task/task_tracker/struct.TaskTracker.html) requires the tracker to be both closed and empty.

Rust accepts missing or misordered phases because each operation remains locally valid.

KDA can prove:

- exact component, task, channel, sender, permit, and tracker identities;
- close, cancel, drain, join, and completion events;
- happens-before edges;
- retained endpoints that prevent closure;
- wait-for cycles;
- parent exits that precede child termination.

Cross-function summaries must expose parameter-relative lifecycle events and child wait dependencies.

The bounded analysis should operate only on declared component roots and a finite shutdown vocabulary. Emit on:

- a required terminal phase missing on a proven exit;
- resource teardown before a proven dependent task join;
- a definite wait cycle;
- waiting for channel closure while a reachable supervised child retains a sender;
- cancel without subsequent termination confirmation where the runtime requires it.

The abstract phase model generalizes. Concrete close, drain, and task-set semantics are runtime- or library-specific.

## 5. Synchronization: ordering, wait dependencies, and notification protocols

A generic “guard across await” warning is too weak. Tokio’s async mutex permits that by design, while even a standard mutex may be accepted in a current-thread `!Send` future. The important question is what the awaited work needs.

### High-value proofs

KDA should target:

- definite lock-order cycles;
- waiting while holding resource A for a task/event whose progress requires A;
- self-dependency through a helper;
- state published after its notification;
- waiter registered after the authoritative state check;
- coalesced notifications used as if they counted events;
- snapshot/notification generation mismatches.

Rust prevents unsafe data races through sound synchronization APIs, but not deadlock, starvation, or lost logical events.

Tokio’s [`Notify`](https://docs.rs/tokio/latest/tokio/sync/struct.Notify.html) illustrates why primitive semantics matter: it stores at most one permit, notifications can coalesce, and some multi-consumer patterns must enable a waiter before checking shared state. Tokio’s [`Mutex`](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html) is FIFO, and cancellation loses queue position; other mutexes have different fairness behavior.

### Bounded analysis

Use exact resource identities and parameter-relative summaries for:

- acquire/release;
- wait;
- publish;
- register;
- notify;
- observe generation.

Diagnose only when all edges of a lock or wait-for cycle are exact, or when a configured notification protocol has a proven ordering contradiction. Fairness and eventual progress should remain unknown unless the primitive contract and control flow make starvation inevitable.

Lock-order and happens-before reasoning are portable. Notification capacity, fairness, and wake-registration rules require adapters.

## 6. Executor blocking and cooperative starvation

`Future::poll` is expected to return promptly, but the type system does not enforce this. Cooperative executors cannot schedule other tasks on a worker while a task blocks or runs indefinitely. Tokio states this directly in its [task documentation](https://docs.rs/tokio/latest/tokio/task/index.html).

KDA can prove a useful subset:

- an exact known-blocking call is reachable in executor polling context;
- a local synchronous helper transitively performs that blocking call;
- the call is outside a recognized blocking/offload domain;
- synchronous destructor cleanup on an executor path performs blocking work.

Required summaries are chiefly `may_block` plus execution domain:

- executor poll;
- blocking pool;
- dedicated thread;
- inline caller;
- background/custom domain.

The bounded checker should use exact APIs and local direct calls. It should not classify arbitrary calls from names. CPU-loop starvation is only precise for very narrow cases—such as a syntactically nonterminating loop with no suspension or blocking-domain transfer—and otherwise belongs in a query.

The principle is portable. Offload APIs are adapters: Tokio and async-std use `spawn_blocking`; smol commonly uses `unblock`; custom runtimes must declare their domains.

## 7. Timeout and deadline integrity

### Semantics and compiler gap

A timeout is normally a race plus cancellation, not preemption. Tokio’s [`timeout`](https://docs.rs/tokio/latest/tokio/time/fn.timeout.html) drops the inner future on expiration, polls the inner future before checking the deadline, and may therefore overrun when the inner future does not yield.

A timeout also does not necessarily stop:

- a detached child;
- already-started blocking work;
- a process;
- an external operation already committed or enqueued.

Repeated relative timeouts can silently expand a supposed end-to-end budget:

```text
retry N times:
    timeout(5s, phase())
```

is not a five-second operation.

### Provable facts and summaries

KDA can track:

- deadline provenance;
- absolute deadline versus fresh relative duration;
- remaining-budget calculations;
- propagation into helpers;
- spawned, blocking, process, and external effects inside the timed operation;
- cancellation containment and subsequent reap/join.

Summaries need deadline transformations and the same completion/cancellation dimensions used elsewhere.

A bounded checker should start from declared deadline-bearing entry points and support simple affine duration/deadline expressions. Strong diagnostics include:

- recreating a full relative timeout on a retry path governed by one total-budget contract;
- a child operation receiving a duration unrelated to the parent deadline;
- timeout success/error handling that leaves proven background work uncontained;
- timeout followed by teardown before cancellation completion.

Deadline lineage is runtime-independent; exact timeout polling and cancellation behavior require an adapter. A blanket “missing timeout” lint is not justified.

## 8. `select` is a cancellation and scheduling surface, not one property

A selection construct may cancel losers, preserve reusable futures, poll in biased or randomized order, evaluate guards eagerly, or impose fused-future requirements. Those semantics are not standardized across runtimes and combinator libraries.

For Tokio specifically:

- branches run concurrently in the same task, not necessarily in parallel;
- losing branch futures are canceled;
- default polling order is randomized;
- `biased;` uses source order and can starve a lower shutdown branch behind an always-ready stream;
- all disabled branches without `else` panic.

Precise checks are therefore:

- feed every losing branch into cancellation-cut analysis;
- warn about biased starvation only when a higher branch is proven always ready in the enclosing loop;
- detect all-disabled panic only when guards/pattern states make it definite;
- model persistent versus reconstructed futures;
- model `futures::select!` fused-future requirements separately.

These checks need macro/combinator contracts, not a common suffix list. Unknown selection constructs should remain unknown.

## 9. Stream consumption

The [`Stream` trait](https://docs.rs/futures-core/latest/futures_core/stream/trait.Stream.html) specifies `poll_next` and termination, but says nothing about delivery guarantees, replay, acknowledgment, drain policy, or whether abandoning the stream loses work.

Consequently:

- “stream not fully consumed” is not a general bug;
- sequential item processing may be intentional;
- losing an item after it has been yielded is different from canceling a cancel-safe `next()` call;
- reliable-consumption semantics belong to the channel, protocol, or application contract.

The high-value bounded check is:

```text
item acquired → process/await* → ack | commit | requeue | explicit discard
```

It reuses resource-obligation and cancellation analysis. Shutdown-specific stream checks can require close-before-drain and drain-before-drop. The core is portable, but delivery, close, lag, and acknowledgment semantics need exact contracts.

## 10. Accidental serialization should not be a correctness lint

Two sequential awaits express a valid order. Replacing them with concurrency changes:

- side-effect ordering;
- cancellation behavior;
- which error wins;
- peak memory and connection use;
- rate limiting and backpressure.

An analyzer could identify a concurrency opportunity only when effect summaries show that both operations are independent, commute, have no shared resource, and are permitted by a concurrency-budget contract. Even then, absence of a dependency does not prove concurrency was intended.

This belongs in an opt-in semantic query or performance advisory, not the quality gate. The same applies to sequential stream loops versus buffered unordered consumption.

# Strongest general architecture

KDA should use a **cut-sensitive relational effect architecture** rather than add independent async lints.

## 1. Make coroutine cuts first-class

Represent each async body as:

- its resume CFG;
- every suspension cut;
- the exact coroutine-drop CFG reachable from each cut;
- normal, error, unwind, and cancellation exits.

KDA’s MIR protocol already requests coroutine resume/drop bodies, cleanup blocks, and explicit drops in [mir-fact-protocol.md](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/docs/mir-fact-protocol.md:28>). That is the correct foundation.

## 2. Maintain a symbolic obligation and ownership ledger

Track exact or parameter-relative identities for:

- resources and terminal obligations;
- snapshots, generations, and leases;
- tasks and handles;
- channel endpoints and permits;
- deadlines;
- synchronization and shutdown events.

At every cut, ask:

> Which obligations are open, and what does every reachable discard path do to them?

## 3. Enrich shared effect summaries

KDA already has phase, completion, lifecycle, and per-family incompleteness in [effects.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/effects.rs:176>). Extend the conceptual lattice with:

- cancellation/discard outcome;
- execution domain;
- task-handle drop policy;
- termination confirmation;
- wait/acquire/signal/close/drain/join effects;
- deadline transformation;
- freshness source/invalidation/revalidation.

Keep `must` versus `may`, success/failure/drop conditions, bounded witness paths, and family-specific `Unknown`.

## 4. Use versioned semantic adapters

Contracts should be keyed by:

- canonical callable/type identity;
- crate and compatible version range;
- feature configuration;
- runtime/library family;
- optional workspace policy override.

The current audited suffix tables in [async_lints.rs](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/async_lints.rs:37>) demonstrate why. The unsafe table includes `read`, `read_buf`, `write`, and `write_buf` under a workspace policy, while current Tokio documentation classifies those operations as cancellation-safe. A strict workspace policy may be legitimate, but it must be scoped and distinguished from the runtime’s semantic guarantee.

Custom runtimes get no guessed behavior: they supply contracts or KDA reports `Unknown`.

## 5. Compose several bounded solvers over one fact model

The same facts should power:

- cancellation-obligation closure;
- task ownership and supervision;
- shutdown/quiescence;
- lock and wait-for cycles;
- notification ordering;
- freshness across suspension;
- deadline lineage;
- executor-domain blocking;
- query-only concurrency opportunities.

Use finite SCC iteration, caps on summaries and place projections, exact call remapping, and three-valued results. This matches KDA’s existing rule to [emit only proven contradictions](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/docs/bounded-cross-function-reasoning.md:98>).

## Bottom line

The strongest general contribution cargo-kda can make is to prove that **logical obligations remain closed under suspension, cancellation, task separation, and shutdown**.

That subsumes the valuable parts of cancellation safety, resource ownership, task supervision, streams, selection, and timeout analysis. Lock/wait graphs, freshness, and executor domains complement it. Accidental serialization and broad intent questions should remain queries.

The decisive precision rule is:

> Diagnose an async correctness error only when exact control flow, exact resource/task identity, and complete relevant effect summaries establish a contradiction; otherwise preserve `Unknown`.

That architecture generalizes across production codebases while keeping runtime differences explicit instead of pretending Rust’s async ecosystem has one set of spawn, selection, timeout, and synchronization semantics.

# Research conclusion

The right analysis boundary is not “uses a mutex/atomic incorrectly.” It is:

> A component maintains a semantic obligation across concurrent actors, but the events that establish, preserve, publish, or discharge that obligation do not form a valid protocol.

Safe Rust largely guarantees memory validity and freedom from unsynchronized non-atomic data races through ownership, borrowing, `Send`, and `Sync`. It does not prove that a value is current, several individually safe operations form one logical transaction, a notification corresponds to a particular state change, a task is eventually joined, or any actor makes progress. [The Rust Book](https://doc.rust-lang.org/book/ch16-00-concurrency.html) describes the compile-time safety boundary; `Send` and `Sync` govern safe transfer and sharing, not application-level protocols. [Send and Sync documentation](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html)

## The reusable semantic substrate

KDA should treat a bounded component—normally an ADT plus selected callers—as a protocol slice:

```text
Protocol slice
├── Actors: task, thread, owner, supervisor
├── State: exact place, logical key, generation/version
├── Events: observe, mutate, publish, register, wake,
│           acquire, release, send, receive, spawn, cancel, join
├── Relations
│   ├── program order / control dependence
│   ├── owns / protects / derives-from
│   ├── publishes / signals / acknowledges
│   └── exact happens-before
└── Projections
    ├── lock-order and wait-for graphs
    ├── synchronization-domain graph
    ├── state/publication graph
    ├── task-ownership tree
    └── logical-interference matrix
```

The important design constraint is that these relations remain distinct. “Uses the same channel,” “touches the same lock,” and “has the same cancellation token” do not by themselves prove a particular handoff or happens-before edge. KDA already expresses this well in [async_protocol_collector.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/async_protocol_collector.rs:7), and its bounded-summary policy correctly degrades unresolved or capped reasoning to unknown in [bounded-cross-function-reasoning.md](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/docs/bounded-cross-function-reasoning.md:3).

For diagnostics, I would use three confidence classes:

- **Definite protocol violation:** exact identities, feasible control flow, relevant concurrency, and the semantic obligation are all established. “Definite” can mean that a violating execution exists, not that every schedule fails.
- **Structural hazard:** the bad execution is plausible, but aliasing, concurrent reachability, or the obligation is not fully established.
- **Unusual design:** mechanism use looks uncommon, but a valid bridge, supervisor, serializer, generation, or snapshot contract explains it. No diagnostic.

## Analyzable classes

| Class | Why Rust does not prevent it | Required semantic model | Definite versus unusual | Whole-program need and valuable bounded subset |
|---|---|---|---|---|
| **1. Stale observations and revoked authority** | A copied, cloned, or atomically loaded value remains memory-safe after an `await`, unlock, callback, or message receipt. Its freshness or authority may nevertheless have expired. | Value provenance from authoritative state; logical key and generation; invalidating events; refresh/revalidation operations; control dependence of generation or liveness checks. | Definite when a known invalidation or newer generation occurs before the old value is used in an operation requiring the current generation. Merely retaining configuration, an intentional snapshot, or a monotonic value is unusual but valid. | Usually component-level, occasionally cross-task. Bound it to exact field-derived snapshots that cross an invalidation boundary and reach configured authority-sensitive sinks without refresh or generation validation. Avoid name-based “revision” heuristics as primary evidence. |
| **2. Inconsistent synchronization domains and split invariants** | Rust can safely protect `state.a` with one mechanism and `state.b` with another while the application requires an invariant over `(a, b)`. Each access is safe; the compound transition is not atomic. | A synchronization-domain graph or hypergraph: operations → invariant cohort/state places → serializing mechanisms. ## Most valuable bounded subset

I would prioritize the following, in order:

1. **State/register/publish/wake protocols**
   - Exact `Notify` registration-before-check.
   - State mutation before notification.
   - Structural `watch` projection consistency.
   - High signal and usually contained within one ADT.

2. **Lost-update RMW with semantic writer domains**
   - ArcSwap and whole-record persistent RMW.
   - Recognize CAS/RCU, transactions, and separate writer serializers.
   - Do not use variable names such as `write_lock` as proof.

3. **Task lifecycle and cancellation obligations**
   - Cancel/abort must be followed by join or another quiescence proof before “stopped.”
   - Result-bearing tasks need an observer or recognized supervisor.
   - Destructive handoff and raw accounting across cancellation points need transfer, rollback, or RAII cleanup.

4. **Bounded lock-order and wait-for cycles**
   - Exact resources, live guard intervals, parameter-relative helper summaries.
   - Direct self-deadlock and two-node cycles first.
   - Keep general cycles at “potential” unless concurrency and path feasibility are established.

5. **Contract-declared synchronization domains**
   - Let projects declare invariant cohorts, publication pairs, terminal ordering, and concurrency keys.
   - Check local and shallow cross-function conformance rather than trying to infer business invariants globally.

Atomic state-machine checks and starvation analysis should follow later. Both are important, but without explicit roles or strong structural proof they will generate many diagnostics about legal, intentional designs.

## Architectural recommendation for KDA

KDA already has most of the right pieces: the event/HB model, parameter-relative lock summaries, logical interference, state projection, ownership handoff, and managed-component lifecycle analyses. The next conceptual step should be convergence on one shared protocol-slice identity and summary layer, not more independent syntax detectors.

In particular:

- Resource identities should be exact HIR-resolved places plus logical key/generation, not receiver-name suffixes.
- Helper summaries should expose preconditions, effects, acquired/retained resources, spawned task effects, and outstanding obligations.
- Unknown aliases, dynamic dispatch, macro opacity, and summary caps must remain explicitly incomplete.
- Every diagnostic should show the violated semantic relationship and the smallest counterexample path.
- Separate “feasible protocol violation” from “design smell”; do not present lack of a proof of safety as proof of a bug.

That bounded, contract-assisted approach can find meaningful logical concurrency failures without pretending to solve arbitrary temporal logic, alias analysis, scheduling, or whole-program liveness.

## Promising KD4 analyses

### 1. Terminal publication must follow completed terminal detachment

The real invariant is unusually explicit in KD4:

> The completed turn must be detached before `TurnComplete` becomes observable, because the client may immediately submit another turn.

The code awaits terminal registration, then awaits detachment, then awaits live delivery in [`tasks/mod.rs`](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1619). The explanation appears immediately before the detach operation ([comment](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:1629)). Later, terminal milestone publication must finish before idle is emitted or pending work starts ([tasks/mod.rs](C:/Users/kuh/Desktop/kd4/codex-rs/core/src/tasks/mod.rs:3717)).

The implicit facts are:

```text
authoritative terminal registration completes
    → terminal detachment completes
    → terminal event becomes externally observable
    → idle/replacement may become observable
```

Ordinary CFG dominance is insufficient because dominating a call to an async function proves call/future construction order, not completion order. The invariant also crosses helpers and distinguishes durable authority, live delivery, and external observability.

The smallest workable model is:

- semantic events with `Start`, `Complete`, and `Observable` points;
- `await f()` adds `Complete(f) → continuation`;
- summarized helper effects can expose `Complete(detach)` and `Observable(terminal-event)`;
- must/may ordering is joined across outcomes;
- contracts identify which operation makes an event observable.

Unknown calls affecting the terminal coordinator should invalidate only terminal-related must-order proofs. A timeout, abort request, or failed delivery must not be treated as successful completion.

Diagnostics enabled include:

- terminal delivery may become observable before terminal detachment completes;
- idle/replacement may be published before the terminal milestone completes;
- durable terminal state is constructed or enqueued but not awaited before success;
- cleanup capable of holding the turn fence occurs after the declared cleanup boundary.

Precision should be high because the operations and protocol identity are explicit. Complexity is medium and this is the best initial adopter. It would replace the lexical assumptions in the current specialized [`terminal_order`](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/terminal_order.rs:54) analysis with completion-sensitive facts.

- `writer.finish(...).await`

- notification

- successful await completion;
- protected-state publication after lock release;

## Recommended reusable primitive

I would evolve `AsyncProtocolGraph` into a bounded **causal/observable-order graph** and bridge it to semantic summaries and `AsyncRelationshipIndex`.

Calling everything “happens-before” would be misleading. The graph should contain several edge kinds:

- program order and CFG dominance;
- awaited completion;
- spawn and successful join;
- matched channel transfer;
- matched lock handoff;
- restricted release/acquire publication;
- waiter registration, notification, and observation;
- durable publication;
- callback enablement;
- ownership transfer/discharge;
- task or endpoint closure.

Each edge should carry:

- strength: `Must`, `May`, or absent because unknown;
- provenance: await, CFG, channel match, contract, atomic observation, join, etc.;
- protocol/resource identity;
- outcome or condition where relevant.

Nodes need semantic endpoints such as `Start`, `Complete`, `Publish`, `Observe`, `Transfer`, and `Drop`. This is the important addition: “call A precedes call B” is weaker than “A has observably completed before B becomes enabled.”

The existing summary join behavior—must intersection and may union—is appropriate. The existing policy that unknown notification identity never matches as a wildcard is also appropriate. What must change is the lexical total-order lowering: task-local must edges should come from CFG dominance/evaluation order, not sorted source ranges.

## Degradation and scope

Unknown concurrency should degrade locally:

- An unresolved call touching resource `R` removes must proofs involving `R`, not the entire graph.
- Unmatched channel messages receive no send/receive edge.
- Escaping clones prevent last-owner/channel-close proofs.
- Dynamic callbacks produce may-events.
- Branch joins intersect must edges and union may edges.
- Loops do not imply cross-iteration order without a generation/epoch identity.
- Cancellation and abort create requests, never implicit completion.
- External durable writers create eventual-observation obligations, not invented local HB edges.

A default diagnostic should require either a definite reversed order or a missing must-path in a fully modeled protocol slice. In incomplete slices, kda should normally report “cannot prove” only under an opt-in strict contract.

This remains bounded and deliberately excludes schedule enumeration, data-race detection, general memory-model verification, fairness, arbitrary channel matching, and full deadlock verification.

## Final assessment

Yes, ordering should become a reusable semantic primitive in kda.

The most valuable path is:

1. Integrate completion-sensitive semantic facts with the existing async graph.
2. Make task-local edges CFG-aware and must/may-sensitive.
3. Adopt it first for terminal detachment/publication.
4. Add the unified-exec release/latch protocol.
5. Then add keyed callback handoff.
6. Treat durable polling and last-owner shutdown as later, higher-complexity extensions.

That would let existing specialized analyses—`terminal_order`, `sticky_completion`, `generation_wake`, `keyed_temporal`, callback effects, ownership handoff, and managed async components—share causal proofs without turning cargo-kda into a concurrency model checker.

### 1. Contract-driven destruction ordering

**Semantic rule.** For a value of type `T`, Rust first calls `T::drop`, then recursively drops its fields. Struct and active enum fields drop in declaration order; locals in the same scope drop in reverse declaration order; temporaries drop in reverse creation order. Move-captured closure fields have unspecified order. Partial initialization drops only initialized fields. [Rust Reference](https://doc.rust-lang.org/reference/destructors.html)

**Compile-correct bug.**

```rust
struct ServerFixture {
    home: TempDir,       // removed first
    child: ChildServer,  // stopped second
}
```

If the child may still use `home` as its current directory, this is wrong on platforms where removing an in-use directory fails. Reordering fields silently changes behavior without a type error.

Other cases include:

- a logging sink dropped before a worker that logs during shutdown;
- a runtime dropped before a resource whose destructor schedules onto it;
- a mapping or allocator released before an object whose destructor accesses it;
- two shadowed lock guards, where the earlier binding remains alive until the block exits.

**Required relationships.**

- Exact field/local/temporary drop order from MIR.
- A type-level finalizer summary such as:
  - `finalizes(child_process)`;
  - `invalidates(path)`;
  - `requires_live(runtime)`;
  - `releases(lock identity)`.
- Resource identity substitution between constructor arguments, stored fields, and destructor effects.
- Wrapper propagation through `Option`, tuples, enums, and collections where bounded.
- Recognition that the user-written `Drop` body runs before automatic field destruction and may `take` or explicitly drop fields.

**Local or interprocedural?** The ordering is local. Learning what each destructor does usually requires a type-level interprocedural summary. Cross-field semantic identity—such as “this child’s cwd is that `TempDir`”—may require constructor summaries.

**False-positive boundary.** Do not report merely because two fields implement `Drop`. Require a proven ordering edge from an explicit project contract, a trusted library model, or a resolved resource relationship. For closure captures, report only that a required order is not guaranteed; do not predict a particular order.

This is an excellent regression guard for invariants like the one already documented in `TestAppServer`.

### 2. Effective drop-point conflicts

**Semantic rule.** Destructor timing follows drop scopes, not last source use. In particular, a `match` scrutinee is not itself a temporary scope, so a guard temporary can survive through the match. Rust 2024 narrows some `if let` and tail-expression temporaries, but does not eliminate all surprising scopes. Temporary lifetime extension is syntax-driven, and its detailed rules remain explicitly subject to change. [Rust Reference](https://doc.rust-lang.org/reference/destructors.html)

**Compile-correct bug.**

```rust
match mutex.lock().unwrap().is_ready() {
    true => mutex.lock().unwrap().update(), // deadlock
    false => {}
}
```

The first guard can remain alive through the match. Another subtle case is shadowing:

```rust
let guard = mutex.lock().unwrap();
let guard = mutex.lock().unwrap(); // first guard was not dropped by shadowing
```

**Required relationships.**

- MIR `Drop`/`StorageDead` points rather than a source-level lifetime approximation.
- Guard type and protected-resource identity.
- Conflicting operations while the guard is live:
  - reacquiring the same non-reentrant lock;
  - waiting for work that requires the guard to release;
  - deleting or closing a resource whose release is deferred to guard destruction.
- Optional helper summaries such as “this call acquires parameter-relative lock `self.state`.”

**Local or interprocedural?** Direct conflicts are local. A helper that reacquires or waits on the same resource requires bounded parameter-relative summaries.

**False-positive boundary.** A long-lived guard is not by itself a correctness bug. Report only a proven conflict or a declared maximum-lifetime contract. Generic “tighten this significant drop” checks already overlap with Clippy’s `significant_drop_in_scrutinee` and `significant_drop_tightening`; KDA’s value would be resource identity and call composition, not another stylistic warning. [Clippy lint documentation](https://rust-lang.github.io/rust-clippy/master/index.html#significant_drop_in_scrutinee)

### 3. Suppressed-finalizer obligations

**Semantic rule.** `mem::forget` consumes a value without running its destructor. This is safe at the language level because Rust does not guarantee that destructors always run; resources may nevertheless leak or semantic rollback may be skipped. [std::mem::forget](https://doc.rust-lang.org/core/mem/fn.forget.html)

`ManuallyDrop<T>` similarly suppresses automatic destruction until the value is explicitly taken or dropped.

**Compile-correct bugs.**

```rust
let guard = mutex.lock().unwrap();
std::mem::forget(guard);
let _again = mutex.lock().unwrap(); // permanently blocked
```

For a reservation guard, forgetting it may retain a capacity slot forever. For a transaction guard, it may suppress rollback. For a child-process guard, it may suppress reaping.

**Required relationships.**

- Exact resolved suppression operations:
  - `mem::forget`;
  - `ManuallyDrop::new`;
  - `Box::leak`;
  - `Arc::into_raw`/`Rc::into_raw`;
  - project-specific leak or disarm operations.
- The suppressed type’s semantic on-drop transition.
- Path-sensitive matching of ownership reconstruction:
  - `Vec` raw parts reconstructed by `from_raw_parts`;
  - `Arc::into_raw` paired with `Arc::from_raw`;
  - every `ManuallyDrop` field taken exactly once.
- Declared accepted outcomes such as transfer to FFI, process-lifetime retention, or bounded safety leak.

**Local or interprocedural?** Direct `forget(guard)` is local. Helper functions that consume and reconstruct ownership need bounded summaries. Raw ownership passed to FFI generally requires a declared transfer contract.

**False-positive boundary.** Never equate forgetting with a bug automatically. The Windows pipe code is a strong counterexample: retaining the allocation is an intentional safety disposition, and retaining its permit bounds the leak. The right result is “explicitly abandoned/retained under a declared policy,” not “missing drop.”

Clippy’s `mem_forget` only prohibits the mechanism broadly; a semantic analyzer should instead check whether the finalization obligation has an accepted disposition. [Clippy lint documentation](https://rust-lang.github.io/rust-clippy/stable/index.html#mem_forget)

### 4. Last-owner finalization for `Arc` and `Rc`

**Semantic rule.** Dropping an `Arc<T>` drops `T` only when the last strong `Arc` is destroyed. `Weak` does not keep `T` alive, while strong cycles prevent finalization indefinitely. [Arc documentation](https://doc.rust-lang.org/std/sync/struct.Arc.html)

Therefore:

```rust
drop(service);
```

means “release this ownership share,” not necessarily “close the service.”

A particularly precise `Arc` trap is `Arc::try_unwrap(x).ok()`: concurrent owners can all observe that they are not unique, discard their `Err(Arc<T>)`, and collectively destroy `T` without any caller receiving it. `Arc::into_inner`, when called on every clone, guarantees exactly one winner. [Arc::try_unwrap and into_inner](https://doc.rust-lang.org/std/sync/struct.Arc.html#method.try_unwrap)

**Compile-correct bugs.**

- Dropping the apparent “main” owner and then assuming a file, channel, runtime, or service has closed.
- A background task retains a clone, so shutdown waits or never happens.
- A strong parent/child cycle prevents a destructor-based terminal action.
- Several owners use `try_unwrap(...).ok()` to elect exactly one finalizer, but no owner wins.

**Required relationships.**

- Allocation identity across `Arc::clone`, moves, fields, task captures, returns, and trait-object coercions.
- Strong versus weak edges.
- A finalization contract on the inner value.
- Knowledge of which aliases remain live or have escaped.
- For the `try_unwrap` race, result-use analysis and evidence that exactly-one extraction/finalization is required.

**Local or interprocedural?** Occasionally local, but normally requires bounded clone/escape summaries and task-capture facts. Fully general reference-count reasoning is neither necessary nor realistic.

**False-positive boundary.**

- Unknown aliases must produce “unknown,” not a diagnostic.
- Do not count `Weak` as a strong owner.
- Strong cycles should be reported only when the cycle is fully proven and finalization matters; “an `Arc` points to something containing an `Arc`” is insufficient.
- `try_unwrap(...).ok()` is not necessarily wrong when opportunistic extraction is genuinely acceptable.

The existing RMCP close path is a good negative example: it explicitly handles the non-unique case and waits for transport closure.

### 5. Async finalization and cancellation parity

**Semantic rule.** Dropping an in-progress future cancels it: it will make no further progress, and only ordinary destruction of its current state remains available. An async function can therefore stop after any suspension point. [Async Book](https://rust-lang.github.io/async-book/part-guide/more-async-await.html)

Task handles have different destruction semantics:

- Dropping Tokio `JoinHandle<T>` detaches the task; it does not cancel it. [Tokio JoinHandle](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html)
- Dropping `AbortOnDropHandle<T>` requests abortion. [tokio-util](https://docs.rs/tokio-util/latest/tokio_util/task/struct.AbortOnDropHandle.html)
- Awaiting a task observes completion.
- Cancelling a token requests cooperative cancellation; it does not itself prove that cleanup completed.
- On stable Rust 1.95, `Drop` cannot await. The target is pinned to 1.95 in [`rust-toolchain.toml`](/C:/Users/kuh/Desktop/kd4/codex-rs/rust-toolchain.toml:2). A nightly experimental `AsyncDrop` now exists, so this analysis must be toolchain-aware rather than assuming the restriction forever. [AsyncDrop documentation](https://doc.rust-lang.org/stable/core/future/trait.AsyncDrop.html)

**Compile-correct bugs.**

- Letting a connection or process wrapper fall out of scope when correctness requires awaiting `close`, `flush`, `shutdown`, or `wait`.
- Dropping a `JoinHandle` under the mistaken belief that it cancels its task.
- Cancelling a child but dropping resources it still uses before joining its termination.
- Performing a state mutation before `.await`, then relying on later async code—rather than a synchronous guard destructor—to undo it on cancellation.
- Scheduling cleanup from `Drop` onto a runtime that may already be absent or shutting down.

**Required relationships.**

- Coroutine resume and drop bodies, including which locals are initialized at each suspension.
- Task-handle type and exact on-drop disposition: detach, abort-request, join, or no effect.
- Async terminal-operation summaries such as `shutdown().await`, `cancel-and-wait`, `flush`, and `reap`.
- Capture/ownership relationships between tasks and resources.
- Runtime liveness and execution-domain summaries where cleanup is spawned from `Drop`.
- Exit-specific policy: normal completion may require graceful close, while cancellation may permit rollback or abort.

**Local or interprocedural?** Path analysis within a future is local once summaries exist. Task spawning, helpers, runtime ownership, and child completion normally require bounded interprocedural summaries.

**False-positive boundary.**

- Detachment is sometimes intentional.
- Cancellation request is not completion, but completion is not always required.
- Abrupt rollback may be exactly the desired cancellation behavior.
- A best-effort destructor is acceptable if the API contract says so.
- Do not infer semantics from names such as `close`, `cancel`, or `guard`; use resolved built-ins or declared contracts.

KDA already catches dropped result-producing tasks and runtime-dependent cleanup in `Drop`. The new value is terminal **parity**: prove that normal, error, cancellation, and unwind exits reach an allowed disposition.

### 6. Panic-capable destructors during unwinding

**Semantic rule.** Destructors run on unwind cleanup paths. If a destructor panics while another panic is already unwinding, the process will likely abort. Rust’s `Drop` documentation therefore recommends avoiding panics in destructors. With `panic = "abort"`, ordinary unwinding cleanup does not run at all. [Drop documentation](https://doc.rust-lang.org/std/ops/trait.Drop.html)

**Compile-correct bugs.**

```rust
impl Drop for Guard {
    fn drop(&mut self) {
        self.registry.lock().unwrap().release(self.id);
    }
}
```

If the mutex is poisoned, `unwrap` may panic. If this destructor was reached while unwinding another panic, the application aborts instead of completing other cleanup.

Other sources include explicit panic, indexing, assertions, user `Display` implementations during formatting, and calls with transitive panic behavior.

**Required relationships.**

- MIR unwind cleanup edges and which destructors are armed on them.
- Transitive `may_panic` summaries, including resolved trait calls.
- Build-profile panic strategy.
- Optional `must-not-panic-on-drop` contracts for critical guards.
- Recognition of `thread::panicking()` branches and explicit abort behavior.

**Local or interprocedural?** Direct `panic!`, `unwrap`, and assertions are local. Useful coverage requires bounded call summaries.

**False-positive boundary.** “May panic” is often too weak for a diagnostic. Emit only for direct/high-confidence panic paths or contract-marked critical destructors. Exclude deliberate abort strategies, test-only panic guards, unreachable branches, and configurations that cannot unwind into the destructor.

### 7. `ManuallyDrop` state and extraction invariants

**Semantic rule.** `ManuallyDrop<T>` has `T`’s layout and permits safe access to the contained value. Once its contents have been manually dropped, exposing or reading that value through safe APIs is unsound; derived `Debug`, `Clone`, comparison, ordering, or hashing implementations may perform such reads. Controlling order with `ManuallyDrop` is also difficult under unwinding. [ManuallyDrop documentation](https://doc.rust-lang.org/std/mem/struct.ManuallyDrop.html)

For the project’s pinned Rust 1.95 toolchain, there is an additional version-specific rule: manually dropping a contained `Box` and then moving the `ManuallyDrop` wrapper was considered undefined behavior before Rust 1.96. The current documentation explicitly records that boundary.

**Compile-correct bugs.**

- A public safe method calls `ManuallyDrop::drop`, after which another safe method or derived trait reads the field.
- One branch extracts only some fields and leaks the rest unintentionally.
- A field is `ptr::read` twice.
- A panicking call occurs between taking ownership from the wrapper and re-establishing the intended owner.
- On Rust 1.95, a dropped `Box`-containing wrapper is subsequently moved.

**Required relationships.**

- Per-place state: initialized, manually dropped, extracted, reconstructed, or inaccessible.
- Path-sensitive exactly-once extraction.
- Reads, moves, derived trait access, and public-safe reachability after manual drop.
- Generic instantiations that may contain `Box` for toolchain-specific rules.
- Panic edges between suppression and reconstruction.

**Local or interprocedural?** Extraction is mostly local MIR analysis. Public API soundness and generic contained types require type/reachability analysis.

**False-positive boundary.** The presence of `ManuallyDrop` is not suspicious by itself. `ConPty::into_handles` is a good accepted pattern: the wrapper is immediately consumed conceptually, every field is read exactly once, and no panicking work intervenes. Report only an invalid state transition or an unclosed extraction obligation.

## Reusable destruction-obligation model

KDA already has most of the right foundation:

- [`DropEffectIndex`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/drop_effects.rs:220) summarizes destructor effects and carriers.
- [`resource_obligations.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/resource_obligations.rs) supplies path-sensitive live/discharged/transferred/abandoned/unknown states.
- [`raii_obligation.rs`](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/raii_obligation.rs:25) handles armed rollback and commit transfer.
- The [MIR fact protocol](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/docs/mir-fact-protocol.md:27) already preserves cleanup blocks, explicit drop terminators, and coroutine drop bodies.
- The existing design explicitly supports different accepted dispositions for normal, error, cancellation, and drop exits in the [README](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:1352).

The reusable abstraction should treat destruction as an event with metadata, not automatically as discharge:

```text
obligation:
    semantic resource identity
    carrier place and ownership mode
    armed predicate / typestate
    accepted dispositions by exit cause
    ordering prerequisites
    execution requirements
    evidence completeness

possible dispositions:
    graceful completion
    release
    rollback
    abort requested
    cancellation requested
    joined / termination observed
    detached
    transferred
    retained / intentionally leaked
    one shared owner released
    last-owner finalization
    unknown
```

Examples:

- Dropping a mutex guard → `release`.
- Dropping a reservation guard → `rollback`.
- Dropping `JoinHandle` → `detached`.
- Dropping `AbortOnDropHandle` → `abort requested`, not necessarily `termination observed`.
- Dropping one `Arc<T>` → `one owner released`; only the last drop finalizes `T`.
- `forget` → `retained/suppressed`, unless ownership is reconstructed or transferred.
- `close().await` → potentially `graceful completion`.
- Spawning cleanup from `Drop` → `cleanup scheduled`, not `cleanup completed`.

This extends KDA’s existing obligation substrate with three important dimensions:

1. **Multiplicity:** unique owner, last strong owner, aggregate members.
2. **Execution envelope:** synchronous, requires runtime, async, blocking, or may panic.
3. **Ordering:** finalization of one resource must precede invalidation of another.

## What should not become standalone lints

I would not add generic diagnostics for:

- every `Drop` implementation;
- every explicit `drop(value)`;
- every `mem::forget`;
- every `ManuallyDrop`;
- every strong `Arc`/`Rc` cycle candidate;
- every unawaited `JoinHandle`;
- every guard whose lifetime could be shortened;
- every destructor that calls a fallible-looking function.

Also, directly invoking `Drop::drop` is already a compiler error; explicit `mem::drop` matters only when it violates an ordering, alias, or terminal-disposition relationship.

The highest-value direction is therefore a small number of contract-driven checks sharing one destruction-obligation model, with MIR determining actual drop points and bounded summaries determining what those drops mean.

## Outcome

The promising target is not “interior mutability exists.” It is a shared class of capability-protocol bugs:

> A program acquires, publishes, transfers, or drops mutable authority, but fails to preserve the logical invariant associated with that authority.

This model generalizes across `Cell`, `RefCell`, locks, once-initialization, atomics, and custom `UnsafeCell` wrappers. The primitives differ in how authority is obtained, but the proof obligations have the same shape:

- What storage or logical state does this authority cover?
- Is it shared, exclusive, one-shot, conditional, or externally held?
- Which values must change together?
- What event publishes the change?
- What must be restored or discharged when the authority ends?
- Can another call reenter, observe, or mutate the state in between?

Rust itself deliberately leaves these questions to the abstraction. `RefCell` moves borrowing to runtime; locks introduce blocking, poisoning, and scheduling behavior; atomics only give the guarantees implied by their ordering; and `UnsafeCell` removes shared-reference immutability without legalizing data races or aliased `&mut` references. [RefCell](https://doc.rust-lang.org/std/cell/struct.RefCell.html), [Mutex](https://doc.rust-lang.org/std/sync/struct.Mutex.html), [RwLock](https://doc.rust-lang.org/std/sync/struct.RwLock.html), [atomic ordering](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html), [UnsafeCell](https://doc.rust-lang.org/std/cell/struct.UnsafeCell.html).

## Concrete integration-target finding

The clearest conditional defect is the ambient absolute-path guard:

- The thread-local slot is declared in [absolute-path/src/lib.rs](C:/Users/kuh/Desktop/kd4/codex-rs/utils/absolute-path/src/lib.rs:326).
- [`AbsolutePathBufGuard`](C:/Users/kuh/Desktop/kd4/codex-rs/utils/absolute-path/src/lib.rs:334) is a public zero-state guard. Construction overwrites the slot, while `Drop` unconditionally resets it to `None`.
- Relative-path deserialization consumes that ambient slot in [the same file](C:/Users/kuh/Desktop/kd4/codex-rs/utils/absolute-path/src/lib.rs:353).

The violated abstraction contract is:

> Every acquisition must own either the previous ambient value or an acquisition generation, and dropping it must restore only the state belonging to that acquisition.

A nested guard therefore destroys the outer guard’s base when the inner guard drops. A publicly constructible unit guard can also perform cleanup without performing acquisition. The user-visible consequence would be a relative path failing to deserialize, or resolving under the wrong ambient base, after an inner scope exits.

I did not prove a currently reachable nested production path, so the correct classification is `conditional`, with an `unknown_reentrancy_or_nesting` frontier—not an unconditional bug report. ## Shared semantic foundation

KDA should represent every mechanism through a common “interior authority” domain:

```text
storage identity
+ logical state identity
+ authority mode
+ owner/actor
+ acquisition and release events
+ protected fields/resources
+ protocol phase or epoch
+ publication/synchronization edges
+ escape, unwind, and transfer behavior
```

Wrapper adapters would then supply different semantics:

| Mechanism | Authority semantics |
|---|---|
| `Cell` | Unguarded, same-thread mutation events through shared references |
| `RefCell` | Runtime shared/exclusive leases; conflict may panic or return an error |

| `RwLock` | Shared/exclusive blocking leases with platform-dependent scheduling |
| `OnceCell` / `OnceLock` | One-shot `Uninit → Initializing → Ready` transition |
| Atomics | Indivisible events on one location plus ordering-derived edges |
| Custom `UnsafeCell` | Contract-declared lease, phase, pinning, and ownership semantics |

## Viable analysis directions

### 1. Reentrant and overlapping dynamic leases

**Model:** Logical storage identity, lease mode, guard lifetime, call graph, and a compatibility matrix for shared/exclusive/reentrant acquisition.

**Statically provable:** An exact `RefCell` is mutably borrowed while a live `Ref`/`RefMut` exists; the same mutex is relocked; a write lock is requested while a related read guard remains live; a guard crosses a call that is proven to reacquire the same resource.

**Runtime limits:** Aliasing through smart pointers, trait-object callbacks, recursion selected from data, `try_*` outcomes, scheduler behavior, and platform-specific `RwLock` policy. Relocking a mutex is not specified as safely succeeding, and even reader acquisition can deadlock under some writer-preference policies. [Mutex](https://doc.rust-lang.org/std/sync/struct.Mutex.html), [RwLock](https://doc.rust-lang.org/std/sync/struct.RwLock.html).

**Unknowns:** `unknown_alias`, `unknown_callback_target`, `unknown_reentrancy`, `unknown_try_acquire_result`, `scheduler_dependent`.

**Value/complexity:** High value, medium-high complexity. This is a natural extension of KDA’s current guard-lifetime and lock-order work.

### 2. Protected-state and authority correspondence

**Model:** A contract mapping logical fields or resources to the guard, lock, permit, or capability required to access them, including the required access mode.

**Statically provable:** Writes under the wrong lock; mutation after a guard is dropped; an optimistic read not followed by required version validation; different methods protecting the same state with different locks; poison recovery that calls `clear_poison` without a declared repair transition.

**Runtime limits:** Arbitrary data invariants cannot be inferred from a mutex alone. Poisoning is advisory and cannot serve as a soundness boundary. Recovery may depend on external validation or opaque callbacks.

**Unknowns:** `missing_authority_contract`, `unknown_alias`, `opaque_repair`, `poison_state_runtime_dependent`.

**Value/complexity:** Very high value but high complexity. Enforcement should be contract-backed; inference should produce candidates only.

### 3. Relational state, duplicated authority, and cache coherence

**Model:** A cohort of interior-mutable locations, their required relation, mutation effects, cache dependencies, key/version fields, and the synchronization domain covering updates.

**Statically provable:** One-sided writers; cache-source mutations without invalidation; incomplete cache keys; fields that must change together but are governed by different locks; suspension, callback, or unwind points splitting an intended transaction.

This covers multiple `Cell`s, multiple atomics, lock-plus-flag designs, and caches stored in `RefCell`. Representative correct patterns include scoped cache borrowing in [textarea.rs](C:/Users/kuh/Desktop/kd4/codex-rs/tui/src/bottom_pane/textarea.rs:1817). The paired `Cell<Option<_>>` cache in [pager_overlay.rs](C:/Users/kuh/Desktop/kd4/codex-rs/tui/src/pager_overlay.rs:364) is a useful inference target, though its present consecutive setters do not themselves establish a bug.

**Runtime limits:** Semantic dependencies on environment, time, FFI, or dynamically selected callbacks cannot generally be discovered. Whether intermediate state is observable depends on reentrancy and unwind behavior.

**Unknowns:** `unknown_dependency`, `unknown_observer`, `unknown_unwind_effect`, `candidate_relation_unconfirmed`.

**Value/complexity:** High value, medium complexity if implemented as operation adapters feeding KDA’s existing invariant machinery. Building a new standalone cache checker would be less attractive.

### 4. Once-initialization and publication protocols

**Model:** `Uninit → Initializing(owner) → Ready(epoch)` plus dependencies among initialized cells, getter preconditions, failure/unwind behavior, and publication edges.

**Statically provable:** A `get().expect(...)` not dominated by initialization; a local recursive initialization cycle; ignored `set` failure where unique initialization is required; two `OnceLock`s forming a logical cohort but admitting partial or mixed initialization; a ready flag published before its payload.

The paired theme cells in [highlight.rs](C:/Users/kuh/Desktop/kd4/codex-rs/tui/src/render/highlight.rs:50) and connection session state in [message_processor.rs](C:/Users/kuh/Desktop/kd4/codex-rs/app-server/src/message_processor.rs:134) illustrate these multi-object protocols.

**Runtime limits:** Racing initializer identity, panic behavior inside opaque initialization, and dynamically recursive initialization. `OnceCell` remains uninitialized after an initializer panic and documents reentrant initialization as a panic; `OnceLock` also remains uninitialized, while its reentrant outcome is deliberately unspecified. [OnceCell](https://doc.rust-lang.org/std/cell/struct.OnceCell.html), [OnceLock](https://doc.rust-lang.org/std/sync/struct.OnceLock.html).

**Unknowns:** `unknown_initializer`, `unknown_init_cycle`, `racing_winner`, `partial_cohort_possible`.

**Value/complexity:** Medium-high value, medium complexity, especially for recursive initialization and declared initialization cohorts.

### 5. State-transition and notification correspondence

**Model:** A condition predicate, mutations that can enable it, waiter registration, notification events, close/terminal state, and the ordering between publication and wakeup.

**Statically provable:** A state change that can satisfy a waiter without notification; notification before state publication; checking state before registering a non-buffered waiter; sleeping without rechecking; reporting closure before draining queued state.

The file watcher is a strong positive example: [recv](C:/Users/kuh/Desktop/kd4/codex-rs/file-watcher/src/lib.rs:127) registers notification before checking state, while [add_changed_paths](C:/Users/kuh/Desktop/kd4/codex-rs/file-watcher/src/lib.rs:149) updates the state and notifies. A useful analyzer must recognize this correct ordering.

**Runtime limits:** Scheduler interleavings, primitive-specific notification permits, cancellation, and opaque mutations.

**Unknowns:** `unknown_notification_semantics`, `unknown_scheduler`, `opaque_condition_mutation`.

**Value/complexity:** High value and high complexity. Best limited initially to declared state/event pairs and known primitives such as `Notify` or condition variables.

### 6. Atomic logical protocols

**Model:** Per-location modification order, reads-from edges, acquire/release synchronization, RMW success/failure behavior, returned old values, and a higher-level protocol state.

**Statically provable:** `load` followed by `store` where a declared invariant requires an RMW; publication without the required release/acquire edge; ignored CAS failure; counter decrement without a matching capability; possible wraparound or underflow; snapshots assembled from unrelated atomics despite requiring a common epoch.

**Runtime limits:** Complete interleaving and reads-from analysis is generally intractable; weak CAS may fail spuriously; ABA depends on unbounded histories and address reuse. A generic warning about `Relaxed` would be wrong—`Relaxed` still provides atomicity, just not cross-location ordering. [Ordering](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html).

**Unknowns:** `unknown_reads_from`, `unknown_cas_outcome`, `missing_publication_contract`, `aba_bound_exceeded`.

**Value/complexity:** Very high value for contract-selected protocols, very high complexity globally.

There is also a concrete KDA modeling gap here: [logical_interference.rs](C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/logical_interference.rs:443) treats two atomic additions as commuting based on final state. Two `fetch_add` operations have the same final total, but their returned old values differ with order. KDA should distinguish:

- final-state commutativity;
- observable-return commutativity;
- trace/event commutativity.

Without that distinction, interference results can be too optimistic when the RMW result is consumed.

### 7. Restoration and cleanup authority

**Model:** Ambient state as a stack or generation-tagged slot; the acquisition token owns the previous state or generation; `Drop` restores only its own acquisition.

**Statically provable:** Zero-state guards that overwrite then reset a slot; publicly forgeable cleanup tokens; unconditional sentinel restoration; nested acquisition without saved prior state; cleanup performed by a different logical owner.

**Runtime limits:** Whether nesting or reentrancy is actually reachable through dynamic callbacks, TLS behavior, and external slot writers.

**Unknowns:** `unknown_nesting_reachability`, `unknown_external_writer`.

**Value/complexity:** High value, low-to-medium complexity. This is the strongest near-term direction and already has an initial implementation domain in KDA.

### 8. Custom `UnsafeCell` abstraction boundaries

**Model:** Protected storage, valid protocol phases, pin/address-stability requirements, external mutation leases, pointer escape, ownership transfer, completion, cancellation, and terminal cleanup.

The Windows overlapped-I/O abstraction in [windows_pipe.rs](C:/Users/kuh/Desktop/kd4/codex-rs/tui/src/ide_context/windows_pipe.rs:165) is an excellent model case. It combines pinned `UnsafeCell` storage, an `unsafe impl Send` at [line 312](C:/Users/kuh/Desktop/kd4/codex-rs/tui/src/ide_context/windows_pipe.rs:312), OS-held pointers, completion/reaping, and permit accounting.

**Statically provable:** Pinning before pointer escape; no move or resize while an external lease is active; every exit waits, cancels, transfers, or deliberately retains the operation; safe methods do not return references beyond the lease; ownership transfers at most once.

**Runtime limits:** Whether the OS actually stopped accessing memory, external write bounds, callback behavior, and foreign completion guarantees cannot be derived from Rust code.

**Unknowns:** `external_effect_unmodeled`, `unknown_completion`, `pointer_escape_unbounded`, `unsafe_contract_missing`.

**Value/complexity:** High value per finding but high complexity and relatively low frequency. This should be contract-only, reusing KDA’s resource obligations, typestate, and unsafe-contract machinery.

## Unknown-result policy

Unknown must be a first-class result, not reduced to low confidence:

```text
proven
violated(path, invariant, producer, consumer)
conditional(predicate, witness)
unknown(reason, analysis frontier, evidence needed)
```

Query-resolution status and protocol verdict should remain separate. For example, a call may resolve exactly while its reentrancy remains unknown.

Positive evidence, counterexamples, and unknown frontiers should also remain separate. A concrete violating path should win even if other paths are unknown; absence of a violation should not become “proven” while an opaque callback or alias frontier remains.

# Review outcome

Your analyzer’s strongest ecosystem opportunity is not “more lints.” It is detecting when individually legal Rust operations violate a higher-level semantic law or protocol.

Rust’s type system is very good at ownership, borrowing, and memory safety within its modeled boundaries. It generally does not prove:

- algebraic laws between trait implementations;
- that a resource reached the correct terminal state;
- that callbacks cannot re-enter a dynamically borrowed object;
- panic and unwind safety of transient invariants;
- multi-operation synchronization protocols;
- the semantic promises made by `unsafe`, `Pin`, atomics, or FFI abstractions.

Clippy predominantly handles local patterns and idioms. The most valuable space left for a semantic quality gate is therefore:

> Cross-expression, cross-path, and sometimes cross-function correctness properties where every operation is legal, but their composition is wrong.

## 1. Standard trait-law coherence

**Bug class.** Related trait implementations operate on different semantic identities:

- `Eq` compares one field set while `Hash` hashes another;
- `Ord` uses fields or normalization inconsistent with `Eq`;
- `PartialOrd` disagrees with `Ord`;
- `Borrow<Q>` exposes a key whose equality or hashing differs from the owned key;
- key-relevant state can mutate through interior mutability after insertion.

These errors produce failed lookups, duplicate logical keys, unstable ordering, or collection corruption at the logical level.

**Why Rust permits it.** Trait checking proves signatures and associated types, not algebraic laws. The standard library explicitly requires equal values to hash equally, and requires `Borrow`ed and owned forms to behave equivalently for `Eq`, `Ord`, and `Hash`; violating collection key invariants is categorized as a logic error rather than a type error. [Hash contract](https://doc.rust-lang.org/std/hash/trait.Hash.html), [Borrow contract](https://doc.rust-lang.org/std/borrow/trait.Borrow.html), [HashMap key requirements](https://doc.rust-lang.org/stable/std/collections/struct.HashMap.html).

**Tooling gap.** Clippy has narrow checks such as `derived_hash_with_manual_eq` and `non_canonical_partial_ord_impl`. Its `mutable_key_type` documentation acknowledges both false positives and false negatives because it reasons mainly from type shape rather than the fields actually used by equality and hashing. [Relevant Clippy lints](https://rust-lang.github.io/rust-clippy/stable/index.html#mutable_key_type).

**Semantic information needed.**

- Resolved canonical trait implementations, including derived and delegated implementations.
- Normalized field and projection dependencies for comparison and hashing.
- Recognizable normalization operations such as case folding or canonicalization.
- `Borrow` target construction and delegation.
- Interior mutation paths affecting key-relevant fields.

Your existing relational machinery is already the right foundation: [relational_theory.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/relational_theory.rs:1). The missing high-value piece is automatic lowering of standard trait implementations into that theory.

**Assessment.** High precision for mismatched field sets, inconsistent delegation, or contradictory normalizers; medium precision for arbitrary user-defined equivalence relations. Medium–high difficulty. Applies to caches, interners, database indices, compiler symbol tables, protocol identifiers, distributed systems, and almost any collection-heavy application.

## 2. Fallible finalization and resource protocols

**Bug class.** An owned object is dropped successfully from Rust’s perspective but never reaches its required semantic terminal state:

- buffered data is not flushed;
- a compressor, encoder, cryptographic context, or archive is not finished;
- a transaction is dropped instead of committed;
- an output file is not atomically persisted;
- a child process pipe or protocol session is not closed in the required order.

The particularly dangerous case is when finalization can fail but `Drop` cannot report that failure. `BufWriter`, for example, documents that Drop-time flushing errors are ignored. [BufWriter](https://doc.rust-lang.org/std/io/struct.BufWriter.html).

**Why Rust permits it.** Ownership ensures destruction on ordinary paths; it does not mean that destruction is equivalent to successful completion. Destructors cannot return `Result`, can be bypassed through deliberate leaking, and are not guaranteed after abort or process termination. [Destructors](https://doc.rust-lang.org/reference/destructors.html), [`mem::forget`](https://doc.rust-lang.org/core/mem/fn.forget.html).

**Tooling gap.** `#[must_use]` and Clippy can catch an ignored `Result` after a finalization call. They cannot generally diagnose that the call was never made.

**Semantic information needed.**

- Exact type and constructor identities.
- Ownership transfers, returns, field storage, and escape points.
- Terminal operations such as `finish`, `flush`, `commit`, `persist`, or `shutdown`.
- Whether terminal-operation errors are handled or propagated.
- All success, error, unwind, and cancellation exits.
- Interprocedural obligation transfer.

The analyzer already contains most of this proof domain through resource obligations and exit-sensitive effects: [README.md](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/README.md:1343).

**Assessment.** High precision using a curated, versioned model catalog; medium if terminal operations are inferred from names. Medium difficulty because the core machinery exists. Applies to file and network I/O, compression, serialization, databases, cryptography, temporary files, subprocesses, and cloud SDKs.

## 3. Range and arithmetic proofs at dangerous sinks

**Bug class.** Length, capacity, index, offset, or allocation arithmetic wraps in release mode or panics in debug mode, then reaches a consequential sink:

- allocation under-sizing;
- slice-bound or capacity-check bypass;
- malformed FFI length;
- unsafe pointer offset;
- truncated wire length;
- attacker-controlled amplification calculation.

**Why Rust permits it.** Ordinary integer arithmetic is not a proof of a mathematical range. Overflow behavior depends on context and compiler settings, while casts can intentionally truncate. [Rust overflow rules](https://doc.rust-lang.org/reference/expressions/operator-expr.html#overflow).

**Tooling gap.** Clippy’s `arithmetic_side_effects` is intentionally broad: it flags arithmetic operations rather than proving whether a particular result can be invalid at an important use site. [Clippy `arithmetic_side_effects`](https://rust-lang.github.io/rust-clippy/stable/index.html#arithmetic_side_effects).

**Semantic information needed.**

- Concrete integer widths and signedness.
- Affine/range facts learned from guards and pattern matches.
- Checked, wrapping, saturating, and overflowing operation semantics.
- Cast truncation and sign conversion.
- Data provenance from lengths or untrusted inputs.
- Relation between the expression and a semantic sink such as allocation, indexing, `set_len`, pointer arithmetic, or an FFI count.

Your `BodyIr` already represents affine expression facts, making a sink-driven analysis plausible.

**Assessment.** High precision if findings require a dangerous sink and a demonstrated insufficient guard; medium if it merely reports unproven arithmetic. High difficulty. Applies to parsers, protocol stacks, storage engines, image/media processing, allocators, cryptography, embedded software, and unsafe collections.

## 4. Guard-held reentrancy and dynamic-borrow conflicts

**Bug class.** Code holds a `Ref`, `RefMut`, mutex guard, registry guard, or application-specific exclusion token while invoking user-controlled code that can re-enter the same object. The re-entry causes a `RefCell` panic, self-deadlock, inconsistent callback observation, or recursive mutation.

**Why Rust permits it.** Interior-mutability borrowing is checked dynamically, and lock reentrancy is a runtime protocol. The type system cannot know what an arbitrary callback or trait-object call will invoke. `RefCell::borrow_mut`, for example, panics if the value is already borrowed. [RefCell](https://doc.rust-lang.org/stable/core/cell/struct.RefCell.html).

**Tooling gap.** Clippy’s relevant analysis focuses on holding a `RefCell` guard across `await`; it does not trace callback re-entry and documents limitations even around explicit drops. [Clippy `await_holding_refcell_ref`](https://rust-lang.github.io/rust-clippy/stable/index.html#await_holding_refcell_ref).

**Semantic information needed.**

- Guard origin and precise drop/liveness extent.
- Receiver and place identity across references and projections.
- Closed callback targets where available.
- Summaries of which receiver places a callback may borrow or lock.
- Re-entry paths through trait calls, closures, hooks, and event dispatch.
- `Unknown` rather than a warning for unresolved open dispatch.

**Assessment.** High precision for direct calls and closed callback sets; medium for trait objects or externally supplied callbacks. High difficulty. Applies to GUIs, event loops, ECS engines, plugin systems, interpreters, registries, caches, and single-threaded async applications.

## 5. Panic/unwind safety and panic-capable destructors

**Bug class.**

- A destructor transitively invokes code that can panic, risking a double panic and abort.
- A mutation temporarily violates an invariant and then calls panic-capable code before restoring it.
- Unsafe code exposes or drops a partially transitioned representation during unwinding.
- Cleanup assumes normal completion and becomes incorrect on `?`, panic, or cancellation.

**Why Rust permits it.** Panic safety is a semantic property. Safe Rust generally preserves memory safety, but unsafe abstractions must ensure that unwinding cannot expose an invalid state. The Rustonomicon treats exception safety as a separate design obligation, and panicking while already unwinding commonly aborts the process. [Exception safety](https://doc.rust-lang.org/stable/nomicon/exception-safety.html), [`Drop` behavior](https://doc.rust-lang.org/std/ops/trait.Drop.html).

**Tooling gap.** Clippy’s `panic_in_result_fn` explicitly does not inspect called functions; `fallible_impl_from` primarily catches direct panic-like operations. Neither proves transitive unwind behavior or identifies an invariant-restoration window. [Clippy `panic_in_result_fn`](https://rust-lang.github.io/rust-clippy/stable/index.html#panic_in_result_fn).

**Semantic information needed.**

- Interprocedural `may_unwind` effects.
- MIR cleanup and destructor edges.
- State transitions that open and close a temporary invariant hole.
- RAII rollback guards and `catch_unwind` boundaries.
- Distinction between process-aborting and unwinding configurations.
- Unsafe operations performed while the invariant is open.

**Assessment.** High precision for a known panic path from `Drop`; medium for inferred invariant windows. Medium difficulty for destructor analysis, very high for general exception safety. Applies to collections, allocators, transaction guards, FFI, plugin hosts, services, and safety-critical or embedded systems.

## 6. Condition-variable predicate and mutex protocols

**Bug class.**

- `Condvar::wait` is used without a loop that rechecks the predicate after spurious wakeups.
- A condition variable becomes associated with different mutexes.
- Notification occurs after changing an unrelated predicate or before the intended state is visible.

**Why Rust permits it.** A condition variable’s correctness depends on a relationship among a mutex, shared predicate, wait loop, and notifier. These are ordinary values and calls, not a type-level unit. The standard documentation requires predicate rechecking and warns about using one condition variable with more than one mutex. [Condvar](https://doc.rust-lang.org/stable/std/sync/struct.Condvar.html).

**Tooling gap.** Clippy does not model the protocol; its mutex-related documentation explicitly notes difficulty recognizing condition-variable usage. [Clippy `mutex_atomic`](https://rust-lang.github.io/rust-clippy/stable/index.html#mutex_atomic).

**Semantic information needed.**

- Condition-variable and mutex identities.
- Guard provenance.
- Loop dominance and back edges around waits.
- Predicate fields read before and after waiting.
- Mutex association through helper functions.
- Notification-side mutations of the same predicate.

**Assessment.** High precision in direct code and medium in helper-heavy abstractions. Medium difficulty. Applies to thread pools, blocking queues, storage engines, servers, schedulers, and embedded runtimes.

## 7. Concrete `Rc`/`Arc` strong-cycle construction

**Bug class.** Runtime construction creates a strong-reference cycle through fields, interior-mutability containers, or callback captures. Objects, file handles, tasks, or other resources then remain alive indefinitely and their destructors never run.

**Why Rust permits it.** Reference-counted cycles are memory-safe, so they are explicitly allowed. The `Arc` documentation recommends `Weak` for breaking cycles. [Arc cycles](https://doc.rust-lang.org/std/sync/struct.Arc.html).

**Tooling gap.** Clippy can flag explicit `mem::forget`, but acknowledges that it cannot generally detect all leak mechanisms. It does not build a runtime ownership graph for constructed `Rc`/`Arc` values. [Clippy `mem_forget`](https://rust-lang.github.io/rust-clippy/stable/index.html#mem_forget).

**Semantic information needed.**

- Allocation identities within a bounded construction region.
- Strong clones versus `downgrade`.
- Assignments through `RefCell`, mutexes, and container fields.
- Closure capture modes.
- Strong-edge SCC detection.
- Teardown paths that clear an edge.

**Assessment.** Medium–high precision if restricted to concrete constructed cycles with no observed clearing path; lower for purely type-level possibilities. High difficulty. Applies to GUIs, actor systems, callback registries, object graphs, caches, plugin systems, and async task ownership.

## 8. Unsafe generic ownership and auto-trait contracts

**Bug class.** A generic unsafe abstraction misstates ownership or thread-safety:

- `unsafe impl Send` or `Sync` omits a necessary generic bound;
- a raw-pointer wrapper owns `T` but its `PhantomData` says otherwise;
- variance permits an invalid lifetime substitution;
- destructor behavior conflicts with the advertised ownership model;
- a thread-affine native handle is made transferable.

**Why Rust permits it.** Unsafe marker implementations are assertions by the programmer. Raw pointers and `PhantomData` deliberately let library authors express semantics the compiler cannot infer automatically. [Send and Sync](https://doc.rust-lang.org/nightly/nomicon/send-and-sync.html), [`PhantomData`](https://doc.rust-lang.org/nomicon/phantom-data.html).

**Tooling gap.** Clippy’s nursery `non_send_fields_in_send_ty` catches obvious field contradictions, but is heuristic and has documented exceptions around raw pointers—the important representation used by custom owners. [Clippy `non_send_fields_in_send_ty`](https://rust-lang.github.io/rust-clippy/stable/index.html#non_send_fields_in_send_ty).

**Semantic information needed.**

- Generic parameter occurrences and variance.
- Auto-trait solutions for parameters and projections.
- Evidence that a raw pointer is owning: deallocation in `Drop`, dereference APIs, length/capacity fields.
- `PhantomData` form and drop-check effects.
- Unsafe impl predicates.
- Thread-affine operations in destructors.

**Assessment.** High precision for definite missing bounds or contradictions backed by ownership evidence; medium for inferred raw-pointer ownership. High difficulty. Applies to FFI wrappers, allocators, custom collections, async runtimes, device handles, embedded code, and database drivers.

## 9. Structural `Pin` invariants

**Bug class.** An abstraction promises structural pinning but later moves or invalidates a pinned field through assignment, `mem::replace`, unchecked projection, manual `Unpin`, or destructor logic.

**Why Rust permits it.** `Pin` deliberately relies on unsafe constructors and projections to make promises that the compiler does not independently verify. [Pin documentation](https://doc.rust-lang.org/std/pin/).

**Tooling gap.** Generated projection crates can enforce their own patterns, but there is no general whole-type proof for handwritten pin projections and their interaction with mutation and `Drop`.

**Semantic information needed.**

- `Pin`, `Unpin`, and `PhantomPinned` identities.
- Which projections expose structural pinning.
- Moves, replacements, swaps, and storage invalidation.
- Manual `Unpin` implementations and generic bounds.
- Destructor behavior and implicit moves.
- Macro provenance so generated, already-validated projection code is handled appropriately.

**Assessment.** High precision for definite moves through an exposed structural projection or a clearly contradictory manual `Unpin`; medium for inferred intent. Very high difficulty. Applies to futures, streams, runtimes, intrusive collections, self-referential buffers, and native device or FFI handles.

## 10. Atomic publication and ordering protocols

**Bug class.** Atomic operations use locally valid orderings but fail to create the intended global happens-before relationship—for example, publishing initialized data with `Relaxed` and reading it after a `Relaxed` flag load.

**Why Rust permits it.** Each atomic operation can be type-correct and use an ordering valid for that operation while the overall concurrency protocol remains wrong. The compiler’s `invalid_atomic_ordering` lint only rejects orderings that are intrinsically invalid for an individual operation. [Atomic orderings](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html), [`invalid_atomic_ordering`](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_lint/types/static.INVALID_ATOMIC_ORDERING.html).

**Tooling gap.** Neither rustc nor ordinary Clippy analysis reconstructs publication protocols across helpers, closures, and shared fields.

**Semantic information needed.**

- Atomic object and associated non-atomic data identities.
- Reads and writes ordered around atomic operations.
- Ordering constants and fences.
- Control dependency from a load to subsequent accesses.
- Writer and reader roles in spawned closures or known entrypoints.
- Optional annotations identifying state-machine or publication relationships.

**Assessment.** Medium–high precision for canonical one-writer publication patterns; substantially lower for arbitrary lock-free algorithms. Very high difficulty. Applies to runtimes, allocators, reference counters, lock-free queues, kernels, embedded systems, caches, and lazy initialization.

I would not expose these as another large flat collection of independent lint names. The existing registry is already broad: [config.rs](/C:/Users/kuh/Documents/ChatGPT/kd-analzyer/src/config.rs:40). Instead, organize the general-purpose gate around proof domains:

2. **Versioned ecosystem model packs**

3. **Opt-in advanced proofs**

4. **Evidence-tiered diagnostics**

   - Closed-world protocol violation: warning/error.
   - Open-world or alias-sensitive suspicion: advisory or `Unknown`, not a normal finding.

## Verdict

`Pin` deserves first-class semantic modeling in `cargo kda`, but not a “Pin code is suspicious” lint family.

The right abstraction is a broader **address-stability obligation** with Pin-specific sources and rules:

- The obligation belongs to the pointee or projected place, not to the `Pin<Ptr>` wrapper.
- It tracks structural pinning, `Unpin`, address exposure, registration, projection, replacement, and destruction.
- Diagnostics require a demonstrated contradiction, such as moving a still-pinned field or deallocating a registered intrusive node.
- Missing alias or lifecycle evidence must produce `Unknown`, not a warning.

This is worthwhile because Pin is explicitly a library/unsafe-code contract rather than compiler magic; rustc does not verify many of its semantic promises. [`std::pin`](https://doc.rust-lang.org/std/pin/) defines the guarantee as keeping the pointee unmoved and valid at the same address through destruction.

## Important non-diagnostics

KDA should deliberately remain quiet for:

- The mere presence of `Pin<&mut T>`, `Pin<Box<T>>`, `PhantomPinned`, or unsafe Pin methods.
- Moving or returning a `Pin<Box<T>>` handle.
- `Pin<Box<dyn Future>>` used for type erasure.
- Explicit `Unpin` implementations whose bounds cover all structurally pinned fields.
- Generated `async` state machines and projection APIs used through their safe surfaces.
- Replacing an inactive enum variant or using `Pin::set`.
- Stable allocations hidden behind a movable outer handle.
- Intentional leaks that preserve a still-retained address.
- Any case where alias escape or call resolution makes the contradiction unknown.

One subtle macro-specific point is worth modeling: under `pin-project`, an unannotated `PhantomPinned` field does not affect the generated `Unpin` implementation; it must itself be pinned or the type declared `!Unpin`. [pin-project documentation](https://docs.rs/pin-project/latest/pin_project/attr.pin_project.html)

The main semantic gap is type identity. The current `type_identity` reduces an ADT to its short name, losing generic structure and dereference target identity. Pin reasoning needs at least:

- Canonical `core::pin::Pin<Ptr>` identity.
- `Ptr` and resolved `<Ptr as Deref>::Target`.
- Tri-state `Target: Unpin` resolution.
- Structural parent-field pin relationships.
- Pin/address obligations attached to places or allocations.
- Escape state and lifecycle phase.
- Provenance indicating compiler-, macro-, dependency-, or locally-authored unsafe code.

KDA’s existing policy of recording precision losses and treating them as `Unknown` is appropriate; its MIR protocol already disclaims exact heap aliasing and complete unsafe/FFI semantics in [`mir-fact-protocol.md`](</C:/Users/kuh/Documents/ChatGPT/kd-analzyer/docs/mir-fact-protocol.md:32>).

## Expected coverage without full alias analysis

Rough engineering estimates—not measured recall:

- **70–90%** of direct, local violations such as moving through an unchecked mutable escape, contradictory handwritten projection/`Unpin`, or moving a declared pinned field in `Drop`.
- **40–70%** when the relevant operation passes through a small number of resolved local helpers.
- **Useful but contract-dependent coverage** for intrusive lists and retained FFI pointers.
- **Below 30%** for arbitrary custom smart pointers, dependency internals, dynamic dispatch, shared heap aliases, or undocumented external retention.

That is still valuable. Unsafe Pin implementations tend to concentrate the critical operations in constructors, projection methods, polling, registration, and destruction—the exact bounded regions KDA can reason about well.

The final design recommendation is therefore: **make Pin a first-class semantic vocabulary inside a general address-stability model, but expose only proof-backed diagnostics and opt-in lifecycle contracts.** A broad Pin lint would be noisy; semantic contradiction checks could catch bugs rustc intentionally leaves to unsafe API discipline.

## Finding: public dyn-compatible adapters are rejected by implicit `Sized` bounds

[Rust Reference: trait bounds](https://doc.rust-lang.org/reference/trait-bounds.html), [trait objects](https://doc.rust-lang.org/reference/types/trait-object.html), [FLS types and traits](https://rust-lang.github.io/fls/types-and-traits.html).

[`UnwindSafe`](https://doc.rust-lang.org/std/panic/trait.UnwindSafe.html), [`AssertUnwindSafe`](https://doc.rust-lang.org/std/panic/struct.AssertUnwindSafe.html)
5. Both execution paths call `args.into_iter().collect()` inside the catch boundary. A custom iterator can mutate externally borrowed state and then panic from `next()`.
6. The panic is converted to `KdaError`, after which the caller can continue using that potentially half-mutated state—the exact situation `UnwindSafe` is intended to flag.

These functions do not exist under HEAD. The dirty tree therefore introduces new public boundaries that accept a strictly broader set of captures than rustc would infer as unwind-safe.

No in-tree consumer currently exercises this case, but these functions are explicitly documented as embedding/code-mode APIs, where returning to and continuing in the caller is expected. In contrast, the dirty version of the older `run` function now collects its generic iterator into `Vec<OsString>` before entering `catch_unwind`, which avoids this problem. That makes the discrepancy appear unintentional.

Collecting the arguments before `catch_unwind`, as `run` now does, would narrow the assertion to owned `Vec<OsString>` state. Requiring `I: UnwindSafe` would also preserve rustc’s check.

`UnwindSafe` is advisory rather than an unsafe soundness contract, so I rate this P2 rather than a memory-safety defect.
