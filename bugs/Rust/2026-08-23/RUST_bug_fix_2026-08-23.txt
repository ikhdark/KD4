FINDING KD4-RUST-2026-08-23-001

Severity: high
Status: fixed
Confidence: high
Component: codex-core initial model context, compaction, resume/fork, model-visible
context refresh
Affected implementation and consumers:
- codex-rs/core/src/session/mod.rs, including digest_context_fragments,
  InitialContextBuild, build_context_fragment_digests, and
  build_initial_context_with_world_state_and_mcp.
- codex-rs/core/src/compact.rs, codex-rs/core/src/compact_remote.rs, and
  codex-rs/core/src/compact_remote_v2.rs.
- session, compaction, remote-compaction, resume/fork, and model-visible-layout tests
  and snapshots under codex-rs/core/src and codex-rs/core/tests/suite.

Observed symptom:
Numerous compaction and context-layout tests disagreed about whether semantically
unchanged model context had changed, and snapshots contained duplicated or stale
context-fragment representations after compaction and resume/fork paths.

Violated invariant:
Runtime context fragments that are semantically identical must have stable identities
and digests across construction, compaction, and reinjection. Dynamic identifiers and
opaque skill locators must not make an otherwise identical fragment appear changed.
The same accepted fragment baseline must be available to every compaction variant and
to subsequent model turns.

Established cause:
The initial-context construction boundary did not propagate one canonical stable
fragment digest set through all consumers. Dynamic context data participated in
identity comparison, and remote compaction did not consistently use the same V2
initial-context representation. Model-visible AGENTS context could also retain a stale
snapshot between turns.

Fix/disposition:
- Canonicalized context-fragment digest inputs so dynamic identifiers and opaque skill
  locators do not invalidate semantic equality.
- Carried stable fragment digests through InitialContextBuild and the compaction
  injection paths.
- Aligned remote compaction expectations with the V2 path.
- Refreshed the model-visible AGENTS snapshot between turns.
- Accepted the nine context-fragment deduplication snapshots produced by the corrected
  canonical representation.

Reachable effect and regression risk:
Without this repair, users can receive duplicated/stale hidden context, lose prompt
cache stability, or observe inconsistent behavior after compaction, resume, or fork.
The main regression risk is over-canonicalizing genuinely distinct context; the direct
session/compaction tests and the full workspace run cover this boundary.

Validation evidence:
The relevant session, compaction, remote-compaction, and model-visible-layout tests
passed in focused and final workspace runs. Final full-workspace result is recorded
below.

RUST-2026-08-23-25 - timing history cap fixture did not model logical generations
---------------------------------------------------------------------------------

Severity/status/confidence: medium test blocker / fixed / high.
Affected files and symbols:

  timing_histories_evict_oldest_entries_at_their_caps.

  TurnTimingState::begin_model_generation, begin_model_request_wait,

Trigger and reproduction:
The focused 32-test core route failed at turn_timing_tests.rs in the assertion that the
latest retained request contained 64 progress-kind records. The exact observed values
were left 0 and right 64. The same route showed that request-count and request-history
eviction assertions before it succeeded.

Expected behavior and violated fixture invariant:
The cap test must create a sequence of production-valid logical generations when it
expects each request to own distinct generation outcome metadata. A generation outcome
is intentionally attached to that logical generation's primary request; creating 1,025
nominally primary requests without advancing the generation does not represent that

The fixture called begin_model_request_wait repeatedly after only the implicit first
generation. All retained requests therefore shared one generation index, and

established.

The fixture now begins a model generation before each request. This preserves the cap,
oldest-entry eviction, physical-attempt-ID eviction, and progress-kind truncation checks
while modeling the producer's real generation/request relationship.

Regression risk:
Low. The change is test-only. A possible risk was accidentally weakening the cap
assertions; those assertions remain exact for the 1,024 request cap, the 64 attempt-ID
cap, the 64 progress-kind cap, and oldest-entry eviction.

RUST-2026-08-23-26 - terminal recovery fixture confused repair events and lacked rollout storage
------------------------------------------------------------------------------------------------

Severity/status/confidence: medium test blocker / fixed / high.
Affected files and symbols:
- codex-rs/core/src/tasks/mod_tests.rs,
  permanent_rollout_repair_failure_stops_live_retry_and_recovers_after_restart.
- codex-rs/core/src/session/tests.rs, attach_thread_persistence (test helper visibility).
- Runtime contracts inspected in codex-rs/core/src/tasks/mod.rs and
  codex-rs/core/src/session/mod.rs, including recover_bound_terminal_intent,
  recover_authoritative_terminal_delivery, record_conversation_items_durable, and
  terminal event fingerprinting.

Trigger and reproduction sequence:
1. Recovery durably emitted the required pre-terminal developer repair item.
2. That RawResponseItem event and the later TurnComplete event shared the same turn ID.
3. The fixture stopped at the first matching turn ID and compared the repair event to
   TurnComplete, causing the initial focused failure.
4. After selecting the terminal event by fingerprint, the fixture reached its history
   assertion and exposed that make_session_and_context_with_rx intentionally has no
   LiveThread rollout storage.
5. After attaching test rollout persistence, strict ResponseItem equality still failed
   because the durable history boundary prepares persisted items with runtime metadata
   such as the passthrough turn ID; the stable developer role/content remained intact.

Expected behavior and violated fixture invariant:
Recovery must replay the exact durable repair plan before terminal publication, and a
test that asserts persisted ordering must use a persistence-backed session. Event
selection must identify the terminal semantic event rather than assume turn ID uniquely
identifies an event type. Persisted repair matching must compare stable semantic content,
not metadata assigned by the normal durable history boundary.

Established cause:
The newly extended test combined an event-only session helper with rollout-history
assertions and used equality criteria that were weaker than terminal identity for event
selection but stronger than semantic identity for prepared ResponseItems. Runtime
recovery produced the required repair-first sequence; the fixture could not observe it
correctly. No runtime terminal-recovery defect was established by these failures.

Fix:
- Select the recovered terminal event by both turn ID and terminal event fingerprint.
- Reuse the existing attach_thread_persistence helper from the tasks test and expose that
  helper at crate test scope.
- Locate the persisted repair item by stable developer role and content while continuing
  to locate the terminal item by fingerprint and assert repair_position <
  terminal_position.

Direct consumers and impact:
The corrected test exercises the persisted authoritative-terminal claim, restart reload,
pre-terminal repair, live delivery, rollout ordering, and final pending-ledger cleanup.
Without the fixture fixes, valid recovery behavior was reported as a blocker and the
ordering contract was not actually reached.

Regression risk:
Low and test-scoped. Semantic matching intentionally ignores persistence-assigned item
metadata but still requires the exact developer role/content, exact terminal fingerprint,
and strict persisted order. The helper performs the same LiveThread creation and rollout
flush already used by session persistence tests.
