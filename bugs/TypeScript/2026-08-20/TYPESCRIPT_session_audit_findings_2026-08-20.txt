## Findings

1. **P1 — Recipient preview excludes push recipients.**

   The dry-run handler queries only confirmed email subscribers and returns `emailRecipients`; the final workflow separately loads and snapshots active push subscriptions. The composer treats the email-only preview as sufficient authorization to send. An operator can therefore approve “0 matching recipients” and still deliver to push devices, or substantially undercount the audience.
   [dry-run handler](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/alert-broadcasts/route.ts:110) · [summary shape](C:/Users/kuh/Desktop/mdpwa-main/src/lib/alertBroadcastNotifications.ts:129) · [final push selection](C:/Users/kuh/Desktop/mdpwa-main/src/workflows/alertBroadcastDelivery.ts:60) · [send gate](C:/Users/kuh/Desktop/mdpwa-main/src/components/AlertBroadcastComposer.tsx:576)

2. **P1 — Broadcast completion stops before the operator UI.**

   The workflow durably computes `sent`, `partial`, `failed`, or `no_recipients`. A dedicated endpoint exposes that state and implements cancellation and failed-target retry. But the composer only shows the initial queued acknowledgment, discards the broadcast ID/run metadata, resets the form, and never polls. Repository search found no production client for `/api/alert-broadcasts/[id]`. Administrators cannot observe final per-broadcast delivery or invoke the implemented recovery actions.
   [terminal-state computation](C:/Users/kuh/Desktop/mdpwa-main/src/lib/alertBroadcastRepository.ts:1114) · [lifecycle endpoint](<C:/Users/kuh/Desktop/mdpwa-main/src/app/api/alert-broadcasts/[id]/route.ts:27>) · [composer result handling](C:/Users/kuh/Desktop/mdpwa-main/src/components/AlertBroadcastComposer.tsx:233) · [admin page projection](C:/Users/kuh/Desktop/mdpwa-main/src/app/[locale]/admin/alerts/page.tsx:35)

3. **P2 — Newly returned resident outcome metadata is dead on the wire.**

   Current routes return `notificationStatus`, `replayed`, `stored`, `confirmationStatus`, and `signupStatus`, but no component reads any of them. The shared hook always installs a fixed success message, and all three form callbacks ignore `data`.

   Consequences include:

   - A replayed, already-confirmed alert subscriber still sees “check your email to confirm.”
   - `stored: true` after confirmation-email failure is not explained as partial success.
   - Failed or unknown map/community staff-notification state produces the same success UI as `sent`.

   [signup outcomes](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/alert-signups/route.ts:389) · [community outcome](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/community-input/route.ts:258) · [map outcome](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/map-feedback/route.ts:369) · [fixed hook result](C:/Users/kuh/Desktop/mdpwa-main/src/components/useResidentFormSubmission.ts:177) · [ignored signup result](C:/Users/kuh/Desktop/mdpwa-main/src/components/AlertSignupForm.tsx:102)

   The API accepts and persists `duplicateOf` and `reviewFlags`; the client normalizer preserves them. The admin action sends neither field, and the panel does not display existing flags, duplicate linkage, prior review note, reviewer, or review timestamp. Thus imported or API-authored moderation metadata becomes invisible, while duplicate classification is only usable through handcrafted HTTP.
   [review handler](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/map-feedback/route.ts:523) · [client normalization](C:/Users/kuh/Desktop/mdpwa-main/src/lib/mapFeedback.ts:358) · [admin request projection](C:/Users/kuh/Desktop/mdpwa-main/src/components/useMapFeedbackAdminActions.ts:107) · [panel](C:/Users/kuh/Desktop/mdpwa-main/src/components/MapFeedbackAdminPanel.tsx:346)

### 1. Legacy admin UX is internally inconsistent

The completed path is PostgreSQL-backed named administrators with passwords, TOTP, permissions, and revocable sessions. The operations guide explicitly says to remove legacy browser credentials after cutover ([security-data-operations.md](C:/Users/kuh/Desktop/mdpwa-main/docs/security-data-operations.md:35)).

The remaining wiring conflicts with that path:

- The login form always requires email, password, and MFA ([AdminLoginForm.tsx](C:/Users/kuh/Desktop/mdpwa-main/src/components/AdminLoginForm.tsx:105)).
- Without PostgreSQL, the backend legacy branch only validates the password and ignores email/MFA ([route.ts](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/admin/session/route.ts:164), [route.ts](C:/Users/kuh/Desktop/mdpwa-main/src/app/api/admin/session/route.ts:214)).
- `MARTINDALE_ADMIN_TOKEN` alone marks admin identity as configured, but it cannot create the browser session the form needs ([adminIdentity.ts](C:/Users/kuh/Desktop/mdpwa-main/src/lib/adminIdentity.ts:123)).
- The public setup message incorrectly says either the password or API token enables sign-in ([AdminLoginPage.json](C:/Users/kuh/Desktop/mdpwa-main/messages/en/AdminLoginPage.json:3)).
- The guarded map moderation screen still puts an “Admin token override” ahead of its controls ([MapFeedbackAdminPanel.tsx](C:/Users/kuh/Desktop/mdpwa-main/src/components/MapFeedbackAdminPanel.tsx:318)). With PostgreSQL it is ignored; without PostgreSQL, the page already requires a signed legacy session, making it redundant.

Recommended completion: retire visible browser-token compatibility and stale setup copy, while retaining only explicitly scoped service-token API support. If password-only local login must remain, expose the active auth mode to the form so it does not require meaningless email/MFA fields.

### 2. PWA recovery exists but is conservatively suppressed

A complete bilingual recovery prompt now exists and is loaded globally. However, production only displays it after three recorded failures ([pwa-register.tsx](C:/Users/kuh/Desktop/mdpwa-main/src/app/pwa-register.tsx:99), [pwaServiceWorkerRegistration.ts](C:/Users/kuh/Desktop/mdpwa-main/src/app/pwaServiceWorkerRegistration.ts:20)). This also applies when a resident explicitly presses “Update now” and activation fails.

That leaves the first two failures silent even though the recovery component already explains what happened and how to reopen safely ([PWAUpdatePrompt.tsx](C:/Users/kuh/Desktop/mdpwa-main/src/components/PWAUpdatePrompt.tsx:24)).

Recommended completion: show `updateApplyFailed` immediately because it follows a user action. Retain a threshold for passive background `updateCheckFailed` events if suppressing transient network noise is still desired.

### 3. Admin readiness stops at environment presence

The readiness branch returns `ready` whenever `DATABASE_URL` exists ([deploymentReadiness.ts](C:/Users/kuh/Desktop/mdpwa-main/src/lib/deploymentReadiness.ts:313)). Likewise, named identity is considered configured based solely on transactional storage availability ([adminIdentity.ts](C:/Users/kuh/Desktop/mdpwa-main/src/lib/adminIdentity.ts:117)).

A deployment can therefore appear ready even when no active named administrator has been bootstrapped, while every login attempt fails. Completing this means distinguishing “database connected” from “named administrator verified,” ideally through an async database probe or bootstrap attestation.

### Compatibility paths that are not blocking newer implementations

- PostgreSQL already wins before Blob/local compatibility stores for map feedback, community input, and broadcasts ([mapFeedbackStore.ts](C:/Users/kuh/Desktop/mdpwa-main/src/lib/mapFeedbackStore.ts:1387), [communityInputStore.ts](C:/Users/kuh/Desktop/mdpwa-main/src/lib/communityInputStore.ts:895)).
- Production alert signups explicitly reject compatibility storage when PostgreSQL is absent.
- Weather now has shared-cache response headers and a five-minute process cache; older no-cache concerns are stale.
- Legacy idempotency keys, calendar IDs, versioned JSON readers, the unversioned service-worker sentinel, and manifest copy are active migration/compatibility consumers—not shadows.
- The Tailwind v3 border-color compatibility layer still has a few real dependents in `LocalCalendar`; removing it now would alter calendar borders rather than unlock newer behavior.
