MDPWA STATIC PERFORMANCE ARCHITECTURE PROFILE
Date: 2026-08-07

Scope
-----
This is a static source review, not a production trace or bundle build. Findings
were retained only where the source shows a credible reduction in transferred
JavaScript, hydration/parse work, early network requests, or server response
latency. File sizes and line counts are directional; shipped-byte savings must
be confirmed with the existing bundle analyzer and a browser trace.

PRIORITIZED OPPORTUNITIES
========================

1. HIGH: Do not initialize the homepage Leaflet map until it is near the viewport
-------------------------------------------------------------------------------
Evidence:
- The homepage renders MapFeedbackShell below the hero/actions without an
  intersection or intent gate (src/app/[locale]/page.tsx:172-205).
- MapFeedbackShell uses a dynamic import, but immediately renders that dynamic
  component, so the split chunk is requested as soon as the shell hydrates
  (src/components/MapFeedbackShell.tsx:8-14, 34-43).
- The imported 1,592-line client module immediately brings in Leaflet and
  react-leaflet (src/components/MapFeedbackMap.tsx:1-19), fetches viewport
  reports (src/components/MapFeedbackMap.tsx:760-841), and creates an OpenStreetMap
  TileLayer (src/components/MapFeedbackMap.tsx:1110-1154).

Change:
- On the homepage only, render a fixed-height server placeholder and instantiate
  MapFeedbackShell through IntersectionObserver with a generous root margin, or
  after an explicit "Open map" action. Keep /map-feedback immediate because the
  map is that route's primary task.
- If Next's emitted CSS graph permits it, move the homepage Leaflet stylesheet
  into the same lazy boundary so it is not an initial homepage stylesheet.

Why measurable:
- Visitors who never reach the map avoid the Leaflet/react-leaflet chunk, map
  parse/execute work, the /api/map-feedback request, and OSM tile requests.

Measure:
- Homepage JS transferred/parsed before interaction, main-thread time, requests
  to /api/map-feedback and tile.openstreetmap.org before the section is visible,
  and mobile Lighthouse TBT/INP.

2. HIGH: Split the map's display core from report/abuse form code
---------------------------------------------------------------
Evidence:
- MapFeedbackMap is one 1,592-line client module. Besides Leaflet rendering it
  statically imports form controls, abuse UI, draft recovery, integrity-token,
  and resident-submission hooks (src/components/MapFeedbackMap.tsx:21-65).
- Abuse UI is needed only for an opened report popup, and the submission form is
  rendered only after a pin is selected (src/components/MapFeedbackMap.tsx:1320-1390).

Change:
- Keep a small map/display chunk for Leaflet, markers, viewport loading, and pin
  selection. Dynamically import the resident report form after a pin is selected
  and the abuse form after the abuse action is opened. Keep admin-only controls
  in their existing separate dynamic boundary.

Why measurable:
- Map viewers currently parse form/draft/integrity code even when they only read
  the map. This split reduces the Leaflet route's initial client chunk and main-
  thread work for the common read-only path.

Measure:
- Initial / and /map-feedback route chunks, unused-JavaScript coverage, parse/
  execute time before the first map interaction, and async form chunk size.

3. HIGH: Make public header weather cacheable across page loads and instances
---------------------------------------------------------------------------
Evidence:
- HeaderWeather is mounted from the site header on every locale route
  (src/components/SiteHeader.tsx:45-67).
- It immediately fetches /api/weather with cache: "no-store" and repeats every
  five minutes (src/components/HeaderWeather.tsx:35-92).
- The API also returns Cache-Control: no-store for successful responses
  (src/app/api/weather/route.ts:5-20).
- The NWS adapter already defines a five-minute freshness window, but that cache
  is process memory only (src/lib/nwsWeather.ts:27-30, 566-585). Its independent
  forecast, alerts, and stations calls are already concurrent
  (src/lib/nwsWeather.ts:543-556).

Change:
- Remove the client no-store override and return a short public/browser cache
  plus Vercel shared-cache policy aligned with the existing five-minute TTL
  (for example a conservative max-age, s-maxage=300, and stale-while-revalidate).
  Keep unavailable/error responses short-lived or uncached.
- Preserve the current client refresh interval so a long-open tab still updates.

Why measurable:
- Repeat navigations and multiple visitors can reuse one public weather payload
  instead of paying an API invocation on every cold header mount. Shared caching
  also avoids instance-local cache misses that trigger the upstream NWS chain.

Measure:
- /api/weather request count, Vercel function invocations/cache-hit ratio, header
  weather time-to-display, and upstream api.weather.gov calls.

4. HIGH: Keep PWA registration immediate, but lazy-load PWA user-interface code
-------------------------------------------------------------------------------
Evidence:
- DeferredClientRuntime immediately instantiates PWARegister and the native
  InstallBanner on every route (src/components/DeferredClientRuntime.tsx:98-107).
- PWARegister combines immediate service-worker registration with update checks,
  listeners, state, and update UI in a 362-line client component; registration
  starts at src/app/pwa-register.tsx:208-235.
- InstallBanner hydrates translations, state, dismissal behavior, and UI merely
  to capture beforeinstallprompt (src/components/InstallBanner.tsx:1-82).
- The iOS banner chunk is requested after the idle gate for every non-install
  route, but device/standalone eligibility is checked only inside that 249-line
  component (src/components/IosInstallBanner.tsx:17-44, 142-144;
  src/components/DeferredClientRuntime.tsx:108-117).

Change:
- Preserve a tiny, immediately hydrated service-worker registration/update-event
  bridge, then import the update prompt only when a waiting worker exists.
- Preserve a tiny first-hydration beforeinstallprompt listener/store, then import
  InstallBanner UI only after that event is captured.
- Run the small iOS/standalone eligibility predicate before importing
  IosInstallBanner, so non-iOS and already-installed users never request it.

Why measurable:
- These components are global. Event-gating removes JS download, parse, state,
  effects, and hidden UI hydration for the large majority of visits that have no
  update or install prompt, without delaying service-worker registration or the
  one-shot browser event listener.

Measure:
- Global initial/shared client JS, number/timing of PWA chunks, hydration time,
  and update/install behavior on eligible Chrome and iOS devices.

5. HIGH (product tradeoff): Move Google Analytics out of afterInteractive
--------------------------------------------------------------------------
Evidence:
- Google Analytics is instantiated immediately after hydration rather than using
  the shared idle gate (src/components/DeferredClientRuntime.tsx:100-105).
- Both the remote gtag loader and initialization script use afterInteractive
  (src/components/Analytics.tsx:90-125).
- Vercel Analytics and Speed Insights are already held behind the idle/
  interaction gate (src/components/DeferredClientRuntime.tsx:108-115).

Change:
- Use lazyOnload or the existing idle/first-interaction gate for gtag. If short-
  visit counting is a hard requirement, test an idle callback with a bounded
  timeout instead of immediate afterInteractive loading.

Why measurable:
- This removes a third-party download and execution from the hydration-critical
  window. The cost is intentional: later loading can miss very short bounces.

Measure:
- Main-thread tasks and network contention through hydration, mobile TBT/INP,
  gtag request timing, and the change in counted short visits.

6. MEDIUM-HIGH: Keep Zod and phone normalization out of resident form chunks
----------------------------------------------------------------------------
Evidence:
- AlertSignupForm is a Client Component that imports only alert topics and a
  simple issue-code predicate from @/lib/alerts
  (src/components/AlertSignupForm.tsx:13-20).
- That module imports Zod and defines schemas at module scope
  (src/lib/alerts.ts:1-8, 98-99).
- CommunityInputForm likewise imports only client constants/predicates from
  @/lib/communityInput (src/components/CommunityInputForm.tsx:10-23), while that
  module imports Zod and phone normalization and creates Zod schemas at module
  scope (src/lib/communityInput.ts:1-5, 64-65). Its server validation calls phone
  normalization at src/lib/communityInput.ts:130-182.

Change:
- Move browser-safe constants, types, and issue-code predicates into small
  client-safe contract modules. Make the server validation modules import those
  contracts, not the reverse. Keep Zod and libphonenumber-js reachable only from
  server/API/store code.

Why measurable:
- Top-level schema initialization crosses the Client Component dependency graph.
  Separating the graph gives the bundler an unambiguous boundary and should
  remove Zod (and any retained phone-normalization code) from /alerts and
  /community-input client chunks.

Measure:
- Bundle-analyzer contents and compressed JS for /alerts and /community-input;
  verify that zod and libphonenumber-js are absent from client chunks.

7. MEDIUM: Do not hydrate both desktop navigation and a closed mobile dialog
--------------------------------------------------------------------------
Evidence:
- SiteHeader passes all translated navigation into SiteHeaderMobileMenu, a
  320-line Client Component, on every route
  (src/components/SiteHeader.tsx:83-101;
  src/components/SiteHeaderMobileMenu.tsx:1-18).
- That component client-renders the desktop nav, hamburger, and mobile dialog.
  The dialog/links are mounted even while closed, then portaled after mount
  (src/components/SiteHeaderMobileMenu.tsx:178-269).

Change:
- Render desktop navigation as server markup. Keep a narrow Client Component for
  the hamburger/focus-trap behavior, and mount the mobile dialog contents only
  on first open (retaining the current focus restoration and keyboard handling).

Why measurable:
- Every page currently hydrates duplicate desktop/mobile link trees and a closed
  dialog. The change lowers global client JS, initial DOM nodes, and hydration
  work on both desktop and mobile.

Measure:
- Shared client chunk size, hydrated node count, React hydration duration, and
  first-open latency for the mobile menu.

8. MEDIUM: Overlap independent server work on the home and meetings routes
-------------------------------------------------------------------------
Evidence:
- Home awaits LocalCalendar translations, performs synchronous formatting, and
  only then awaits the active-broadcast store
  (src/app/[locale]/page.tsx:87-107). The store can use remote Blob in production.
- Meetings loads MeetingDocuments and LocalCalendar translations sequentially
  (src/app/[locale]/meetings/page.tsx:39-50).

Change:
- After locale setup, request the homepage calendar translator and active
  broadcast together with Promise.all, then perform formatting.
- Request the two meetings translators with one Promise.all.
- Apply the same pattern only where store/message reads are demonstrably
  independent; do not parallelize the NWS observation call, which depends on the
  stations result.

Why measurable:
- The homepage's translation load and potentially remote broadcast read currently
  contribute serial latency. Overlap caps that portion of TTFB at the slower
  operation instead of their sum. Meetings receives a smaller version of the
  same benefit.

Measure:
- Server-Timing around setup/translations/store reads and p50/p95 TTFB for / and
  /meetings, especially with Vercel Blob enabled.

REVIEWED WITHOUT A RETAINED OPPORTUNITY
=======================================
- No exact duplicate client/server fetch was found on one render path. The map
  status list and viewport report query serve different data, and the unused
  WeatherPanel component is not imported into the application.
- Leaflet is already route-scoped through dynamic import and route-specific CSS;
  the measurable issue is when its homepage chunk starts and how much code is in
  that chunk, not the absence of any split.
- Vercel Analytics and Speed Insights are already deferred behind idle or first
  interaction.
- NWS forecast, alerts, and station requests are already parallel; the subsequent
  observation request correctly depends on the station response.
- Server-only QR, Resend, Blob, web-push, and react-email imports did not show a
  client-boundary leak in this static pass.
