# KD4 instruction ownership and delivery

This is an architecture reference, not a model-facing instruction source. Paths
below are repository-relative. The map records production relationships; check
the current implementation before making a change. Historical audit reports and
prompt snapshots are evidence, not policy owners.

## Maintenance procedure

1. Consult this map.
2. Identify the authoritative component for the requested change.
3. Inspect its current implementation and the affected consumers.
4. Change only the necessary owner and dependent contracts. A text match in
   another file is not proof that it needs the same edit.
5. Verify effective delivery, including the distinct supported composition that
   changes; follow equivalent production branches and their actual consumers.
6. Update this map when ownership or delivery relationships change.

Ordinary instruction changes do not require another repository-wide architecture
audit. Expand only for a concrete dependency, contradictory evidence, missing
delivery, or an explicitly requested broad audit. The map guides investigation;
it never substitutes for current source.

## Delivery overview

```text
catalog / bundled metadata / fallback
  -> models-manager prompt_resolver + explicit config override
  -> session base instructions -----------------------> request.instructions

config + role + project/home guidance + host/extension contributions
  -> contextual developer/user fragments + world state -> request.input

native tool owners + extension schemas + feature/role gates
  -> tool registry -> direct tools OR Code Mode descriptions/declarations
                                                     -> request.tools

parent assignment -> TaskCapsule / history fork -> child session composition
compaction/review task -> task-specific prompt + relevant session composition
```

These channels are not interchangeable: reference documents are not injected
automatically, a tool description cannot grant permissions, and task-local prose
must not silently become a second general policy.

## Verification and maintenance boundaries

Use the production contract and composition owners named above. Repository test
implementations, executable Rust doctests and test-only support targets have been
removed; historical test names are not current verification entrypoints. Check
the actual provider request, accepted fragment, callable schema, task bootstrap
or retained history boundary affected by the change; matching a source string
alone is not delivery verification. Run compilation or other checks/probes only
within the active authorization, mode and explicit user limits, through repository
runners. The map is not validation authorization or a new validation framework.

For changes like the ones establishing this map, relevant compile targets are
the owning `codex-protocol`, `codex-models-manager`, `codex-prompts`,
`codex-home`, `codex-core-skills`, `codex-skills`, `codex-skills-extension`,
`codex-code-mode-protocol`, `codex-code-mode-runtime` and `codex-core`. Select
only those actually affected by an ordinary future change. Prompt/doc-only
changes do not justify a Rust rebuild. Preserve failed-check diagnostics;
unrelated shared-checkout failures are not permission to edit unrelated code or
claim unperformed checks passed.

Output truncation lives in `utils/output-truncation/src/lib.rs`, with numeric
estimates in `utils/string/src/truncate.rs`. These are delivery/budget primitives,
not general-policy owners. Preserve their public budget/count types, mixed-item
ordering, bounded recovery and lazy counting when changing prompt projection;
compile-time compatibility is required even for helpers not currently called by
the coding-agent hot path. Task-store dependency admission similarly owns its
transaction-local contract prerequisites, not a new prompt or validation layer.
