# KD4 instruction ownership and delivery

This is an architecture reference, not a model-facing instruction source. Paths
below are repository-relative. The map records production relationships; check
the current implementation before making a change. Historical audit reports and
prompt snapshots are evidence, not policy owners.

## Maintenance procedure

1. Consult this map.
2. Identify the authoritative component for the requested change.
3. Inspect its current implementation and the affected consumers.
4. Change only the necessary owner and dependent contracts. A text match in
   another file is not proof by itself: check each match and fix every site
   sharing the root cause.
5. Verify effective delivery, including the distinct supported composition that
   changes; follow equivalent production branches and their actual consumers.
6. Update this map when ownership or delivery relationships change.

Ordinary instruction changes do not require another repository-wide architecture
audit; follow every concrete dependency, contradiction, delivery gap and site
sharing the root cause, and audit broadly when the request asks for it. The map
guides investigation; it never substitutes for current source.

## Delivery overview

```text
catalog / bundled metadata / fallback
  -> models-manager prompt_resolver + explicit config override
  -> session base instructions -----------------------> request.instructions

config + role + project/home guidance + host/extension contributions
  -> contextual developer/user fragments + world state -> request.input

native tool owners + extension schemas + feature/role gates
  -> tool registry -> direct tools OR Code Mode descriptions/declarations
                                                     -> request.tools

parent assignment -> TaskCapsule / history fork -> child session composition
compaction/review task -> task-specific prompt + relevant session composition
```

These channels are not interchangeable: reference documents are not injected
automatically, a tool description cannot grant permissions, and task-local prose
must not silently become a second general policy.

## Composition, roles, tools, extensions and continuation

### Live default policy

`protocol/src/default_instructions.rs::default_base_instructions` rereads the
build checkout's `protocol/src/prompts/base_instructions/default.md`. A relocated
binary can select an absolute path through `CODEX_DEFAULT_INSTRUCTIONS_FILE`
before startup. Policy is never discovered from a task's cwd. Reads are bounded
to 1 MiB of nonempty UTF-8; failed reads retain the last valid policy, with the
embedded text as the initial fallback. There is no watcher or metadata-only
freshness shortcut.

`ModelInfo::uses_default_base_instructions` carries runtime-only provenance
through model selection; the private models cache preserves it separately from
public catalog JSON. Explicit base overrides clear it, and authored catalog
policies do not acquire it. The normal sampling loop rereads the default before
each logical model request, including within an active turn. Changed text
invalidates the existing request scaffold; unchanged text preserves its bytes.
Compaction uses the same loader. New children keep default-policy inheritance
live rather than freezing it as an explicit override. Dedicated reviews capture
the current default when they start, retaining their separate rubric.

The runtime loader requires one initial binary update. Subsequent edits to the
selected `default.md` require neither rebuilding nor restarting that binary.

The remaining component inventory is maintained below with its owning paths,
delivery gates and change-specific follow-through.

## Verification and maintenance boundaries

Use the production contract and composition owners named above. The checkout is
test-free ([repository state](../../.codex/README.md#current-repository-state));
historical test names are not verification entrypoints. Check
the actual provider request, accepted fragment, callable schema, task bootstrap
or retained history boundary affected by the change; matching a source string
alone is not delivery verification. Run compilation or other checks/probes only
within the active authorization, mode and explicit user limits, through repository
runners. The map is not validation authorization or a new validation framework.

For changes like the ones establishing this map, relevant compile targets are
the owning `codex-protocol`, `codex-models-manager`, `codex-prompts`,
`codex-home`, `codex-core-skills`, `codex-skills`, `codex-skills-extension`,
`codex-code-mode-protocol`, `codex-code-mode-runtime` and `codex-core`. Select
only those actually affected by an ordinary future change. Only
`protocol/src/prompts/base_instructions/default.md` is reread live (or from
`CODEX_DEFAULT_INSTRUCTIONS_FILE`); every other delivered template or prompt file
in this map is compiled in with `include_str!`, and `prompts/src/review_request.rs::REVIEW_PROMPT` embeds a
compile-time copy of `default.md` (live reviews use `review_base_instructions()`).
Verify a template edit through a build that contains it; the running app keeps the
old text until that build is published. Pure documentation edits need no
rebuild. Preserve failed-check diagnostics;
unrelated shared-checkout failures are not permission to edit unrelated code or
claim unperformed checks passed.

Output truncation lives in `utils/output-truncation/src/lib.rs`, with numeric
estimates in `utils/string/src/truncate.rs`. These are delivery/budget primitives,
not general-policy owners. `session/step_context.rs::model_output_token_limit`
captures one context estimate per sampling step (reset on retry) and caps each
model-facing result at half the remaining effective context. Generic projection,
direct source/recovery reads and outer Code Mode exec/wait consume this cap;
script-visible selection/processing budgets remain independent. Existing typed
diagnostics, mandatory controls, exact recovery and coherent-packet defaults
remain owned by their result projectors. This is not a batch reservation or a
replacement for compaction, and unknown context retains the existing ceiling.
Preserve the public budget/count types, mixed-item
ordering, bounded recovery and lazy counting when changing prompt projection;
compile-time compatibility is required even for helpers not currently called by
the coding-agent hot path. Task-store dependency admission similarly owns its
transaction-local contract prerequisites, not a new prompt or validation layer.
