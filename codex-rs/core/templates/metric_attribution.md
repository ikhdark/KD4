# Metric-cause attribution

Name the quantity the user wants explained and its observation boundary: request, turn, process tree, workload or account window. Separate measured events from classifier labels and metadata. A recorded client/source label does not independently prove which UI was used; a purpose/waste label does not measure where compute time went. Describe an unexplained change as unexplained, not as its own diagnosis.

Before comparing arms, match workload, binary/source identity, build profile, configuration, isolation and counting units. Do not transfer debug-build costs to optimized builds or compare corrected workloads with earlier incomparable baselines. Distinguish inclusive phase intervals, exclusive time and overlapping parent/child work; do not add overlapping totals or attribute an unexplained remainder to a favored component.

For causal or exact-weight claims, identify the observation or controlled contrast that distinguishes the proposed cause from alternatives. Correlation and fitted weights are not a measured charging rule. If the distinction is unobservable, retain that uncertainty; if instrumentation can resolve it, extend the existing owner narrowly. Explain drivers rather than expanding a balance/history display when the user asked why a metric changed. This guide grants no execution, validation or configuration authority.
