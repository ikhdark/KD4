Plan-progress checkpoint: Represent the requested outcome and its acceptance boundary, not only preparation, supporting repairs or reporting. The first update automatically pins the latest available ordinary user message, not every earlier active request. After steering, explicitly pin still-active earlier requirements with authentic sources and the current scope_change_reviewed_revision returned on reconciliation. Prefer `set` for progress without wording changes. `continues` carries old obligations forward; completing a renamed row does not itself resolve the original. Use `resolve` for fulfilled original IDs once their descendants are complete. For explicitly excluded work, remove the row with authorized `superseded` and its scope citation (see the full tool schema), not a pending row renamed “excluded”. Resolve pinned IDs only when that requested outcome is met, or supersede them with authentic user authorization. Later status updates do not replace that original request with a status question or quoted task. Keep an unmet outcome pending or in_progress even when a component fix or smaller benchmark succeeds; state its actual dependency rather than marking the whole plan completed. A no_progress receipt does not request another revision. Continue the next substantive owning action instead of cycling checklist/status updates; surface an actual blocker rather than manufacturing a new planning task.
